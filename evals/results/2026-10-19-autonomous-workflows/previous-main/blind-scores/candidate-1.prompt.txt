+# 多文件分片上传架构设计
+
+## 1. 目标、事实与边界
+
+本设计把现有单文件入口扩展为页面存活期内的多文件上传能力：用户可以一次或多次添加文件；全局最多两个文件同时执行上传流水线；每个文件可暂停、继续、取消和失败重试；界面展示由服务端确认的进度；只有服务端明确返回完成状态后才报告成功。
+
+已知且作为实现依据的事实：
+
+- 前端是浏览器 React + TypeScript 应用。
+- 现有 `src/uploads/upload.ts` 仅将 `File` 和 `AbortSignal` 交给 `appApi.upload`。
+- `appApi` 已拥有认证、取消信号传递和标准错误映射。新模块继续调用它，不增加 HTTP 客户端、认证层或通用请求框架。
+- 服务端分片契约为 `create`、`putPart`、`inspect`、`complete`、`status` 和 `abort`。`confirmedIndices` 是已确认分片的权威来源。
+- 不要求刷新后恢复 `File`，也不要求后台上传；页面结束时只保证释放前端持有的资源。
+
+不在本次范围内：跨刷新持久化、Service Worker/后台上传、跨标签页协调、服务端接口改造、预览 UI、拖放样式和通用任务调度框架。
+
+### 可验收行为
+
+1. 添加任意多个文件后，任一时刻最多两个文件占用上传执行槽；同一文件同一时刻只发送一个分片。
+2. 每个条目的进度为 `服务端已确认字节数 / 文件总字节数`；最后一片按实际长度计数，不能用 `confirmedCount * partSize` 造成溢出。
+3. 暂停会停止继续调度并中止当前 `putPart`。继续或失败重试时先调用 `inspect`，只发送缺失分片。
+4. 取消会从等待队列移除条目、中止本地进行中的请求；已有 `uploadId` 时调用 `abort(uploadId)`，服务端确认终结后才进入 `canceled`。
+5. `complete` 返回 `fileId` 后进入成功；若响应结果未知，调用 `status(uploadId)` 对账，只有 `completed + fileId` 才进入成功。
+6. 页面所有者卸载时，中止本地请求，撤销该模块创建的对象 URL（如果未来 UI 创建了它们），清空定时器、订阅和 `File` 引用，不再发布迟到结果。
+
+## 2. 核心选择
+
+### 页面级管理器 + 纯状态转换
+
+`UploadManager` 是一次页面会话内上传资源的唯一所有者。它持有 `File`、每个运行任务的 `AbortController`、FIFO 等待队列和最多两个执行槽，并把状态快照发布给 React。稳定身份和明确的 `dispose()` 生命周期使这里适合用对象；文件状态的计算和转换仍放在纯 reducer/selector 中，便于穷举竞态测试。
+
+不引入状态机库或全局 store。状态转换已经复杂到需要可辨识联合类型，但尚不需要额外运行时。React 通过 `useUploadQueue()` 创建并订阅一个页面级管理器；多个显示组件消费同一快照，不复制第二份上传状态。
+
+### 以服务端确认为进度和恢复依据
+
+`putPart` 契约只在整片确认时提供确认结果，没有字节级发送事件。因此当前进度按已确认分片阶梯式增长；不通过计时器伪造平滑进度。若以后 `appApi` 提供可信的发送进度，可在视图模型中增加独立的瞬时 `sendingBytes`，但持久恢复点仍只能来自 `confirmedIndices`。
+
+暂停时，浏览器的 abort 与服务端是否已接收当前分片之间可能竞态。管理器立即停止后续调度并使旧运行代次失效；继续时的 `inspect` 解决该片究竟是否确认，不依赖旧请求最终回调。
+
+### 两个“文件流水线”槽，而非两个任意请求槽
+
+调度器最多让两个文件处于 `creating/reconciling/uploading/completing` 执行态。每个文件串行发送分片，因此峰值内存约为两个分片加请求层开销，且暂停边界清楚。`canceling` 的服务端清理不占上传槽，避免慢取消阻塞其他文件，但其 stale-result 规则与上传请求相同。
+
+队列采用 FIFO；暂停、取消或失败都会释放槽并触发下一条。继续/重试作为新的入队动作排到现有等待项之后，避免一个反复失败的文件饿死其他文件。
+
+## 3. 状态、身份与不变量
+
+每次添加文件生成页面内唯一 `clientId`，不能以文件名作为身份。同名文件是独立条目。`File` 只保存在管理器私有资源表中，React 状态和公开快照不携带它。
+
+建议内部类型：
+
+```ts
+type UploadPhase =
+  | { kind: 'queued' }
+  | { kind: 'creating' }
+  | { kind: 'reconciling'; reason: 'resume' | 'retry' | 'complete-unknown' }
+  | { kind: 'uploading'; partIndex: number }
+  | { kind: 'paused' }
+  | { kind: 'completing' }
+  | { kind: 'canceling' }
+  | { kind: 'failed'; operation: FailureOperation; message: string }
+  | { kind: 'succeeded'; fileId: string }
+  | { kind: 'canceled' };
+
+type UploadSession = {
+  uploadId: string;
+  partSize: number;
+  confirmedIndices: ReadonlySet<number>;
+};
+
+type UploadRecord = {
+  clientId: string;
+  fileName: string;
+  size: number;
+  phase: UploadPhase;
+  session?: UploadSession;
+  runGeneration: number;
+};
+```
+
+`FailureOperation` 至少区分 `create | inspect | putPart | complete | status | abort`，使 UI 给出正确动作。`abort` 失败只能重试取消，不能恢复上传；其他失败可按下述恢复策略重试。标准错误对象仍来自 `appApi`，reducer 中只保存展示所需、可诊断但不含文件内容的错误信息。
+
+必须由 reducer 和管理器共同保持的不变量：
+
+- `succeeded` 必有非空 `fileId`；只有 `complete` 或 `status` 的服务端结果可产生它。
+- 只有 `create` 成功后才存在 `session`；后续重试复用该 `uploadId`。
+- `confirmedIndices` 只接受 `0 <= index < ceil(size / partSize)` 的服务端值；协议异常作为不可继续的标准错误暴露，不能静默当作空集合。
+- 公开进度由 `session`、文件大小和已确认索引派生，不单独保存可漂移的百分比。
+- 每个异步结果携带开始时的 `runGeneration`；暂停、取消、重试和 `dispose` 都递增它。旧代次的成功、失败和 `finally` 均不得改写当前状态或重复释放新任务的槽。
+- 调度器内部 `activeClientIds.size <= 2`，同一 `clientId` 不得同时进入队列和活动集合。
+
+### 命令和合法转换
+
+| 命令 | 合法来源 | 结果/副作用 |
+| --- | --- | --- |
+| `addFiles(files)` | 页面存活 | 为每个文件创建 `queued` 条目并参与 FIFO 调度 |
+| `pause(clientId)` | `queued/creating/reconciling/uploading/completing` | 使旧运行失效并中止可取消请求，进入 `paused`；不调用服务端 `abort` |
+| `resume(clientId)` | `paused` | 进入队尾；有会话则先 `inspect`，无会话则 `create` |
+| `retry(clientId)` | 可重试的 `failed` | 进入队尾；有会话先对账，无会话重新 `create`；完成结果未知时先 `status` |
+| `cancel(clientId)` | 除终态外 | 移出队列、中止本地请求；有会话则 `canceling -> abort -> canceled`，无会话直接 `canceled` |
+| `dispose()` | 页面卸载，一次或多次 | 失效所有运行、中止请求、释放本地资源和订阅；不再发布状态 |
+
+按钮是否可用由 `phase` 派生，组件不自行猜测状态。重复点击同一命令必须幂等或被合法来源检查拒绝。

+### 流水线细节
+
+1. `create` 成功后检查 `partSize` 为正数并建立会话；由 `ceil(size / partSize)` 得出合法分片数。零字节文件没有分片，直接进入 `complete`。
+2. 初次上传可从空确认集开始；任何已有会话的继续或重试必须 `inspect`。采用服务端返回集合整体替换本地集合，而非做并集，防止本地对未确认结果产生错误记忆。
+3. 分片使用 `file.slice(index * partSize, min(size, ...))` 按需生成，不预先把整文件读入内存。`putPart` 成功事件原子地加入确认索引并发布进度。
+4. 所有分片确认后调用 `complete`。明确的业务拒绝进入 `failed(complete)`；超时、断网等未知结果先走 `status`。`status=uploading` 证明尚未完成，后续重试可以再次 `inspect` 后调用 `complete`；不盲目重放结果未知的完成请求。
+5. 任一步失败都释放调度槽。其他文件继续执行，单文件失败不使批次整体失败。

+## 6. 失败、取消和页面清理
+
+### 恢复矩阵
+
+| 失败点 | 保留内容 | 重试行为 |
+| --- | --- | --- |
+| `create` 未得到 `uploadId` | `File` 和元数据 | 重新 `create`；旧请求若实际成功但响应丢失，前端无法找回其 ID |
+| `putPart` | `uploadId`、本地确认集合 | `inspect` 后仅发送缺失片 |
+| `inspect` | `uploadId`、旧集合仅供展示 | 再次 `inspect`，在成功前不发送分片 |
+| `complete` 结果未知 | `uploadId` | 先 `status`，不直接宣告失败或成功 |
+| `status` | `uploadId` | 再次 `status` 对账 |
+| `abort` | `uploadId` 和取消意图 | 只重试 `abort`，不能恢复上传 |
+
+`create` 没有提供客户端幂等键或通过文件信息找回会话的能力。因此响应丢失时可能产生不可寻址的服务端孤儿会话；前端不能伪造恢复。实现依赖服务端对未完成会话设置过期清理。若产品要求绝不产生孤儿，会需要后端新增幂等创建/会话查询契约，这不是前端架构可以自行补齐的保证。
+
+### 页面结束
+
+`useUploadQueue` 的 effect cleanup 调用幂等 `manager.dispose()`：先标记 disposed 并递增所有代次，再 abort 本地 controller，清空调度队列和订阅，撤销自有 URL，最后删除 `File` 引用。清理后任何 promise 回调都只执行自身必要的 `finally`，不得发布 UI 状态或释放新代次的槽。
+
+页面关闭时不通过裸 `fetch`、`sendBeacon` 或绕过 `appApi` 的方式调用 `abort`，因为这会丢失既有认证和错误策略，而且浏览器不保证卸载期间异步请求完成。远端未完成会话仍依赖服务端过期清理；用户在页面存活时点击取消则正常等待 `abort` 确认。
+
+## 7. UI 与可访问性约束
+
+- 列表中每个文件是独立命名区域，文件名与对应进度条通过可访问名称关联；原生 `<progress max={1}>` 或等价语义报告确认进度。
+- 进度更新不使用高优先级打断式播报；状态从上传变为暂停、失败或成功时，以条目内文本提供可感知反馈。失败文本包含失败阶段和可执行恢复动作。
+- 暂停、继续、重试、取消使用真实按钮，并根据 `actions` 禁用或隐藏不合法操作。键盘焦点不因条目状态更新而跳走。
+- 添加文件的 input 支持多选。选择相同文件再次添加仍生成新条目；处理后清空 input value，允许再次选择同一文件。

+## 8. 迁移与兼容

+## 10. 验证重点
+
+单元级使用受控 promise 和假的 `UploadTransport`，不使用任意 sleep，至少覆盖：
+
+- 第三个文件只有在前两个之一释放槽后才开始；
+- pause 与 putPart 确认竞态，resume 的 inspect 返回“已确认”和“未确认”两种结果；
+- retry 不重新发送 inspect 已确认的索引；
+- A 代次失败发生在 B 代次成功之后，A 的 error/finally 不覆盖 B；
+- complete 响应丢失后 status completed/ uploading/失败三条路径；
+- cancel 与 complete 竞态中，只有当前代次和服务端权威状态能进入终态；
+- dispose 幂等，释放资源且禁止迟到发布；
+- `activeClientIds` 在所有事件序列中不超过 2。
+
+浏览器级验证真实 `File.slice`、`AbortController`、React 卸载和焦点行为。网络层用项目既有 mock 方案模拟慢分片与断网；不以“调用了 handler”代替对最终 UI 状态、服务端调用序列和资源释放的断言。
+
+## 11. 后续变化检查
+
+现实的后续需求是把并发文件数从 2 调成可配置，或允许单个文件并发发送多片。本设计把全局槽策略集中在 `UploadManager`，因此前者只需把常量提升为构造参数并补调度测试，不影响 UI、模型或传输层。后者会改变暂停竞态、内存上限和分片确认策略，应该在 manager 内新增“每文件分片并发”策略，而不是改动 `UploadTransport` 或让组件感知请求数。
+
+这个边界也支持未来增加刷新恢复：持久化的只能是会话元数据和确认索引，`File` 重新授权必须由新的产品交互取得；当前设计没有声称序列化 `File`，因此不会形成错误兼容承诺。
