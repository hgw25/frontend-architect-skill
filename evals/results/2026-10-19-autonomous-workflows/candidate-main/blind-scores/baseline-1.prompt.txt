+# 多文件分片上传架构
+
+## 1. 结论
+
+在页面作用域内引入一个与 React 解耦的 `UploadManager`，由它统一持有 `File`、上传任务状态、
+待运行队列和最多两个任务槽。React 只通过订阅只读快照来渲染，并把暂停、继续、取消、重试
+等用户意图交给 manager。
+
+每个文件在一个任务槽内串行上传分片。进度只按服务端已经确认的字节计算，不把刚发出但尚未
+确认的请求计入进度。暂停、网络错误或响应不确定后，先调用 `inspect(uploadId)` 对账，再选择
+下一片；因此服务端已确认的片不会被重复发送。`complete` 的响应不确定时使用 `status` 对账，
+只有拿到 `complete` 的成功响应或 `status` 返回 `completed` 和 `fileId` 才报告成功。
+
+所有请求继续通过已有 `appApi`；本模块不处理认证、不拼请求头、不包装第二套网络层，也不改写
+它的标准错误。
+
+## 2. 模块边界
+
+建议的源码结构如下：
+
+```text
+src/uploads/
+  upload.ts                 # 保留现有单文件入口，迁移期兼容
+  upload-api.ts             # 只把 appApi 的六个稳定方法适配成窄接口
+  upload-manager.ts         # 页面级任务集合、FIFO 调度、对外命令和订阅
+  upload-task.ts            # 单文件状态机、切片、对账、完成流程
+  upload-types.ts           # 对外快照、状态与命令结果类型
+  UploadProvider.tsx        # 创建/销毁 manager，向页面提供上下文
+  useUploads.ts             # 通过 useSyncExternalStore 订阅快照
+  __tests__/
+```
+
+依赖方向保持单向：
+
+```text
+React UI -> Provider/hooks -> UploadManager -> UploadTask -> upload-api -> appApi
+```
+
+`upload-api.ts` 的接口只表达当前后端契约，便于用内存 fake 做确定性测试：
+
+```ts
+interface MultipartUploadApi {
+  create(fileName: string, size: number): Promise<{
+    uploadId: string;
+    partSize: number;
+  }>;
+  putPart(
+    uploadId: string,
+    index: number,
+    bytes: Blob,
+    signal: AbortSignal,
+  ): Promise<void>;
+  inspect(uploadId: string): Promise<{ confirmedIndices: number[] }>;
+  complete(uploadId: string): Promise<{ fileId: string }>;
+  status(uploadId: string): Promise<
+    | { status: 'uploading' }
+    | { status: 'completed'; fileId: string }
+  >;
+  abort(uploadId: string): Promise<void>;
+}
+```
+
+适配器应直接委托 `appApi`。如果仓库中真实返回类型的字段形状不同，只在该适配器做一次映射，
+不让传输 DTO 扩散到状态机。
+
+## 3. 对外契约
+
+manager 提供小而完整的页面级接口：
+
+```ts
+interface UploadManager {
+  add(files: readonly File[]): readonly string[];
+  pause(taskId: string): void;
+  resume(taskId: string): void;
+  retry(taskId: string): void;
+  cancel(taskId: string): Promise<void>;
+
+  getSnapshot(): UploadsSnapshot;
+  subscribe(listener: () => void): () => void;
+  dispose(): void;
+}
+```
+
+- `taskId` 是前端任务标识，与创建成功后才有的 `uploadId` 分开；同名文件也能独立操作。
+- `getSnapshot()` 不暴露 `File`、`AbortController`、队列节点等可变对象，只暴露文件名、大小、
+  状态、确认字节数、进度、标准错误和成功后的 `fileId`。
+- 命令按 `taskId` 定位，重复点击应为幂等操作。例如暂停已暂停任务、继续已排队任务都不产生
+  第二条执行链。
+- `UploadProvider` 在挂载时创建一个 manager，在卸载时调用 `dispose()`；不要把任务放进全局
+  store，因为产品明确只要求页面存活期。
+
+## 4. 状态机
+
+对 UI 暴露以下稳定状态：
+
+```text
+queued -> creating -> uploading -> completing -> succeeded
+   |          |           |             |
+   +----------+-----------+-------------+-> failed
+              |           |
+              |           +-> pausing -> paused -> queued
+              |
+              +-------------------------------> canceling -> canceled
+```
+
+内部可有 `reconciling` 步骤，但对 UI 合并进 `uploading` 或 `completing`，并额外暴露
+`phase: 'checking'`，避免页面依赖过细的实现状态。
+
+关键转换规则：
+
+| 用户/系统事件 | 当前状态 | 行为 |
+| --- | --- | --- |
+| 添加文件 | - | 建立 `queued` 任务并进入 FIFO 队列 |
+| 获得任务槽 | `queued` | 无 `uploadId` 则 `create`，否则先 `inspect` |
+| 暂停 | `uploading` | 中止当前 `putPart`；请求落定后进入 `paused` 并释放槽 |
+| 暂停 | `queued` | 直接进入 `paused`，不调用后端 |
+| 继续 | `paused` | 回到队尾；有 `uploadId` 时运行前先 `inspect` |
+| 失败重试 | `failed` | 清除展示错误、回到队尾；有 `uploadId` 时先对账 |
+| 取消 | 任意非终态 | 阻止新步骤、中止在途分片；有 `uploadId` 时调用 `abort` |
+| 所有片确认 | `uploading` | 进入 `completing` 并调用 `complete` |
+| 完成响应不确定 | `completing` | 调用 `status` 对账，不提前成功 |
+
+`succeeded` 与 `canceled` 是终态。取消只有在服务端 `abort` 成功后才进入 `canceled`；若终结
+服务端会话失败，保留为带标准错误的 `failed`，重试执行的是取消操作，而不是继续上传。这样 UI
+不会把仍可能存在的服务端会话误报为已经取消。
+
+每个异步步骤捕获启动时的任务 `generation`。暂停、取消和重试会递增 generation；旧 Promise
+即使稍后返回，也不能再写入新一轮状态。AbortSignal 负责尽快停止传输，generation 负责保证
+状态正确，二者不能互相替代。
+
+## 5. 调度与分片算法
+
+`UploadManager` 维护一个 FIFO 队列和 `activeTaskIds` 集合。只有 manager 可以分配或释放槽，
+不依赖 React effect 的触发时序。
+
+- `creating`、`uploading`、`completing` 以及其对账步骤都占用同一个文件任务槽。
+- `activeTaskIds.size` 始终不超过 2；暂停、失败、取消完成或成功后立即释放槽并调度下一项。
+- 单个文件同时只有一个 `putPart`。这足以并发两个文件，暂停边界清晰，也不会额外放大内存和
+  请求压力。以后若有吞吐数据证明需要片内并发，可仅在 `UploadTask` 内增加受限 part worker，
+  不改变 manager 或 UI 契约。
+
+创建会话后校验 `partSize` 是正数。总片数为 `Math.ceil(file.size / partSize)`，每片使用
+`file.slice(start, end)`，不把整个文件复制进内存。`confirmedIndices` 先去重，并只接受
+`0 <= index < partCount` 的整数；超出契约的数据作为协议错误进入 `failed`，不能静默算进进度。
+
+运行或恢复一个已有会话的伪代码：
+
+```text
+confirmed = inspect(uploadId)
+for index in [0, partCount):
+  if index in confirmed: continue
+  await putPart(uploadId, index, file.slice(start, end), currentSignal)
+  confirmed.add(index)       // 仅在确认响应后增加
+await finishWithReconciliation(uploadId)
+```
+
+若 `putPart` 因暂停、断网或响应丢失而结果不确定，不立即重发该 index。暂停后保持 `paused`；
+继续或失败重试时先 `inspect`，由服务端确认集合决定是否重发。
+
+## 6. 进度与 UI 语义
+
+确认字节数按各确认片的实际范围求和：
+
+```ts
+confirmedBytes = sum(
+  min(partSize, fileSize - index * partSize),
+  for each confirmed index,
+);
+```
+
+`progress = confirmedBytes / fileSize`，并限制在 `[0, 1]`。零字节文件在服务端确认完成前显示
+0%，成功后显示 100%。因为既有 `putPart` 契约没有上传字节回调，进度会在每片确认后阶梯式
+更新；不要用定时器伪造平滑进度。若将来 `appApi` 增加单请求进度事件，可新增
+`transientBytes` 仅用于视觉插值，但持久的确认进度仍以服务端为准。
+
+每行至少展示：文件名、大小、百分比、状态、与当前状态匹配的操作和标准错误。操作可用性由
+状态推导，不在各组件重复维护。例如 `uploading` 可暂停/取消，`paused` 可继续/取消，普通
+`failed` 可重试/取消，`succeeded` 无上传操作。
+
+## 7. 完成对账与错误
+
+`complete` 成功返回 `fileId` 后可以进入成功态。如果请求抛出的是可能已经到达服务端的错误，
+则调用 `status(uploadId)`：
+
+1. 返回 `completed + fileId`：进入 `succeeded`。
+2. 返回 `uploading`：本轮进入 `failed`，由用户重试；重试时先 `inspect`，确认片齐全后再次
+   `complete`。
+3. `status` 自身失败：保留原始完成错误，并把对账错误作为诊断信息；仍不得报告成功。
+
+是否属于“响应结果不确定”必须复用 `appApi` 已有的标准错误分类。若它没有可判定的分类，安全
+做法是所有非明确业务拒绝的 `complete` 错误都先查询 `status`，而不是在上传模块里解析状态码
+或错误文案。
+
+创建响应丢失是当前后端契约的一个边界：客户端拿不到 `uploadId`，无法通过 `inspect/status`
+找回或 `abort` 该会话。前端只能把创建标为失败并在重试时重新 `create`；服务端需要自行过期
+无主会话。除非后端增加由客户端提供的幂等键或按文件查询会话的 API，前端不应声称解决了
+这个问题。
+
+## 8. 生命周期与资源释放
+
+`dispose()` 必须同步完成本地释放：
+
+1. 标记 manager 已销毁，使后续异步回调不能发布快照。
+2. 中止全部在途 `putPart` 的 controller，清空调度队列和订阅者。
+3. 删除任务对 `File`、分片 `Blob`、错误和快照的引用；如 UI 创建了 object URL，由创建它的
+   层调用 `URL.revokeObjectURL`。
+4. 对已经创建但未完成的 `uploadId` 发起尽力而为的 `appApi.abort`，但不依赖页面卸载时的异步
+   请求一定送达，也不使用自建 `fetch`/`sendBeacon` 绕过认证框架。
+
+这里不使用 IndexedDB、localStorage、Service Worker 或后台同步。它们无法可靠恢复原始 `File`
+权限，也超出了“页面存活期内恢复”的产品范围。
+
+## 9. 测试与验收
+
+用可控 Promise 的 fake API 对状态机和调度器做单元测试，React 层只测试渲染与命令转发。
+至少覆盖：
+
+- 添加三个文件时任意时刻只有两个任务占槽，完成或暂停一个后第三个开始。
+- 暂停中止当前片且释放槽；继续先 inspect，服务端已确认的当前片不再发送。
+- putPart 响应丢失后重试先 inspect，不重复传已确认片。
+- 普通失败保留同一个 uploadId，重试从服务端确认集合继续。
+- complete 成功、complete 响应丢失但 status 已完成、status 仍上传中三条路径。
+- 取消等待 abort 确认；旧请求晚到不会把 canceled/paused 改回 uploading。
+- 最后一片尺寸、重复确认 index、非法 index、零字节文件。
+- Provider 卸载后中止请求、清空 File 引用，晚到 Promise 不再通知 React。
+
+集成测试应使用真实的 `appApi` 适配器验证 AbortSignal 透传和标准错误不被改写。验收时通过浏览器
+网络限速与断网模拟检查暂停/继续、响应丢失对账，以及三个以上文件的两槽调度。
+
+## 10. 实施顺序
+
+1. 先固化 `MultipartUploadApi` 适配器和 fake，确认真实 `appApi` 的方法签名与标准错误分类。
+2. 实现并测试纯 TypeScript 的 `UploadTask` 状态机，包括 inspect 与完成对账。
+3. 实现两槽 `UploadManager` 和竞态测试。
+4. 接入 Provider/hooks 与文件列表 UI；最后再决定旧 `uploadFile` 的调用方迁移和废弃节奏。
+
+一个现实的后续变化是把并发数从 2 改为服务端下发配置。当前设计只需把 manager 构造参数
+`maxActiveTasks` 从固定值 2 改为配置值，任务、React 接口和进度模型都无需改动；这说明调度
+边界足够清晰，同时没有提前建设通用任务平台。
