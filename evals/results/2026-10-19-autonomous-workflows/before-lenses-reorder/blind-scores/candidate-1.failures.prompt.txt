+# 看板卡片排序技术设计
+
+状态：设计提案，待在真实应用仓库中映射文件并实施。本文只依据题目提供的项目事实；当前工作区没有应用源码、测试、浏览器支持矩阵或性能基线。
+
+## 1. 目标、边界与判定
+
+### 已知事实与沿用契约
+
+- 浏览器端使用 React + TypeScript；已有 `Card`、`Button`、标准错误提示和 `boardApi`。
+- 卡片以稳定的 `card.id` 作为 React key；卡片列表位于可滚动容器内，使用 CSS Grid，卡片高度会随内容变化。
+- 现状是数组换序后直接跳到新位置；没有专用动画或拖拽库。
+- 保存必须复用 `boardApi.saveOrder(ids)` 及其标准错误，不另建请求协议或错误体系。
+- 用户可以拖动，也可以使用每张卡的上移/下移按钮。两种入口必须调用同一排序规则。
+- 顺序在操作成立时立即反映到 DOM；位置过渡不得锁住下一次排序。用户可能在过渡中再次排序、滚动、调整容器大小或离开页面。
+- 尊重 `prefers-reduced-motion`；操作后焦点留在同一卡片的可操作控件上。
+
+### 本设计的产品语义
+
+1. `ids` 的数组顺序是唯一业务顺序，也是在 CSS Grid 中的 DOM 顺序。上移/下移分别表示在该数组中向前/向后一个位置，不按视觉上的某一列跳跃。
+2. 按钮操作立即提交一次顺序变更。拖动期间的 `draftIds` 是明确的交互草稿：越过插入位置时立即更新 DOM 预览，放下时一次性提交最终顺序；`Escape`/`pointercancel` 放弃草稿。动画状态永远不参与排序计算。
+3. 保存采用乐观更新。没有更新的排序入口会因为网络请求或动画而被禁用。
+4. 若当前最新顺序保存失败，显示项目标准错误并回到最近一次服务端确认的顺序；该回退也是普通的 DOM 换序，可按同一规则过渡。若失败请求之后已经有更新的本地顺序，则不回退覆盖新操作，继续尝试保存更新的完整快照。
+5. 拖动把卡片放到自身原位置、边界按钮再次激活等无变化操作不改状态、不保存、不播报。
+
+这些语义使视觉失败最多导致“没有过渡”，不会产生另一份卡片顺序。拖动草稿与已提交顺序是交互阶段的显式区别，不是动画维护的副本。
+
+### 明确不在本次设计中推定的事项
+
+- 未提供目标浏览器矩阵。方案以 Pointer Events、ResizeObserver 和 Web Animations API（WAAPI）为候选基线，但必须在实施前对照项目正式浏览器范围核实；不支持 WAAPI 时可直接跳过过渡，不能据此删掉必需的拖动能力。
+- 未提供服务端版本号、冲突检测或多标签页规则；本方案只能保证当前页面发起的保存顺序，不能声称解决跨标签页/多人并发覆盖。
+- 未提供整页卸载时 `boardApi` 的 keepalive/beacon 能力。SPA 路由离开后队列可继续运行，但浏览器关闭、刷新或跨站导航时无法仅凭现有签名保证未完成写入落库。该能力若是验收要求，需要扩展既有 API/导航策略，而不是在组件中私自使用另一条保存通道。
+- 未提供列表规模和性能测量，不预先引入虚拟化、广泛 memo 或动画库。

+## 2. 状态、规则与职责
+
+### 建议类型和纯规则
+
+以下是建议契约，实际文件名需按真实仓库约定映射。
+
+```ts
+type CardId = Card["id"];
+
+type MoveIntent =
+  | { cardId: CardId; kind: "by"; delta: -1 | 1 }
+  | { cardId: CardId; kind: "to"; index: number };
+
+type OrderChangeSource = "move-up" | "move-down" | "drag-drop" | "save-rollback";
+
+function reorder(ids: readonly CardId[], intent: MoveIntent): readonly CardId[];
+```
+
+`reorder` 是按钮和拖动唯一使用的规则：保留全部 ID、保持非目标卡片的相对顺序、将目标索引限制到 `[0, ids.length - 1]`，无变化时返回原引用。它不读 DOM、不发请求、不处理动画。
+
+### 顺序模型：建议 `useCardOrder`
+
+板级所有者（而非单卡片）持有：
+
+- `confirmedIds`：最近一次成功保存的完整快照；
+- `optimisticIds`：当前已提交且 UI 使用的顺序；
+- `dragSession?: { cardId; originIds; draftIds; pointerId }`：仅在直接操作期间存在；
+- `displayedIds = dragSession?.draftIds ?? optimisticIds`：派生值，不单独存储；
+- 保存队列状态：一个 `inFlight` 快照和至多一个 `queuedLatest` 快照；
+- `mounted`/发布代次：只阻止卸载后的 React 状态与错误发布，不用于取消已经授权的保存。
+
+公开给页面的窄接口建议为：
+
+```ts
+interface CardOrderController {
+  displayedIds: readonly CardId[];
+  move(cardId: CardId, delta: -1 | 1): void;
+  beginDrag(cardId: CardId, pointerId: number): void;
+  previewDrag(targetIndex: number): void;
+  commitDrag(): void;
+  cancelDrag(): void;
+}
+```
+
+所有会改变 `displayedIds` 的方法先请动画协调器记录当前视觉矩形，再同步更新 React 状态。`commitDrag` 只把最终 `draftIds` 写入 `optimisticIds` 并入保存队列一次；它不重复换序。
+
+### 有序、合并的保存策略
+
+`saveOrder` 接收完整快照，因此连续操作只要求服务端最终收到按发起顺序执行的、包含最新意图的快照，不要求每个短暂中间排列都落库：
+
+```text
+本地提交 A：UI=A，立即 save(A)
+save(A) 未完成时提交 B/C：UI 立即=B/C，queuedLatest 依次被 B、C 替换
+save(A) 成功：confirmed=A；随后 save(C)
+save(C) 成功：confirmed=C
+```
+
+同一时刻只允许一个 `saveOrder` 调用，避免服务端提交次序与调用次序相反。防抖本身不提供这个保证，因此不作为正确性机制。
+
+失败按请求快照与当前意图的关系处理：
+
+- `save(A)` 失败且 `A` 仍是最新意图：通过同一个顺序模型将 UI 回到 `confirmedIds`，展示已有标准错误；不自动盲重试。
+- `save(A)` 失败但队列已有 `C`：保留 UI 的 `C`，展示标准错误，然后调用 `save(C)`；A 的旧闭包不得回退 C 或清除 C 的 pending 状态。
+- 卸载后不再发布 React 状态、焦点、动画或错误；在 JS 上下文仍存活时，已创建的队列继续按序完成。整页卸载保证受前述 API 待核对项限制。
+
+错误只由顺序模型调用项目现有错误提示一次。动画协调器、拖动会话和纯排序函数都不捕获或翻译保存错误。
+
+## 3. 交互与动画设计
+
+### 按钮、焦点与播报
+
+- 每张卡继续复用已有 `Button`，提供可见/可访问名称“上移”“下移”；位于首/尾时按现有 Button 能力表达不可用。
+- 激活按钮时，记录 `{ cardId, control: "up" | "down" }`。稳定 `card.id` key 通常会让 React 移动同一 DOM 节点并自然保留焦点；布局提交后只做校验：若原控件仍可操作则不干预，若它因抵达边界变为不可用，则聚焦同卡的拖动把手，次选同卡另一可用移动按钮。绝不按数组索引找卡片。
+- 拖动把手使用可聚焦的原生按钮语义，具有卡片名称和“拖动排序”说明；拖动结束或取消后聚焦同一卡片的把手。
+- 板级 `aria-live="polite"` 区域在按钮提交或拖放结束后播报一次“已将 {卡片名} 移到第 {n} 位，共 {total} 项”；拖动经过每个槽位时不连续刷屏。卡片名取真实 Card 的既有可访问名称契约，不能临时读取展示文本拼凑。
+
+### 无第三方库的 Pointer Events 拖动
+
+此选择服务于单个板内的一维业务顺序，并复用按钮作为完整的非拖动替代；不建设通用拖放框架。
+
+1. 在拖动把手 `pointerdown` 后调用 `setPointerCapture`，建立 `dragSession`。只有把手设置适合直接操作的 `touch-action`，不能禁用整个滚动容器的触摸滚动。
+2. 使用复用 Card 外观的、`aria-hidden` 且 `pointer-events: none` 的固定定位拖动预览层跟随指针；原网格仍包含同一真实卡片位置。每帧只通过一个 `requestAnimationFrame` 写预览层的 `transform`，不让每个像素移动触发 React render。
+3. 目标索引由 `resolveGridInsertion(rects, point, direction)` 计算。它读取当前 DOM 顺序的卡片矩形，按 CSS Grid 的视觉行分组，并按 LTR/RTL 排列行内槽位；单列退化为按卡片垂直中点选择。卡片高度、列数或容器大小不能写死。只有目标索引变化时才调用 `reorder(originIds, { kind: "to", ... })` 更新草稿。
+4. 指针接近滚动容器上下边缘时，由同一拖动会话的 RAF 执行有上限的 `scrollBy`，随后用最后指针坐标重新求插入位置。滚轮/触控板产生的滚动也在下一帧重新测量，不能缓存失效矩形。
+5. `pointerup` 提交；`Escape`、`pointercancel`、卡片被移除或板组件卸载时取消。结束路径统一释放 pointer capture、RAF、监听器和预览层，且可重复调用。
+
+浏览器矩阵核实后若 Pointer Events 不满足正式范围，应在这个 `DragInteraction` 边界内改用项目认可的成熟拖拽方案；`reorder`、顺序模型、保存和动画契约无需改变。
+
+### 可中断 FLIP：建议 `useOrderLayoutMotion`
+
+CSS Grid 的布局位置不能仅靠普通 CSS transition 表达；卡片高度不固定又不适合 scale，因此使用只做 `translate` 的 FLIP，并以 WAAPI 管理中断：
+
+1. **First**：每次顺序状态改变前，按 `card.id` 从 ref map 读取各卡当前 `getBoundingClientRect()`。若旧动画正在运行，这个矩形代表屏幕上用户实际看到的位置。
+2. **Last**：React 写入新的真实 DOM 顺序后，在 `useLayoutEffect` 中先取消旧动画，再批量读取自然布局矩形。若 First/Last 期间滚动偏移已经改变，则校正共同滚动量；无法可靠配对时直接跳过该次动画。
+3. **Invert/Play**：对仍存在且发生位移的卡片从 `translate(first.left-last.left, first.top-last.top)` 动画到 `translate(0, 0)`。不改变布局宽高，不用 scale 扭曲内容。
+4. 新排序到来时重新从当前视觉位置取 First，并替换旧动画；任何动画都不阻止 `move`、拖动预览或保存。
+
+建议默认时长约 180–220ms，并按距离限制在一个短区间内；具体时长与 easing 应在真实页面验证后确定，不作为已测结论。`prefers-reduced-motion: reduce` 时不创建位置动画，DOM 直接到最终位置。
+
+`ResizeObserver` 发现容器或卡片尺寸变化时取消当前动画并清理 transform，让真实响应式布局立即显现；滚动不取消附着在卡片上的 transform，但会使下一次命中测试重新测量。路由离开/卸载时取消全部 `Animation`、RAF、observer 和临时样式。WAAPI 缺失、测量异常或动画 promise 失败都只清理视觉状态，不回写任何顺序。
+
+## 4. 技术架构图

+以下均为建议模块，需在真实应用目录中按现有结构落位。

+```text

+          | failure + snapshot 仍最新
+          |   -> 标准错误 -> optimisticIds = confirmedIds -> 同一 FLIP 回退
+          + failure + 已有更新快照
+              -> 标准错误 -> 不覆盖当前 UI -> saveOrder(更新快照)
+  -> DOM 提交后校验 card-7 内焦点 -> 一次 polite 播报

+## 6. 依赖顺序明确的 5 个实施步骤
+
+### 步骤 1：建立共享排序规则和板级顺序模型
