+
+状态：拟议设计，未实施  
+范围：React + TypeScript 管理系统中的商品页、订单页筛选区

+## 1. 目标、事实与边界
+
+### 1.1 目标与验收行为
+
+1. 商品页包含关键词、分类、上架状态。用户可以编辑草稿；只有“应用”才更新 URL 并触发查询。
+2. 订单页包含关键词、日期范围、订单状态。每次形成合法值后立即更新 URL 并触发查询；暂时不合法的日期编辑留在控件中并显示字段级错误，不污染 URL，也不查询。
+3. URL 是**已生效筛选**的唯一来源。刷新、直接打开链接及浏览器前进/后退后，控件和结果都恢复为该 URL 表示的值。
+4. 商品重置为“已上架 + 不限分类 + 空关键词”；订单重置为“近 30 天 + 全部状态 + 空关键词”。
+5. 结果列表和结果数量都来自页面查询返回数据，不复制保存 count。
+6. 两页使用一致的视觉密度、反馈位置和长标签布局；在窄容器、200% 缩放、较长译文与纯键盘操作下仍可用。
+
+### 1.2 已知可复用能力
+
+- 既有设计系统的 `Field`、`Input`、`Select`、`Button` 与布局 tokens 继续负责主题、标签、焦点、键盘和禁用语义；业务代码不重做控件。
+- 既有路由能力继续读写查询参数；新代码只补页面筛选的 codec 和提交策略。
+- 既有页面查询层继续负责数据、loading 和标准错误。筛选层提供由 URL 解码出的查询入参，不复制请求生命周期。
+
+### 1.3 非目标
+
+- 不更换表单库、路由或查询方案，不建设通用 schema 框架。
+- 不修改查询层的标准错误 UI，不增加缓存、预取、防抖、动画或性能优化。
+- 不把两页不同的业务状态合并成一个“通用状态枚举”。
+- 不在本设计中决定真实枚举成员、后端字段名或仓库路径；这些必须在实施前从现有领域类型、路由和查询调用处确认。

+### 1.4 待源码确认的约束
+
+以下不阻塞结构设计，但会阻塞对应实现提交：

+- 商品上架状态、订单状态的真实 TypeScript 类型和值集合，以及查询层所需字段名。
+- 路由 API 的 `push`/`replace` 形式、URL 参数删除方式，以及查询层对快速换参时取消或丢弃陈旧结果的既有保证。
+- “近 30 天”的业务时区和边界。本文暂按业务时区内包含今天的 30 个自然日（`from = today - 29 days`，`to = today`，两端包含）设计；如现有查询契约不同，只替换日期策略函数。
+- 日期输入/格式化是否已有设计系统或项目级封装；应优先复用，不能从本文名字推断其存在。
+
+## 2. 关键决定
+
+### 2.1 URL、草稿与查询各自只拥有一种事实
+
+- `applied filters` 不放入 React state；每次渲染都由当前路由 query 经页面 codec 解码得到。
+- 查询 key / 查询参数只由 `applied filters` 产生。因此改变控件本身不会暗中请求，路由导航一定能驱动同一查询。
+- 商品页单独拥有 `draft`，用于“先编辑、后应用”。URL 变化（含前进/后退）时，以新 URL 覆盖商品草稿，避免表单显示旧草稿而列表显示新结果。
+- 订单页的关键词和状态没有第二份长期 state；合法编辑直接导航。日期控件仅保留完成一次合法范围所需的短暂 `dateDraft`，URL 变化时同步回 URL 值。
+- 数量使用查询结果中的 count/total 字段或由查询数据按真实契约推导；组件不维护 `resultCount` state。
+
+该模型允许的短暂差异只有两种：商品明确未应用的草稿，以及订单日期明确报错的局部输入。其余时刻，控件、URL 和查询入参一致。
+
+### 2.2 两套领域 codec，不能用一个泛型 status codec
+
+两个页面可共享纯结构工具（如去掉空参数、稳定排序），但拥有独立 codec：
+
+```ts
+// 拟议类型；真实枚举从现有领域模块导入。
+type ProductFilters = Readonly<{
+  keyword: string;
+  categoryId: string | null;
+  listingStatus: ProductListingStatus;
+}>;
+
+type OrderFilters = Readonly<{
+  keyword: string;
+  dateRange: Readonly<{ from: LocalDate; to: LocalDate }>;
+  orderStatus: OrderStatus | 'all';
+}>;
+
+interface QueryCodec<T> {
+  parse(search: URLSearchParams, context: ParseContext): T;
+  serialize(value: T): URLSearchParams;
+}
+```
+
+`ProductListingStatus` 与 `OrderStatus` 保留各自业务含义和允许值。建议参数名也显式区分为 `listingStatus` 和 `orderStatus`；页面位于不同路由不构成混用它们的理由。
+
+每个 codec 是各自页面 URL 规则的唯一实现位置，负责：
+
+- 缺省值、已知枚举校验、日期格式与区间合法性；
+- 空关键词和默认的“不限分类”/“全部状态”如何省略；
+- 参数稳定顺序和规范值输出；
+- 未知值回退到该字段默认值，并通过一次 `replace` 写回规范 URL，避免无效地址长期存在；
+- 保留不归筛选区所有的 query 参数（例如分页规则若已存在），只替换筛选区拥有的 keys。
+
+关键词只做既有查询契约要求的规范化；在源码确认前不擅自添加长度或字符限制。分类 ID 先按既有路由/查询契约解析，不能假设全部分类选项已同步加载。
+
+### 2.3 默认值与可恢复日期
+
+商品默认值是稳定常量，可在 URL 中省略，由 parser 补出。
+
+订单“近 30 天”是随时间变化的默认值。为了让复制链接和跨日刷新仍恢复**同一个已生效范围**：
+
+1. 首次进入且 URL 没有 `from`/`to` 时，用注入的 `getToday(businessTimeZone)` 计算范围；
+2. 立即用 `replace` 将两个明确的本地日期写回 URL；
+3. 查询使用同一计算结果，不能在 render 和导航两个位置各读一次时钟；
+4. 点击重置时重新计算当日近 30 天并显式写入 URL。
+
+这样 URL 才是可恢复的来源，而不是“URL + 访问时刻”共同决定已生效值。日期序列化使用不带时刻的 `YYYY-MM-DD`；转换为后端边界由现有查询适配层依业务时区完成。
+
+### 2.4 导航历史策略
+
+- 商品“应用”和两页“重置”是明确提交动作，使用 `push`，从而浏览器返回可恢复上一个已生效筛选。
+- 订单合法的逐字段编辑使用 `replace`，避免关键词每输入一个字符产生一个历史节点；浏览器访问任何历史 URL 时仍由 parser 恢复筛选。
+- 若序列化结果与当前筛选参数规范等价，不导航也不重复查询。商品“应用”在无改动或非法时禁用。
+- 路由更新不得通过组件 `key` 重挂载整个页面，输入焦点保持在原控件；不自动把焦点移到结果区。
+
+### 2.5 共享布局，不共享业务控制器
+
+新增一个无领域状态的 `FilterLayout`（名称可按仓库惯例调整），只统一：容器、字段网格、操作区、反馈插槽和设计 tokens。商品和订单各自的表单/控制器保留提交语义。这样一致性由结构保证，业务变化不会堆成 `mode`、`autoApply` 等布尔组合。
+
+拟议用法：
+
+```tsx
+<FilterLayout
+  fields={<>...页面自己的 Field...</>}
+  actions={<>...页面自己的 Button...</>}
+  feedback={<FilterFeedback queryState={queryState} total={data?.total} />}
+/>
+```
+
+`FilterFeedback` 仅呈现既有查询状态和数据，不拥有它们；若项目已有等价反馈组件则直接复用，不新增组件。

+## 4. 交互、布局与无障碍
+
+### 4.1 语义和键盘
+
+- 每页筛选区使用带可访问名称的原生 `<form>` 语义，内部继续使用设计系统控件；每个 `Field` 的 label 与控件程序化关联。
+- 商品页 Enter 提交表单，效果等同“应用”；“重置”是 `type="button"`，避免隐式提交。应用按钮仅在 draft 合法且与 applied 不同时可用。
+- 订单页的变更由控件 change/commit 事件处理；表单 submit 不制造第二次导航。状态和日期控件沿用既有设计系统的键盘契约。
+- Tab 顺序与 DOM 顺序一致：关键词 → 分类/日期 → 状态 → 操作。CSS 不做视觉重排。
+- 路由更新和查询完成后不抢焦点。字段错误通过 `Field` 既有错误关联暴露；仅靠红色不能表示错误。
+
+### 4.2 响应式约束
+
+字段使用内容驱动的 Grid，而不是设备型号断点：
+
+```css
+.fields {
+  display: grid;
+  grid-template-columns: repeat(auto-fit, minmax(min(100%, var(--filter-field-min)), 1fr));
+  gap: var(--space-filter-row) var(--space-filter-column);
+  align-items: start;
+}
+
+.field,
+.actions,
+.feedback {
+  min-inline-size: 0;
+}
+```
+
+- `--filter-field-min` 与 gap 映射为现有布局 tokens；不引入孤立像素值。
+- 标签在控件上方，允许自然换行，不设固定高度、单行截断或依赖英文长度。
+- 操作区另起一行并允许按钮换行；窄容器自然成为单列。触控目标大小和焦点样式沿用设计系统。
+- 使用逻辑属性；不假定左到右。翻译使用完整消息 key，日期显示走项目 formatter。
+- 200% 缩放时不产生页面级水平滚动，标签不遮挡控件，焦点不被 sticky/overlay 遮住。
+
+### 4.3 查询反馈
+
+- 结果容器复用查询层 loading/error，并设置适当的 `aria-busy`；筛选控件在加载期间仍可编辑。
+- 反馈区位置在两页一致。可见 loading 不把旧结果冒充新结果；具体保留旧结果还是 skeleton 沿用现有查询层策略。
+- 查询成功后显示由当前响应得到的结果数量；必要时用克制的 `aria-live="polite"` 宣告最终数量。订单关键词连续输入期间不逐次朗读“正在加载”。
+- 查询失败时 URL 和已生效筛选保持不变，由现有标准错误提供重试；重试仍使用当前 URL 解码值。
+- 快速连续变更时，页面只能展示当前 route key 对应的响应。实施前若发现既有查询层不保证取消或忽略陈旧响应，应在查询适配边界补齐，而不是在筛选组件中比较时间戳。

+边界要点：`FilterLayout` 不能依赖两个 codec 或查询层；两个 codec 不能互相导入状态枚举；查询只接收 URL 所表示的 applied filters。

+## 6. 数据流图
+
+两个代表性流程覆盖两种 materially different 的提交语义：
+
+```text
+商品页：编辑后应用
+
+用户键入/选择
+  -> useProductFilters.setDraft()
+  -> 商品 draft 更新
+  -> 重新渲染表单（URL、查询、结果均不变）
+  -> 用户点击“应用”或按 Enter
+     -> 校验 draft
+        ├─ 非法：Field 显示错误；URL/查询不变
+        ├─ 与 applied 规范等价：no-op
+        └─ 合法且有变化：productFilterCodec.serialize(draft)
+           -> router.push(合并后的 query)
+           -> router 提供新 params
+           -> productFilterCodec.parse(params) = applied
+           -> 页面查询层以 applied 为 key 请求
+              ├─ loading：反馈区/结果区显示既有 loading 行为
+              ├─ error：标准错误；保留 URL 与筛选，可用当前 applied 重试
+              └─ success(data)：渲染结果；数量取自 data
+
+浏览器前进/后退
+  -> router 提供历史 params
+  -> parse 为新 applied
+  -> useProductFilters 用新 applied 覆盖 draft
+  -> 查询与表单共同恢复
+
+订单页：合法编辑立即应用
+
+用户改变关键词/订单状态
+  -> useOrderFilters 校验领域值
+  -> orderFilterCodec.serialize(nextApplied)
+  -> router.replace(合并后的 query)
+  -> parse -> 页面查询层 -> loading/error/success -> 结果与数量
+
+用户编辑日期一端
+  -> dateDraft 更新
+  -> validateDateRange(dateDraft)
+     ├─ 不完整或 from > to：Field 错误；URL/查询仍使用原 applied
+     └─ 合法：serialize(nextApplied) -> router.replace -> parse -> 查询
+
+订单首次无日期参数
+  -> 读取一次 injected today
+  -> recent30Days(today)
+  -> replace 写入明确 from/to
+  -> 同一范围进入 applied 和查询
+
+任一查询快速换参
+  -> 查询层将响应关联到 route/query key
+     ├─ 旧响应：取消或忽略，不进入当前页面
+     └─ 当前响应：渲染并产生当前数量
+```

+## 7. 依赖有序的实施计划（5 步）
+
+### 步骤 1：确认真实契约并建立两套 URL codec
+
+功能：从现有商品/订单领域类型、路由和 query adapter 落实 `ProductFilters`、`OrderFilters`、参数 keys、默认值、日期边界和规范化规则。实现两个独立 codec 与 `recent30Days(today)`。  
+前置：读取真实源码与现有测试惯例。  
+影响所有者：各页面 route adapter；领域 enum 只被导入，不重定义。  
+完成检查：codec 单测覆盖缺省、完整值、空值、未知枚举、非法/反向日期、parse/serialize 往返、保留非筛选 query keys；类型检查证明商品状态不能传给订单 codec。
+
+### 步骤 2：接通 URL 到查询的单向主链
+
+功能：两个页面都只以 codec 解析结果调用现有查询；规范化无效 URL；订单首次缺日期时将一次计算出的范围写回 URL。  
+前置：步骤 1。  
+影响所有者：页面 route adapter、现有 query hook 的调用点。  
+完成检查：集成测试从直接 URL、刷新等价装载、前进/后退三条入口断言同一 applied filters 和查询参数；结果数量只取查询数据。验证快速换参不会显示旧 key 的响应。
+
+### 步骤 3：实现两种页面控制器和交互
