+# 多文件分片上传前端技术设计
+
+## 1. 结论与边界
+
+采用“页面级上传队列 + 单文件会话执行器 + `appApi` 适配器”的结构。队列只允许两个单文件执行器同时占用运行槽；每个文件顺序上传分片，以服务端 `confirmedIndices` 为恢复依据。React 只订阅快照并发送用户命令，不直接编排请求。
+
+这是设计文档，不代表代码已经实现。当前工作区没有应用源码；以下 `src/uploads/*` 均为拟新增或拟迁移路径。已知的现有入口来自题目提供的 `src/uploads/upload.ts`，已知产品契约来自题目提供的 `docs/uploads.md` 内容，二者均未在工作区中找到。实施前必须先确认真实仓库中的调用方、测试框架以及 `appApi` 已暴露的分片方法名。
+
+范围内：页面存活期内的多文件队列、最多两个活动文件、确认进度、暂停/继续、取消、失败重试、完成响应丢失后的对账，以及卸载时本地资源释放。
+
+范围外：刷新恢复、持久化 `File`、Service Worker/后台上传、跨标签页协调、分片内字节级进度、同一文件多个分片并行、重新实现认证或通用请求框架。

+## 2. 已接受事实和架构决定
+
+- 所有网络调用继续经过现有 `appApi`；认证、取消信号和标准错误归它负责，上传模块不拼认证头、不建立第二套 HTTP 客户端。
+- 后端会话由 `uploadId` 标识。`create` 给出 `partSize`；`putPart` 确认单片；`inspect` 返回已确认片；`complete` 返回 `fileId`；`status` 可对账；`abort` 终止会话。
+- “已上传进度”只按服务端确认的分片字节计算。当前 `putPart` 契约没有上传进度回调，因此不伪造分片内的平滑进度。若以后要求字节级进度，应扩展 `appApi` 的传输能力，而不是在 UI 中用计时器模拟。
+- 一个运行槽表示一个仍在执行异步步骤的文件工作流（创建、检查、传片或完成）；暂停/取消请求只有在该执行器退出后才释放槽。因此实际同时运行的文件工作流不会超过两个。
+- 单文件内一次只发送一片。这样暂停、重试和确认集合的语义简单；产品没有要求片级并行，不引入第二层并发调度。
+- 暂停只停止本地继续发送，不调用服务端 `abort`。继续和失败重试都先 `inspect(uploadId)`，以服务端确认集合覆盖本地认知，随后跳过已确认片。
+- 取消立即阻止后续分片并中止当前 `putPart`，随后调用 `abort(uploadId)`。只有服务端 `abort` 成功才进入 `canceled`；失败进入可重试取消的错误态，避免把仍存在的服务端会话报告为已终结。尚未取得 `uploadId` 的任务可直接本地取消。
+- `complete` 报错可能是“请求失败”或“响应丢失”。执行器必须调用 `status(uploadId)`：若为 `completed`，以返回的 `fileId` 成功结束；若仍为 `uploading`，进入可重试的完成失败态。重试时再次先查 `status`，而不是盲目重复报告成功。
+- 页面卸载会中止所有本地 `putPart`、使迟到结果失效、清空订阅与 `File` 引用。浏览器卸载阶段不保证异步请求送达，所以不把逐个 `abort(uploadId)` 作为卸载正确性的前提；显式取消仍执行服务端 `abort`。
+- 用户重复添加内容相同的文件仍创建不同任务，以本地 `taskId`（`crypto.randomUUID()`）区分；不根据文件名、大小或时间戳猜测去重。

+## 3. 状态、规则和公开契约
+
+### 3.1 最小状态
+
+每个任务内部持有：
+
+```ts
+type UploadPhase =
+  | 'queued'
+  | 'creating'
+  | 'reconciling'
+  | 'uploading'
+  | 'pausing'
+  | 'paused'
+  | 'finalizing'
+  | 'canceling'
+  | 'failed'
+  | 'completed'
+  | 'canceled';
+
+type UploadSession = {
+  uploadId: string;
+  partSize: number;
+  confirmedIndices: ReadonlySet<number>;
+};
+
+type FailureStage =
+  | 'create'
+  | 'inspect'
+  | 'putPart'
+  | 'complete'
+  | 'status'
+  | 'abort';
+
+type UploadTaskBase = {
+  taskId: string;
+  fileName: string;
+  size: number;
+  confirmedBytes: number;
+  progress: number;
+};
+
+type UploadTaskSnapshot = UploadTaskBase & (
+  | { phase: Exclude<UploadPhase, 'failed' | 'completed'> }
+  | {
+      phase: 'failed';
+      error: { stage: FailureStage; message: string };
+      recovery: 'resume' | 'finalize' | 'cancel';
+    }
+  | { phase: 'completed'; fileId: string; progress: 1 }
+);
+```
+
+`File`、`AbortController`、运行代次和内部 Promise 不进入公开快照。内部记录保存 `File` 与可选 `UploadSession`；`confirmedBytes`、进度、可否暂停/重试/取消均由当前阶段、文件大小和确认集合派生，不维护互相矛盾的布尔值。非完成的零字节任务进度为 0，服务端确认完成后为 1。失败态明确携带恢复命令，完成态必有 `fileId`，从类型上排除“成功但没有文件标识”等组合。
+
+确认字节数按每个合法分片索引的区间长度求和：`min(partSize, size - index * partSize)`。适配器在外部边界拒绝非正 `partSize`、非整数/负数索引和缺失的完成态 `fileId`；知道文件大小的模型层再拒绝越界索引。两层都沿用 `appApi` 的标准错误类型，领域层不重复解析认证或传输错误。
+
+### 3.2 传输边界
+
+```ts
+interface UploadGateway {
+  create(input: { fileName: string; size: number }): Promise<{
+    uploadId: string;
+    partSize: number;
+  }>;
+  putPart(
+    uploadId: string,
+    index: number,
+    bytes: Blob,
+    signal: AbortSignal,
+  ): Promise<void>;
+  inspect(uploadId: string): Promise<{ confirmedIndices: number[] }>;
+  complete(uploadId: string): Promise<{ fileId: string }>;
+  status(uploadId: string): Promise<
+    | { status: 'uploading' }
+    | { status: 'completed'; fileId: string }
+  >;
+  abort(uploadId: string): Promise<void>;
+}
+```
+
+`src/uploads/uploadApi.ts` 提供唯一具体实现并委托 `appApi`。这里的 `UploadGateway` 是聚焦测试和隔离外部响应形状的端口，不是新请求框架。题目没有给出 `appApi` 分片方法的 TypeScript 名称；实施时应映射真实方法，不能假定一定是 `appApi.upload.create`。`Blob.slice` 按需产生单片，不把整个文件读入内存。

+### 3.3 页面级能力
+
+```ts
+interface UploadQueue {
+  getSnapshot(): readonly UploadTaskSnapshot[];
+  subscribe(listener: () => void): () => void;
+  add(files: readonly File[]): readonly string[];
+  pause(taskId: string): void;
+  resume(taskId: string): void;
+  retry(taskId: string): void;
+  cancel(taskId: string): void;
+  dispose(): void;
+}
+
+function createUploadQueue(options: {
+  gateway: UploadGateway;
+  maxConcurrent?: number; // 产品入口固定传 2；默认值也为 2
+}): UploadQueue;
+```
+
+`src/uploads/uploadQueue.ts` 是有身份和生命周期的页面级对象，拥有任务记录、FIFO 等待队列、两个运行槽、每任务运行代次、当前分片控制器和订阅。所有阶段变更经同一内部 transition 完成。每个异步回调提交结果前比较 `taskId + runGeneration`；暂停、取消、重试或 `dispose` 增加代次，迟到的成功、失败和 `finally` 都不能覆盖新状态。对 `useSyncExternalStore` 返回的快照按 transition 缓存：无变化时保持引用不变，有变化时生成新的不可变快照。
+
+调度规则：
+
+1. `add` 建立 `queued` 任务；调度器按添加顺序填补空槽。
+2. 首次运行执行 `create`；已有会话的继续/重试执行 `inspect`。
+3. 找到最小的未确认索引，`file.slice(start, end)` 后调用 `putPart`；成功才把该索引计入确认集合。
+4. 所有片确认后进入 `finalizing` 并执行 `complete`；失败按上述 `status` 规则对账。
+5. 执行器到达暂停、失败、取消或完成终态后在 `finally` 释放自己的槽并触发下一次调度，但代次检查保证旧执行器不能释放新执行器的槽。
+
+`create` 没有取消信号，但它会取得必须释放的服务端会话。若创建期间收到暂停，创建响应仍只用于保存新 `uploadId/partSize`，随后进入 `paused`，不发送首片；若收到取消，响应到达后立即执行 `abort(uploadId)`；若页面已经 `dispose`，不再发布 UI 状态，并在运行环境仍可执行时尽力 `abort`，但页面卸载正确性不依赖该请求送达。这个资源接管是代次失效规则的唯一特例，不能简单丢弃创建响应并泄漏已取得的会话。
+
+`pause` 仅在 `queued/creating/reconciling/uploading` 可用；对 `uploading` 中的分片调用当前控制器的 `abort()`。`finalizing` 不显示暂停，因为全部字节已经确认且 `complete/status` 没有取消信号；仍允许取消，取消意图使完成结果失效并在当前不可取消请求返回后执行 `abort`。若此时服务端已经完成且 `abort` 被拒绝，显示可操作错误并允许用 `status` 对账，不能同时显示“已取消”和“已完成”。
+
+`src/uploads/useUploadQueue.ts` 在页面实例内创建一次队列，以 `useSyncExternalStore` 订阅快照，并在 effect cleanup 中调用 `dispose`。组件只能通过该 hook 的快照和命令工作。若真实应用已有页面级 provider/store 约定，则把同一 `UploadQueue` 生命周期接到该约定，不能再复制一份任务状态。

+## 5. 代表性数据流
+
+```text
+User selects [A, B, C]
+  -> UploadPanel.add(files)
+  -> UploadQueue creates taskId A/B/C as queued
+  -> scheduler assigns slots to A and B; C remains queued
+
+A runner
+  -> gateway.create({name, size})
+  <- {uploadId, partSize}
+  -> slice File for index 0
+  -> gateway.putPart(uploadId, 0, blob, signal)
+  <- acknowledgement
+  -> transition adds confirmed index 0
+  -> snapshot derives confirmedBytes/progress -> React renders
+  -> repeat only for unconfirmed indices
+
+Pause branch during a part
+  -> pause(A) increments runGeneration and aborts A's part controller
+  -> stale putPart success/error/finally cannot publish
+  -> runner exits, phase becomes paused, slot starts C
+  -> resume(A) queues a new generation
+  -> inspect(uploadId) <- authoritative confirmedIndices
+  -> replace local confirmation set, skip confirmed parts, continue
+
+Completion branch
+  -> complete(uploadId)
+  <- {fileId} -> completed -> visible 100%
+  X response/error
+  -> status(uploadId)
+     <- completed + fileId -> completed -> visible 100%
+     <- uploading -> failed(stage=complete) -> visible Retry
+     X status error -> failed(stage=status) -> Retry first runs status again
+
+Cancel branch
+  -> cancel(A) invalidates generation and aborts current part locally
+  -> abort(uploadId)
+     <- acknowledgement -> canceled; File reference released
+     X error -> failed(stage=abort); no further parts; visible Retry cancel
+
+Page unmount
+  -> dispose()
+  -> invalidate all generations + abort local controllers
+  -> clear listeners, queue entries and File references
+  -> late callbacks are ignored
+```
