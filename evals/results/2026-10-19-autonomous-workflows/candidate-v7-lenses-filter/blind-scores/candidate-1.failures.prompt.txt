+# 商品页与订单页筛选区技术设计
+
+- 状态：拟议设计，尚未实施
+- 范围：React + TypeScript 管理系统中的商品页、订单页筛选区
+- 依据：题目给定的项目事实与已接受需求；工作区未提供应用源码

+## 1. 结论
+
+采用“页面领域模型 + 共享展示骨架”的结构：商品和订单分别拥有筛选类型、默认值、URL 编解码、校验和提交策略；仅共享基于既有设计系统的 `FilterRegion` 布局与反馈约定。不要建立接收字段配置数组的万能筛选器，也不要复用名为 `status` 的跨领域枚举。
+
+URL 是唯一已生效筛选来源。页面从 URL 解析出 `effectiveFilters`，再生成既有查询层的查询参数；查询数据同时提供列表和结果数量。表单只在确有编辑期需求时保存草稿：商品始终有本地草稿，订单只为日期范围的未完成或非法中间输入保留表单值。任何路径都不单独保存一份“已生效筛选”或结果计数。

+## 2. 已知事实、范围和待接入事实

+### 已知并沿用

+- 已有 `Field`、`Input`、`Select`、`Button` 和布局 tokens，且已处理主题、标签、键盘与禁用语义。

+## 3. 产品契约
+
+### 3.1 领域类型与默认值
+
+拟议类型表达领域差异，而不是追求表面复用：
+
+```ts
+type ProductFilters = Readonly<{
+  keyword: string;
+  categoryId: ProductCategoryId | null;
+  listingStatus: ProductListingStatus;
+}>;
+
+type OrderFilters = Readonly<{
+  keyword: string;
+  placedFrom: LocalDate;
+  placedTo: LocalDate;
+  orderStatus: OrderStatus | null;
+}>;
+```
+
+- `ProductListingStatus` 与 `OrderStatus` 必须引用或贴合各自现有领域定义；即使展示文案相同也不能互相赋值。
+- 商品默认值：`keyword = ''`、`categoryId = null`、`listingStatus = 已上架对应的真实枚举值`。
+- 订单默认值：`keyword = ''`、`orderStatus = null`、`placedTo = 业务时区中的今天`、`placedFrom = placedTo 往前 29 个日历日`，即包含今天在内共 30 个日历日。若现有后端使用半开区间，只在查询 DTO 适配处转换，不改变 UI 领域含义。
+- 日期使用无时刻的 `YYYY-MM-DD` 日历日期参与 URL 序列化；不能用 UTC 时间戳隐式改变用户所见日期。业务时区须从项目现有日期策略取得，若项目尚无该策略，实施前这是唯一需要产品/后端确认的日期契约。
+
+### 3.2 URL 契约
+
+每个页面有自己的纯解析器和序列化器：
+
+```ts
+declare function parseProductFilters(search: URLSearchParams): ProductFilters;
+declare function writeProductFilters(
+  current: URLSearchParams,
+  value: ProductFilters,
+): URLSearchParams;
+
+declare function parseOrderFilters(
+  search: URLSearchParams,
+  today: LocalDate,
+): OrderFilters;
+declare function writeOrderFilters(
+  current: URLSearchParams,
+  value: OrderFilters,
+): URLSearchParams;
+```
+
+拟议的自有参数名如下，最终须与现有路由/后端外部契约对齐：
+
+| 页面 | 自有 URL 参数 | 说明 |
+| --- | --- | --- |
+| 商品 | `q`、`category`、`listingStatus` | 明确是上架状态 |
+| 订单 | `q`、`from`、`to`、`orderStatus` | 明确是订单状态 |
+
+规则：
+
+1. 解析器只读取本页自有参数；未知键留给其他页面能力，不因筛选写入而删除。
+2. 空关键词归一为 `''`；应用时裁掉首尾空白，保留中间空白。
+3. 缺失、空值或未知枚举值回退到该页默认值。非法日期范围不进入查询；对外部非法 URL，整个日期范围回退为近 30 天。
+4. 序列化使用稳定键序；等于默认值的字段省略，生成规范 URL。读取非法 URL 时不自动改写历史记录，但页面展示与查询都使用解析后的安全值；下一次用户提交时写成规范 URL。
+5. 序列化从当前 `URLSearchParams` 复制后仅更新本页自有键，保留排序、分页等非自有键。若真实页面已有“筛选变化时回到第一页”的契约，由页面路由适配器同时执行；本文不擅自规定新的分页行为。
+6. 相同规范 URL 的写入是 no-op，不产生历史项或重复查询。
+
+### 3.3 状态与转换
+
+商品页：
+
+- `effectiveFilters = parseProductFilters(location.search)`，只由 URL 决定。
+- `draftFilters` 是筛选表单拥有的本地状态，首次渲染及 URL 导航变化时重置为 `effectiveFilters`。因此浏览器前进/后退会恢复 URL 对应筛选，并丢弃未应用草稿；这符合 URL 权威性。
+- 编辑只改变 `draftFilters`，不写 URL、不查询。
+- “应用”先归一化并校验草稿；合法且与当前生效值不同则 `push` 新 URL。查询层随后因 URL 参数变化而查询，事件处理器不直接再调用查询。
+- “重置”同时把草稿设为商品默认值，并在生效值非默认时 `push` 默认 URL；即使生效值已默认，也必须清掉未应用草稿。
+- “应用”在草稿非法或未改变时禁用；“重置”仅在草稿和生效值均为默认时禁用。
+
+订单页：
+
+- `effectiveFilters = parseOrderFilters(location.search, today)`，只由 URL 决定。
+- 关键词、状态等单字段编辑一旦得到合法规范值，立即以 `replace` 写 URL；不为每个字符制造浏览历史项，也不延迟或防抖（需求要求合法编辑后立即更新）。
+- 日期控件可产生“只填一端”或起始日晚于结束日的中间态，因此日期输入拥有最小的 `dateDraft`。合法完整时立即 `replace` URL；非法或未完成时保留输入、显示字段组错误，不写 URL、不查询。URL 导航变化时以 URL 值覆盖该中间态。
+- “重置”是明确命令：清空关键词并写入近 30 天/全部状态，以 `push` 产生一个可返回的历史点；若已是默认规范 URL，则 no-op。
+- 浏览器前进/后退只需让路由位置变化；页面重新解析 URL 并由查询层恢复结果，不以 effect 把旧表单状态反写 URL。
+
+选择 `replace` 处理订单的连续即时编辑，是为了同时满足即时生效和可用的浏览历史；刷新以及所有真实历史项的前进/后退仍可恢复相应筛选。若项目已有统一 history 策略，应保留该策略，但必须增加“关键词逐字输入不能污染历史栈”的验收。
+
+### 3.4 查询、并发和反馈
+
+- 页面把 `effectiveFilters` 显式映射为既有查询层 DTO。URL 写入是触发查询的唯一入口；禁止同时执行 `setSearchParams` 和手工 `refetch`。
+- 既有查询层继续拥有数据、loading、标准错误、缓存/取消等职责。订单可能连续改 URL，接入时必须验证旧请求不能覆盖当前 URL 对应结果；若既有查询层以查询键隔离并只发布当前订阅结果则直接复用，否则应在查询层修正，而不是在表单里增加请求序号。
+- 结果数量从当前查询成功数据派生，与列表一起展示；不保存本地计数。加载中保留或清空旧数据遵循查询层现有契约，但 loading 必须可见，且不能把旧结果数量冒充为新筛选已完成的数量。
+- 查询错误使用页面现有标准错误与重试路径。表单只负责同步输入错误（例如日期倒置），不吞掉或重写查询错误。
+- 结果区域在加载时使用既有视觉反馈并设置合适的 `aria-busy`；查询成功后的结果数量使用项目已有公告模式，若没有则在计数容器使用克制的 `aria-live="polite"`，避免每次输入同时产生多处播报。
+
+## 4. 组件与模块边界
+
+拟议结构（仅表达所有权，落地服从仓库已有目录）：
+
+```text

+  FilterRegion.tsx          # 共享布局、区域命名、操作/反馈槽位
+  filterRegion.css          # 仅使用既有 tokens 的容器自适应规则

+`FilterRegion` 的拟议 API 保持结构复用而不接管业务：
+
+```tsx
+type FilterRegionProps = {
+  label: string;
+  fields: React.ReactNode;
+  actions?: React.ReactNode;
+  feedback?: React.ReactNode;
+};
+```
+
+它渲染有可访问名称的语义化筛选区域和布局槽位，但不决定是否使用 `<form>`；商品业务组件拥有 form/submit 语义，订单业务组件拥有即时编辑语义。实际 API 可改为 `children`/子组件组合以符合既有组件风格，但不得接受 `fields: FilterConfig[]` 后自行解释商品与订单规则。业务组件直接组合既有 `Field`、`Input`、`Select`、`Button`；共享层不包装这些控件的标签、键盘或禁用实现。
+
+若真实设计系统已有等价的表单布局/工具栏组件，则直接使用并删除拟议 `FilterRegion`；共享新组件只有在它实际统一容器布局、区域语义和反馈槽位时才成立。

+## 5. 布局与交互规范
+
+- 筛选字段采用容器感知的 CSS Grid，例如 `repeat(auto-fit, minmax(min(100%, <tokenized-min>), 1fr))`；断点由长标签或控件发生挤压的位置决定，不按设备型号决定。
+- 字段允许换行和增高，不设置文字区域固定高度；每个 Grid 子项使用 `min-inline-size: 0`。操作区可换行，在窄容器中占满一行，按钮保持合理点击面积。
+- 长标签保持在对应控件之前，使用既有 `Field` 的关联标签；日期范围以 `<fieldset>`/`<legend>` 形成组名，起止日期各有独立标签。不要用 placeholder 代替标签。
+- DOM 顺序与视觉、Tab 顺序一致：关键词 → 分类/日期 → 状态 → 操作。200% 缩放或窄容器时不做 CSS 视觉重排。
+- 所有间距、字号、颜色、焦点和禁用状态来自既有 tokens/组件；不复制设计系统内部 CSS，也不以颜色单独表示非法、加载或选中。
+- 商品 `<form>` 支持 Enter 提交“应用”，按钮使用原生 submit 语义；重复提交同一规范值为 no-op。订单无整表提交要求，字段的既有键盘交互保持不变。
+- 日期错误与字段组稳定关联（`aria-describedby` 或设计系统等价能力），修正后清除。查询 loading 不禁用所有筛选控件；用户可以继续修改，当前 URL 永远决定应展示哪次结果。
+- 没有动画。主题、强制颜色、长翻译、LTR/RTL（若项目已支持）、窄容器和 200% 缩放均通过真实消费页面验证。
