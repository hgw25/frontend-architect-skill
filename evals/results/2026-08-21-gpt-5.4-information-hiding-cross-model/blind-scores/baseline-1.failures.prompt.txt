**公开 API 与所有权**
`CheckoutPage.tsx`
- 只负责装配流程，不再持有业务细节。
- 公开 API：页面级 props，例如 `cartId`、`initialAddressId`、`onSuccess(orderId)`.
- 拥有权：跨模块编排状态，比如“当前是否允许提交”“哪些错误显示为 toast/inline”。

`useCheckoutDraft`
- 负责表单草稿的读取、更新、校验触发、脏态判断、持久化策略。
- API：
  - `draft`
  - `updateField(name, value)`
  - `validation`
  - `isDirty`
  - `commitDraft()` / `resetDraft()`
- 副作用：本地草稿持久化；不要夹带价格、优惠券、支付逻辑。

`useCheckoutPricing`
- 负责从 `draft + cart + coupon + inventory status` 推导可展示金额。
- API：
  - `priceBreakdown`
  - `pricingState` (`idle | recalculating | ready | stale`)
  - `refreshPricing()`
- 约束：优先做纯计算；如果必须请求服务端重算，网络调用放到 `checkoutService`，hook 只协调。

`useCoupon`
- 负责优惠券输入、验证、应用、移除、请求取消。
- API：
  - `couponCode`
  - `setCouponCode(code)`
  - `appliedCoupon`
  - `applyCoupon()`
  - `removeCoupon()`
  - `status`
  - `error`
- 副作用：调用 `couponService`。
- 不拥有最终价格；只产出“优惠上下文”。

`useInventoryReservation`
- 负责库存订阅/预占/失效感知。
- API：
  - `inventoryState` (`available | low | unavailable | expired`)
  - `reservationToken`
  - `refreshReservation()`
- 副作用：订阅、轮询、清理。
- 不直接弹 UI；只提供状态和事件。

`usePaymentSession`
- 负责支付 SDK 生命周期。
- API：
  - `mountPayment(element)`
  - `unmountPayment()`
  - `paymentState`
  - `confirmPayment(submitPayload)`
  - `sdkError`
- 副作用：SDK 初始化、实例缓存、卸载清理、事件绑定。
- 约束：不要把下单请求也塞进这里；它只处理支付侧会话与确认。

`useCheckoutSubmit`
- 负责提交编排和竞态控制，是“提交总线”。
- API：
  - `submit()`
  - `status` (`idle | submitting | awaiting_payment | success | failed`)
  - `submitError`
  - `canSubmit`
- 内部依赖：读取 draft/pricing/inventory/payment 的只读快照，调用 `checkoutService` 和 `paymentSession.confirmPayment`。
- 副作用：幂等键、重复点击防护、过期结果丢弃、提交流程状态机。

`services/*`
- 只做 IO 协议，不持有 React 状态。
- `couponService`: `validateCoupon`, `applyCoupon`, `removeCoupon`
- `inventoryService`: `subscribeAvailability`, `reserveInventory`, `releaseReservation`
- `paymentGateway`: `createSession`, `loadSdk`, `confirm`
- `checkoutService`: `repriceCheckout`, `submitOrder`
- 返回值要是稳定的领域对象，不把接口原始响应直接泄漏给组件。

`components/*`
- 以“可独立理解的界面块”拆，不以 DOM 小片段拆。
- `CheckoutForm`: 地址、联系人、配送方式等。
- `OrderSummary`: 金额明细与价格刷新状态。
- `CouponSection`: 输入和应用反馈。
- `PaymentSection`: SDK 容器和支付错误。
- `SubmitBar`: CTA、提交中态、禁用原因。
- `CheckoutAlerts`: 页面级错误/警告汇总。
- 原则：组件尽量接收值和回调，不自己偷偷请求服务。

**依赖方向**
推荐单向依赖，避免回流：

```text
page -> hooks -> services
page -> components
hooks -> model
components -> model(types only)
services -> model(types only)
utils -> model/types or primitive values
```

具体限制：
- `components` 不能直接依赖 `services`。
- `services` 不能依赖 React hook。
- `useCheckoutSubmit` 可以依赖其他 hooks 暴露出的只读接口，但不要反过来让其他 hooks 知道“提交流程”。
- `pricing` 和 `submission` 里的纯领域逻辑可被 hooks 与 services 共同复用；这样测试最稳。

**测试放置**
测试也按职责放，不按技术层硬分：

- `model/__tests__/`

**停止继续拆分的条件**
满足这些条件就应该停，不要继续把目录切碎：

- 一个模块只有一个清晰原因会变化。
- 页面装配层能用几屏代码读懂主流程，但不重新实现业务。
- 价格、优惠券、库存、支付、提交五类副作用已经彼此隔离。
- 大部分业务规则能在 `model` 或单个 hook 测到，不需要通过整页联调才能验证。
- 组件拆出来后有独立语义，而不是“把 JSX 搬文件”。
- 新需求能明确落到一个现有模块，不需要同时改 4 个以上层级。

**不建议的继续拆法**
以下情况通常已经过拆：
- 为了“hooks 目录整齐”把一个强一致流程拆成多个互相 callback 的微 hook。
- 把 `CheckoutForm` 再拆成大量只包一层 `div` 的展示组件。
- 为每个 service 再额外包一层无业务价值的 repository/client/adapter。
- 纯本地、只在 checkout 使用的逻辑提前抽到全局 `shared`.

如果你把真实的 `CheckoutPage.tsx` 和 `features/checkout` 目录贴出来，我可以把这份建议收敛成更具体的模块边界和迁移顺序，而不是停留在职责模板层面。
