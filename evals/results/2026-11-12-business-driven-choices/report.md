## 实际修改与维护归属

| 原问题 | 最终处理 |
| --- | --- |
| 从思想名录开始选方案，容易增加不需要的机制 | 入口先建立业务行为、已确认契约、消费者和已有能力。架构专题负责具体选择：现有能力足够时直接复用，有真实缺口才比较相称的局部扩展/替换；模式目录只解答匹配的缺口。条件必填、不同筛选语义、SDK 映射及搜索/保存并发给出具体起点，不建设新决策引擎 |
| 所有业务变化都可能触发独立文档和两图 | 既有所有权、状态、依赖和失败机制内的窄规则扩展采用简短理由及相关检查，只更新真实变化的契约。新所有权、非平凡状态/并发、跨消费者契约及迁移继续先设计；实质架构/数据流工作保留两视图及最终核对，用户明确要求继续有效 |
| 数字字段及自写测试被当作服务保证 | 架构专题在决定性算法选择前核对语义来源；异步专题区分版本排序、相等语义与本地请求身份，验证专题检查测试预期的独立来源。已确认保证直接复用；未决保证保留为未决，继续独立工作，不静默削弱所需交互或增加防御框架 |
| 绝对低分被解释为技能无收益 | rubric 的区间只描述当前交付质量；收益另依同条件成对结果与必要复测判断。保留原阈值和失败覆盖机制，没有增加评分器或把历史分数重标成新版结果 |

实际入口为 `SKILL.md`，主要选择过程在 `architecture-and-code.md`，方法目录只保留指针。
README 的旧全局文档要求已改写；`cases.yaml` 的共用验收、rubric、协议及
`score_behavior_evals.py::build_failure_prompt` 同步采用相同准备边界，避免生成规则放轻、
评分端仍强制复制文档。没有更改评分数据结构、阈值、安装、版本或发布流程。

业务选择沿用现有工程判断和
[Google 的设计/复杂度审查](https://google.github.io/eng-practices/review/reviewer/looking-for.html)、
[Fowler 的 YAGNI](https://martinfowler.com/bliki/Yagni.html)及既有抽象指导，不将本地判断
包装成新的行业模式。异步专题以 [RFC 9110 的 ETag](https://www.rfc-editor.org/rfc/rfc9110.html#name-etag)
说明不透明校验标记与可排序修订的区别，并明确不能将该机制推定为其他服务的语义。

## 独立判断及限制

四份原始判断分别覆盖 [业务选择](judgments/response-1.md)、
[服务保证](judgments/response-2.md)、[收益解释](judgments/response-3.md)和
[准备深度](judgments/response-4.md)。实际答复保留不同筛选工作流、使用既有 Angular
组件作用域、拒绝用自写说明/测试证明服务语义，同时复用另一个已确认服务的保障；
区分低绝对分与配对改善信号、相同满分与增益、不同模型与指导归因。统一登录迁移
仍需要真实契约、增量实施与两种视图，窄规则无需额外文档。

服务判断没有展开完整数值反例；上面的数值检查由宿主后置补充，不能写成生成方自主
发现或文字用例已满覆盖。未运行这些文字场景对应的真实 Angular/迁移应用。

所有原生任务继承同一主代理配置、没有模型覆盖，但准确模型 ID/effort、完整读取
事件与标准两阶段盲评分不可取得。这是有界独立检查和一次指导版本对照，不是有效
CLI 量化发布批次。没有运行全部 83 项模型场景、无技能全量配对、多次重复、人类长期
接手、浏览器/真机或生产服务；不据此宣称稳定优势或整体代码质量已量化提升。
