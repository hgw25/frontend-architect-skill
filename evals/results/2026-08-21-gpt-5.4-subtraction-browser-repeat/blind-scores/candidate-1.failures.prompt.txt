**成本链路**
1. `pointermove -> board 根 state`
   指针位置写进看板根组件，会让根组件和其 300 张卡片一起进入 React 更新链路。这里的首要成本不是“单张卡片渲染慢”，而是高频输入把整棵子树都标记为需要重新计算。Chrome trace 里的长任务，第一嫌疑就是这段同步 JS。

2. `React render/commit -> DOM/class 变更`
   即使很多卡片最后 DOM 不变，render 比较、props 传递、commit 前后的对象创建和 diff 仍然发生。这里先看“状态拥有者是否过高”，不是先给所有卡片加缓存。

3. `layout effect 里先写 class，再读 rect，再写 top`
   这是最明确的热点。你描述的是典型的强制同步布局链：
   DOM/class 写入 -> `getBoundingClientRect()` 触发 style/layout flush -> 再写 `top` 触发后续样式/布局失效。
   如果这个流程遍历很多卡片，trace 里反复出现 `Style`、`Layout`、`Paint` 是预期结果，不是偶发噪声。

4. `top/class 驱动布局与绘制`
   用 `top` 推动位置变化，通常会让浏览器重新算布局；如果卡片还有阴影、圆角、渐变等视觉效果，后面还会跟着较大的 paint 成本。也就是说，当前瓶颈大概率是：
   高频根 state invalidation + layout thrash + layout-affecting writes。

**最小改动顺序**
1. 先把拖拽中的指针坐标从“看板根 React state”移出去。
   边界：只把“高频、仅拖拽预览需要的瞬时坐标”移到拖拽控制器、`ref`、或拖拽中的局部状态；提交排序结果、落点、业务数据仍留在 React state。
   目标：300 张卡片不再因每次 pointer move 一起参与 render。

2. 再收敛订阅范围，只让真正受影响的实体更新。
   边界：拖拽中的卡片、占位符、可能受重排影响的那一列/那几个相邻项更新；其他列和其他卡片保持静止。
   这一步是“缩小 invalidation”，不是“全量 memo 化”。如果现有数据流做不到，先改状态边界，不要先堆缓存。

3. 重写布局 Effect 的读写顺序，禁止“循环里写后立刻读”。

   这是最直接消除 `Style/Layout` 反复刷新的改动。

4. 把位移从 `top` 改成 `transform: translate(...)`，仅用于拖拽中的视觉位移。
