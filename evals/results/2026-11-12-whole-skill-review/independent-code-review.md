## 搜索交付

### 原始契约与实现

原始 README 第 5–9 行明确给出公开方法、五个状态字段、独立快照、草稿与提交分离、空提交无操作、最近启动请求拥有发布权、错误恢复、retry 使用已提交查询和 dispose 冻结状态等要求。

最终 `src/search.js` 的实现直接对应这些契约：

- 第 6–10 行的私有 `runSearch(query)` 是提交和重试共用的请求入口。在空查询或释放后返回，不错误地使空提交抢走现有请求所有权；实际请求开始时生成请求身份，保存已提交查询并保留成功列表。
- 第 13–28 行在成功与失败路径各检查存活状态和请求身份。相同查询的重复提交也能正确区分；没有会让旧请求清空新请求状态的 finally 分支。
- 第 18 行将 DTO 转成 `{ id, label }`，第 38 行克隆整个公开快照。DTO 数组和消费者快照均不能反向修改内部列表。
- 第 34–39 行明确区分草稿编辑、当前草稿提交、已提交查询重试和释放。disposed 属于实例寿命，不需要框架、订阅或不受服务支持的 AbortController。

原始测试的八条核心路径与新增测试的空提交、同步失败、retry 抢占和释放后别名隔离均通过。没有发现违反已说明输入契约的反例。

### 维护成本与后续变化

调用者只需理解一个实例、一个状态对象、一个请求身份和一个生命周期标记。共用的私有执行入口有今天的收益：submit 和 retry 的输入来源不同，但加载、成功、失败、所有权规则一致。不存在第二套请求策略、外置管理器或要求调用方拼装的内部协议。

用“接口将 `display_name` 改名”检查修改成本，只需修改第 18 行映射，公开项目形状和调用者不变。将来服务真的提供取消能力时，也有一个明确的请求入口可接入，同时保留当前身份检查即可；现在没有为该变化建立通用机制。结构足以接续维护，无需修改。

## 资料编辑交付

### 原始契约与实现

原始 README 第 3–11 行要求立即显示保存值、允许保存重叠、失败恢复最新已确认资料、旧响应不替换最新可见编辑但可成为回退值、草稿编辑不触发保存，以及将 HTTP 和无效响应体视为可访问错误。

最终调用链为 `ProfileForm` → `ProfileEditor.handleSubmit` → `updateProfile` → reducer action → `getVisibleName`。职责与数据来源可以顺着公开入口读完：

- `src/ProfileForm.tsx:15–27` 的本地输入值只是草稿；提交时捕获名称与递增请求身份，原生 form 负责点击和 Enter，未把请求效果移入渲染或状态推导中。
- `src/api.ts:18–34` 保留原 PATCH 入口与请求体。HTTP 成功和 JSON 类型检查均在外部边界完成；表单捕获失败并显示统一 alert，没有内部层层验证或静默吞掉用户失败。
- `src/profileSaveState.ts:8–16` 区分已确认资料和最新提交意图。`submitted`、`accepted`、`rejected` 在一个纯 reducer 中完成保存状态转换，避免用多个独立 setter 同步乐观名称、错误和回退值。
- `src/profileSaveState.ts:42–49` 只让最新提交更新成功/失败反馈；旧成功仍可更新 confirmed。第 53–61 行按最新提交状态推导可见名称，因此旧成功不会盖过新的 pending/succeeded 名称，最新失败后能显示回退值，同时保留草稿和 alert。
- `src/ProfileForm.tsx:10–12` 的 key 让不同 profile.id 拥有不同的编辑器实例。旧请求的 dispatch 留在旧实例，不会写入新资料。没有引入客户端无法兑现的服务器取消或撤销承诺。

新增的测试清理配置只改变测试隔离，保留既有测试和清单。新增恢复测试确实覆盖了不同的外部可见行为，而非仅重复内部 action：草稿保持、服务返回的规范名称、旧失败、旧成功晚到、重试、资料身份替换及 Enter 提交。

### 服务版本排序假设，未列为已证缺陷

原始 README 第 9 行仅说 API 返回 numeric version；原有测试使用初始 version 1、成功 version 2。它没有明确说明版本单调性、相同版本是否必然代表相同资料、或应按请求启动顺序、到达顺序还是服务器版本判断“latest confirmed”。

最终 `src/profileSaveState.ts:39–41` 只接受严格更大的版本作为 confirmed。最终 `docs/profile-save.md:17–25` 将其明确解释为服务器修订号，但这是交付自身增加的解释，不是原始 API 保证的独立证据。新增关于版本的两个表单测试也只能证明实现执行了所选规则。

已用实际 reducer 正文确认以下行为：

1. 初始资料 `{ id: 'p1', displayName: 'Ada', version: 1 }`。
2. 提交 A = Grace，再提交 B = Lin。
3. A 成功返回 `{ id: 'p1', displayName: 'Grace', version: 1 }`，字段类型满足原 README 描述；此时仍显示 Lin。
4. B 失败，最终显示 Ada，Grace 没有成为 confirmed。

如果服务允许成功保存返回相同版本但更新后的资料，这会违反原 README 第 7–8 行“旧 accepted 响应仍作为新保存失败后的已确认回退”的要求。如果 version 保证代表不可变且单调排序的资源修订，上述第 3 步则不是符合真实服务契约的输入，严格比较是合理的。四份快照无法决定哪一种服务保证成立，因此这里是已确认的代码行为和未证的服务假设，不认定为确定缺陷。

后续应从服务契约确认版本的排序与相等语义；若保证存在，把保证写进源 API 契约即可。若不存在，再据实际语义调整确认规则及相关测试，不能仅把 `>` 改成 `>=` 就认为解决了乱序确认问题。

### 其他契约空白与维护成本

同一 profile.id 的新 prop 是否应刷新已有编辑器，以及返回资料 id 是否必须与传入 id 一致，原始契约与消费者没有说明。当前资料只作为编辑器种子；同 ID 刷新不被消费，响应只验证 id 是字符串。没有足够证据把这些行为列成问题，也不建议据此自行添加同步 effect、跨资源校验或缓存。

Reducer 的存在有实际理由：最新可见意图与已确认回退不是同一事实，旧成功仍可能有确认价值，旧失败却没有发布权。拆出纯转换让这组协议集中可见，表单保留草稿与请求效果，API 保留外部数据边界。维护者没有被迫理解通用状态机、请求注册表或额外依赖。

用“再编辑一个资料字段”检查修改成本，需要调整 Profile/外部校验、PATCH 参数和类型化草稿/提交快照，再改相应展示；确认与意图的区分及请求归属逻辑可保留。这个变化能够沿现有职责边界完成，无需预先引入字段注册表或通用表单框架。除需核实版本语义外，没有发现因当前结构而必须返工的维护障碍。
