结论：A、B 不需要持久化设计文档；C 必须在修改实现前创建或更新持久化技术设计。设计文档不是审批门槛，用户已有授权后，设计完成即可按顺序实施。

| 任务 | 是否需要持久化设计文档 | 判断与最小准备 | 后续行动 |
|---|---|---|---|
| A：按钮间距 8px → 6px | 不需要 | 这是沿用既有 token 和边界的确定性局部调整。先确认 token 的真实消费者、按钮尺寸/变体以及现有视觉验证方式。 | 修改 token；检查主要按钮变体及受影响页面，运行现有视觉、组件或快照检查。若调查发现该 token 同时承担多个不同语义，再先拆清语义，但不能仅因“公共”二字自动升级为设计项目。 |
| B：列表页增加 URL 状态筛选 | 不需要 | 题设明确遵循现有 URL 筛选约定，属于既有筛选能力的绑定。先检查相邻筛选器、路由参数的解析/序列化、状态值来源、默认值及列表查询契约。 | 复用现有筛选组件和 URL 状态流程；验证选择、清除、刷新、前进/后退、分享链接，以及加载、空结果和请求失败。若实际调查发现需要创造新的筛选协议或跨页面状态所有权，才转为需要设计。 |
| C：三个应用统一登录状态迁移 | 必须 | 这是跨应用共享基础、兼容迁移和职责重分配；旧新接口并存、两团队分阶段接手以及身份/刷新/退出所有权未定，都会直接影响公共契约和迁移安全。 | 先调查现有会话实现和调用方，随即形成持久化技术设计；确定所有权后按可验证增量实施，两周兼容期结束且退出条件满足后再移除旧路径。无需等待额外文档审批。 |

C 的最小文档应放在仓库既有文档位置；若没有约定，则创建一个可发现并能被后续维护者找到的文档。至少包含：

1. 已确认事实、范围、验收条件，以及仍未确定的事项。
2. 用户身份、刷新调度、凭证存储、跨应用同步和退出传播各自唯一的 owner；旧、新接口的适配边界和权威状态源。
3. 明确计数、按依赖排序的实施步骤；每步标出受影响模块、契约和完成检查。
4. 技术架构图：三个应用、统一会话层、旧/新接口、存储或传播边界及调用方向。
5. 数据流图：至少覆盖登录态建立、刷新成功/失败、退出传播，并标出并发、过期结果和清理路径。
6. 两周兼容窗口的启用、观测、回退和旧接口删除条件；同时记录两个团队的阶段性交接边界。
7. 各阶段的决定性验证，以及一个现实后续变化，例如再接入第四个应用时需要修改哪些边界。

建议把 C 分成五个有完成条件的增量：

1. 盘点三个应用及旧、新会话接口，依据现有代码和维护关系确定候选 owner。
2. 固化统一会话契约、状态机、兼容适配及回退策略。
3. 选择一个应用完成端到端试迁移，验证身份、刷新、退出和故障恢复。
4. 由两个团队按文档边界迁移其余应用，并保留旧接口兼容。
5. 经过两周观测且满足退出条件后，关闭回退路径、移除旧接口并更新文档为实际状态。

所有权不能靠实现细节默认为“大家共同负责”。应先从现有模块职责、运行边界和团队维护关系中求证；若证据仍无法唯一决定，则这是 C 唯一需要负责人明确裁决的阻塞项。A、B 可独立推进，不必等待该裁决。
