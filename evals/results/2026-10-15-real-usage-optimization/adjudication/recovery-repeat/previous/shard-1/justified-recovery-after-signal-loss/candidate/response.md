建议把现有生命周期管理器扩展为“前台期间的权威状态收敛器”，而不是补做推送重连或游标恢复。

推送继续承担低延迟通知；只要任务仍为非终态且应用位于前台，就由现有管理器按“账号 + 任务”低频查询服务端，直到得到终态。返回前台时已有的核对即为第一次立即查询。

### 修复设计

状态流建议如下：

```text
任务处于非终态
    ├─ 收到推送 ───────────→ 更新状态；终态则停止核对
    ├─ 应用返回前台 ───────→ 立即查询
    └─ 前台定时核对 ───────→ 查询仍非终态则安排下一次
                                  └─ 得到终态后停止
```

具体约束：

- 复用现有按账号和任务查询状态的生命周期管理器，不在页面组件中新增 timer、缓存或第二套状态。
- 应用进入前台后立即查询一次；若仍为非终态，继续轮询。
- 初始间隔可取 10 秒并加少量随机抖动；如果项目已有刷新规范则沿用。请求失败后退避，建议上限 60 秒；再次返回前台时恢复为立即查询。
- 使用“上一次查询完成后再安排下一次”的单次 timer，避免慢请求造成请求堆叠。
- 以下情况停止轮询：服务端返回终态、应用进入后台、账号切换或退出、任务不再受管理、管理器销毁。
- 查询失败不能把任务判为失败或成功；保留当前状态并继续恢复。鉴权失败、任务不存在等结果按项目已有领域契约处理。
- 不增加持久化游标、推送补偿队列或通用任务调度框架：协议没有可恢复游标，而服务端查询已经提供了所需的最终一致性能力。

### 必须处理的竞争条件

管理器应统一拥有推送和查询结果的发布策略：

- 查询身份必须包含账号和任务；账号切换后，旧账号的响应不得写入当前状态。
- 同一身份使用请求序号或 generation，只允许当前请求发布结果。
- 推送已将任务更新为终态时，应停止轮询并使在途的旧查询失效，避免旧的“处理中”响应把终态覆盖回去。
- 连续的前台事件、推送唤醒和轮询 tick 应合并为同一在途查询，避免重复请求。
- 不需要假定所有终态之间存在大小关系；具体终态仍按服务端状态契约映射。

若现有推送路径已经正确发布状态，不必重写它，只需让它能够终止对应轮询并失效旧查询。

### 验证方案

| 场景 | 操作 | 必须观察到的结果 |
|---|---|---|
| 后台漏推送 | 应用进入后台，服务端完成任务，丢弃推送，再返回前台 | 立即查询并显示服务端终态 |
| 前台漏最终通知 | 保持前台，服务端完成，丢弃最终推送 | 最迟在一个轮询周期加请求耗时内收敛到终态 |
| 正常推送 | 正常交付终态推送 | UI 立即更新，轮询停止，不产生持续请求 |
| 首次查询过早 | 返回前台时查询仍为处理中，随后服务端完成且推送丢失 | 后续轮询取得终态 |
| 请求失败 | 查询发生超时或离线，之后恢复网络 | 不伪造状态；退避后重新查询并收敛 |
| 乱序完成 | 用可控 Promise 让旧查询晚于新查询或终态推送完成 | 旧结果不能覆盖较新的可见状态 |
| 账号切换 | A 账号查询在途时切换到 B | A 的响应不得写入 B 的任务状态 |
| 生命周期清理 | 非终态任务轮询时将应用切到后台或销毁管理器 | timer 被释放，后台不再查询；返回前台仅启动一条查询链 |

单元测试使用假时钟和可控 Promise 验证轮询、退避、去重和乱序发布；集成测试模拟应用前后台事件、推送和状态查询。最后应在真机做两条决定性验证：后台完成且丢推送、前台完成且丢推送，并检查 UI 与实际请求次数。

当前工作区没有应用源码或测试配置，只有任务 Skill，因此无法核实现有管理器的具体 API，也未做代码修改。上述方案刻意以现有管理器为唯一生命周期所有者，避免引入与项目事实不符的新模块。
