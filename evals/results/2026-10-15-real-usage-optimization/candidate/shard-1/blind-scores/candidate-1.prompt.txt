## 修复方案

复用现有按 `(accountId, taskId)` 工作的生命周期管理器，由它统一拥有查询、定时器和结果发布：

1. 保留返回前台时的立即查询。
2. 应用处于前台且任务为非终态时，在每次查询结束后安排下一次核对。
   - 建议初始间隔 15 秒；具体值需符合服务端限流约定。
   - 使用“请求结束后再调度”，不要用可能产生重叠请求的裸 `setInterval`。
   - 同一账号、任务最多一个查询在途。
3. 权威查询返回终态后更新现有任务状态并停止核对。
4. 正常推送路径保持不变；推送使任务进入终态时，同样停止核对。
5. 进入后台、任务终态、账号切换、任务替换或管理器销毁时取消定时器；取消请求仅作为节省资源，正确性仍由结果发布条件保证。
6. 查询失败时保留最后已知状态，不伪造完成或失败；按现有错误策略重试，可采用 15、30、60 秒封顶的简单退避。
7. 每次结果发布前校验完整身份和生命周期代次：
   - 响应仍属于当前 `(accountId, taskId)`；
   - 管理器尚未失效；
   - 请求开始后没有接受更新的终态信号。
   
   这样，账号切换后的旧响应或“查询先发出、终态推送后到达、旧查询最后返回”的情况不会把 UI 从终态退回处理中。

- 推送补发或恢复游标，因为协议明确不支持；

| 证据 | 最小修复 |
|---|---|
| 标题或其容器覆盖按钮，禁用其命中后问题消失 | 修复分组标题的布局所有权：折叠态移除造成覆盖的尺寸/负 margin。若标题在折叠态纯装饰且确实无需选择或交互，可对该状态使用 `pointer-events: none`。 |
| 覆盖来自本应参与交互的元素 | 不使用 `pointer-events: none`；调整间距、尺寸或定位，使命中区域不重叠。不要只用更高 `z-index` 掩盖错误几何关系。 |
| 按钮能被命中，但事件在 Tooltip/Dropdown 组合处丢失 | 保持现有库，先按该版本公开 API 改成单一、明确的 trigger 元素，并正确合并 handler/ref。 |
| Tooltip 已打开并挂载，但不可见 | 修复 portal、overflow、stacking context 或定位边界；这不是 hover 监听问题。 |
| 在相同 DOM、CSS 和 trigger 配置下，仅旧 Tooltip 失败，而候选替代实现稳定通过 | 才考虑替换 Tooltip；同时核对键盘、焦点、延迟、portal、受控状态和 Dropdown 组合兼容性。 |

换言之，替换 Tooltip 的门槛应是一次受控 A/B 已经把布局覆盖和本地组合差异排除，而不是“换了以后症状消失”。否则容易把覆盖问题暂时藏住，并引入新的焦点和浮层行为差异。

## 验收方法

现有 `dispatchEvent` 测试可以保留为处理器级测试，但不能作为该缺陷的回归证明。新增或改造一条真实浏览器测试，渲染实际侧栏组合并通过鼠标坐标移动：

- 侧栏处于折叠状态，并包含真实的透明标题、负 margin、Tooltip 和 Dropdown。
- 将鼠标从外部移动到最后一个按钮的中心以及靠近覆盖边界的位置。
- 断言 `elementFromPoint` 命中按钮或其约定 trigger。
- 等待产品规定的 hover 延迟后，断言 Tooltip 以可访问名称/角色出现。
- 移出后断言 Tooltip 按预期关闭。
- 点击同一按钮，断言 Dropdown 正常打开，证明修复没有牺牲另一项交互。
- 用键盘 Tab 到按钮，检查焦点可见；按 Enter/Space 打开 Dropdown，Escape 后焦点回到 trigger。
- 至少复查折叠态、展开态和会触发该布局的窄视口；若支持多浏览器，覆盖实际受影响浏览器及一个基准浏览器。

最终通过标准不是“测试绿了”，而是：真实指针在最后一个按钮的可见点击区域能够命中它，Tooltip 与 Dropdown 都工作，且透明标题不再截获本不属于它的指针输入。

工作区目前没有应用源码、依赖清单或框架约定，只有本次指定的 Skill 文件，因此下面是可直接落地的框架无关设计，不假定项目已有能力。

### 建议边界

```text
订单页
  ├─ loadOrder()：唯一的页面加载操作，维护 loading/success/error
  ├─ render：只使用内部 Order，不认识 total_in_cents
  └─ 初次加载、刷新、重试事件：都调用 loadOrder()

order-api
  ├─ 发起请求
  ├─检查 HTTP 状态和响应结构
  └─ 将接口响应转换为内部 Order
```

最小契约可以是：

```ts
// 仅存在于接口边界内
type OrderResponse = {
  total_in_cents: number
}

// 页面使用的稳定模型
type Order = {
  totalCents: number
}

async function fetchOrder(
  orderId: string,
  options?: { signal?: AbortSignal },
): Promise<Order>
```

`fetchOrder` 内完成：

1. 请求接口；
2. 处理非成功 HTTP 状态；
3. 验证 `total_in_cents` 是有效整数；
4. 映射成 `{ totalCents }`；
5. 抛出页面可以统一处理的错误。

不要让 `OrderResponse` 或 `total_in_cents` 越过这个边界。接口字段以后改名、嵌套或改变单位，只需修改这里。

### 格式化的归属

金额格式化应是纯派生值，不存进状态，也不分散在事件函数中：

```ts
function formatOrderTotal(
  totalCents: number,
  options: { locale: string; currency: string },
): string {
  return new Intl.NumberFormat(options.locale, {
    style: 'currency',
    currency: options.currency,
  }).format(totalCents / 100)
}
```

优先复用项目已有的金额格式化能力。币种必须来自已知业务配置或接口契约，不应根据 `_in_cents` 猜测。

页面渲染时调用它：

```ts
const displayedTotal = formatOrderTotal(order.totalCents, {
  locale,
  currency,
})
```

### 请求错误的归属

页面只保留一个加载入口：

```ts
type LoadState<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error }

async function loadOrder() {
  setState({ status: 'loading' })

  try {
    const order = await fetchOrder(orderId)
    setState({ status: 'success', data: order })
  } catch (error) {
    setState({
      status: 'error',
      error: normalizeOrderError(error),
    })
  }
}
```

初次加载、刷新按钮、重试按钮只调用 `loadOrder`，不要各自重复 `try/catch`、提示文案和金额转换。

错误只分类到页面确实会区别展示或恢复的程度，例如“无权限”“不存在”“暂时不可用”。若 UI 对它们没有不同处理，就不要预先设计庞大的错误码体系。错误不能被转换成金额 `0` 或空订单，否则失败会伪装成成功。

若路由中的订单 ID 可能在请求期间变化，应使用现有数据层的请求标识或 `AbortSignal`，防止旧订单结果覆盖新订单；固定 ID 页面无需为此自建请求框架。

### 暂时不要增加

- `IOrderRepository`、多数据源 Provider 或适配器注册表；
- 全局订单 Store；
- 自制缓存、重试引擎或 Result 类型体系；
- 仅为了 `total_in_cents` 创建多层 DTO → Entity → ViewModel。

现实的后续变化也能被这个小边界吸收：接口将金额改成嵌套结构时，只改响应解析和映射；展示改币种或本地化时，只改格式化入口；未来真的出现第二数据源时，再根据两个真实来源提取共同接口。

本次是设计建议，且工作区没有应用代码，因此未修改文件或运行应用测试。
