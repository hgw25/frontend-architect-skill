### 修复方案

由现有生命周期管理器统一负责：

```text
前台 + 非终态
  → 立即查询(accountId, taskId)
  → 终态：发布状态并停止
  → 仍处理中：延迟后再次查询
  → 临时错误：退避后重试
后台 / 换账号 / 换任务 / 销毁
  → 停止调度并使旧结果失效
```

具体约束：

- 返回前台立即查询，不等待下一个轮询周期。
- 前台期间，只要任务仍是非终态，就继续查询。可先用 5 秒间隔；传输失败采用 5/10/20/30 秒封顶退避，最终数值应结合现有 API 限流调整。
- 使用完成后再安排下一次的 `setTimeout`，不使用 `setInterval`，保证同一账号和任务最多一个查询在途。
- 重复的前台事件或推送触发只合并为一次查询；若查询正在进行，记录一次待补查即可。
- 仅重试网络、超时等临时错误；鉴权、任务不存在等沿用项目现有错误语义，不能无限重试或伪装成成功。
- 查询失败时不把任务改成完成或失败，也不吞错；保留当前状态并继续可信恢复路径。
- 发布结果前校验当前 `(accountId, taskId, lifecycle generation)`，旧账号、旧任务或已销毁实例的响应不得更新 UI，包括旧请求的 `finally`。

   依次单独切换，不要同时改多个变量：

   - 给透明标题临时加 `pointer-events: none`；
   - 临时隐藏标题；
   - 临时取消负 margin；
   - 临时移除 Tooltip，但保留 Dropdown；
   - 临时移除 Dropdown，但保留 Tooltip。

   哪一个单变量变化恢复真实 hover，哪一个才是修复入口。不要把临时 `z-index` 调整直接当成修复。

3. **若命中正确，再查 Tooltip/Dropdown 组合**

   核对：

   - 两层组件是否都要求唯一 DOM trigger；
   - `ref` 最终是否指向真实按钮；
   - 两层是否合并而非覆盖 `onPointerEnter`、`onMouseEnter`、`onFocus` 等处理器；
   - 包装顺序、trigger 配置和受控 `open` 状态是否与正常按钮一致；
   - 关闭状态的浮层是否意外残留并截获事件。

4. **最后才做最小复现**

   将相同 Tooltip、Dropdown 和按钮放到侧栏布局之外，再逐项加回折叠容器、分组标题和负 margin。若脱离本地布局仍失败，再与同版本上游 demo 对齐 props、包装顺序和样式入口。

### 最小修复的决策条件

- **若顶层命中对象是透明标题或其容器，且禁用其命中后恢复：**  
  修复侧栏布局，不换 Tooltip。

  - 标题在折叠态完全无意义：条件渲染或 `display: none`。
  - 需要保留布局占位但不应交互：`visibility: hidden`，必要时明确 `pointer-events: none`。
  - 标题仍需显示：消除重叠的负 margin 或修正布局约束。
  - 不优先使用任意增大的 `z-index`，因为它只改变谁覆盖谁，容易制造新的重叠问题。

- **若按钮确为顶层命中对象，但 Tooltip/Dropdown 组合丢失事件或 ref：**  
  按当前组件库支持的组合方式修正包装顺序、事件合并或 ref 转发。不要盲目增加额外 `<span>`；它可能改变焦点、键盘行为和布局。

- **只有满足以下全部条件，才建议替换 Tooltip：**

  1. 实际 hit testing 已确认没有遮挡；
  2. 支持的组合方式、ref 和事件合并均正确；
  3. 脱离侧栏自定义 CSS 的最小复现仍失败；
  4. 仅替换 Tooltip、保持其他条件不变即可稳定恢复；
  5. 新实现的 hover、focus、键盘、portal 和清理行为已验证。

当前证据没有达到这个门槛。直接替换很可能只是通过不同 DOM 或 stacking 行为掩盖布局缺陷。

### 验收方法

保留现有 `dispatchEvent` 测试可以覆盖“事件已经送达后的组件逻辑”，但它不能作为这个缺陷的回归测试。应新增真实浏览器测试，例如 Playwright：

```ts
await lastButton.hover()
await expect(page.getByRole('tooltip')).toBeVisible()
```

不要使用强制 hover，也不要直接派发事件，否则仍会绕过遮挡。验收至少包括：

- 折叠侧栏下，真实鼠标 hover 最后一个按钮能显示正确 Tooltip；
- 鼠标移出后 Tooltip 正常关闭；
- Dropdown 的打开、选择和关闭行为没有回归；
- 按钮可通过键盘聚焦，Tooltip/Dropdown 的既有键盘行为仍成立；
- 展开侧栏不受影响；
- 最后一个按钮在侧栏滚动、窄视口及项目支持的缩放条件下仍可命中；
- 修复前该浏览器用例能复现失败，修复后通过；
- 至少在项目主要支持浏览器中执行原始路径，其他浏览器按现有支持矩阵抽查。

工作区中除 `.frontend-architect` 外没有应用源码或测试文件，因此本次无法核对具体组件结构、样式选择器或执行测试；没有修改任何文件。

建议采用“一个接口适配器 + 一个请求状态所有者 + 一个纯格式化函数”的小边界。它既解决当前字段和错误处理散落的问题，也不为不存在的第二数据源提前建设 Repository、Provider 或通用请求框架。

当前工作区没有应用源码或框架配置，只有本次 Skill 文件，因此以下是框架无关的具体结构，命名和目录应落到项目现有约定中。

### 1. 接口适配边界

页面不再直接接触 `total_in_cents`。接口模块私有保存 DTO，并向页面返回稳定的内部模型：

```ts
// orderApi.ts

type OrderDto = {
  id: string
  total_in_cents: number
}

export type Money = {
  minorUnits: number
  currency: CurrencyCode
}

export type Order = {
  id: string
  total: Money
}

export async function getOrder(
  orderId: string,
  options?: { signal?: AbortSignal },
): Promise<Order> {
  const dto = await requestOrder(orderId, options)
  return mapOrder(dto)
}
```

边界职责：

- 沿用已有 HTTP 客户端和响应校验能力。
- 在这里验证外部响应必须满足的条件，例如金额是否为整数；不要在页面中散布断言和默认值。
- 在这里完成 `total_in_cents → total.minorUnits` 的字段语义转换。
- 货币从已确认的接口字段或产品配置取得，不能仅凭字段名猜测。
- 不要把无效金额降级成 `0`，否则接口异常会被伪装成真实订单。

`OrderDto` 不导出，避免接口命名渗入页面。`getOrder` 本身已经是未来替换实现的接缝，当前不需要额外的 `OrderRepository` 接口或服务类。

### 2. 展示格式边界

金额文本是派生值，不进入请求状态，也不在点击、刷新等事件函数中计算：

```ts
function formatMoney(money: Money, locale: string): string {
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency: money.currency,
  }).format(money.minorUnits / 100)
}
```

优先复用项目已有的金额或国际化工具。若没有，可先把这个函数放在订单功能内部；只有其他功能确实共享相同货币语义时再上移为公共工具。

页面只表达：

```ts
formatMoney(order.total, locale)
```

这样 locale 变化时直接重新派生，不会出现请求状态中的旧格式文本。

### 3. 请求生命周期边界

由路由 loader、页面级 hook/composable，或项目现有数据请求库中的一个位置统一拥有加载过程：

```ts
type OrderLoadState =
  | { status: 'loading' }
  | { status: 'success'; order: Order }
  | { status: 'error'; error: OrderLoadError }
```

它对页面暴露类似：

```ts
const { state, retry } = useOrder(orderId)
```

所有入口采用同一条执行路径：

- 首次进入触发加载。
- 刷新按钮调用 `retry()`。
- 错误页的重试按钮也调用 `retry()`。
- 事件函数不再各自 `try/catch`、格式化数据或弹出重复提示。

只有当界面确实需要不同恢复行为时，才把错误归类为 `not-found`、`forbidden`、`unavailable` 等稳定类别。其他网络或运行时异常保留为失败，由这一状态所有者记录并转成统一的用户提示；不要在每层捕获后原样抛出，也不要转换为空订单。

如果 `orderId` 可能在组件不卸载时变化，请使用现有请求库的 query key/取消机制；否则至少保证旧请求的成功、失败和 `finally` 都不能覆盖新订单状态。

### 4. 建议的责任分布

| 边界 | 拥有内容 | 不应拥有 |
|---|---|---|
| 接口适配器 | DTO、响应校验、字段映射、必要的错误归类 | 页面文案、通知、缓存框架 |
| 请求所有者 | loading/success/error、重试、过期响应策略 | 金额格式、接口原始字段 |
| 金额格式器 | minor units 到本地化文本 | 请求状态、业务错误 |
| 页面 | 根据状态渲染、触发 `retry` | 网络调用细节、DTO、重复 `try/catch` |

一个现实的后续变化是接口把 `total_in_cents` 改成 `{ amount, currency }`：此时只需修改 DTO、映射函数及其边界测试，页面、请求状态和格式化调用保持不变。这已经为常见变化提供了足够的小型边界；第二数据源真正出现后，再根据两者的实际差异决定是否引入 provider/repository 抽象。

本次仅提出实现边界，没有修改任何文件。
