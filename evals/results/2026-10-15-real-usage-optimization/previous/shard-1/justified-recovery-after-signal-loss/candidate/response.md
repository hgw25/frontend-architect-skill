结论：不要补推送、造游标或新增第二套状态机制。应扩展现有“按账号和任务查询”的生命周期管理器，让它在应用前台且任务仍为非终态时持续做权威核对。

但有一点需要先查清：既然服务端在恢复前已经完成，一次成功的前台查询理应立即结束“处理中”。若仍未更新，说明还存在查询未触发、身份不一致、结果未发布或被旧结果覆盖的问题，不能只靠增加轮询掩盖。

### 修复方案

由现有生命周期管理器统一负责：

```text
前台 + 非终态
  → 立即查询(accountId, taskId)
  → 终态：发布状态并停止
  → 仍处理中：延迟后再次查询
  → 临时错误：退避后重试
后台 / 换账号 / 换任务 / 销毁
  → 停止调度并使旧结果失效
```

具体约束：

- 返回前台立即查询，不等待下一个轮询周期。
- 前台期间，只要任务仍是非终态，就继续查询。可先用 5 秒间隔；传输失败采用 5/10/20/30 秒封顶退避，最终数值应结合现有 API 限流调整。
- 使用完成后再安排下一次的 `setTimeout`，不使用 `setInterval`，保证同一账号和任务最多一个查询在途。
- 重复的前台事件或推送触发只合并为一次查询；若查询正在进行，记录一次待补查即可。
- 仅重试网络、超时等临时错误；鉴权、任务不存在等沿用项目现有错误语义，不能无限重试或伪装成成功。
- 查询失败时不把任务改成完成或失败，也不吞错；保留当前状态并继续可信恢复路径。
- 发布结果前校验当前 `(accountId, taskId, lifecycle generation)`，旧账号、旧任务或已销毁实例的响应不得更新 UI，包括旧请求的 `finally`。
- 若上传任务契约规定终态不可逆，应在状态归并处禁止同一任务从终态退回“处理中”；否则需要服务端版本信息才能可靠处理这种竞态。
- 进入后台时停止后续计时，返回前台重新立即查询。不要尝试在后台维持客户端轮询。
- 保留已经正确的推送链路。推送负责降低完成延迟，查询负责最终收敛；不增加补发游标、持久化事件队列或新的全局 store。

轮询应属于生命周期管理器，而不是页面组件。这样页面卸载、导航或重渲染不会制造重复计时器，后续调整轮询策略也只有一个修改点。

### 验证方案

先用可控请求和假时钟做管理器级回归测试：

1. 任务处理中，应用进入后台；服务端完成且无推送；恢复前台后验证立即查询正确账号和任务，查询返回后 UI 进入终态。
2. 应用始终在前台，无最后一条推送；前几次查询返回处理中，后一次返回完成；验证 UI 在一个轮询周期内收敛并停止查询。
3. 查询过程中收到正常推送；验证原有成功路径不回归，旧查询结果不会把终态覆盖成处理中。
4. 查询未完成时重复触发前台事件或推送；验证无并发请求风暴，并在必要时补查一次。
5. 查询在途时切换账号或任务；旧响应晚到，验证不会更新新账号或新任务。
6. 进入后台或管理器销毁；验证计时器停止，旧回调不会重新启动轮询。
7. 首次查询出现临时网络错误，后续恢复；验证按退避策略重试并最终收敛，同时没有把错误当成终态。
8. 鉴权或任务不存在；验证沿用既有错误处理，不进行无意义的永久轮询。

再做一次真机或移动端集成验证：启动上传、切后台、让服务端完成、确保推送不交付、恢复应用，确认无需用户手动刷新即可更新；另做一次保持前台并屏蔽最终推送的长任务验证。管理器单测不能替代真实的前后台生命周期测试。

验收标准是：

- 后台漏推送时，恢复后在一次查询延迟内显示权威终态。
- 前台漏最终通知时，在“轮询间隔 + 查询耗时”内收敛。
- 终态后不再请求。
- 不发生跨账号、跨任务或旧请求覆盖新状态。
- 正常推送路径行为不变。
