结论：个人主页使用 `/users/:userId` 作为唯一标准路由；页面原样展示服务端判定后返回的 `profile` 和 `applications`，前端不再按公开性过滤。`developerLogin` 不得拼成用户主页地址，当前作者署名只能保持开发者身份入口或纯文本。

当前仓库的 `HEAD` 是空树，没有 Vue 源码、路由、类型或测试可修改，因此以下是可直接落地的最小方案，未虚构具体目录和现有组件。

## 路由与页面

建议路由契约：

```ts
{
  path: '/users/:userId',
  name: 'user-profile',
  component: () => import(/* 个人主页页面 */),
  props: true,
}
```

- `userId` 是用户身份标识，不能接受 `developerLogin`。
- “我的主页”也进入这个标准路由。只有当前会话确实提供用户体系的 `userId` 时，头像菜单才能构造该链接。
- 暂不增加 `/me`、用户名别名、标签页子路由或独立应用详情请求。
- Vue Router 复用页面实例、仅改变 `userId` 时必须重新加载。旧请求晚返回不能覆盖新用户页面。

视觉采用 GitHub 式信息层级，而非复制 GitHub：

- 宽屏为左侧个人信息、右侧应用列表的双栏结构。
- 窄屏按个人信息、应用列表顺序单栏排列，DOM 阅读顺序与视觉顺序一致。
- 应用使用紧凑的带边框列表或卡片；不在最小版本中加入贡献图、关注关系、复杂筛选和动画。
- 使用现有颜色、排版、间距和控件体系。
- 空状态写“暂无可见应用”，避免访问者把“看不到私有应用”理解为“该用户没有应用”。

建议最小职责划分：

- 页面组件：读取 `userId`、管理加载状态、组合页面区域。
- API 边界：调用 `GET /users/{userId}`，返回完整响应。
- `ProfileSummary`：只负责资料展示。
- `ApplicationList`：只负责当前响应中的应用展示。

如果现有页面很小，后两个区域可以先留在页面内，不需要预建完整 feature 分层或全局 Store。

## 数据流

```text
/users/:userId
    ↓
个人主页页面
    ↓
现有认证 HTTP 客户端
    ↓
GET /users/{userId}
    ↓
{ profile, applications }
    ↓
资料区与应用列表同时发布
```

关键规则：

1. 请求沿用现有会话凭证，由服务端识别查看者。
2. `applications` 的准确含义是“当前查看者可见的应用”：
   - 本人可能得到公开和私有应用。
   - 其他用户或匿名查看者只得到服务端允许的数据。
3. 前端不得使用 `isSelf`、登录状态或 `visibility` 再次过滤响应，也不能靠隐藏卡片保护私有数据。
4. `isSelf` 只能用于“编辑资料”等表现层能力；当前最小版本没有相应 mutation 时不要加入编辑按钮。
5. `profile` 和 `applications` 来自同一响应，应作为一次结果一起更新，不额外制造请求瀑布。
6. 路由快速从 A 用户切换到 B 用户时采用“只发布最新请求结果”；可取消旧请求，但仍需用请求身份或既有查询机制避免旧结果覆盖。
7. 如果项目已有查询缓存，缓存身份至少包含目标 `userId` 和查看者会话范围；登录、退出或切换账号后清除相关缓存。不得把该响应放进跨用户共享的公开缓存。

旧生成注释不能作为当前行为依据。应修改生成源，例如 OpenAPI 描述，再按项目生成流程更新产物，含义写成：

> applications 包含当前查看者有权看到的应用；本人可包含公开和私有应用。

不要直接手改生成文件，也不要用前端过滤去迁就旧注释。由于相同 URL 会按会话返回不同数据，服务端或 CDN 的缓存策略也必须保证不会跨查看者共享响应。

## 作者入口

用户和开发者是两个身份体系，应明确保留这条边界：

| 数据 | 能做什么 | 不能做什么 |
|---|---|---|
| `userId` | 构造 `/users/:userId` | 当作开发者登录名 |
| `developerLogin` | 展示作者；进入已有的开发者身份页面（如果确实存在） | 构造用户个人主页 |
| 当前会话用户的 `userId` | 进入“我的主页” | 从 `developerLogin` 猜测获得 |

因此当前应用作者署名的最小处理是：

- 已有开发者主页时，继续指向开发者主页。
- 没有开发者主页时，显示为普通文本。
- 不生成 `/users/${developerLogin}`。
- 其他用户的个人主页入口只从确实携带 `userId` 的用户列表、搜索结果或用户署名进入。

未来若产品希望从应用作者进入用户主页，接口需要返回明确的跨身份导航契约，例如可选的 `authorUserId` 或服务端生成的标准资料链接，并说明无映射、多映射及隐私情况。前端不自行维护映射表。

## 实现顺序

1. 修正 API 描述源并重新生成类型/客户端，确认字段含义是“查看者可见”，保留外部字段名 `applications`。
2. 接通 `/users/:userId`、一次 GET 请求以及加载、成功、空、错误四种状态，先完成可直接访问的纵向链路。
3. 按 GitHub 式双栏层级完成资料区和应用列表；仅在响应中有可靠的可见性字段时展示“私有”标记，不能根据“当前是本人”推断每一项都是私有。
4. 加入来源可靠的用户入口；作者入口继续遵守开发者身份边界。
5. 补齐会话切换、路由切换、接口错误、窄屏和可访问性验证。

## 验收方式

必须覆盖以下行为，而不只检查组件是否挂载：

- 本人会话访问自己的 `userId`：接口返回的公开和私有应用全部显示，没有前端过滤。
- 其他账号或匿名访问同一 `userId`：私有应用不出现在网络响应和页面中。前端测试只能证明展示行为，服务端集成测试才可证明授权。
- 先以本人访问，再退出或切换账号并访问相同 URL：旧的私有应用不会短暂闪现或从缓存恢复。
- 快速从用户 A 导航至用户 B，并让 A 的请求最后完成：最终仍显示 B。
- 作者只有 `developerLogin` 时：页面中不存在把它拼成用户路由的链接。
- 应用为空、请求失败和重试均有明确状态；失败不能被转换成空列表。
- 直接打开 URL、刷新、前进后退都得到正确用户。
- 桌面和窄屏下无溢出、遮挡或不可达内容；长昵称、长简介和长应用名可正常换行。
- 标题层级、列表语义、键盘焦点和链接名称明确；“私有”状态不能只靠颜色表达。
- 类型检查、生成产物一致性检查以及项目现有单元、组件或端到端测试通过。

本方案中特别保留的后续变化点只有两个：查看者相关缓存边界，以及未来可能新增的开发者到用户的明确映射。两者都服务于当前正确性，没有引入通用身份转换层。
