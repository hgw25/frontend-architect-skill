## 核心决策

个人主页采用独立用户域路由：

```text
/users/:userId
```

不要复用开发者路由，也不要把 `developerLogin` 当作 `userId`。两者即使都是字符串，也属于不同身份体系。

`GET /users/{userId}` 的当前有效契约应解释为：

```text
profile：目标用户资料
applications：服务端判定当前查看者有权看到的应用集合
```

本人查看时可以包含公开和私有应用，其他查看者只得到服务端允许的数据。旧生成注释“applications 仅公开”已经过期，不能继续作为实现依据。

前端不再二次筛选 `applications`，也不能用客户端的 `isOwner` 判断来保护私有数据。

## 路由与页面范围

路由建议命名为 `user-profile`，参数只接受 `userId`。不要套用开发者登录名的格式校验；除非接口契约已有明确格式，否则将 `userId` 当作不透明标识处理。

最小页面参考 GitHub 的信息层次即可：

- 左侧或顶部展示 `profile` 提供的头像、名称、简介等已有字段。
- 主区域展示接口返回的应用列表。
- 桌面端采用资料栏加内容栏，窄屏改为上下布局。
- 不实现贡献热力图、关注关系、Tab 体系、资料编辑等接口未支持的能力。
- 列表标题使用“应用”或“可见应用”，不要写“公开应用”。
- 私有标记仅在应用模型已有可靠可见性字段时展示，不能根据“当前用户是不是本人”推测。

建议将页面拆成一个请求所有者和两个纯展示区域，例如 `UserProfilePage`、`ProfileSummary`、`ApplicationList`。具体命名应服从现有项目惯例，不需要为该页面建立新的全局状态体系。

## 数据流

```text
路由 userId
  → 用户域 API/query 层调用 GET /users/{userId}
  → 服务端依据会话决定 applications 的内容
  → 页面统一处理加载、成功、空列表、404 和失败
  → ProfileSummary 与 ApplicationList 直接消费成功响应
```

关键规则如下：

1. 使用项目现有 HTTP 客户端和会话传递方式，不在页面自行拼装认证信息。
2. `profile` 和 `applications` 来自同一个响应，应作为一次页面加载结果管理，不需要拆成两次请求。
3. 路由从一个 `userId` 切换到另一个时，应取消旧请求或忽略迟到响应，避免显示错用户。
4. `applications.length` 只代表“当前查看者可见数量”，不能解释为该用户的公开应用总数。
5. 因为同一个 URL 会随查看者身份返回不同内容，缓存不能仅由 `userId` 决定：
   - 优先沿用现有登录态切换时清理用户相关查询缓存的机制；
   - 如果没有该机制，查询键需包含稳定的会话身份版本，并在登录、退出、切换账号时失效；
   - 不把该响应持久化到跨账号共享的浏览器缓存。
6. 服务端或 CDN 同样不能把本人的响应作为公共缓存复用。若该边界尚未配置，接口至少需要采用与会话匹配的私有缓存策略。这是服务端保障，前端隐藏内容不能代替它。

## 作者入口

当前作者署名只有 `developerLogin`，没有可靠的 `userId` 映射，因此不能生成：

```text
/users/{developerLogin}
```

这会把一个身份域的标识错误地带入另一个身份域。

当前最小处理：

- 应用作者署名继续显示 `developerLogin`。
- 如果项目已有开发者详情入口，就继续链接到该入口。
- 如果没有开发者详情入口，署名只展示文本，不增加个人主页链接。
- 用户个人主页的入口只能来自明确持有 `userId` 的位置，例如登录用户菜单、用户搜索结果或已有用户实体。
- “我的主页”使用当前用户身份对象中的 `userId`；开发者会话里只有 `developerLogin` 时，不得猜测对应用户。

可以保留一个很小的扩展点，让作者组件接收“可选目标地址”。将来服务端提供正式的 `developerLogin → userId` 关系后，由用户域适配层提供链接，无需改写每个应用卡片。

## 实现顺序

1. 先修正契约来源  
   修改 OpenAPI、接口描述或生成器的上游定义，将 `applications` 说明改为“当前查看者有权看到的应用”。通过项目既有生成流程更新类型和注释，不直接手改生成文件。

2. 接通最小纵向流程  
   增加 `/users/:userId`，接入现有 API 层，先完成加载、成功、404、失败和路由参数变化。

3. 完成 GitHub 风格页面  
   使用现有设计令牌和组件实现资料区、应用列表及响应式布局，不引入新的 UI 库。

4. 增加明确入口  
   只在能够获得真实 `userId` 的位置添加“个人主页”入口；保持作者署名属于开发者域。

5. 补齐身份切换处理  
   验证退出或切换账号会清除、隔离或重新请求个人主页数据，防止上一账号的私有应用残留。

6. 最后补测试和浏览器验收  
   优先覆盖权限响应消费、身份切换和错误身份链接，而不是测试内部组件结构。

## 验收方式

至少使用一名有公开及私有应用的用户准备以下场景：

| 场景 | 预期结果 |
|---|---|
| 本人访问 `/users/{userId}` | 展示接口返回的公开和私有应用 |
| 其他用户访问同一路径 | 只展示服务端返回的可见应用 |
| 未登录访问 | 结果严格服从接口策略，前端不自行补数据或推断权限 |
| 本人页面退出登录或切换账号 | 立即失效并重新请求，不残留私有应用 |
| 连续切换两个 `userId` | 不出现前一个用户的迟到响应 |
| 应用数组为空 | 展示明确空状态，不写成“没有公开应用” |
| 用户不存在 | 展示既有 404 页面或等价恢复入口 |
| 请求失败 | 展示错误及可用的重试操作 |
| 点击作者署名 | 只进入既有开发者入口；绝不把 `developerLogin` 拼进用户路由 |
| 点击“我的主页” | 使用登录用户身份中的真实 `userId` |
| 桌面和窄屏浏览器 | 资料与列表无溢出、遮挡，链接可键盘访问，头像具有合适替代文本 |

自动化测试中，最有价值的是两个接口响应夹具：本人响应含私有应用，其他查看者响应不含私有应用。组件测试应证明前端完整呈现“服务端已返回的集合”，端到端测试则覆盖同一 URL 在身份切换后重新取数。最终还需在真实浏览器中检查桌面、窄屏、键盘导航和账号切换；仅靠类型检查或 DOM 快照不能证明这些行为。
