## 核心决定

`user` 与 `developer` 是两个独立身份域：

- 个人主页使用 `userId`。
- 应用作者只有 `developerLogin`。
- 禁止把 `developerLogin` 当作 `userId`，也不能生成 `/users/{developerLogin}`。
- `GET /users/{userId}` 返回的是“当前查看者有权看到的 applications”，本人可收到公开和私有应用。前端完整展示服务端返回值，不再做公开性过滤。
- 旧生成注释已经过时，应修改生成源并重新生成，不能手改生成文件后留下下一次生成会复现的问题。

## 路由

新增公开可进入的详情路由：

```ts
{
  path: '/users/:userId',
  name: 'user-profile',
  component: () => import(/* 个人主页页面 */),
  props: route => ({ userId: String(route.params.userId) }),
}
```

具体路径和文件名沿用项目现有 Vue Router 约定。

路由不应因为“可能包含私有应用”而加前端登录守卫。请求是否返回私有应用由服务端根据会话决定，路由守卫不能承担授权职责。

页面必须支持：

- 地址栏直达、刷新和前进后退。
- 同一组件内从一个 `userId` 导航到另一个时重新请求。
- 无效或不存在的用户按照现有 API 状态码约定展示错误。
- `userId` 只来自路由，不复制进全局 Store。

## 数据流

```text
/users/:userId
       ↓
个人主页页面
       ↓
用户领域数据访问层
       ↓ 携带现有会话
GET /users/{userId}
       ↓
{ profile, applications }
       ↓
页面直接渲染服务端筛选后的 applications
```

前端领域类型应表达真实含义：

```ts
interface UserProfilePageData {
  profile: UserProfile
  applications: ApplicationSummary[]
}
```

不要命名为 `publicApplications`，也不要执行类似：

```ts
applications.filter(app => app.visibility === 'public')
```

实现注意点：

- 复用现有 HTTP 客户端、认证传递和错误处理。
- 请求状态由页面或现有查询机制负责，至少区分 loading、success、error。
- 路由参数变化时取消旧请求，或忽略已经过期的响应。
- 没有跨页面复用需求时，不新增全局 Store。
- 应用是否标记“私有”，只取决于响应中是否已有可靠的可见性字段；没有该字段就不要推断或新增角标。

该接口响应随查看者身份变化，缓存必须按身份隔离：

- 登录、退出或切换账号后，清除或失效该用户主页查询。
- 如果现有查询缓存不会随会话清理，查询键需包含稳定的 viewer/session scope。
- SSR、代理或 CDN 不得把本人响应作为公共缓存复用；服务端需提供适当的私有缓存策略。这是服务端契约验收项，不用前端隐藏数据来补救。

## 作者入口

第一版不把应用作者链接到用户个人主页。

按以下优先级处理：

1. 如果项目已经存在以 `developerLogin` 为参数的开发者详情路由，作者名链接到该路由。
2. 如果没有开发者详情能力，作者名展示为普通文本。
3. 不查询、不猜测、也不维护前端 `developerLogin → userId` 映射。

如果产品以后要求“从作者进入用户主页”，接口必须显式提供关联，例如 `authorUserId` 或明确的 `authorProfileUrl`。这是服务端身份关系能力，不应由前端字符串拼接解决。

## GitHub 风格的最小页面

只借鉴信息层级，不复制 GitHub 品牌资产：

- 宽屏使用左侧个人资料、右侧应用列表的双栏布局。
- 窄屏按“头像与资料 → 应用列表”自然堆叠。
- 资料区包含现有 `profile` 真正提供的字段，不臆造贡献、关注者等数据。
- 应用使用简洁列表或卡片，名称为主标题，描述和已有元数据为次级信息。
- 使用项目现有颜色、字号、间距、头像和卡片组件。
- 提供骨架或加载提示、空应用状态、错误与重试入口。
- 使用语义化标题和列表；头像需要合适的替代文本，键盘焦点样式沿用设计系统。

## 实现顺序

1. 查找 `GET /users/{userId}` 的 OpenAPI、IDL 或其他生成源，把 `applications` 描述更新为“服务端根据查看者返回其可见应用；本人包含公开和私有应用”，随后走项目规定的生成流程。
2. 更新或确认生成类型，确保字段名称不再表达“仅公开”的错误语义。
3. 在用户领域数据访问层接入接口，复用认证、错误和取消机制。
4. 增加 `/users/:userId` 路由，先连通资料与应用列表的完整主路径。
5. 补齐加载、空、失败、重试和路由参数切换。
6. 增加 GitHub 风格响应式布局。
7. 按上述身份规则实现作者展示或开发者入口。
8. 补充缓存身份隔离和关键验收测试。

## 验收方式

| 场景 | 预期结果 |
|---|---|
| 本人访问 | 服务端返回的公开、私有应用都被渲染，前端没有二次过滤 |
| 其他用户或匿名查看 | 只显示服务端实际返回的应用 |
| 本人查看后退出登录 | 不得从客户端缓存继续看到私有应用 |
| 切换账号 | 重新取得新查看者权限下的数据 |
| 路由切换 `userId` | 最终只显示新用户数据，慢响应不能覆盖当前页面 |
| 直接刷新个人主页 | 路由和数据加载正常 |
| 空应用列表 | 显示明确空状态，不把它解释成请求失败 |
| 请求失败 | 显示错误及可用的重试入口 |
| 作者只有 `developerLogin` | 不产生 `/users/{developerLogin}` 链接 |
| 开发者路由存在 | 作者入口使用该路由规定的 login 参数 |
| 响应式视觉 | 宽屏双栏、窄屏单栏；长名称、长描述及 200% 缩放下无截断或不可达内容 |

最关键的自动化用例应覆盖“本人响应包含私有应用”和“退出后不能复用该响应”。视觉验收则在真实浏览器中检查一个桌面宽度、一个窄屏宽度以及长内容状态。
