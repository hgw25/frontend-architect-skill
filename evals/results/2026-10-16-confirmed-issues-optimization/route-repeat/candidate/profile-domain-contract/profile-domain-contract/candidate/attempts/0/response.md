当前工作区没有 Vue 应用源码或历史提交，只有 `.frontend-architect` 指引，因此无法确认现有文件名、Vue Router 版本、请求库或生成命令。下面给出不依赖虚构仓库结构、可直接映射到现有约定的最小方案。

## 核心决策

- 用户和开发者是两个独立身份域，`userId` 与 `developerLogin` 不得互换。
- 个人主页使用 `/users/:userId`，不用 `developerLogin` 作为路由参数。
- `GET /users/{userId}` 返回的是“当前查看者有权看到的应用集合”。前端完整渲染 `applications`，不自行过滤私有应用。
- 作者署名暂时不能链接到用户主页。没有可靠映射时，宁可保留文本，也不能猜测 `developerLogin === userId`。
- GitHub 只作为信息层级和布局参考，不引入贡献图、Tab 系统等非必要功能。

## 路由与入口

新增命名路由：

```ts
{
  path: '/users/:userId',
  name: 'user-profile',
  component: () => import(/* 现有懒加载约定 */),
  props: true,
}
```

具体原则：

- 这是可分享、可刷新、支持前进后退的规范地址。
- 路由默认不加登录守卫。匿名、其他用户和本人看到什么，由服务端结合当前会话决定。
- `userId` 作为不透明标识处理，不从显示名或 `developerLogin` 推导。
- 账号菜单增加“我的主页”，使用当前登录用户真实的 `userId` 跳转。
- 不额外增加 `/me` 路由，避免两个地址表示同一资源。

## 数据流

```text
route.params.userId
        ↓
个人主页页面
        ↓
现有 API/client 层：GET /users/{userId}
        ↓
{ profile, applications }
        ↓
ProfileSummary + ApplicationList
```

实施约束：

1. 页面负责根据路由参数发起一次查询，并呈现 loading、success、empty、error、404 状态。
2. 优先沿用项目现有请求或查询方案；如果项目没有查询库，用页面级组合函数和明确的加载联合状态即可，不为一个页面新增依赖。
3. 路由从用户 A 切换到用户 B 时，取消旧请求或忽略过期响应，防止 A 的结果覆盖 B。
4. `applications` 原样进入展示层。不要写下面这类逻辑：

```ts
applications.filter(app => app.isPublic || isOwnProfile)
```

授权和可见性已经由服务端决定，`isOwnProfile` 最多用于展示“编辑资料”等界面能力。

5. 此响应依赖查看者身份，不能只按 `userId` 放入公共缓存。缓存键至少包含会话/查看者范围；如果现有缓存无法表达这一点，就不做跨会话缓存，并在登录、退出及切换账号后失效该查询。
6. 应用卡片复用已有组件。若响应中已有可见性字段，本人的私有应用应显示现有的“私有”标识；没有该字段则不能由前端猜测。

## 契约修正

旧生成注释与已确认行为冲突，属于过期记录。应修改生成源，例如 OpenAPI 描述，而不是手改生成文件：

> `applications` contains applications visible to the current viewer. Owners may receive both public and private applications; other viewers receive only public applications.

然后走项目已有生成流程重新生成客户端并提交生成产物。类型仍可保持：

```ts
type UserProfileResponse = {
  profile: UserProfile
  applications: ApplicationSummary[]
}
```

不需要为了表达授权结果新增另一套前端模型。

## 作者入口

第一版明确不把 `developerLogin` 链接到 `/users/...`。

- 如果产品已有开发者详情路由，署名继续链接到开发者域。
- 如果没有开发者详情页，署名保持普通文本。
- 只有未来服务端提供明确关系，如 `authorUserId`、`authorUserProfileUrl` 或专门的身份解析接口后，才能增加用户主页入口。
- 不应在浏览器端遍历用户、按字符串相等匹配，或为每个署名额外尝试查询。

建议把署名组件保留一个很小的扩展点：收到明确的用户主页标识时才渲染 `RouterLink`，否则渲染文本。这样后续增加映射无需重写应用卡片。

## 页面结构

GitHub 风格的最小版本：

- 左侧或顶部：头像、显示名、简介等已有 `profile` 字段。
- 主区域：Applications 标题、数量和应用卡片列表。
- 宽屏双栏，窄屏按“资料 → 应用”顺序单栏排列。
- 使用现有颜色、间距、头像和卡片组件，只借鉴 GitHub 的弱边框、清晰层级和紧凑列表。
- 不新增关注数、贡献图、复杂筛选、分页或编辑功能，除非接口和现有产品已经支持。

## 实现顺序

1. 修正接口描述源并重新生成客户端，建立正确契约。
2. 接通 `/users/:userId`、请求层和最简页面，先跑通本人及他人两个数据分支。
3. 复用现有头像、应用卡片、加载和错误组件完成页面布局。
4. 添加账号菜单中的“我的主页”入口。
5. 检查所有 `developerLogin` 作者署名，确保没有错误链接到用户路由。
6. 补充身份分支、缓存隔离、路由切换和响应式验收。

## 验收方式

| 场景 | 预期结果 |
|---|---|
| 匿名查看用户 | 页面可访问，只显示服务端返回的公开应用 |
| 其他登录用户查看 | 只显示该查看者有权看到的应用 |
| 本人查看 | 同一接口返回的公开和私有应用都可见 |
| 本人退出登录后刷新或返回 | 私有应用不从旧缓存中残留 |
| 切换账号 | 不复用上一查看者的授权相关响应 |
| 快速从用户 A 导航到用户 B | 最终只显示 B，迟到的 A 响应不能覆盖 |
| 无应用 | 显示明确空状态，而非空白页面 |
| 请求失败、404 | 显示现有错误反馈；可恢复错误提供重试 |
| 点击“我的主页” | 使用当前用户的 `userId` 到达规范路由 |
| 点击作者署名 | 不误进用户主页；仅保留文本或已有开发者入口 |
| 窄屏、长名字和长简介 | 无横向溢出，阅读顺序保持资料在前、应用在后 |
| 契约维护 | 生成注释明确描述“对当前查看者可见”，重新生成后无旧表述 |

自动化上至少覆盖“本人包含私有应用”“其他查看者不包含私有应用”“退出后不残留私有数据”三个高风险流程；权限集合最好通过接口集成或端到端测试验证，因为组件测试无法证明服务端授权正确。当前工作区没有应用代码，因此本次没有修改文件，也无法执行项目级构建或测试。
