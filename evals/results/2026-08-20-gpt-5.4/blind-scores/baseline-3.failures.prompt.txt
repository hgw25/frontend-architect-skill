+# Booking Confirmation Data-Layer Rollout Plan
+
+## Repository Reality
+
+This workspace contains no application source files, only an empty Git repository. The plan below is therefore an implementation design for the frontend booking confirmation page rather than a code-specific diff.
+
+## Goals
+
+- Replace the booking confirmation page data layer without assuming a single successful full rollout.
+- Prevent duplicate bookings during the two-week period when legacy and new APIs coexist.
+- Support progressive delivery, fast rollback, and production diagnosis with minimal user-impacting ambiguity.
+
+## Non-Negotiable Safety Position
+
+The frontend must reduce duplicate submissions, but it cannot be the only control preventing duplicate bookings. A server-recognized idempotency key or equivalent booking token is required before traffic moves beyond internal testing. Without that, the rollout should be blocked.
+
+## Compatibility Boundary
+
+Define a narrow adapter boundary between page logic and transport:
+
+- `BookingConfirmationController`
+  - Owns submit lifecycle, retries, error states, and telemetry.
+- `BookingConfirmationDataSource`
+  - Stable frontend interface used by the page.
+  - Example operations:
+    - `loadConfirmationContext()`
+    - `submitBooking(request, requestContext)`
+    - `pollBookingStatus(bookingAttemptId)`
+- `LegacyBookingApiAdapter`
+  - Maps stable interface to the old API contract.
+- `NewBookingApiAdapter`
+  - Maps stable interface to the new API contract.
+- `ResponseNormalizer`
+  - Converts both responses into one canonical client shape.
+
+The page should not branch on raw old/new API fields. All branching belongs inside adapters. That keeps the blast radius inside one boundary and lets rollout happen via configuration instead of page rewrites.
+
+## Canonical Frontend Request Contract
+
+Every booking submission should carry a shared envelope, regardless of backend version:
+
+- `bookingAttemptId`
+  - Client-generated UUID created when the user first enters the confirmation page.
+  - Stable across retries, refresh recovery, and transport fallback for the same intent.
+- `idempotencyKey`
+  - Equal to or derived from `bookingAttemptId`.
+  - Must be honored server-side.
+- `checkoutSessionId`
+  - Existing session/cart identifier if present.
+- `schemaVersion`
+  - Distinguishes the canonical client contract from backend transport versions.
+- `traceId`
+  - For observability correlation.
+- `clientTimestamp`
+  - Diagnostic only, not used for uniqueness.
+
+Persist `bookingAttemptId` only for the active booking flow and expire it aggressively after terminal success/cancel.
+
+## Progressive Delivery Strategy
+
+Rollout should use separate controls for read path and write path. Do not tie them together.
+
+### Phase 0: Dark Launch
+
+- Ship adapter boundary with legacy API still serving writes.
+- Call new API in shadow mode only for non-authoritative reads or mirrored validation where safe.
+- Compare normalized response shape and error distribution offline.
+
+### Phase 1: Internal Write Canary
+
+- New write path enabled only for staff/internal accounts and synthetic monitoring flows.
+- Legacy remains default for all user traffic.
+- Success criterion:
+  - No unexplained booking status divergence.
+  - No rise in duplicate-attempt indicators.
+  - P95/P99 latency within agreed envelope.
+
+### Phase 2: Cohort-Based Canary
+
+- Route a small fixed cohort, for example:
+  - 1%
+  - 5%
+  - 10%
+  - 25%
+- Cohort assignment should be sticky by user/session/device bucket for the whole checkout session.
+- Rollout key should come from remote config / feature flag service, not a build-time switch.
+- Exclude high-risk segments initially:
+  - Guests if guest recovery is weak.
+  - Payment methods with delayed confirmation.
+  - Regions with stricter data handling rules if not yet validated.
+
+### Phase 3: Majority Traffic With Kill Switch
+
+- Keep instant rollback flag available until the full two-week coexistence window ends.
+- Maintain legacy adapter code until post-rollout audit confirms no hidden dependence remains.
+
+## Read/Write Routing Rules
+
+Use explicit routing modes:
+
+- `legacy_only`
+- `new_read_legacy_write`
+- `new_read_new_write`
+- `new_write_with_legacy_fallback_blocked`
+
+Recommended default during migration:
+
+- Reads may move earlier.
+- Writes move later and only after idempotency is proven.
+- Do not silently fail over a timed-out write from new API to old API using a new idempotency key. That is a duplicate-booking trap.
+
+If fallback is needed after an ambiguous write outcome:
+
+- Reuse the same `bookingAttemptId` and `idempotencyKey`.
+- Query booking status first.
+- Only resubmit if the backend explicitly states the attempt is absent and safe to retry.
+
+## Duplicate Submission and Idempotency Design
+
+### Client Controls
+
+- Disable the confirm CTA immediately on first submit.
+- Replace repeated clicks with a non-interactive pending state.
+- Guard against double-fire sources:
+  - button double-click
+  - Enter key repeat
+  - browser back/forward resubmission
+  - page refresh during in-flight request
+  - duplicate tabs
+- Use a client-side in-flight registry keyed by `bookingAttemptId`.
+- Persist the active attempt in session storage to restore state after refresh.
+
+### Cross-Tab Protection
+
+- Broadcast in-flight and terminal booking states with `BroadcastChannel` or storage events.
+- When another tab detects an active attempt for the same checkout session:
+  - block new submission
+  - show “booking in progress”
+  - offer status refresh instead of another submit
+
+### Ambiguous Result Handling
+
+Treat the following as `UNKNOWN_FINAL_STATE`, not as immediate failure:
+
+- request timeout after submission
+- network disconnect after request sent
+- 5xx after write entered downstream processing
+- client navigation during in-flight state
+
+For `UNKNOWN_FINAL_STATE`:
+
+- Lock further submits for that `bookingAttemptId`.
+- Start status reconciliation:
+  - poll booking status by `bookingAttemptId` or `checkoutSessionId`
+  - if confirmed success, render success
+  - if confirmed absent/failure, allow retry with same idempotency key or a new attempt only after explicit reset
+- Show user copy that avoids encouraging repeated submission.
+
+## Error Recovery Model
+
+Use explicit terminal and non-terminal states:
+
+- `idle`
+- `submitting`
+- `submitted_unknown`
+- `confirmed`
+- `failed_retryable`
+- `failed_terminal`
+
+Recovery rules:
+
+- Validation or 4xx contract mismatch:
+  - `failed_terminal`
+  - capture payload class and adapter version
+- Network failure before request dispatch is confirmed:
+  - `failed_retryable`
+- Network failure after dispatch uncertainty:
+  - `submitted_unknown`
+- Server 5xx:
+  - default to `submitted_unknown` unless server guarantees no side effects
+
+The page should never return from `submitted_unknown` to a fully fresh form with an enabled submit button without first reconciling booking status.
+
+## Production Signals Required
+
+### Core KPIs
+
+- booking submit success rate by adapter version
+- duplicate booking rate
+- ambiguous outcome rate (`submitted_unknown`)
+- retry rate per booking attempt
+- reconciliation success rate
+- fallback invocation rate
+- abandonment rate after submit
+- P50/P95/P99 submit latency
+
+### Guardrail Signals
+
+- count of multiple successful bookings sharing the same:
+  - idempotency key
+  - checkout session
+  - user + inventory + close time window
+- divergence between frontend terminal state and backend truth
+- old/new adapter response normalization errors
+- client-side double-submit prevention triggers
+- cross-tab collision count
+- feature flag cohort error skew
+
+### Logging Shape
+
+Emit structured events for:
+
+- `booking_confirmation_loaded`
+- `booking_submit_started`
+- `booking_submit_response`
+- `booking_submit_unknown_state`
+- `booking_status_reconciled`
+- `booking_submit_blocked_duplicate`
+- `booking_rollout_route_selected`
+
+Each event should include only the minimum needed diagnostics:
+
+- `traceId`
+- `bookingAttemptId`
+- adapter version
+- rollout cohort
+- normalized error category
+- latency buckets
+- region / platform / app version
+
+Do not log raw personal data or payment details.
+
+## Privacy Controls
+
+- Do not place PII in:
+  - feature flag targeting payloads
+  - client logs
+  - analytics event names or free text
+  - session storage / local storage keys or values
+- Prefer opaque identifiers:
+  - hashed user ID if needed
+  - checkout session ID
+  - booking attempt ID
+- Keep persisted client recovery state minimal:
+  - `bookingAttemptId`
+  - checkout session reference
+  - submit state
+- Expire recovery state on:
+  - terminal success
+  - explicit cancel
+  - TTL timeout
+- Redact server error bodies before telemetry if they may contain user or payment metadata.
+
+## Rollback Conditions
+
+Rollback must be a runtime config change, not a redeploy.
+
+Immediate rollback triggers:
+
+- any confirmed duplicate-booking pattern attributable to the new path
+- ambiguous outcome rate above agreed threshold for 5 to 10 minutes
+- reconciliation endpoint failing or lagging enough to strand users
+- submit success rate materially worse than legacy cohort
+- normalization bug causing wrong confirmation state
+- privacy regression in telemetry payloads
+
+Partial rollback options:
+
+- revert `new_write` to `legacy_write`, keep `new_read`
+- disable only risky payment methods / regions / guest traffic
+- keep canary only for internal users while investigating
+
+## Release Checklist
+
+- Backend confirms idempotency semantics for both old and new APIs.
+- Frontend adapters share one canonical normalized model.
+- Kill switch tested in production-like environment.
+- Synthetic test covers:
+  - normal success
+  - timeout after dispatch
+  - duplicate click
+  - refresh during submit
+  - second tab submit
+  - rollback during active canary
+- Dashboard and alert thresholds exist before traffic shift.
+- Support/runbook prepared for `submitted_unknown` incidents.
+
+## Recommended Decision
+
+Proceed only with a frontend adapter migration plus server-enforced idempotency and status reconciliation. Do not ship a write-path canary that relies only on disabling the button or client retries. The safe shape is:
+
+1. isolate old/new transports behind one frontend boundary
+2. dark launch reads first
+3. canary writes with sticky cohorts and runtime kill switch
+4. treat uncertain outcomes as recoverable reconciliation states, not clean failures
+5. rollback on duplicate indicators before waiting for broad business impact

+# Headless Dialog Primitive Spec
+
+## Context
+
+三个 React 产品各自维护 Dialog，已经出现以下共性问题：
+
+- 焦点可逃逸到遮罩层外或页面底层
+- `Escape` 行为不一致，含嵌套弹层时更明显
+- `aria-*` 标注缺失，屏幕阅读器体验不稳定
+- 样式和动画实现散落在业务侧，难以复用
+
+目标是在前端基建层发布一个可复用的 headless Dialog primitive，统一可访问性、交互语义和状态模型，同时把视觉风格留给消费者。
+
+## Scope
+
+本 primitive 必须支持：
+
+- React 18+
+- `portal`
+- 受控和非受控打开方式
+- 嵌套 Dialog
+- SSR 和 hydration
+- 消费者自定义样式与动画
+
+本 primitive 明确不负责：
+
+- 业务文案
+- 业务按钮、表单、确认/取消逻辑
+- 品牌样式、主题、动效 token
+- toast、drawer、popover 等非 modal 语义组件
+
+## Release Decision
+
+发布一个独立包：`@acme/dialog`
+
+设计原则：
+
+- `headless only`：只提供结构、状态、焦点和 a11y 语义，不提供视觉样式
+- `compound components`：通过 `Root + Trigger + Portal + Overlay + Content + Title + Description + Close`
+- `single behavior model`：无论三个产品怎么写样式，交互都走同一套底层状态机
+- `modal-first`：默认 `modal=true`，非模态作为显式 opt-in
+- `controlled/uncontrolled parity`：受控和非受控行为一致，事件时序一致
+
+## Package Layout
+
+建议目录：
+
+```text
+packages/dialog/
+  src/
+    index.ts
+    dialog-root.tsx
+    dialog-trigger.tsx
+    dialog-portal.tsx
+    dialog-overlay.tsx
+    dialog-content.tsx
+    dialog-title.tsx
+    dialog-description.tsx
+    dialog-close.tsx
+    context.ts
+    stack.ts
+    focus-scope.ts
+    dismissable-layer.ts
+    portal.tsx
+    id.ts
+    types.ts
+  package.json
+  README.md
+```
+
+内部能力拆分：
+
+- `stack.ts`：管理嵌套层级，只允许顶层 active dialog 响应 `Escape` 和 outside interaction
+- `focus-scope.ts`：负责初始聚焦、tab 环、关闭后焦点恢复
+- `dismissable-layer.ts`：统一 `Escape`、pointer down outside、focus outside
+- `id.ts`：SSR 稳定 id，避免 hydration 时 `aria-labelledby` / `aria-describedby` 不一致
+
+## Core Boundaries
+
+### 1. `Dialog.Root`
+
+职责：
+
+- 持有打开状态
+- 连接受控/非受控模式
+- 建立上下文
+- 向子组件暴露 `open`, `modal`, ids, refs, stack metadata
+
+边界：
+
+- 不渲染 DOM
+- 不附带默认 className

+### 2. `Dialog.Trigger`
+
+职责：
+
+- 触发 open
+- 暴露 `aria-haspopup="dialog"`

+
+- 默认渲染 `button`

+
+### 3. `Dialog.Portal`
+
+职责：
+
+- 控制内容是否挂到 `document.body` 或指定容器
+- 在 SSR 阶段保持无副作用
+
+边界：
+
+- 不注入额外布局样式
+- 未 hydration 前不访问 `document`

+### 4. `Dialog.Overlay`
+
+职责：
+
+- 提供遮罩语义节点
+- 透出 data attributes 供动画和样式使用

+- 不强制背景色

+
+职责：
+

+- 处理 `Escape`
+- 处理 outside interactions
+- 在 modal 模式下隔离页面其他可交互内容
+
+边界：
+
+- 不注入业务布局
+- 不耦合标题、描述是否必须渲染；只在缺失时给开发警告

+
+职责：
+

+
+职责：
+
+- 触发关闭
+
+边界：
+
+- 不写死文案和 icon

+- `[data-state="open" | "closed"]`
+- `[data-disabled]`
+- `[data-dialog-content]`
+- `[data-dialog-overlay]`
+- `[data-nested="true"]`
+
+### Refs
+
+- `Trigger` 转发到触发元素
+- `Content` 转发到对话框根节点
+- `Overlay` / `Close` / `Title` / `Description` 均转发到底层 DOM
+
+## Behavioral Rules
+
+### Open / Close Semantics
+
+- `Trigger` click 或 keyboard activation 打开
+- `Close` click 关闭
+- 顶层 active dialog 才响应 `Escape`
+- modal 模式下，outside pointer interaction 默认关闭；若事件被阻止则保持打开
+- 非 modal 模式下允许底层页面继续可聚焦，但 `Escape` 仍只作用于 active dialog
+
+### Focus Management
+
+- 打开时默认聚焦 `Content` 内第一个可聚焦元素
+- 若无可聚焦元素，则聚焦 `Content`
+- 关闭时恢复到触发元素；若触发元素已卸载，则尝试恢复到先前 active element，否则不抛错
+- 嵌套 Dialog 打开时，父级焦点陷阱暂停，子级接管
+- 子级关闭后，焦点回到父级最后活跃元素，而不是页面底层
+
+### Nested Dialog Stack
+
+- 维护 LIFO stack
+- 只有 stack 顶部实例可以：
+  - 响应 `Escape`
+  - 响应 outside interactions
+  - 设置 `aria-hidden` / inert 隔离外围内容
+- 父弹窗打开子弹窗时不自动关闭父弹窗
+
+### SSR / Hydration
+
+- 服务端渲染阶段不访问 `window` / `document`
+- id 使用 React `useId` 或等价稳定方案
+- portal hydration 前允许内容先内联渲染，hydration 后再挂入目标容器
+- 不依赖 mount order 生成随机 id
+
+### Accessibility Baseline
+
+`Content` 在 modal 模式下必须满足：
+
+- `role="dialog"` 或 `role="alertdialog"`
+- `aria-modal="true"`
+- `aria-labelledby` 指向 `Title`，若无 `Title` 则允许消费者显式传 `aria-label`
+- `aria-describedby` 在有 `Description` 时自动绑定
+
+开发态 warning：
+
+- 同时缺失 `Title` 与 `aria-label`
+- `alertdialog` 未提供可感知标题
+- `Dialog.Content` 脱离 `Dialog.Root` 使用
+
+## Internal Implementation Decisions
+
+### State Model
+
+- 使用 `useControllableState` 统一受控/非受控
+- 所有关闭来源都归一为 `requestOpenChange(false, reason)`
+- `reason` 为内部枚举，不进入公开 API，避免过早锁死事件模型
+
+内部关闭原因建议：
+
+```ts
+type CloseReason =
+  | "trigger"
+  | "close-button"
+  | "escape-key"
+  | "pointer-down-outside"
+  | "programmatic";
+```
+
+### Dismiss Strategy
+
+- `Escape` 监听挂在 active content document 上
+- pointer down outside 先判定 overlay/content/portal 树，再决定是否请求关闭
+- focus outside 和 pointer outside 统一进入 `onInteractOutside`
+
+### Page Isolation
+
+modal 模式优先级：
+
+1. 对非 dialog subtree 设置 `inert`
+2. 不支持 `inert` 的环境退化到 `aria-hidden`
+
+说明：
+
+- `inert` 用于真实阻止 tab/点击穿透
+- `aria-hidden` 仅作为兼容退化，不单独承担交互隔离
+
+### Styling Contract
+
+- primitive 不输出任何内联视觉样式
+- 只输出最小语义属性和 data attributes
+- `forceMount` 交给消费者处理 exit animation

+# @frontend-architect-eval/feature-flags
+
+Vite plugin that exposes a typed `virtual:feature-flags` module from a server-owned JSON source while only shipping an explicit public allowlist to the client.
+
+## Usage
+
+```ts
+// vite.config.ts
+import { fileURLToPath } from 'node:url'
+
+import { featureFlags } from '@frontend-architect-eval/feature-flags'
+import { defineConfig } from 'vite'
+
+export default defineConfig({
+  plugins: [
+    featureFlags({
+      source: fileURLToPath(new URL('./flags.json', import.meta.url)),
+      expose: ['checkoutV2', 'theme'] as const,
+    }),
+  ],
+})
+```
+
+```ts
+// src/feature-flags.d.ts
+import '@frontend-architect-eval/feature-flags'
+
+declare module '@frontend-architect-eval/feature-flags' {
+  interface FeatureFlagsRegistry {
+    checkoutV2: boolean
+    theme: string
+  }
+}
+```
+
+```ts
+import { flags } from 'virtual:feature-flags'
+
+flags.checkoutV2
+flags.theme
+```
+
+## Public types
+
+- `FeatureFlagPrimitive`: values allowed to cross the client boundary.
+- `FeatureFlagsRecord`: reusable `Record<string, FeatureFlagPrimitive>` alias.
+- `FeatureFlagsRegistry`: augmentation point for consumer-owned public flag typing.
+- `FeatureFlagsShape`: readonly view used by `virtual:feature-flags`.
+- `FeatureFlagsOptions`: plugin configuration contract.
+
+The package keeps runtime configuration and public TypeScript shape decoupled on purpose. Build tools can load JSON at runtime, but TypeScript cannot safely infer JSON allowlists from `vite.config.ts` without a code generation step. Module augmentation keeps editor and CI typing explicit and stable across dev, build and published package consumption.
+
+## Package exports
+
+- `.`: plugin runtime and public types.
+- `./virtual`: type-only entry used from `tsconfig.compilerOptions.types`.
+- `./package.json`: export preserved for tooling and pack verification.
+
+`virtual:feature-flags` is resolved by Vite at runtime; `./virtual` exists only to give TypeScript a stable ambient declaration.
+
+## Diagnostics
+
+The plugin throws actionable errors when:
+
+- the source file is not valid JSON
+- the source JSON is not an object
+- `expose` references a missing key
+- `expose` contains duplicates or empty names
+- an exposed value is not `boolean | number | string`
+
+Each message includes the flag name or source path and the next action to take.
+
+## Secrets boundary
+
+Only keys listed in `expose` are serialized into the virtual module. All other keys remain server-side and never enter dev responses, production bundles or HMR payloads.
+
+## Source maps
+
+The generated virtual module returns a source map whose source points back to the JSON input file. Consumers can debug the virtual module in devtools while package consumers still get `.js.map`, `.d.ts`, and `.d.ts.map` from the published build.
+
+## Cache and HMR
+
+The plugin caches the raw JSON text and parsed public subset. Re-reads only happen when the watched source file changes. On HMR, the plugin invalidates the virtual module and its importers, so dev behavior stays aligned with build output. If no importer is registered yet, it falls back to a full reload.
+
+## Integration tests
+
+Repository checks cover:
+
+- `test:build`: production bundle contains public flags and excludes secrets
+- `test:dev`: Vite dev server reloads updated flags through the virtual module
+- `test:diagnostics`: misconfigured exposure fails with actionable messaging
+- `test:package`: packed tarball includes runtime, types and source maps
+
+## Version evolution
+
+- Patch: diagnostics wording, internal caching changes, non-breaking HMR fixes.
+- Minor: additive public types, new optional plugin options, new diagnostics.
+- Major: changes to virtual module shape, TypeScript augmentation contract, or stricter runtime validation defaults.
