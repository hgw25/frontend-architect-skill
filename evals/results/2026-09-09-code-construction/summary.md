# 代码构造与连续需求评测

本轮修改实现层指导：函数主流程与调用契约、数据表示与入口归一化、异步政策选择、
错误与资源生命周期。主入口改为优先比较项目契约与平台能力；额外专题读取需要具体
决策依据，由独立审查判断，不再因数量直接失败。两项新夹具及连续需求均无外部依赖。

## 方法

2026-09-09，冻结本轮开始前的已安装候选内容为 previous，并保留新内容为 candidate。
每个条件各用新上下文生成代理，继承当前 GPT-6 Astra 配置；每个任务的第二轮延续自身
第一轮上下文。不是无技能 baseline，也没有更换模型或重复采样。

首轮只提供 Skill、缺陷源码、明确公共契约和受保护验收。首轮冻结后再提供第二轮需求
与新增只读测试。仅允许修改 src。主代理独立复跑所有检查、逐字核对受保护文件，并
保存两阶段源码和差异。匿名代码再交由新上下文审查者检查；审查者不知道版本映射。

## 结果

搜索的第二轮新增 reset，两个条件都复用既有请求失效机制，只局部新增方法。

新搜索实现读取 async-and-lifecycles；其余三个实现仅用主入口。第一轮各失败均在初始
夹具运行中暴露，临时参考修复也验证验收可通过，参考代码未给生成代理。

[独立代码审查](independent-review.md) 未发现重要契约缺陷，认为对应两份代码实质等价。
因此本次证据支持这两个场景没有观察到退化，**不支持“新版明显优于旧版”或量化提升**。

## 范围与后续解释

共有 25 个场景，其中 6 个配置可执行 fixture；本轮实际运行两个新增场景的四组两轮
实现，没有运行全部其他场景。静态校验与 26 项评测脚本测试通过。文档中的 TypeScript
示例经过 Node 类型擦除后运行了关键行为检查；这不是 TypeScript 静态类型检查。

题目明确且无框架，本轮只能证明局部算法、数据和生命周期契约；不能证明真实 UI、
复杂仓库导航、浏览器、Flutter/原生性能或完整产品交付质量。生成与审查使用同系列模型，
单次、少量用例无法估计稳定提升。没有以高通过数或更多指导文本替代这些证据限制。
