当前最小方案应把“用户主页”和“开发者作者身份”严格分开。个人主页使用 `userId`；现有 `developerLogin` 不能转换成用户主页链接。

由于工作区只有 `.frontend-architect` 和 Git 元数据，没有 Vue 源码、接口定义或测试配置，以下方案不虚构项目目录、组件名或命令，也未修改任何文件。

## 1. 路由

新增公开路由：

```text
/users/:userId
```

建议路由名为 `user-profile`，参数在代码中命名为 `targetUserId`，避免和当前登录者混淆。

- 不设置登录守卫：匿名查看者也能访问，服务端只返回公开应用。
- 路由切换到另一个 `userId` 时重新请求。
- 服务端 404 显示“用户不存在”；其他错误显示可重试错误态。
- 页面包含加载态、无应用态和正常内容态。
- 不根据前端判断跳转到“本人主页”或决定能否查看私有内容。

## 2. 数据流与权限边界

```text
route.params.userId
        ↓
GET /users/{userId}（携带现有会话凭证）
        ↓
{ profile, applications }
        ↓
页面直接渲染服务端返回的 applications
```

核心决策：

- `profile` 与 `applications` 作为一次页面查询的结果维护，不再额外请求应用列表。
- 前端不执行“仅保留公开应用”的过滤，也不通过 `targetUserId === viewerUserId` 推导权限。
- 本人、其他登录用户和匿名用户使用同一个请求流程；差异完全由服务端响应体现。
- 若应用对象已有公开/私有字段，本人视图可显示现有语义对应的私有标识；若没有该字段，不猜测、不添加伪标签。
- 登录、退出或账号切换时，必须失效或清除用户主页查询缓存。只按 `targetUserId` 长期缓存会造成本人私有应用在退出后残留。
- 如果项目已有查询缓存，沿用其会话隔离机制；否则至少在认证状态变化时统一 invalidate 用户主页查询，不另建全局 store。
- 快速切换不同用户时应采用项目已有的取消请求或过期结果保护，避免旧响应覆盖新页面。

建议前端契约保持服务端结构：

```ts
interface UserProfilePageData {
  profile: UserProfile
  applications: ApplicationSummary[]
}
```

旧生成注释“applications 仅公开”已经被产品确认的现行契约推翻，应修正契约源文件并重新生成客户端；不要只手改生成文件。准确含义应类似：

> 返回服务端授权当前查看者可见的应用；本人可能同时获得公开和私有应用。

如果生成源不在前端仓库，则先在前端补一条临时准确说明，同时将上游契约修正列为合入条件。

## 3. 页面与 GitHub 风格

保持最小、信息优先的双栏布局：

- 左侧：头像及 `profile` 中现有的身份简介字段。
- 右侧：应用标题、描述及接口已有的辅助信息。
- 使用克制的边框、圆角、灰阶和强调色，参考 GitHub 的资料页信息密度，不复制其品牌资产。
- 窄屏改为上下排列。
- 应用入口使用真实链接元素；标题层级、空状态和错误提示具备可读语义。
- 只展示接口实际存在的字段，不为了贴近 GitHub 假设用户名、统计数或社交字段。

## 4. 作者入口

`developerLogin` 属于开发者身份，不能当作 `userId`：

- 禁止生成 `/users/${developerLogin}`。
- 如果项目已有以 `developerLogin` 为键的开发者详情路由，作者署名继续链接到该开发者路由。
- 如果没有开发者详情路由，作者署名暂时显示为不可点击文本。
- 若产品以后要求作者署名进入用户主页，需要服务端提供明确的 `authorUserId`、身份映射或规范化 `authorHref`；不在前端建立猜测映射。

这既避免错误跳转，也为以后增加开发者—用户绑定留下了清晰边界。

## 5. 实现顺序

1. 修正接口契约来源和生成注释，确认生成后的类型仍返回完整 `{ profile, applications }`。
2. 在现有 API 层增加或复用 `getUserProfile(targetUserId)`，保持认证凭证、错误处理和取消策略一致。
3. 注册 `/users/:userId`，先接通路由参数、请求、加载/错误/404/空状态。
4. 实现 GitHub 风格响应式页面，直接消费接口返回的数据。
5. 接入站内已有的用户入口；作者署名只走已有开发者路由，否则保持文本。
6. 补充认证状态切换时的缓存失效，再完成自动化和浏览器验收。

## 6. 验收方式

权限和数据至少覆盖以下矩阵：

| 场景 | 预期 |
|---|---|
| 匿名查看用户 | 页面成功，展示响应中的公开应用 |
| 其他登录用户查看 | 不出现目标用户的私有应用 |
| 本人查看 | 同时展示服务端返回的公开和私有应用 |
| 本人页面退出登录 | 私有应用立即从页面和缓存中消失 |
| 两个账号切换 | 不复用前一账号可见的私有数据 |
| 连续切换两个 `userId` | 最终页面只显示当前路由用户的数据 |
| 用户不存在 | 显示明确的 404 状态 |
| 请求失败后重试 | 能恢复到完整页面 |
| 点击作者署名 | 进入已有开发者页，或保持不可点击；绝不误进用户页 |

自动化检查建议：

- API/数据层测试：断言前端不再过滤 `applications`，并原样保留服务端结果。
- 路由组件测试：加载、成功、空、404、错误与参数变化。
- 认证集成测试：本人查看后退出或换号，验证私有应用不残留。
- 浏览器验收：桌面和窄屏布局、键盘导航、链接语义、长名称与长描述。
- 运行项目已有的类型检查、单元测试和构建命令；具体命令需以实际仓库配置为准。
