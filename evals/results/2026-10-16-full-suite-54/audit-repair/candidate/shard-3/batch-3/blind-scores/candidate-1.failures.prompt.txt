## 恢复并继续表单工作

同步 PR 合入后：

```bash
git fetch origin
git switch wip/form-before-template-sync-YYYY-MM
git rebase origin/<团队默认分支>
```

此处 rebase 只作用于个人 WIP 分支，不改写团队共享分支。若 WIP 分支已有其他协作者，则改用：

```bash
git merge origin/<团队默认分支>
```

## 回退策略

- 合并尚未提交时发现问题：`git merge --abort`。
- 同步分支尚未进入团队默认分支：修正或关闭该 PR，不影响团队主线。
- 已进入共享分支后发现严重问题：新建回退分支并 `git revert -m 1 <模板同步merge提交>`，通过 PR 回退；不要重置共享分支。
- 表单修改始终保存在独立 WIP 分支，不依赖同步操作是否成功。

## 固化为每月流程

以后每月不再重复添加 remote，只需：

1. 保存或提交当前工作区修改。
2. `fetch --prune` origin 与 upstream。
3. 从最新 `origin/<团队默认分支>` 创建带年月的同步分支。
4. `--no-ff` 合并 upstream 默认分支。
5. 人工处理冲突并重新生成锁文件/生成物。
6. 运行构建与表单回归。
7. PR 合入，并记录 upstream SHA 和验证结果。

这样既保留团队业务提交与未完成表单工作，也让每次模板升级都有清晰来源、审查边界和可恢复路径。

RESPONSE:
结论：现在不应立即引入完整的 feature/domain 分层。

两个页面、十几个源文件更适合保持浅层结构。完整分层会增加目录跳转、转发文件和边界维护成本，而目前还没有足够的变化模式证明这些边界真实存在。

当前建议采用轻量的混合结构：

```text
src/
  main.tsx             # 启动
  App.tsx              # 路由、全局 Provider、应用外壳
  pages/
    PageA.tsx
    PageB.tsx
  components/          # 仅放真正跨页面复用的组件
  api/                 # 仅在已有共享请求客户端时设置
  lib/                 # 少量无业务归属的通用能力
```

遵循所用框架规定的路由目录；不要为了凑齐结构创建空的 `features/`、`domain/`、`model/`、`ui/`、`services/` 等目录。

页面出现多个私有实现文件时，只局部加深：

```text
pages/
  orders/
    OrdersPage.tsx
    OrdersTable.tsx
    useOrders.ts
    orders.api.ts
    OrdersPage.test.tsx
```

这些文件先由页面共同拥有。不要因为有一个 hook、一种类型或一次请求，就分别搬进全局 `hooks/`、`types/`、`services/`。真正跨页面共享的基础能力再提升到 `shared` 或现有对应目录；业务规则即使不复用，也应有明确文件所有者，而不是长期堆在页面组件中。

未来出现以下信号时，再按能力逐步迁移：

- 同一产品能力连续多次改动，都要同时穿梭于全局 `components/hooks/services/types`。
- 一个用户可识别的能力跨越两个页面，并拥有自己的状态、规则、请求与测试。
- 页面开始同时管理大量表单状态、请求、恢复流程和业务规则，已经不是单纯的用例协调者。
- 通用目录成为杂物箱，文件归属需要靠团队成员口头解释。
- 不同能力能独立演进，或开始由不同维护者负责。
- 出现重复业务规则、跨功能循环依赖、路由级拆包或独立交付需求。

届时应一次迁移一个最活跃的能力，例如：

```text
src/
  app/
  pages/
  features/
    approval/
      ApprovalPanel.tsx
      approval.api.ts
      approval.model.ts
      approval.test.ts
      index.ts
  shared/
```

依赖方向保持为 `app/pages → features → shared`；页面负责组合能力，feature 不反向依赖页面。`api/model/ui` 子目录也应等单个 feature 的文件数量确实影响导航后再增加，避免小目录套小目录。

现实的检验方式是：如果明天只给其中一个页面增加“导出记录”，改动应该集中在该页面附近，并最多复用已有请求客户端；不需要重构全局目录。若以后“审批”同时进入两个页面，并形成独立规则和流程，它才是值得抽出的 feature/domain 边界。
