结论：这是一个高严重度的对象级授权缺陷。任何已登录用户只要构造他人文档 ID，就可能绕过前端按钮直接调用删除接口。前端隐藏按钮不能作为授权依据，应阻止该接口发布或继续使用，直到服务端修复。

最小必要修复：

1. 服务端从已验证的会话或令牌取得调用者身份，不能信任请求中的 `userId`、`ownerId`。
2. 将调用者身份传入删除用例，并在权威数据操作中同时约束文档和权限。若规则是“仅所有者可删除”，应采用等价于：

   ```sql
   DELETE FROM documents
   WHERE id = :documentId
     AND owner_id = :authenticatedUserId
   ```

   若是软删除，同样把权限条件放进 `UPDATE`。
3. 根据受影响行数判断结果。零行沿用项目现有的非泄露语义，通常统一返回 `404`；只有现有契约明确区分时才返回 `403`。
4. 不保留“先检查存在，再无条件删除”的执行链，避免越权，也避免检查与删除之间的竞态。
5. 若项目已有管理员、租户或协作者删除规则，应复用该规则；不要为这次修复新建通用 RBAC、安全中间件或策略框架。

前端职责：

- 可以继续隐藏无权限用户的删除按钮，但它只负责交互提示。
- 必须接受服务端最终裁决，并正常处理 `401/403/404`。
- 删除成功后再移除本地文档；如使用乐观更新，拒绝或失败时必须恢复。
- 不需要为了此次服务端授权修复新增前端权限框架。若接口已经返回 `canDelete`，优先用它控制展示；否则现有所有者判断可暂时保留为 UX 逻辑。

最低验证覆盖：

- 所有者删除自己的文档成功。
- 用户 B 删除用户 A 的文档被拒绝，并确认文档仍存在。
- 未登录调用被拒绝。
- 不存在的文档不会产生删除。
- 若有租户、管理员或协作者规则，各补一个真实边界用例。
