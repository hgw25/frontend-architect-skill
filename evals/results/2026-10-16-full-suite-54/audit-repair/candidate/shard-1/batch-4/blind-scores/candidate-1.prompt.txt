## 状态与副作用所有权

| 所有者 | 拥有的状态 | 拥有的副作用及策略 | 对外提供 |
|---|---|---|---|
| `CheckoutPage` | 尽量不新增业务状态 | 成功后的路由跳转，以及确属页面级的埋点 | 组合各能力，生成提交命令 |
| `useCheckoutDraft` | 可编辑字段、touched、dirty、字段错误、编辑版本 | 草稿恢复或离开提醒，仅在现有产品有此行为时保留 | `draft`、`updateField`、`validate`、稳定提交快照 |
| `pricing.ts` | 无 | 无；必须是纯计算 | `calculatePricing(input): PriceBreakdown` |
| `useCoupon` | 当前已应用优惠、请求状态、当前请求身份、可重试错误 | 调用券接口；通常采用 latest-wins，旧请求的成功、失败和 `finally` 都不得覆盖新请求 | `appliedCoupon`、`status`、`apply(code)`、`remove()`、`retry()` |
| `CouponControl` | 尚未应用的输入文字、输入框交互状态 | 聚焦、键盘提交等局部交互 | 语义化优惠券输入 UI |
| `useInventoryAvailability` | 当前商品集合对应的库存快照和订阅状态 | 建立、替换、释放订阅；忽略旧订阅迟到回调 | `availability`、`status` |
| `usePaymentSession` | SDK 会话身份、ready/pending/error 状态 | SDK 初始化、挂载、替换、卸载；清理只释放本实例拥有的资源 | `status` 和窄化后的 `confirmPayment` 命令 |
| `paymentSdkAdapter` | 无 React 状态 | 把第三方 SDK 类型、异常和清理方式转换为 feature 内部契约 | SDK 无关的会话/确认接口 |
| `useCheckoutSubmission` | 当前提交尝试、不可变输入快照、幂等键、pending/success/failure/unknown 状态 | 按现有后端协议协调支付和订单请求，防止双击重复提交，处理超时后的未知结果 | `submit(snapshot)`、`retry()`、提交状态 |
| 各 adapter/client | 不拥有展示状态 | HTTP、SDK、订阅和 DTO 映射 | 规范化数据或明确错误，不返回“空成功” |

几个关键约束：

- 价格应由 `draft + cart + 已应用优惠` 派生，不再复制进 React state。
- 如果金额实际由服务端报价决定，就不要创建本地业务计算器；改由报价 adapter 返回规范化 `PriceBreakdown`，前端只做展示派生。最终金额不能以客户端计算结果作为可信依据。
- 支付卡号等敏感输入由支付 SDK/托管控件持有，不能进入草稿状态。
- 提交开始时冻结完整快照。重试默认重用失败的那次快照，不应悄悄读取之后编辑过的草稿。
- 能否点击提交可以在页面派生，但它只是 UI 提示；提交工作流仍需执行真正的校验和服务端约束。
- 字段错误归表单，优惠券错误归优惠券控件，SDK 错误归支付区域，最终提交错误归 submission。不要再建一个吞掉全部异常的 `errorService`。

## API 边界

Feature 对外只保留现有路由真正需要的入口，例如：

```ts
// features/checkout/index.ts
export { CheckoutPage } from './CheckoutPage';
```

除非已有外部调用者，不公开 hooks、clients、SDK adapter 或 `pricing.ts`。外部消费者不得通过深路径导入内部文件。

Feature 内部使用小而明确的契约：

```ts
type PaymentCommand = {
  confirmPayment(input: PaymentConfirmationInput):
    Promise<PaymentAuthorization>;
};

type CheckoutSubmission = {
  state: SubmissionState;
  submit(snapshot: ValidatedCheckout): Promise<void>;
  retry(): Promise<void>;
};
```

不必为了测试给每个 client 建 repository/interface。支付 SDK 确实是高波动外部边界，值得一个窄 adapter；普通 checkout HTTP 请求若项目数据层已处理缓存、取消和错误，直接复用即可。

## 依赖方向

```text
feature index
    ↓
CheckoutPage（组合）
    ├─→ form / coupon / inventory / payment UI
    ├─→ submission workflow
    └─→ pricing / checkoutModel

UI ─────────────→ hooks、纯模型
workflow ───────→ 纯模型、focused clients/adapters
hooks ──────────→ 各自拥有的 client/adapter
clients/adapters → 项目 HTTP 层、浏览器 API、支付 SDK
纯模型 ─────────→ 不依赖 React、网络、SDK 或浏览器全局
```

各能力不应互相读取内部状态。例如 coupon 不直接改 pricing，inventory 不直接禁止 submission。页面把规范化结果交给计算或提交工作流；真正需要原子一致性的提交顺序则集中留在 `useCheckoutSubmission`，不能拆成几个互相观察状态的 effect。

也不要把以上能力重新包进一个巨型 `useCheckout()`。页面可以协调它们，但不能复制它们的状态、清理和错误。

## 测试放置

测试与行为所有者相邻；若项目已有集中式测试目录，则镜像同样的能力结构，不另创第二套惯例。

- `pricing.test.ts`：金额精度、边界值、优惠叠加规则及输入不变性。只测公开计算契约。

## 何时停止继续拆分

满足以下条件就停止：

- 每项状态、规则、外部资源、错误和清理都有唯一且容易定位的所有者。
- `CheckoutPage` 主要表达结算流程和组合关系，没有重新实现子能力政策。
- 删除某个边界会导致生命周期混杂、测试困难或真实变更扩散；否则该边界没有存在价值。
- 私有 helper 只服务一个所有者并与其同步变化，就留在同一文件。
- JSX 片段没有独立交互、可访问性或领域含义，就不单独组件化。
- 单次包装函数没有隐藏 DTO、SDK、错误、缓存或竞态政策，就不叫 service。
- 不再出现通用 `utils.ts`、`types.ts`、`services.ts` 收留无法归属的代码。
- 新目录不是为了和别的目录“对称”。

用“替换支付供应商”检查该方案：正常情况下只修改 `paymentSdkAdapter`，必要时调整 `PaymentSection`，而表单、价格、库存和提交状态机继续依赖稳定的 `confirmPayment` 契约。这说明该边界今天已经隐藏了真实波动；不需要提前建设多供应商注册表或通用插件系统。

| 无动画 | 作为降级路径 | 功能正确，但默认情况下相邻卡片瞬移，快速拖拽时难以理解位置变化 |
| CSS transition | 不足以独立实现 | CSS 无法自动插值 DOM 重排产生的布局位置；手工设置位移后再 transition，本质上已经是 FLIP，且连续中断管理较弱 |
| View Transitions API | 不选 | 更适合离散的页面或 DOM 状态切换；频繁重排、持续滚动和连续中断不是它最合适的生命周期 |
| FLIP | **主方案** | 能通过稳定 ID 对应重排前后的几何位置，保持空间连续性，并只播放 `transform` |
| 动画库 | 暂不新增 | 单次 FLIP 加取消管理不值得新增依赖；若项目实际已有支持布局投影、滚动根节点和中断的库，应复用其既有能力 |

FLIP 是几何映射策略，WAAPI 是播放手段，两者不是两套叠加动画。

## 实现边界

建议将职责分成四部分：

1. **排序状态**

   - 稳定卡片 ID 和当前顺序是唯一业务真相。
   - 拖拽控制器只发出语义动作，例如 `move(cardId, beforeCardId)`，不传 DOM 坐标给业务状态。
   - 拖动过程中可更新临时顺序；放下后提交持久顺序。`Escape` 或 `pointercancel` 恢复拖拽开始时的顺序。
   - DOM 顺序必须与视觉、键盘和读屏顺序一致，不能只用 transform 制造“看似重排”。

2. **拖拽控制器**

   - 负责命中目标、指针/触摸/键盘输入及滚动容器自动滚动。
   - 只有目标索引真正变化时才触发重排；原始 `pointermove` 至多每帧处理一次，不能每个事件都读布局。
   - 拖动卡片使用独立 overlay 跟随指针，原位置保留占位；overlay 不参加兄弟卡片的 FLIP，避免两套逻辑同时写同一个 `transform`。

3. **布局动画控制器**

   - 维护 `cardId → HTMLElement` 注册表和 `cardId → Animation` 活跃句柄。
   - 只负责几何测量、动画和清理，不修改排序状态、命中规则或持久化结果。
   - 仅测量受影响区间内、重排前后都存在的卡片。新增、删除或虚拟列表中未挂载的卡片直接跳过。
   - 使用二维 `x/y` 位移，不做 scale，避免文字和图片失真；因此同一边界也可支持可变高度卡片或未来的网格布局。

一次重排的执行顺序为：

```text
目标索引变化
→ 读取受影响卡片当前可见位置
→ 取消旧动画并提交新的语义顺序
→ DOM 提交后、绘制前读取最终位置
→ 计算 first - last
→ 从 translate(deltaX, deltaY) 动画到 none
```

所有旧位置先批量读取，状态和样式再写入，最终位置再批量读取，避免逐卡片交错读写造成布局抖动。

### 快速连续拖拽

新重排到达时：

- 先读取卡片在旧动画中的**当前可见位置**；
- 在同一绘制周期内取消旧句柄；
- 以当前可见位置作为下一次 FLIP 的 First；
- 新动画替换旧动画，而不是进入队列。

这样快速来回拖动不会等待上一段动画结束，也不会从旧动画的逻辑终点突然跳回。动画完成、取消、卸载时均删除句柄和临时样式；最终 DOM 本身始终处于正确位置。

时长应使用项目 motion token；缺少现有 token 时可从约 `120–180ms` 的短 ease-out 开始，再根据真实设备调整。不要永久设置 `will-change`。

### 滚动容器

几何位置按滚动内容坐标计算，而非直接比较两次 viewport 坐标：

```text
contentX = itemRect.left - containerRect.left + scrollLeft
contentY = itemRect.top  - containerRect.top  + scrollTop
```

这能避免 First 与 Last 之间发生滚动时，把滚动距离误认为卡片重排距离。

其他约束：

- 命中检测每帧使用最新 `scrollTop/scrollLeft`。
- 自动滚动由拖拽控制器负责，先更新滚动位置，再进行该帧的命中和重排。
- 普通滚动不触发 FLIP；已有 transform 附着在内容元素上，随容器自然滚动。
- 容器 resize、方向变化或卡片异步改尺寸时，先取消当前动画并保持正确最终布局；除非实测需要，不建立持续的 ResizeObserver 重算系统。
- 初始实现不承诺支持缩放或旋转后的滚动祖先；若产品存在这种布局，应由统一坐标转换或现有拖拽库处理。

### Reduced motion 与可访问性

监听 `prefers-reduced-motion: reduce`：

- 顺序仍立即更新；
- 取消所有正在运行的重排和落点缓动；
- 不启动新的 FLIP；
- 拖动对象仍可一比一跟随指针，因为这是直接操控反馈，不应增加弹簧或惯性。

偏好在拖拽途中变化时也应立即生效。

拖拽之外还应提供“上移/下移”按钮等非拖拽操作，供鼠标、触摸和键盘使用。移动后焦点继续停留在同一张卡片，并在提交或键盘移动时宣布“已移动到第 X 项，共 N 项”；不要在每次指针经过时轰炸读屏通知。

## 验证方案

### 自动化契约

- 纯排序逻辑：首项、末项、向前/向后移动、重复目标和取消恢复。
- 连续重排：上一动画未结束时再次移动，最终 DOM 顺序和状态顺序一致。
- 删除或卸载：活动动画被取消，没有残留 transform 或句柄。
- Reduced motion：顺序即时完成，动画数量为零。
- 键盘/按钮重排：焦点保留在同一稳定 ID，状态通知正确。

测试用户可见顺序和交互结果，不绑定私有组件名或 FLIP 内部数据结构。

### 真实浏览器交互

在项目支持的浏览器中检查：

- 快速跨越多个位置并立即反向拖动；
- 动画过程中放下、按 Escape、触发 `pointercancel`；
- 滚动容器的顶部、中部、底部以及边缘自动滚动；
- 滚动与重排同时发生时，卡片没有额外跳跃；
- 不同高度、长文本、图片卡片以及窄/宽容器；
- 运行中切换 reduced-motion；
- 键盘、触摸和单指非拖拽替代操作。

### 性能证据

使用产品典型和最大可见卡片量，在代表性低端设备与发布构建中记录浏览器性能轨迹：

- 对比关闭动画和启用 FLIP 的同一拖拽路径；
- 确认原始 `pointermove` 没有引发连续同步布局；
- 每次有效重排只有成批的 First/Last 测量，没有逐元素读写交错；
- 动画主要落在合成阶段，没有大面积重绘或长期保留大量图层；
- 检查输入到显示延迟、掉帧、长任务和动画结束后的内存/句柄；
- 以目标设备刷新率和实际 hitch 证据确定门槛，不把固定 `16ms` 当成所有设备的通用结论。

本地 Skill 的“选择最轻机制、显式处理中断、滚动和 reduced motion，并以真实运行时验证”的要求，直接决定了这里采用有明确降级路径的 FLIP，而不是 CSS 快捷方案或更重的动画依赖。

## 1. 兼容边界

页面只依赖一个稳定的数据层契约，不直接判断新旧接口：

```ts
type ConfirmationOutcome =
  | { kind: 'confirmed'; bookingId: string }
  | { kind: 'rejected'; code: DomainErrorCode; retryable: boolean }
  | { kind: 'pending' };

interface BookingConfirmationService {
  confirm(input: SubmittedBooking): Promise<ConfirmationOutcome>;
  getOutcome(bookingIntentId: string): Promise<ConfirmationOutcome>;
}
```

内部实现：

```text
确认页
  → BookingConfirmationService
      → attempt 路由选择器
          ├─ LegacyBookingAdapter
          └─ NewBookingAdapter
```

具体约束：

- 页面、表单和埋点只认识统一的领域结果，不接触新旧 DTO。
- 两个适配器分别做运行时响应校验、字段规范化和错误码映射。缺失字段不能用空值伪造成成功。
- 明确维护“字段语义、金额与币种、库存/报价版本、时区、身份标识、错误码、超时语义”的兼容矩阵。
- 新接口不支持的请求类型保持走旧接口；首批灰度只覆盖已经证明语义一致的契约交集。
- `401/403`、业务拒绝、确定未创建、结果未知必须是不同结果。客户端不能把权限错误或网络错误翻译成普通库存失败。
- 路由在创建 `bookingIntent` 时确定并持久化；一次预订过程中，即使远程开关改变，也不能换接口。

未来增加第三个提供方时，只需新增适配器和路由规则，不应修改页面状态模型。

## 2. 幂等与重复提交

### 不可绕过的服务端前置条件

每个确认请求必须携带：

- 服务端签发的、不含个人信息的 `bookingIntentId`；
- 随机 `Idempotency-Key`；
- 规范化提交快照的摘要；
- 被选中的接口版本或路由标识。

服务端必须保证：

1. 幂等记录与预订创建在同一个原子边界内。
2. 同一个 key、相同载荷只产生一个预订，并返回该预订的当前结果。
3. 同一个 key、不同载荷返回明确冲突，不能创建第二单。
4. 同一个 `bookingIntentId` 同时只能有一个有效确认过程，防止不同标签页生成不同 key 后重复下单。
5. 新旧接口共享幂等存储或共同经过一个幂等网关。若各自独立，迁移不得上线。
6. 幂等记录至少保留“最长支付/供应商不确定窗口 + 用户恢复窗口”；初始建议不少于 72 小时。

### 前端防护

- 点击时在第一次异步操作之前同步锁定提交命令，并禁用按钮、展示明确的处理中状态。
- 提交使用不可变的表单快照；用户后续编辑不能改变正在执行的请求。
- 通用请求库的自动 mutation 重试应关闭，或限定为同一接口、同一快照、同一 key。
- 刷新后只恢复不含 PII 的 `bookingIntentId`、key、路由和状态，并向服务端查询权威结果。
- `BroadcastChannel` 可用于多标签页提示和禁用，但只作为体验优化，不能承担正确性。
- 用户修改影响预订语义的字段时，不得复用旧 key；旧请求必须先得到确定结果。

## 3. 状态与错误恢复

建议显式建模以下状态：

```text
editing
  → submitting
      → confirmed
      → rejected-definitive
      → outcome-unknown
          → reconciling
              → confirmed
              → rejected-definitive
              → support-required
```

| 情况 | 行为 |
|---|---|
| 本地校验或明确业务拒绝，且服务端保证未创建 | 回到编辑态，可修正后创建新 attempt |
| 超时、断网、连接中断、提交后的 5xx | 进入“结果未知”，不能提示用户重新预订 |
| 结果未知 | 使用原 `bookingIntentId` 查询，或用原 key 向原接口重试 |
| 普通 `404` | 不能直接视为未创建；需服务端返回带处理栅栏的“确定未创建” |
| key 与载荷冲突 | 停止自动操作，提示检查当前预订，不生成第二单 |
| 页面刷新或返回 | 恢复 attempt 并先对账，再允许新提交 |
| 用户要求取消 | 只有服务端确认取消后才能解除未知状态 |

未知状态的页面文案应明确：“正在确认预订结果，请勿再次提交。”同时提供“查询状态”“查看我的预订”和人工支持入口。旧请求的成功、失败或 `finally` 不得覆盖较新的页面状态。

## 4. 两周灰度安排

远程开关以 `bookingIntentId` 稳定分桶。开关服务异常时，在并存期内，新 intent 默认走旧接口；已开始的 intent 始终保持原路由。

| 时间 | 新接口流量 | 要求 |
|---|---:|---|
| D0–D1 | 0% | 双适配器上线但关闭；建立旧接口基线和仪表盘 |
| D2 | 内部名单 | 验证生产配置、对账、kill switch 和告警链路 |
| D3 | 1% | 仅契约交集内的低风险请求 |
| D4–D5 | 5% | 覆盖主要浏览器、网络和业务时段 |
| D6–D7 | 20% | 开始纳入下一批已验证请求类型 |
| D8–D9 | 50% | 检查支持工单、支付/供应商延迟信号 |
| D10–D11 | 95% | 保留 5% 旧接口同分层对照组 |
| D12–D14 | 100% | 至少 48 小时全量浸泡，旧接口仍可回滚 |

每档至少运行一个完整业务日，并达到 1,000 次有效提交；关键细分至少 100 次。任一条件不足就保持当前档位，不按日期强行升级。

确认 mutation 禁止影子写入。只允许镜像无副作用的读取、校验或服务端明确支持的 dry-run。

如果 D14 未满足退出条件，应延长旧接口存活期。按日历强制关闭旧接口，会直接消除可靠回滚能力。

## 5. 生产信号与回滚条件

所有指标同时按接口版本、前端构建、灰度档位、请求类型和主要客户端分层；业务结果以服务端事实为准，不能只统计前端成功页。

核心信号：

- 每个 `bookingIntentId` 对应的实际预订数；
- 幂等命中、载荷冲突、重复创建数；
- 确认成功率、明确拒绝率；
- `outcome-unknown` 比例、最终未收敛比例和收敛耗时；
- 响应解码/契约错误率；
- 确认延迟 p50/p95/p99；
- 刷新恢复、重复点击、多标签页冲突数量；
- 客服重复预订、撤销和退款信号；
- 灰度曝光但未走预期适配器的路由偏差。

默认停止条件：

- 同一幂等 key 或同一 `bookingIntentId` 产生两个预订：立即停止新流量并按严重事故处理。
- 出现越权、跨用户结果或 PII 泄漏：立即停止。
- 新接口契约解码失败率超过 0.1%：停止扩量。
- 结果未知比例连续 15 分钟超过 0.5%，且达到旧接口对照组的 2 倍：回退新 intent。
- 成功率连续 30 分钟比同分层旧接口低 1 个百分点：回退。
- p95 同时超过旧接口 2 倍且超过 5 秒，持续 30 分钟：停止扩量或回退。
- 任何关键监控缺数、分桶失效或 kill switch 未经验证：不得继续扩量。

回滚只影响尚未提交的新 intent。已经通过新接口发出的请求继续在新接口查询和对账，不能因回滚切到旧接口重新提交。

## 6. 隐私控制

- 事件采用字段白名单：接口版本、状态码、稳定错误码、耗时、构建号和经过 HMAC 处理的关联标识。
- 禁止记录姓名、邮箱、电话、支付信息、完整预订内容、请求/响应体、自由文本和访问令牌。
- `bookingIntentId` 与幂等 key 必须随机且不可编码用户信息，不放进 URL。
- 浏览器仅保存恢复所需的最小不透明标识；终态后 24 小时清理，登出和切换账号立即清理。
- 运维遥测与可选产品分析分离；确认页上的第三方脚本默认不得获取 DOM、用户对象或请求载荷。
- 原始关联日志按现有隐私政策保留；如果项目尚无规则，建议原始日志最多 14 天、聚合指标 90 天，并实施访问控制和审计。
- 错误展示使用稳定错误码，不透传服务端堆栈或供应商原始消息。

## 7. 实施与验收拆分

建议按可独立回滚的顺序交付：

1. 先上线统一契约、旧适配器和生产基线，不改变流量。
2. 接入服务端幂等、状态查询和重复预订告警。
3. 加入新适配器及契约测试，开关保持关闭。
4. 完成结果未知恢复 UI、刷新恢复和粘性路由。
5. 验证 kill switch 后开始灰度。
6. 全量稳定且所有未知 attempt 已收敛后，再删除旧适配器和兼容字段。

必须覆盖的测试包括：双击、键盘连续提交、超时但服务端成功、刷新、返回导航、旧响应晚到、多标签页、同 key 不同载荷、开关中途变化、状态查询失败，以及 kill switch 后仍能收敛既有新接口请求。

## 当前能确定的事

- 每 100ms 重建 800 个行对象、样式和回调，会破坏引用稳定性，使行级 `memo` 等优化难以生效；但仅凭描述还不能断定它就是掉帧主因。
- 高分辨率图片是内存、解码和 GPU 上传压力的重要候选，但“内存增长”可能是正常缓存预热，也可能是监听器、计时器、原生图片资源等泄漏。
- 模拟器和 debug 构建不能证明真机性能。React Native 官方也要求用 release 构建判断最终性能，并建议用 Android 原生工具取得准确数据。[React Native Performance](https://reactnative.dev/docs/performance.html)、[Debugging Basics](https://reactnative.dev/docs/debugging.html)
- 800 项本身不证明虚拟化失效；必须检查实际列表组件、嵌套结构、窗口配置和已挂载行数。

## 最小执行方案

### 1. 先固定真实运行条件

从实际项目记录：

- `package.json` 和 lockfile 中解析到的 React、React Native、列表及图片组件版本。
- 当前 Android flavor 的 New Architecture、JS engine 和 release/profile 配置；不能只看模板默认值，要确认安装到设备的实际产物。
- 当前列表类型，以及是否被同方向 `ScrollView` 包裹。
- 行 key、`data`、`extraData`、`renderItem`、窗口化参数、图片 URL/尺寸和音频进度订阅位置。

测试场景固定为：相同 800 条数据、相同图片缓存初始状态、音频播放并每 100ms 更新、同一段快速往返滚动。使用目标档位 Android 真机，分别保存：

- 可分析 React 工作的 profiling 构建；
- 关闭开发开销的 release 构建，用于最终帧表现；
- Perfetto/System Trace 的 FrameTimeline、UI/RenderThread、GC 和图片解码信息；
- Android Studio Memory Profiler：首次进入、滚动多轮、退出页面、等待回收后的 Java/native/graphics 内存。

至少重复 3–5 次，记录中位数和波动，不用一次截图下结论。

### 2. 用三个诊断开关定位责任边界

这些只用于诊断，不直接作为产品修复：

| 对照实验 | 如果现象明显改善 | 优先处理 |
| --- | --- | --- |
| 暂停 100ms 进度更新，图片不变 | JS 工作和掉帧下降 | 状态所有权与行失效范围 |
| 进度照常更新，暂用固定小图/占位图 | 内存或 UI/RenderThread 压力下降 | 图片尺寸、解码和缓存 |
| 两者不变，记录已挂载行数和原生视图数量 | 数量持续增加或接近 800 | 修复现有列表的窗口化/嵌套问题 |

同时检查退出页面后音频订阅、timer 和图片请求是否解除。内存若经过几轮滚动后稳定在平台预算内，不应仅因没有立即下降就判为泄漏。

### 3. 第一笔生产修改：隔离高频音频状态

若 React trace 显示每个 tick 都使大量行重新渲染，最小修复是：

- 父页面不再持有供整张信息流消费的 `progress`。
- 进度只由真正显示它的组件订阅：若只在播放器栏显示，就放在播放器栏；若活动行显示，则只有活动行订阅。
- 父级最多保存低频的 `activeAudioId`、播放/暂停状态，不把每 100ms 的数值写回 800 项数据。
- feed 数据只在服务端数据或用户操作真正改变时更新；更新单项时保留其他行对象的引用。
- 静态样式移到模块级 `StyleSheet.create`。动态进度样式限制在进度组件内部。
- 向行传稳定、语义最小的 props；父级传统一的 `onPress(id)`，避免每个 tick 创建 800 个闭包。
- 只有确认重复渲染成本显著后才给行组件加 `React.memo`；比较函数必须覆盖所有影响 UI/交互的 props，不能用漏字段的比较掩盖更新。

目标不是“零对象分配”，而是让每次进度 tick 只失效真实消费者。这个不变量可以用组件测试保护，但性能收益仍需运行时验证。

### 4. 第二笔修改：按证据控制图片成本

如果图片对照实验有效：

- 优先请求接近显示尺寸 × 设备像素密度的服务端缩略图，不把原始高分辨率资源交给列表行。
- 保持图片 cache key/URI 稳定，避免随渲染添加变化的查询参数。
- 复用项目现有图片组件和缓存策略，不直接更换图片库。
- 只有确认当前 RN 版本支持且原图远大于视图时，才评估 Android 图片下采样选项；当前 `Image` 文档说明 `resizeMethod="resize"` 适合远大于视图的图片，但具体行为必须对照项目版本验证。[React Native Image](https://reactnative.dev/docs/Image)
- 不进行全量预取；它可能把网络问题转成更严重的解码内存峰值。

### 5. 只在证据指向列表窗口时调整现有列表

如果现有组件是 `FlatList`/`VirtualizedList`：

- 保证 `keyExtractor` 使用稳定业务 ID。
- 不把音频进度放进 `data` 或 `extraData`。
- 固定高度时才提供准确的 `getItemLayout`，并计入分隔线；可变高度不得伪造。
- 根据真机结果小步调节 `windowSize`、批量大小和批次周期，同时观察空白区域和点击响应。
- 不把 `removeClippedSubviews` 当成内存修复：官方文档明确它主要是把离屏视图从原生层级分离，并不会显著释放这些视图占用的内存，且可能带来显示问题。[Optimizing FlatList Configuration](https://reactnative.dev/docs/optimizing-flatlist-configuration)

如果当前不是这套列表，先按其现有维护契约检查窗口化，不能据此擅自迁移列表库。

## 必须在真实 RN 运行时和 Android 真机确认的结论

以下任何一项都不能由代码审阅、模拟器或 render counter 单独证明：

- 当前构建实际使用的新旧架构、renderer 和线程边界。
- 100ms 更新是否真的阻塞 JS/React 提交并造成掉帧。
- 掉帧来自 JS、UI/Layout、RenderThread、图片解码、GC，还是多者叠加。
- 行 memo 化和稳定引用是否改善用户可见帧表现。
- 列表窗口化是否正常，以及调参是否引入空白行、错误测量或滚动恢复问题。
- 内存增长是缓存平台、图片解码峰值还是可达对象/原生资源泄漏。
- 页面退出后 timer、订阅、图片资源是否释放。
- 缩略图策略对画质、流量、缓存命中和峰值内存的实际影响。
- 修改前后的慢帧/卡顿帧、输入响应和内存平台是否达到产品目标。Android 官方建议通过 FrameTimeline/系统跟踪定位卡顿，并用内存工具关联分配与 GC。[Android slow rendering](https://developer.android.com/topic/performance/vitals/render)

最终验收应是：同一真机、同一 release 产物和同一滚动脚本下，高频进度只更新其真实消费者，内存在缓存预热后形成稳定平台，慢帧显著下降，同时没有空白行、图片闪烁或播放状态错误。当前因缺少项目源码与真机产物，这些结论均尚未验证，也没有修改任何文件。
