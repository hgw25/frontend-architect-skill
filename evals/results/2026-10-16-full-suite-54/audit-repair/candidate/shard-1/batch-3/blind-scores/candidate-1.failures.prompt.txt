artifact: function groupBy(items, generateKey) {
  if (typeof generateKey === 'string') {
    const propertyName = generateKey

  }

  const result = {}
  let index = 0

  for (const item of items) {

RESPONSE:
结论：这版实现不应进入前端基础库。即使修复循环，也应先确认目标环境能否直接使用 `Object.groupBy()` / `Map.groupBy()`；当前工作区没有业务代码、调用方、`package.json` 或兼容性配置，无法证明存在自研公共封装的实际缺口。

## 主要问题

1. **原型键会直接导致运行时崩溃**

   `result = {}` 配合 `if (result[key])` 会读到继承属性。键为 `constructor`、`toString`、`__proto__` 等时，代码会尝试对函数或原型对象调用 `.push()`，抛出 `TypeError`。

   我用提供的实现实际验证了这三个键，均会抛错。这是正确性缺陷；若键来自外部数据，还可能成为稳定的拒绝服务入口。

2. **键语义不明确，可能静默分错组**

   普通对象会把键转换为属性键：

   - `1` 和 `"1"` 被合并。
   - 两个不同对象通常都变成 `"[object Object]"`，身份丢失。
   - `null`、`undefined` 等也会转换成字符串。
   - 整数形式的键按对象属性规则重新排序，例如输入顺序 `"10"`、`"2"`，枚举结果是 `"2"`、`"10"`。
   - Symbol 虽然可以成为键，但不会出现在 `Object.keys()` 和 JSON 序列化中。

   因此它不能笼统宣称支持任意 `generateKey` 返回值。需要先决定是“属性键分组”还是“按值身份分组”。

3. **字符串重载收益小，公共契约成本高**

   `groupBy(items, "status")` 看起来方便，但带来一组问题：

   - 参数在函数内部从字符串改写成函数，职责和类型不稳定。
   - 只特殊处理字符串属性名，不支持 Symbol 属性名。
   - JavaScript 中属性拼错会把所有项目静默归入 `undefined` 组。
   - TypeScript 需要同时表达 `keyof T`、属性值能否作为对象键以及返回值的部分存在性。
   - 若属性值是对象，当前实现仍会错误地按字符串合并。

   除非真实调用方充分证明该缩写有明显价值，否则保留单一回调 API 更合适。确有需求时，可另设语义明确的 `groupByProperty`，不要塞进同一个参数重载。

4. **Iterable 输入与回调签名不协调**

   实现通过 `for...of` 接受任意 `Iterable`，但又把 `items` 作为第三个参数传给回调。这对数组尚可理解，对 Generator、Set 等并不是可索引集合，回调甚至可能提前消费同一个迭代器。

   建议采用 `(item, index)`，与现代原生 groupBy API 对齐，不暴露来源容器。

5. **非法选择器的行为取决于数据是否为空**

   `groupBy([], null)` 会返回空对象；`groupBy([1], null)` 才抛错。公共 JavaScript API 不应因输入是否为空而改变参数是否合法。若这是公开 JS 边界，应在入口验证；若仅供严格 TypeScript 内部使用，可以依赖类型，但要明确支持范围。

## 推荐方案

根据调用方真正需要的键语义选择：

```ts
// 键是字符串或 Symbol，消费者需要对象访问
const groups = Object.groupBy(items, (item, index) => item.status)

// 键可能是对象，或者要求保持键身份和首次出现顺序
const groups = Map.groupBy(items, (item, index) => item.owner)
```

`Object.groupBy()` 的结果使用无原型对象，避免继承属性冲突；`Map.groupBy()` 不会把对象键字符串化。

落地前应检查项目声明的浏览器、WebView、Node 和 TypeScript `lib` 基线。仅调整编译目标不会自动提供运行时 API；旧环境应沿用项目现有的 polyfill 策略，或提供与原生签名和语义一致的兼容层，而不是创造第三套 groupBy 契约。

如果确实必须维护自有实现，最低要求是：

- 分成明确的 object-key 与 identity-key API，或直接只返回 `Map`。
- 只接受一个回调，签名为 `(item, index)`。
- 对象版本使用无原型对象和自有属性安全策略。
- TypeScript 返回类型反映组可能不存在，例如 `Partial<Record<K, T[]>>`。
- 明确元素不克隆、组内保持输入顺序、结果可变、选择器异常原样传播、异步选择器不受支持。
- 覆盖原型键、Symbol、数字与字符串冲突、对象身份、整数键顺序、Generator、空输入和类型推断测试，并通过包的公共入口验证。

最终建议是：**拒绝当前封装进入基础库；优先直接使用原生 API。只有明确的兼容性缺口或多个调用方共享的特殊策略，才值得增加一个薄且语义兼容的基础设施层。** 本次为只读评审，未修改工作区文件。

参数在函数内部从字符串改写成函数，职责和类型不稳定。\n   - 只特殊处理字符串属性名，不支持 Symbol 属性名。\n   - JavaScript 中属性拼错会把所有项目静默归入 `undefined` 组。\n   - TypeScript 需要同时表达 `keyof T`、属性值能否作为对象键以及返回值的部分存在性。\n   - 若属性值是对象，当前实现仍会错误地按字符串合并。\n\n   除非真实调用方充分证明该缩写有明显价值，否则保留单一回调 API 更合适。确有需求时，可另设语义明确的 `groupByProperty`，不要塞进同一个参数重载。\n\n4. **Iterable 输入与回调签名不协调**\n\n   实现通过 `for...of` 接受任意 `Iterable`，但又把 `items` 作为第三个参数传给回调。这对数组尚可理解，对 Generator、Set 等并不是可索引集合，回调甚至可能提前消费同一个迭代器。\n\n   建议采用 `(item, index)`，与现代原生 groupBy API 对齐，不暴露来源容器。\n\n5. **非法选择器的行为取决于数据是否为空**\n\n   `groupBy([], null)` 会返回空对象；`groupBy([1], null)` 才抛错。公共 JavaScript API 不应因输入是否为空而改变参数是否合法。若这是公开 JS 边界，应在入口验证；若仅供严格 TypeScript 内部使用，可以依赖类型，但要明确支持范围。\n\n## 推荐方案\n\n根据调用方真正需要的键语义选择：\n\n```ts\n// 键是字符串或 Symbol，消费者需要对象访问\nconst groups = Object.groupBy(items, (item, index) => item.status)\n\n// 键可能是对象，或者要求保持键身份和首次出现顺序\nconst groups = Map.groupBy(items, (item, index) => item.owner)\n```\n\n`Object.groupBy()` 的结果使用无原型对象，避免继承属性冲突；`Map.groupBy()` 不会把对象键字符串化。\n\n落地前应检查项目声明的浏览器、WebView、Node 和 TypeScript `lib` 基线。仅调整编译目标不会自动提供运行时 API；旧环境应沿用项目现有的 polyfill 策略，或提供与原生签名和语义一致的兼容层，而不是创造第三套 groupBy 契约。\n\n如果确实必须维护自有实现，最低要求是：\n\n- 分成明确的 object-key 与 identity-key API，或直接只返回 `Map`。\n- 只接受一个回调，签名为 `(item, index)`。\n- 对象版本使用无原型对象和自有属性安全策略。\n- TypeScript 返回类型反映组可能不存在，例如 `Partial<Record<K, T[]>>`。\n- 明确元素不克隆、组内保持输入顺序、结果可变、选择器异常原样传播、异步选择器不受支持。\n- 覆盖原型键、Symbol、数字与字符串冲突、对象身份、整数键顺序、Generator、空输入和类型推断测试，并通过包的公共入口验证。\n\n最终建议是：**拒绝当前封装进入基础库；优先直接使用原生 API。只有明确的兼容性缺口或多个调用方共享的特殊策略，才值得增加一个薄且语义兼容的基础设施层。** 本次为只读评审，未修改工作区文件。"}]}
