## 状态所有权

核心状态建议是普通数据：

```ts
type EditorState = {
  document: DocumentSnapshot
  selection: ModelSelection | null
  history: {
    undo: HistoryEntry[]
    redo: HistoryEntry[]
  }
  revision: number
  composition: 'idle' | 'composing'
}
```

所有权规则：

- `EditorSession` 私有持有唯一 `EditorState`，每次只通过 reducer 替换。
- UI/store 只订阅只读 snapshot，不保存第二份可写副本。
- selection 使用节点 ID、模型 offset 和方向表示，不能保存 `Range`、`Node` 等 DOM 对象。
- 文档变化和 selection 重映射必须属于同一次事务，避免 selection 指向已删除节点。
- history 保存本地事务及其 inverse、分组信息和基准版本，不建议保存整份 DOM 或全量文档副本。
- 协作引擎若内部持有 CRDT 文档，它是规范副本；Reducer 中的 `DocumentSnapshot`只是对应 revision 的不可变投影，不能成为另一份独立可写真相。

Reducer 可以接收这些事件：

```ts
type EditorAction =
  | { type: 'localTransaction'; transaction: Transaction; groupId?: string }
  | { type: 'remoteTransaction'; transaction: Transaction; serverVersion: number }
  | { type: 'selectionObserved'; selection: ModelSelection; revision: number }
  | { type: 'undo' }
  | { type: 'redo' }
  | { type: 'compositionStarted' }
  | { type: 'compositionEnded'; transaction: Transaction }
```

Reducer 不直接发送网络消息。纯 transition 可以返回 `{ state, effects }`，由 `EditorSession` 执行诸如 `sendOperation`、`renderSelection` 的 effect。

history 只记录本地可撤销意图；远端事务不进入本地 undo 栈，但必须通过协作引擎重映射已有 inverse 和 selection。合并连续输入所需的时间或 `groupId` 应由事件传入，Reducer 内不要读取 `Date.now()`。

## DOM 边界

`bindEditorDom(root, dispatch)` 适合闭包：

```ts
const dispose = bindEditorDom(root, dispatch)
```

它负责：

- 注册 `beforeinput`、`selectionchange`、`compositionstart/end` 等监听；
- 将 DOM selection 立即转换为模型 selection；
- 用绑定时的 `root` 和渲染 revision 过滤无关或过期事件；
- 返回幂等 disposer，只释放这一次绑定。

DOM selection 是模型 selection 的镜像，不是权威状态。渲染后再由模型 selection 恢复 DOM selection。受控渲染产生的 DOM 变化不能被误判为用户输入。

## 协作状态机与竞态

连接状态建议显式表达：

```text
idle → connecting → syncing → online
          ↓            ↓        ↓
       backoff ← reconnecting ← disconnected
          └────────────────────→ fatal
任意活动状态 ──────────────────→ closed
```

`CollaborationController` 拥有 socket/SDK、重连计时器、AbortController、待发送队列和 `connectionGeneration`。状态机只决定转换；类执行连接、关闭和计时器等副作用。

必须确定这些策略：

- 每个本地操作携带稳定 `opId`、`clientSeq` 和基准版本；编辑写入是有序队列，不能使用 latest-wins。
- 超时代表结果未知。只有协议支持幂等 `opId` 时才能重发，否则先与服务端版本对账。
- 重连后的旧 socket 回调携带旧 generation，不能发布状态、错误或清除新连接的 loading 状态。
- 服务端版本或 CRDT/OT 算法处理乱序和冲突；不要仅凭客户端到达顺序覆盖文档。
- IME composition 期间暂缓会破坏组合文本的 DOM 发布；远端事务由协作引擎保留并在 composition 结束时重映射/合并。
- `selectionObserved` 带观察时的 revision。若 DOM 事件对应旧渲染，丢弃并在当前文档上重新读取，而不是写入过期 offset。

协作算法本身应复用成熟 CRDT/OT 方案；自研模块只负责适配协议、事务和生命周期。

## 序列化边界

只持久化稳定领域数据：

```ts
type SerializedDocument = {
  schemaVersion: number
  content: SerializedNode
}
```

具体规则：

- 文档使用版本化 JSON 和明确迁移，不以 `innerHTML` 作为规范格式。
- HTML 导入属于不可信边界，需解析、白名单化并转换成内部节点。
- `toPlainText(document, options)` 是纯函数；列表标记、换行、表格和不可见节点的降级规则必须由 `options` 或模块契约明确。
- selection 通常是瞬态状态。若需要草稿恢复，只保存模型位置、方向和文档 revision，并提供节点失效后的就近回退。
- history 默认不持久化；跨版本、协作重放和 schema 迁移很容易使 inverse 失效。
- socket、DOM 节点、监听器、AbortController、计时器和连接状态都不可序列化。
- 离线待发送操作若是产品要求，应作为独立、版本化 outbox 持久化，并由协作协议负责去重，不能混入普通编辑 snapshot。

## 生命周期与销毁

`EditorSession` 的公共面保持较窄：

```ts
interface EditorSession {
  getSnapshot(): Readonly<EditorState>
  dispatch(command: EditorCommand): void
  subscribe(listener: () => void): () => void
  attachDom(root: HTMLElement): () => void
  destroy(): void
}
```

`destroy()` 应幂等，并按以下顺序处理：

1. 标记 session disposed 并递增 generation，立即阻止旧回调发布。
2. 移除 DOM 监听、observer 和框架订阅。
3. 取消重连计时器、请求及尚未发布的异步任务。
4. 释放协作连接租约。
5. 清空外部 listener 引用。

若连接由多个编辑器共享，销毁只能 `release/unsubscribe` 当前租约，不能直接关闭共享连接。

同步 `destroy()` 不应暗示“网络内容已经保存”。如产品要求离开前尽力提交，应另设 `await session.close({ flush: true })`，明确超时和未知结果；框架 unmount 仍调用快速、幂等的 `destroy()`。

至少应验证以下真实顺序：旧连接在新连接成功后报错、远端删除当前 selection、远端编辑发生在本地 undo 前、IME 期间收到远端事务，以及 destroy 后旧 ack/计时器回调到达。

`lib/shopify/server.ts` 应使用 `import 'server-only'`，私有 token 使用非 `NEXT_PUBLIC_` 环境变量。Shopify 明确要求私有 Storefront token 仅用于服务端，并通过 `Shopify-Storefront-Private-Token` 请求头发送。[Shopify Storefront API](https://shopify.dev/docs/api/storefront/latest)

## 渐进式迁移

### 1. 先建立服务端数据边界

不立即重写 JSX，先把现有商品和推荐请求移入 server-only Shopify gateway：

- 固定受支持的 Shopify API 版本。
- 统一处理 HTTP 错误、GraphQL `errors` 和响应结构校验。
- 将 Shopify edges、SDK 实例和原始响应转换为页面 DTO。
- 若请求来自买家流量且部署环境能可靠取得原始 IP，由服务端设置 Shopify buyer-IP 请求头；不能信任浏览器自行提交的该请求头。
- 保留旧客户端页面作为临时消费者时，只允许它调用现有受控服务端接口，不能直接获得私有 token。

建议 DTO：

```ts
type MoneyDTO = {
  amount: string
  currencyCode: string
}

type VariantDTO = {
  id: string
  availableForSale: boolean
  selectedOptions: Array<{ name: string; value: string }>
  price: MoneyDTO
}

type ProductPageDTO = {
  id: string
  handle: string
  title: string
  description: string
  featuredImage: { url: string; alt: string | null } | null
  options: Array<{ name: string; values: string[] }>
  variants: VariantDTO[]
}
```

不要跨边界传 Shopify client、`Response`、`Headers`、`Error`、函数、秘密、未筛选的原始记录或依赖特殊原型的对象。金额保留 Shopify 返回的十进制字符串和 `currencyCode`，不要先转成 JS 浮点数。

### 2. 将商品路由改回 Server Component

`page.tsx` 完成：

1. 解析并规范化 `handle`、国家/市场和语言。
2. 服务端取得商品。
3. 不存在时调用 `notFound()`。
4. 输出标题、描述、图片、价格、可用性等首屏内容。
5. 仅把规格交互所需 DTO 传给 `ProductPurchasePanel.client.tsx`。

`generateMetadata` 与页面复用同一个商品 loader，产生 title、description、canonical、Open Graph。它只能定义在 Server Component 中。[Next.js generateMetadata](https://nextjs.org/docs/app/api-reference/functions/generate-metadata)

如需 Product JSON-LD，只从白名单 DTO 构造；不要直接注入 Shopify HTML。序列化到 `<script>` 时至少转义 `<`，商品正文优先使用纯文本字段；确需 `descriptionHtml` 时在明确的服务端边界使用成熟 allowlist sanitizer。

### 3. 收缩客户端交互岛

`ProductPurchasePanel.client.tsx` 只保存最小交互状态：

- 用户选中的 option 值；
- 加购物车 action 的 pending/result 状态。

当前 variant、价格、库存和按钮可用性都由 `variants + selection` 派生，不再通过 `useEffect` 复制或重新请求商品。

加入购物车提交 `merchandiseId` 和 quantity。服务端必须重新验证：

- variant ID 属于当前商品；
- quantity 范围合法；
- 当前会话/购物车允许修改；
- 价格、折扣和库存以 Shopify 响应为准，绝不接受客户端价格。

提交期间阻止同一按钮的重复触发；成功后用 mutation 返回的权威 cart 数据更新数量。超时属于“结果未知”，不要盲目重复非幂等 mutation，应先重新读取购物车或向用户明确提示确认。

### 4. 独立流式加载推荐商品

商品主体不应等待推荐：

```tsx
<ProductDetails product={product} />

<Suspense fallback={<RecommendationsSkeleton />}>
  <Recommendations promise={recommendationsPromise} />
</Suspense>
```

商品与推荐都可按 handle 查询，因此可以在页面开始时并行启动；页面只先等待商品，推荐在自己的边界中继续等待。

`Suspense` 只处理 pending，不处理失败。建议：

- 推荐请求的可恢复上游错误在 `Recommendations` 内记录脱敏诊断，然后渲染“暂时无法加载推荐”和重试控件。
- 核心商品的暂时性失败交给该路由的 `error.tsx`，`reset()` 重试。
- 商品确实不存在走 `not-found.tsx`，不能伪装成网络错误。
- 推荐失败不能拖垮商品主体。

## 货币与缓存

Shopify 国际价格以国家/Market 上下文查询，不应在浏览器把基础价格自行换汇。对商品和推荐查询统一使用 `@inContext(country: ...)`；Shopify 会返回该国家上下文中的价格和可售商品。[Shopify contextual queries](https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/in-context)

国家来源按项目已有契约选择：

1. 已有国家/市场 URL 段时优先使用它，SEO 和缓存身份最清楚。
2. 否则读取服务端设置的偏好 cookie。
3. 再考虑可信部署平台提供的地理信息。
4. 最后回退到店铺主市场。

不要在 hydration 后根据 `navigator.language` 突然改价。货币选择器应通过 Server Action 更新国家偏好并 `refresh` 或跳转到市场 URL。购物车的 buyer identity country 必须与展示价格上下文一致。

缓存表：

| 数据 | 作用域与 key | 失效 |
|---|---|---|
| 公共商品详情 | `handle + country + language` | TTL，加 Shopify 商品/库存 webhook 精确失效 |
| 推荐商品 | `productId/handle + country + language + intent` | 独立 TTL；商品或推荐配置变化时失效 |
| SEO 商品数据 | 复用商品 loader | 与商品详情同一标签 |
| 普通买家购物车 | session/request，禁止公共共享缓存 | 每次 mutation 以后采用返回值或重新读取 |
| B2B/登录买家上下文价格 | 用户/公司作用域，通常不进公共缓存 | 身份或公司上下文改变即失效 |

私有 token 的存在不代表公开商品响应不能共享缓存；决定因素是响应是否依赖用户身份。反过来，B2B 价格即使形状相同也不能放入公共 key。

具体缓存 API必须在确认项目 Next.js 版本后选择：

- 已启用当前 Cache Components：使用 `'use cache'`、`cacheLife`、`cacheTag`。
- 旧缓存模型：使用 `fetch(..., { next: { revalidate, tags } })`。
- 不要在一次迁移中混用两套模型制造不清晰的所有权。

当前 Next.js 文档推荐目录内容用 `revalidateTag(tag, 'max')` 做 stale-while-revalidate；需要 read-your-own-writes 的 Server Action 才使用 `updateTag`。[Next.js revalidation](https://nextjs.org/docs/app/getting-started/revalidating) Shopify webhook 应先验证签名，再失效 `product:{id}` 和相关 recommendation tag。没有 webhook 时明确采用业务可接受的 TTL，而不是宣称实时。

### 最小实现方案

1. 行情业务状态不要完整镜像到页面 `data`。

   ```js
   {
     'rows[12].price': 10.23,
     'rows[12].changeRate': 0.018,
     'rows[87].volume': 138200
   }
   ```

   不再发送：

   ```js
   this.setData(this.data)
   // 或
   this.setData({ rows: rebuiltAllRows })
   ```

   - `onShow`：先从已有 store 获取当前版本快照，再恢复增量订阅。
   - 对已经进入队列的旧回调增加可见性或 generation 校验，避免取消订阅后仍执行一次 `setData`。

   如果行情连接被多个页面共享，只移除当前页面的订阅，不能关闭共享连接。如果业务确实要求隐藏期间持续计算，则让 store 继续接收和归并数据，但不要继续向隐藏页面传输；恢复时一次追平最新快照。

   “取快照”和“开始订阅”之间需要沿用现有 store 的原子订阅能力；若没有，应使用单调版本号避免在恢复窗口遗漏或倒退数据。

4. 不把虚拟列表作为首个改动。

   500 个已挂载节点也可能导致滚动卡顿，但题设尚未证明瓶颈在节点、布局或绘制。只有缩小传输后，真机轨迹仍显示列表布局、绘制或节点数量占主导，才采用各宿主正式支持的虚拟列表/窗口化能力，并单独验证可变行高、滚动位置、快速更新和兼容版本。

5. 为多宿主保留一个很薄的页面发布适配边界。

   适配层只负责：

   - 将业务 ID 映射到当前稳定行位置；
   - 生成该宿主支持的局部更新路径；
   - 执行一次页面更新；
   - 统计调用次数和估算载荷。

   不直接采用某一宿主的新渲染后端、worklet 或实验 API。是否能使用这些能力，必须先根据实际宿主和最低基础库版本建立兼容矩阵。

### 代码层能够验证的内容

| 可验证项 | 建议检查 |
|---|---|
| 更新范围 | 单元测试确认补丁只包含变化且被模板消费的字段 |
| 更新频率 | 每个输入批次至多一次页面 `setData`，没有额外降频 |
| 行身份 | 行更新命中正确业务 ID；排序变化后不会写入旧索引 |
| 生命周期 | `onHide` 后继续推送行情，断言页面 `setData` 调用数不再增加 |
| 恢复正确性 | 隐藏期间多次更新后 `onShow`，页面直接得到最新版本，而不是逐条补播 |
| 清理行为 | 多次 hide/unload 清理安全；旧订阅回调不能发布到新页面实例 |
| 共享资源 | 页面隐藏只解除自己的订阅，不误关其他消费者使用的连接 |
| 数据量趋势 | 在相同输入下记录调用数、字段数和序列化字节估算，比较整页与增量方案 |

序列化字节估算、调用次数和单元测试只能证明执行边界变小、生命周期正确，不能证明真机已经流畅。

### 必须由宿主工具和代表性真机证明的结论

不能仅凭代码、开发者工具或模拟器断言“卡顿已解决”。需要在每个受支持宿主上，用其性能工具和代表性真机比较修改前后：

- 实际跨逻辑层/视图层的消息数量、载荷大小、序列化时间和排队时间；
- 输入到可见反馈的延迟；
- 连续滚动时的掉帧、卡顿帧和帧时间分布；
- 逻辑线程、视图线程或主线程长任务；
- 布局、绘制、节点更新与垃圾回收占比；
- 页面隐藏后的 CPU、内存、网络及页面更新是否真正停止；
- 恢复页面时是否出现数据倒退、白屏、突发补播或明显卡顿。

测试矩阵至少应记录：宿主、基础库版本、渲染后端、操作系统、低/中档真机、屏幕刷新率、发布或性能构建模式、固定的 500 行数据和 10Hz 输入脚本。用同一滚动和输入场景多次比较基线与改后结果。

因此，目前可以合理判断整页高频传输和隐藏页持续发布是应先消除的明显浪费；但它们是否是部分真机输入延迟、滚动卡顿的主要根因，以及是否还需要宿主虚拟列表，只能由上述真机轨迹决定。
