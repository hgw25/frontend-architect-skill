结论：当前改版应判定为性能回归，停止继续放量；若已有开关或可独立回滚，先恢复上一稳定版本作为并行对照。把 LCP 与筛选 INP 当作两个独立问题处理，CLS 只保留回归守门。现有证据不足以支持重写列表或直接引入虚拟化。

仓库中除 `.frontend-architect` 与 Git 元数据外没有应用、构建或测试文件，因此本次无法把预算接入具体脚本；以下是可直接交给项目落地的执行契约。

## 最小调查与修复顺序

1. 先确认回归归因

   - 固定“移动端商品列表首路由”口径，按发布版本比较相同 URL、设备档位、网络、地区和导航类型。
   - 确认 RUM SDK、采样率、路由归属和指标定义在改版前后未变化。
   - 查看 LCP 元素及四段耗时：TTFB、资源加载延迟、资源加载时间、元素渲染延迟。
   - 查看 INP 的实际交互类型、目标元素及 input delay、processing、presentation delay。先确认 290ms 是否确实主要来自筛选。
   - CLS 仍为 0.04，不投入专项优化，只防止字体修复带来新位移。

2. 用同一个生产构建复现两条独立路径

   - 冷缓存首次进入列表：保存网络瀑布、主线程 trace、LCP 元素和构建产物清单。
   - 使用固定的代表性商品数据连续筛选：保存 Event Timing、主线程长任务、组件更新或 DOM/layout 证据。
   - 将首路由新增的 95KB gzip 拆到模块级，区分下载、解析执行、初始化和渲染成本。
   - 判断字体请求是否真的延迟 LCP；不要仅因“出现新请求”就认定根因。
   - 将 180ms 长任务拆解为筛选计算、状态广播、列表更新、布局或第三方代码。

3. 按已证明的瓶颈做最小修复

   - 若字体位于 LCP 关键链：复用已有字体或系统回退；只预加载真正用于首屏的字形；避免不可见文本等待字体。修复后检查文本换字和 CLS。
   - 若新增 JS 在首屏执行：把非首屏、非默认状态所需的筛选增强或重依赖移出首路由，在首次使用前按需加载。先删除重复依赖、无效导入和初始化副作用，不进行框架级改造。
   - 对 180ms 任务：先减少同步工作，例如把不随交互变化的派生数据移出处理器、缩小订阅范围、保持商品项身份稳定、只更新受影响项。仍超预算时再分片或让出主线程。
   - 只有 trace 证明瓶颈来自大量挂载节点、布局或绘制时，才评估分页、渐进渲染或虚拟化；这不是默认方案。

如果 LCP 退化实际来自 TTFB 或首图，而这些在版本间没有相应变化，则不要用字体或拆包“修复”一个未证明的原因。

## 可执行性能预算

所有相对预算均以最后一个稳定版本 `2.2s / 170ms / 0.04` 为基线。生成并保存该版本的构建清单和测试场景，避免基线漂移。

| 层级 | 指标 | 预算与失败条件 |
|---|---|---|
| 构建 CI | 商品列表首路由 eager JS | gzip 总量相对基线最多 `+10 KiB`；当前 `+95 KiB` 不通过 |
| 构建/瀑布 CI | 首屏字体 | LCP 关键链中新增的阻塞字体请求为 `0`；关键字体请求数量不得高于基线 |
| 稳定实验室 | LCP | 交错运行基线与候选各 20 次冷启动；候选 p75 `≤2.5s` 且不高于基线 `10%` |
| 稳定实验室 | 筛选交互 | 固定数据连续运行 30 次；最长任务时长的 p75 `≤50ms`，任何一次不得 `>100ms` |
| 稳定实验室 | 筛选到下一次绘制 | p75 `≤200ms` 且不高于基线 `10%` |
| 稳定实验室 | CLS | p75 `≤0.10`，并且相对基线增量 `≤0.01` |
| 移动端 RUM | LCP | p75 `≤2.5s`，且候选相对并行控制组的 p75 差值之 95% 置信上界 `≤100ms` |
| 移动端 RUM | INP | p75 `≤200ms`，且相对控制组差值之 95% 置信上界 `≤20ms` |
| 移动端 RUM | CLS | p75 `≤0.10`，且相对控制组差值之 95% 置信上界 `≤0.01` |

相对门槛防止“虽然仍属良好范围，但持续侵蚀余量”。如果无法保留并行控制组，使用同一 RUM 分群的最后稳定版本比较，但要明确其证据弱于同期实验。

每条预算落地时必须登记具体负责人：列表负责人处理运行时预算，构建负责人维护 bundle/瀑布检查，发布负责人执行 RUM 放量门槛。

## 回归验证

固定以下测试条件并随结果保存：

- 生产模式构建、具体提交、浏览器版本、代表性移动设备或固定性能档位、网络配置、缓存状态、视口和数据集。
- 数据集至少覆盖常见结果规模和生产中较大的代表性规模。
- 冷启动与筛选分别测量，不把一次 Lighthouse 总分当证据。Lighthouse 可用于发现审计项，但不作为发布门槛。
- 基线与候选交错运行，避免机器温度、网络或后台负载把先后顺序误判为改进。
- 重复原始 trace，确认字体关键链、95KB eager JS 或 180ms 任务确实消失，而不只是总指标偶然变好。
- 回归商品结果、空结果、快速重复筛选、首次按需加载、键盘焦点、滚动位置和字体切换；懒加载失败必须有可恢复行为。
- 保留构建 manifest、网络瀑布和原始 trace 的制品链接，并绑定被测提交。

## 发布门槛

建议沿用已有发布/开关能力，以 `5% → 25% → 100%` 放量：

1. 合并前：构建预算、字体关键链检查、固定筛选 trace 和功能回归全部通过。
2. 5% 阶段：至少观察一个完整业务高峰周期，不少于 24 小时；未达到样本量只能继续观察，不能视为通过。
3. 进入 100% 前：同一候选版本累计至少有 1,000 个合格移动端 LCP 页面样本和 500 个发生交互的 INP 样本，并满足所有绝对与相对 RUM 门槛。
4. 任一硬预算失败，停止放量并回滚候选；不能通过挑选最好的一次重跑豁免。
5. 全量后继续观察至少一个同等周期。错误率或商品列表核心功能若违反项目已有门槛，同样回滚，即使性能通过。

本地 Skill 的指导直接影响了这里的结构：首次显示和筛选交互被拆成两个性能契约，实验室证据负责定位，RUM 负责最终用户影响，确定性构建检查负责日常防回归。未修改任何仓库文件。
