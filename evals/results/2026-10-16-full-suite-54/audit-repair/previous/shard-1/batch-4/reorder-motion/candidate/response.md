结论：选择 **FLIP 作为重排机制，使用 Web Animations API 执行 Play 阶段**；暂不引入动画库。拖拽中的卡片直接跟随指针，FLIP 只负责其他卡片让位以及放下后的归位。

| 方案 | 判断 |
| --- | --- |
| 无动画 | 仅作为 `prefers-reduced-motion`、测量失效或不支持路径的降级 |
| 纯 CSS transition | 无法独立知道 DOM 重排前后的几何位置，也难以可靠处理中途重定向 |
| View Transitions API | 更适合低频快照式状态切换；高频拖拽、滚动坐标和连续中断不适合作为主机制 |
| FLIP | 最符合“同一卡片从旧槽位移动到新槽位”的空间连续性需求 |
| 动画库 | 只有项目已经依赖并能复用其布局动画，或虚拟列表、弹簧手势编排确实需要时才采用 |

纯 CSS 仍负责静态样式；FLIP 的动画执行建议用 WAAPI，因为 `Animation` 句柄便于取消和重定向。这仍属于 FLIP 层级，不需要为单一交互增加通用动画库。

## 实现边界

订单模型是唯一业务真相：

- 每张卡片必须有稳定 ID，并以该 ID 作为渲染 key。
- 拖拽期间使用局部 `draftOrder`；放下时只提交一次最终顺序。
- `Escape`、`pointercancel` 或拖拽失效时恢复进入拖拽前的顺序。
- 外部列表更新若与当前拖拽冲突，默认取消拖拽并采用最新权威数据，不能用旧草稿覆盖。
- 动画的矩形、transform 和句柄不得写回顺序状态。

职责分配：

- 拖拽控制器：命中测试、目标索引、指针捕获、键盘操作和自动滚动。
- 重排协调器：按 ID 测量几何、执行 FLIP、取消旧动画、清理资源。
- 列表状态：管理 `draftOrder` 和最终提交。
- 卡片组件：语义、视觉与焦点，不自行保存重排状态。
- 建议让外层列表项承载 FLIP transform，内层卡片承载 hover、选中等视觉 transform，避免样式互相覆盖。

每次跨越重排阈值时：

1. 在修改顺序前，批量读取当前已挂载卡片的视觉矩形。正在动画的元素以当前屏幕位置作为新的 First。
2. 取消旧动画，但不等待其结束。
3. 更新 `draftOrder`，保证最终 DOM 布局在下一次绘制前提交。
4. 批量读取 Last 矩形。
5. 对仍存在的同 ID 元素计算位移，仅动画 `translate` 到零；不缩放卡片内容。
6. 约 140–180ms ease-out，结束或取消时移除句柄与临时样式。

快速连续拖拽采用“**最新目标获胜**”：

- 指针事件可以高频到达，但每个动画帧最多应用一次最新目标索引。
- 新重排从卡片当前视觉位置重新测量并重定向，不排队、不等待上一轮动画。
- 新一轮拖拽若发生在放下动画期间，也先取消并从当前视觉位置接管。
- 被拖卡片直接跟随指针，不对其位置添加 transition，否则会产生滞后。

滚动容器需要单独处理：

- First 和 Last 使用同一坐标系。可用 `getBoundingClientRect()` 加对应容器的 `scrollTop/scrollLeft` 转换为内容坐标，再计算差值，避免把自动滚动误判成重排位移。
- 自动滚动由拖拽控制器逐帧驱动；单纯滚动不触发一次新的重排动画。
- 每轮严格先批量读、再写，不能逐卡片交替读取和写入。
- 只测量已挂载且参与布局的卡片。若之后引入虚拟列表，应把几何测量交给虚拟化层的布局接口，而不是让 FLIP 猜测未挂载元素。

`prefers-reduced-motion: reduce` 下：

- 不创建重排或放下动画，DOM 立即进入正确顺序。
- 指针直接跟随和必要的自动滚动仍保留，但不使用平滑滚动或惯性归位。
- 偏好在拖拽期间发生变化时，立即取消现有动画并清理 transform。
- 同时提供键盘移动及“上移/下移”之类的非拖拽操作；焦点跟随稳定 ID，最终移动结果通过 `aria-live` 通知，不在每次指针经过槽位时播报。

卸载、路由离开、`lostpointercapture`、`pointercancel` 和 `Escape` 都必须取消动画、自动滚动帧、媒体查询监听及其他观察器。

## 验证方案

优先使用项目既有的真实浏览器测试工具；DOM 模拟器不能证明布局、滚动和指针行为。

核心浏览器场景：

- 在一轮 140–180ms 动画结束前连续跨越多个槽位，再立即反向拖动；最终顺序必须等于最后目标，不出现排队、倒退或跳回。
- 放下动画尚未结束时立即开始下一轮拖拽，确认新交互即时接管。
- 在滚动容器顶部、中部和底部测试自动滚动与重排；卡片应保持在指针附近，滚动位移不能被 FLIP 抵消。
- 模拟 `prefers-reduced-motion: reduce`，确认顺序正确且没有重排、归位动画。
- 覆盖 `Escape`、`pointercancel`、卸载和外部数据更新，确认顺序策略与资源清理。
- 用键盘及非拖拽按钮完成同样的移动，检查焦点和播报。
- 动画结束后检查所有卡片都处于最终槽位、无残留 transform、无活跃重排动画句柄。

可抽成纯逻辑的部分只做少量单元测试：稳定 ID 映射、目标索引计算、包含滚动偏移的 FLIP delta。中断连续性仍须由真实浏览器验证。

性能验证应在产品支持的最大典型卡片数和代表性设备上录制一次快速拖拽性能轨迹，重点检查：

- 每帧最多应用一次重排；
- 不存在逐卡片的读写交错和反复强制布局；
- transform 动画不触发逐帧 layout/paint；
- 拖拽结束后动画与临时合成层被释放。

若项目尚无性能预算，可先采用“输入后两帧内出现反馈、无超过 50ms 的主线程长任务、重排工作稳定落在单帧预算内”作为初始门槛，再用基线数据调整。

当前工作区没有应用源码、依赖清单或测试配置，因此本次没有修改文件，也无法确认现有框架、拖拽库或浏览器支持矩阵。上述方案保留了对应接入点；真正落地时应优先复用项目已有拖拽库的测量和取消能力。
