## 状态与副作用所有权

| 能力 | 拥有的状态 | 拥有的副作用与策略 | 对外提供 |
|---|---|---|---|
| `useCheckoutDraft` | 可编辑字段、touched/dirty、同步验证、编辑 revision | 如已有草稿恢复机制，由这里负责读写和清理 | `draft`、字段错误、字段更新命令、`validate()`、稳定快照 |
| `pricing.ts` | 无 | 无 | `calculateQuote(input): CheckoutQuote`、相关纯 selector |
| `useCoupon` | 当前已应用优惠券，以及 `idle/checking/applied/rejected` 状态 | 请求、取消、旧响应抑制、移除和重新校验 | `coupon`、`status`、`apply(code)`、`remove()` |
| `useInventoryAvailability` | 最新库存快照及连接状态 | 按完整商品/规格身份订阅、换键、退订、忽略释放后的回调 | 可售状态、阻塞原因、必要时的重连命令 |
| `usePaymentSession` | SDK 会话的 `idle/initializing/ready/failed/disposed` 状态 | SDK 初始化、挂载、替换、卸载和回调失效 | SDK 无关的 `authorize/confirm` 命令与展示状态 |
| `useCheckoutSubmission` | `idle/submitting/succeeded/failed/unknown`，提交时输入快照 | 防重复提交、执行顺序、服务端调用、结果发布、结果不确定时的协调 | `submit(snapshot)`、`retry()`、提交状态和表单级错误 |
| `CheckoutPage` | 原则上不复制上述状态 | 组合能力、把输出传给 UI、生成提交快照 | 页面 JSX |

关键约束：

- `quote`、`canSubmit`、按钮文案等能够从现有状态推出的值不另存为 state。
- 优惠券输入文字可以属于草稿或 `CouponField` 的局部状态，但“已被服务端接受的优惠券”只属于 `useCoupon`，不能用同一个字符串表示。
- client 价格若只是预估，应明确标为展示值；最终金额以现有服务端契约为准。若服务器本来就返回权威 quote，则不要复制一套客户端业务算法，应改成 quote adapter 与纯展示 selector。
- 支付凭证和 SDK 私有对象不进入通用表单 state，也不向组件树广泛传播。
- 提交开始时捕获不可变快照。用户随后继续编辑草稿时，旧提交和重试仍对应原快照。
- 支付是有副作用写入，不能套用“最后一次请求胜出”。本地防双击只解决单页面重复触发；只有服务端明确支持幂等键或状态查询时，才能安全自动重试结果不明的支付。
- 优惠券检查适合 latest-wins：A 后发 B，B 成功后，A 的成功、失败或 `finally` 都不能覆盖 B。
- 错误在能恢复的位置呈现：字段错误归草稿、优惠券拒绝归优惠券区域、SDK 错误归支付区域、库存失效归库存提示、跨步骤提交失败归页面反馈。不要每层都 toast 或 catch 后返回空成功值。

## 内部 API 形状

以下表达契约，不要求照搬命名：

```ts
type CouponState =
  | { status: 'idle' }
  | { status: 'checking' }
  | { status: 'applied'; coupon: AppliedCoupon }
  | { status: 'rejected'; error: CouponError };

type SubmissionState =
  | { status: 'idle' }
  | { status: 'submitting' }
  | { status: 'succeeded'; orderId: string }
  | { status: 'failed'; error: CheckoutError; retryable: boolean }
  | { status: 'unknown'; recoveryMessage: string };

type CheckoutSubmission = {
  state: SubmissionState;
  submit(snapshot: CheckoutSnapshot): Promise<void>;
  retry(): Promise<void>;
};
```

请求序号、取消控制器、SDK 实例等不应出现在这些返回值里。调用方需要的是能力和结果，不是实现机械装置。

`CheckoutPage` 的组合路径应接近：

```text
取得购物车/路由输入
  -> 创建草稿能力
  -> 创建优惠券、库存、支付能力
  -> 纯计算 quote 与 canSubmit
  -> 将稳定快照交给提交能力
  -> 渲染语义组件
```

不要再加一个巨型 `useCheckout()`，把五类状态复制到新的聚合 store 中。页面可以协调，但不能重新拥有各能力的状态、竞态和 cleanup。

## 依赖方向

```text
index.ts
  -> CheckoutPage
      -> components
      -> draft/coupon/inventory/payment/submission
      -> model

components
  -> model 类型和显式 callbacks

draft/coupon/inventory/payment/submission

  -> 不依赖 React、网络、浏览器全局或支付 SDK
```

补充规则：

- adapter 负责外部响应映射、运行时校验和 SDK 差异，不决定提示文案与页面布局。
- UI 不解析 HTTP 响应，也不识别支付 SDK 错误码。
- 内部模块使用直接相对导入，不绕经 feature 的公共 barrel，避免隐藏循环依赖。
- 不为了测试机械引入 repository、依赖注入容器或每个 adapter 一套 interface；只有确实存在替换边界或复杂外部协议时才定义 focused port。

## 组件边界

值得抽出的组件应至少拥有语义、交互或可访问性责任：

- `CheckoutForm`：`<form>` 语义、提交事件和字段级反馈。
- `CouponField`：优惠券输入、应用/移除操作及其局部反馈。
- `PaymentSection`：SDK 挂载区域、支付方式交互和支付错误关联。
- `OrderSummary`：只消费规范化后的 quote，不重新计算价格。
- `CheckoutFeedback`：提交中、失败、未知结果和成功后的页面级反馈。
- `InventoryNotice`：库存变化及阻塞原因。

收货地址字段、联系人字段等只有在它们拥有独立验证、交互或可访问性行为时才继续拆。仅包一层 `<div>` 并转发十几个 props 的组件应留在其父组件中。

2. 提取纯 `pricing` 和 selector；页面继续使用原调用方式。
3. 分别隔离现有 coupon、inventory、payment、checkout 外部调用，但保持请求顺序不变。
4. 一次迁移一个有生命周期的 hook，并补对应竞态或 cleanup 测试。
5. 最后提取有语义的组件，让页面只留下组合代码。
6. 删除已经失去消费者的 loading flag、旧 effect、请求计数器和转发参数，避免同时保留两套所有权。

## 停止继续拆分的条件

满足以下条件就应停止，即使 `CheckoutPage` 或某个 hook 仍然不短：

- 每个业务事实只有一个状态所有者。
- 每个订阅或 SDK 资源都有明确的获取、替换、释放者。
- 普通变更有明显起点，不需要先搜索多个泛化目录。
- 页面只组合能力，没有复制它们的状态或竞态策略。
- 纯规则不依赖 React 和外部系统。
- 外部响应形状或 SDK 对象没有泄漏到 UI。
- 公共 API 明显小于内部实现面。
- 删除任一现有边界都会让生命周期、规则归属或变更定位变差。

反过来，出现以下情况就不要再拆：

- 新文件只能叫 `utils`、`helpers`、`manager`。
- 文件只包含一个仅由单一所有者使用的短私有函数。
- 新组件只是转发 props，没有语义、交互或可访问性责任。
- 新 hook 只是为了把 `useEffect` 从页面挪走，却没有独立能力契约。
- 需要大量 barrel、interface 或配置才能把刚拆开的模块重新连起来。
- 一项普通修改被迫同时穿过多个同级模块，说明原本原子性的流程被拆散了。

用两个现实变化检验这套边界：替换支付 SDK 应主要落在 `paymentAdapter`/`usePaymentSession`，优惠券接口响应变形应主要落在 `couponAdapter`；若两者仍要求改动页面和多个展示组件，说明边界仍在泄漏。以上划分遵循了本地 Frontend Architect Skill 中“按所有权、生命周期和变化原因拆分，而非按行数拆分”的指导；工作区未作任何修改。

## 实现边界

订单模型是唯一业务真相：

- 每张卡片必须有稳定 ID，并以该 ID 作为渲染 key。
- 拖拽期间使用局部 `draftOrder`；放下时只提交一次最终顺序。
- `Escape`、`pointercancel` 或拖拽失效时恢复进入拖拽前的顺序。
- 外部列表更新若与当前拖拽冲突，默认取消拖拽并采用最新权威数据，不能用旧草稿覆盖。
- 动画的矩形、transform 和句柄不得写回顺序状态。

职责分配：

- 拖拽控制器：命中测试、目标索引、指针捕获、键盘操作和自动滚动。
- 重排协调器：按 ID 测量几何、执行 FLIP、取消旧动画、清理资源。
- 列表状态：管理 `draftOrder` 和最终提交。
- 卡片组件：语义、视觉与焦点，不自行保存重排状态。
- 建议让外层列表项承载 FLIP transform，内层卡片承载 hover、选中等视觉 transform，避免样式互相覆盖。

每次跨越重排阈值时：

1. 在修改顺序前，批量读取当前已挂载卡片的视觉矩形。正在动画的元素以当前屏幕位置作为新的 First。
2. 取消旧动画，但不等待其结束。
3. 更新 `draftOrder`，保证最终 DOM 布局在下一次绘制前提交。
4. 批量读取 Last 矩形。
5. 对仍存在的同 ID 元素计算位移，仅动画 `translate` 到零；不缩放卡片内容。
6. 约 140–180ms ease-out，结束或取消时移除句柄与临时样式。

快速连续拖拽采用“**最新目标获胜**”：

- 指针事件可以高频到达，但每个动画帧最多应用一次最新目标索引。
- 新重排从卡片当前视觉位置重新测量并重定向，不排队、不等待上一轮动画。
- 新一轮拖拽若发生在放下动画期间，也先取消并从当前视觉位置接管。
- 被拖卡片直接跟随指针，不对其位置添加 transition，否则会产生滞后。

滚动容器需要单独处理：

- First 和 Last 使用同一坐标系。可用 `getBoundingClientRect()` 加对应容器的 `scrollTop/scrollLeft` 转换为内容坐标，再计算差值，避免把自动滚动误判成重排位移。
- 自动滚动由拖拽控制器逐帧驱动；单纯滚动不触发一次新的重排动画。
- 每轮严格先批量读、再写，不能逐卡片交替读取和写入。
- 只测量已挂载且参与布局的卡片。若之后引入虚拟列表，应把几何测量交给虚拟化层的布局接口，而不是让 FLIP 猜测未挂载元素。

`prefers-reduced-motion: reduce` 下：

- 不创建重排或放下动画，DOM 立即进入正确顺序。
- 指针直接跟随和必要的自动滚动仍保留，但不使用平滑滚动或惯性归位。
- 偏好在拖拽期间发生变化时，立即取消现有动画并清理 transform。
- 同时提供键盘移动及“上移/下移”之类的非拖拽操作；焦点跟随稳定 ID，最终移动结果通过 `aria-live` 通知，不在每次指针经过槽位时播报。

卸载、路由离开、`lostpointercapture`、`pointercancel` 和 `Escape` 都必须取消动画、自动滚动帧、媒体查询监听及其他观察器。

## 验证方案

优先使用项目既有的真实浏览器测试工具；DOM 模拟器不能证明布局、滚动和指针行为。

核心浏览器场景：

- 在一轮 140–180ms 动画结束前连续跨越多个槽位，再立即反向拖动；最终顺序必须等于最后目标，不出现排队、倒退或跳回。
- 放下动画尚未结束时立即开始下一轮拖拽，确认新交互即时接管。
- 在滚动容器顶部、中部和底部测试自动滚动与重排；卡片应保持在指针附近，滚动位移不能被 FLIP 抵消。
- 模拟 `prefers-reduced-motion: reduce`，确认顺序正确且没有重排、归位动画。
- 覆盖 `Escape`、`pointercancel`、卸载和外部数据更新，确认顺序策略与资源清理。
- 用键盘及非拖拽按钮完成同样的移动，检查焦点和播报。
- 动画结束后检查所有卡片都处于最终槽位、无残留 transform、无活跃重排动画句柄。

可抽成纯逻辑的部分只做少量单元测试：稳定 ID 映射、目标索引计算、包含滚动偏移的 FLIP delta。中断连续性仍须由真实浏览器验证。

性能验证应在产品支持的最大典型卡片数和代表性设备上录制一次快速拖拽性能轨迹，重点检查：

- 每帧最多应用一次重排；
- 不存在逐卡片的读写交错和反复强制布局；
- transform 动画不触发逐帧 layout/paint；
- 拖拽结束后动画与临时合成层被释放。

若项目尚无性能预算，可先采用“输入后两帧内出现反馈、无超过 50ms 的主线程长任务、重排工作稳定落在单帧预算内”作为初始门槛，再用基线数据调整。

+
+## 2. 兼容边界与所有权
+
+页面只依赖一个稳定的 `BookingConfirmationGateway`（名称可按项目惯例调整），旧、新接口分别由适配器实现。页面、表单状态和埋点不得根据接口版本解释原始响应。
+
+| 边界 | 责任 | 不负责 |
+| --- | --- | --- |
+| 页面/流程协调器 | 收集已验证的提交快照，展示状态和恢复动作 | 拼接接口字段、决定重试是否安全 |
+| `BookingConfirmationGateway` | 暴露统一的提交与状态查询语义；选择一个适配器 | 同时写两个接口 |
+| 旧/新适配器 | 序列化请求、解析响应、把外部错误归一化 | UI 提示、静默降级 |
+| 灰度路由 | 在预订意图创建时选择版本并保持粘性 | 在一次进行中的提交中途切换版本 |
+| 服务端 | 鉴权、价格/库存校验、幂等落库、最终状态查询 | 依赖客户端锁保证唯一性 |
+
+统一契约至少表达以下信息，具体字段名以真实接口为准：
+
+- 输入：不可变的提交快照、稳定的 `bookingIntentId`、稳定的 `idempotencyKey`、必要的版本/价格确认信息；
+- `confirmed`：服务端确认成功及可向用户展示的预订引用；
+- `rejected`：确定没有创建预订的业务拒绝及可行动原因；
+- `unknown`：请求可能已提交但结果无法确认，附不含敏感信息的关联标识；
+- 状态查询：按同一预订意图或幂等键返回 `confirmed`、`notCreated` 或 `pending/unknown`。
+
+适配器必须做严格的响应形状和领域值检查。字段缺失、未知枚举或互相矛盾的状态记为“契约错误”，不能转换成空成功或安全失败。新旧响应可以不同，但归一化后的领域结果必须一致；页面不保留两份服务端事实。
+
+### 兼容规则
+
+1. **写请求永不双写。** 影子流量只允许用于无副作用的读取、校验或响应归一化比较。
+2. **路由按意图粘住。** 同一 `bookingIntentId` 的首次提交、查询与恢复默认走同一版本。灰度比例变化不影响已创建的意图。
+3. **不做危险回退。** 新接口超时、断网或返回 5xx 后，不能自动改调旧接口，因为新接口可能已成功提交。只有在请求明确未离开客户端，或服务端以权威状态证明 `notCreated` 时，才可重试；重试仍使用原幂等键。
+4. **回滚不重置结果。** 关闭新链路只让新意图走旧接口；新链路上结果未知的意图先查询并对账，不换键重提。若共享幂等层保证跨接口去重，恢复请求才可以由旧链路接管。
+5. **读取兼容先行。** 在写链路灰度前，先用真实分布的只读请求验证新适配器的字段、状态、时区、金额精度和错误映射。涉及价格或库存的比较必须以服务端权威语义为准。
+
+一个现实的后续变化（例如增加第三个供应商接口）只需新增适配器和路由配置；页面契约、提交状态机与恢复语义不变。若新增接口无法满足统一幂等与查询契约，则不得仅靠适配器伪装兼容。

+## 3. 幂等、重复提交与请求状态
+
+### 服务端必需契约
+
+- 幂等键由确认会话创建时生成，或由浏览器使用安全随机源生成；它必须是不含用户信息的高熵不透明值。
+- 同一用户/租户、`bookingIntentId` 和业务载荷指纹绑定同一幂等记录；同键同载荷返回第一次提交的最终结果，同键不同载荷返回明确冲突，不能再创建预订。
+- 旧、新接口使用同一幂等存储，或统一经过具备上述保证的服务端网关。
+- 幂等记录保留时间必须覆盖最长请求超时、用户刷新/离线恢复、客户端自动重试和人工对账窗口；具体 TTL 由后端依据业务窗口确定并在契约中固化。
+- 在创建预订的事务提交后、响应返回前发生断连时，状态查询仍能找到已创建的预订。
+- 鉴权、租户归属、价格与库存始终由服务端校验；客户端标志和隐藏按钮不承担授权。
+
+### 前端状态机
+
+```text
+ready
+  -> submitting
+      -> confirmed         展示唯一成功结果，禁止再次创建
+      -> rejected          已确定未创建；修正输入后生成“新意图/新键”再提交
+      -> unknown           禁止创建式重试；用原键查询最终状态
+
+unknown
+  -> confirmed             查询到已创建
+  -> ready                 仅权威查询返回 notCreated；仍用原键重试同一快照
+  -> unknown               继续有限退避查询，随后转人工恢复
+```
+
+- 点击提交后同步进入 `submitting` 并锁住提交命令；按钮置为忙碌和禁用只是体验保护，不是幂等保证。
+- 键盘提交、双击、触屏连点和代码触发都必须进入同一个命令入口；组件内不得另绑绕过网关的写调用。
+- 提交使用不可变快照。用户随后编辑的草稿不能改变正在恢复的那次请求，也不能被旧请求完成结果清空。
+- 前端取消或页面卸载只表示“不再发布该完成结果”，不代表服务端取消。写操作不用“最后一次请求获胜”覆盖前一次结果。
+- 同一页面生命周期只允许一个创建命令在途；多标签页、多设备和网络重放由服务端幂等处理。
+- 为支持刷新恢复，只持久化恢复所需的最小不透明标识和创建时间，优先复用服务端确认会话；不把旅客、证件、联系方式或完整请求体写入 `localStorage`。登出、账号切换和恢复完成时清理本地恢复状态。
+
+## 4. 错误与恢复体验
+
+| 结果 | 用户界面 | 系统动作 |
+| --- | --- | --- |
+| 确定成功 | 显示预订引用和下一步；保持提交禁用 | 以权威结果刷新相关缓存，清理恢复标识 |
+| 明确业务拒绝 | 显示可修正原因，焦点回到对应字段或错误摘要 | 保留草稿；只有用户改变业务意图后才创建新键 |
+| 请求明确未发出 | 提示网络问题和“重试同一次提交” | 原快照、原幂等键重试 |
+| 超时、断网、5xx 或响应解析失败且可能已提交 | 明确显示“正在确认，勿重复预订”，不显示普通“再试一次” | 立即按原键查询；指数退避加抖动且有上限 |
+| 长时间仍未知 | 保留关联编号和稍后继续入口，提供人工支持路径 | 后台/再次进入页面继续查询；进入对账队列 |
+| 页面刷新或返回 | 先恢复未知提交，不先呈现可再次创建的空表单 | 按最小恢复标识查询，再决定成功、可重试或继续等待 |
+
+请求查询需有明确预算，例如前台快速查询数次后降低频率；具体间隔按现有请求政策和接口容量确定。不要无限循环，也不要吞掉未知状态。离线时停止网络重试并保留诚实状态，恢复联网后继续查询。
+
+错误只在能采取恢复动作的边界处理一次。适配器保留结构化错误码，流程协调器决定用户文案，页面不重复弹多个通知。日志关联号可以帮助排障，但不能让用户看到内部堆栈、原始响应或敏感载荷。
+
+## 5. 两周灰度计划
+
+所有阶段都由服务端/边缘配置的可审计开关控制，配置读取失败时默认旧链路。分桶使用稳定散列（用户标识；未登录时使用确认会话标识），并按 `bookingIntentId` 固定版本。客户端开关不是安全边界。
+
+| 阶段 | 建议时间 | 新链路范围 | 晋级条件 |
+| --- | --- | --- | --- |
+| 0. 契约与暗测 | 第 1–2 天 | 0% 写；测试/预发验证，两适配器契约测试 | 共享幂等和状态查询通过；故障注入能恢复“提交成功但响应丢失” |
+| 1. 只读影子 | 第 3 天 | 旧链路向用户发布；新链路只做无副作用读取比较 | 归一化差异已分类，无敏感数据进入比较日志 |
+| 2. 内部金丝雀 | 第 4 天 | 员工/测试账号的新写链路 | 双击、多标签、刷新、超时、断网和回滚演练通过 |
+| 3. 小流量 | 第 5–6 天 | 1% -> 5% -> 10% | 每档覆盖一个业务高峰并达到最小样本；核心护栏未恶化 |
+| 4. 扩量 | 第 7–10 天 | 25% -> 50% | 关键地区、设备、登录状态和主要业务类型均有代表样本 |
+| 5. 主链路 | 第 11–14 天 | 100%，旧链路和关闭开关仍保留 | 至少连续 48 小时且覆盖一个高峰稳定；未知结果已对账 |
+| 6. 清理 | 并存期结束后单独变更 | 删除旧适配器、旧标志和专用比较埋点 | 产品/运营确认无未结对账；回滚窗口结束；新基线已建立 |
+
+百分比不是自动晋级信号。每一档由发布负责人根据下节看板显式晋级；夜间无人值守时不跨档。采用地域或业务线分批时，必须同时保留随机对照组，避免把流量结构差异误判为接口差异。
+
+影子比较不能调用创建、锁库存、支付、发消息或其他潜在副作用端点。无法证明读取无副作用时，跳过影子阶段，改用离线脱敏回放或预发契约样本。
+
+## 6. 生产信号与决策看板
+
+所有指标按 `api_version`、发布版本、灰度桶、地区、设备/浏览器、登录状态和主要业务类型切分，但必须满足最小聚合人数后才展示细分。`bookingIntentId` 和幂等键只用于受控服务端关联；分析事件使用不可逆、定期轮换的伪匿名关联值。
+
+### 核心护栏
+
+1. **权威重复预订数/率：** 服务端按同一预订意图、载荷指纹及合理时间窗识别创建多笔的情况；这是最高优先级信号，不能只统计重复点击。
+2. **确认成功率：** `confirmed / eligible_intents`，并与同期旧链路对照；同时观察业务拒绝率，避免把拒绝误算成技术错误。
+3. **未知结果率及驻留时间：** 进入 `unknown` 的比例、恢复到最终结果的比例、P50/P95 恢复时间、超过人工介入阈值的数量。
+4. **幂等行为：** 首次接受、同键重放命中、同键不同载荷冲突、幂等存储错误和状态查询未命中。
+5. **契约与可用性：** 响应解析/未知枚举错误，HTTP/传输错误，状态查询错误，提交和恢复查询的 P50/P95/P99 延迟。
+6. **用户伤害代理：** 重复预订客服工单、短时取消/退款、确认页放弃率、重复进入确认页和长时间停留。
+
+### 必要事件（使用允许字段清单）
+
+- `booking_confirmation_submit_started`
+- `booking_confirmation_outcome`：仅记录 `confirmed | rejected | unknown` 和低基数原因码
+- `booking_confirmation_reconcile_started/completed`
+- `booking_confirmation_idempotency_replay/conflict`
+- `booking_confirmation_contract_error`
+
+事件必须有稳定定义、单一发出方和可核对的分母。浏览器“成功”事件只能表示它收到确认，真正的创建数与重复数取自服务端权威记录。浏览器事件丢失不等于业务失败。
+
+## 7. 隐私与安全控制
+
+- 遥测采用字段允许清单：版本、状态、低基数错误码、耗时、灰度桶和粗粒度环境信息。禁止记录姓名、电话、邮箱、证件、支付信息、完整行程、备注、原始请求/响应、访问令牌或会话 Cookie。
+- 不把原始幂等键、预订引用或 `bookingIntentId` 发往通用第三方分析。排障确需关联时，在受控服务端日志中使用访问受限的关联号，或使用带轮换密钥的不可逆伪匿名值；不得使用普通无盐哈希处理可枚举标识。
+- 日志、错误上报、链路追踪和 source map 上传分别检查脱敏；网络库自动捕获的 URL、请求头和请求体默认关闭或过滤。
+- 运营看板只提供达到最小人数的聚合细分，限制访问角色和导出能力，并按组织现有数据政策设置最短可用保留期。保留期和处理依据需由隐私/合规负责人确认，本文不替代其判断。
+- 实验分桶只使用完成灰度所需的稳定伪匿名标识，不为此次迁移新增跨站追踪。未经相应同意/处理依据，不让第三方分析脚本在确认页读取页面内容或用户对象。
+- 服务端对两个接口执行相同的鉴权、租户隔离、CSRF（如适用）、价格/库存重验和速率限制；前端只能改善呈现，不能替代这些控制。
+
+## 8. 暂停、回滚与恢复条件
+
+发布前用最近 7 天旧链路基线固化数值阈值和告警接收人。以下建议值是初始护栏，需在首次放量前结合实际基线确认，不能在告警发生后临时改阈值：
+
+### 立即关闭新意图流量（回到 0%）
+
+- 发现任意一例经服务端确认的“同一幂等键创建多笔预订”，或共享幂等层不可用/不一致；
+- 无法按原键查询未知结果，导致是否已预订不可判定；
+- 鉴权绕过、跨用户/租户数据暴露、敏感信息进入遥测或日志；
+- 契约错误会把失败解释为成功，或金额、币种、日期、旅客对应关系发生错误。
+
+### 暂停晋级并调查；持续越线则回滚
+
+- 新链路未知结果率连续 10 分钟高于 `max(0.1%, 旧链路同期 2 倍)`，且至少 50 次新链路尝试；
+- 新链路确认成功率连续 15 分钟低于对照组 0.5 个百分点以上，且两组各至少 200 次合格意图；
+- 新链路技术错误率达到旧链路 2 倍，或 P95 确认耗时超过旧链路 50%，连续 15 分钟且样本充分；
+- 客服重复预订、快速取消/退款或未知结果积压出现统计/运营上显著异常。
+
+低流量分段以绝对事件和人工判断为准，不能因达不到样本数而忽略严重个案。反之，单个客户端埋点丢失不应自动触发业务回滚，需与服务端权威记录交叉确认。
+
+### 回滚动作顺序
+
+1. 发布负责人关闭新**意图**分配，记录时间、配置版本和受影响桶；不等待重新构建前端。
+2. 保持状态查询与对账能力在线；冻结而非重提所有新链路的 `unknown` 意图。
+3. 若共享幂等层已证明跨接口一致，可让旧链路以原键恢复；否则维持原路由并由人工/服务端对账。
+4. 核对新链路窗口内的创建记录、未知结果、重复预订和敏感日志；主动处理受影响用户。
+5. 修复后从内部金丝雀或 1% 重新开始，不从回滚前比例直接恢复。
+
+代码回退与流量回退分离：正常止损使用运行时关闭开关；只有新代码本身破坏旧链路、页面加载或恢复能力时才回退前端构建。旧适配器和开关在两周并存期及未知结果清零前不得删除。
+
+## 9. 验证与交付清单
+
+### 自动化检查
+
+- 对同一组成功、业务拒绝、鉴权失败、库存/价格变化、未知枚举和畸形响应样本运行两个适配器的契约测试，断言归一化结果一致。
+- 状态机测试覆盖：双击只发一个命令；超时不改键重提；旧完成结果不能覆盖当前页面；旧请求的清理不能解除新请求的忙碌状态。
+- 故障注入覆盖“服务端已创建但响应丢失”，断言页面进入 `unknown`、按原键查询并最终只展示一笔预订。
+- 端到端覆盖键盘提交、触屏连点、刷新/返回、断网恢复、多标签页和账号切换；多标签页应由服务端证明只创建一次。
+- 灰度测试覆盖稳定分桶、意图级粘性、配置失败默认旧链路，以及关闭开关后新意图立刻走旧链路。
+- 遥测契约测试验证事件分母和枚举，并扫描事件、日志与错误上报中是否出现禁止字段或令牌。
+
+### 放量前人工演练
+
+- 在预发或隔离环境完成一次超时、5xx、响应畸形、状态查询暂时失败和幂等存储故障演练。
+- 值班人员实际操作关闭开关，确认无需发版，并验证未知意图仍可查询。
+- 产品、客服和运营确认 `unknown` 文案、关联号查找方式及人工处置手册。
+- 数据负责人确认权威重复预订查询与看板分母能从服务端记录复算。
+
+### 完成定义
+
+迁移完成不是“新接口达到 100%”这一单点，而是：新链路覆盖目标流量并稳定经过约定观察窗；没有未处置的重复预订或未知结果；核心指标能由权威记录复算；隐私检查通过；回滚演练有效；最后再用独立、可审查的变更删除旧适配器、旧标志和临时影子比较。

## 最小修复顺序

### 1. 先补齐事实与基线

从实际项目记录：

- `react-native`、React、列表组件及图片组件的精确版本。
- 锁文件、`android/gradle.properties`、构建参数及最终 APK 的架构标记。
- Hermes、构建模式、目标 Android 版本、设备型号与刷新率。
- 800 项数据中实际挂载数量、行高是否固定、图片请求尺寸和缓存策略。

不能仅凭“现代 RN”判断架构。RN 0.76 起新架构默认启用，但项目可以关闭，最终构建配置才是事实。[React Native New Architecture](https://reactnative.dev/architecture/landing-page)

在同一台中端 Android 真机上，用相同 800 项数据和固定滚动操作录制四组 profile/release 样本：

| 音频进度 | 图片 | 用途 |
|---|---|---|
| 正常 100ms 更新 | 正常图片 | 基线 |
| 暂停进度更新 | 正常图片 | 判断高频 React 更新是否主因 |
| 正常更新 | 固定尺寸占位图 | 判断解码、上传、绘制和缓存是否主因 |
| 暂停更新 | 占位图 | 观察两者叠加及剩余布局成本 |

采集：

- React Profiler：每次进度变化触发哪些组件 commit、耗时多少。
- RN 性能轨迹：若当前版本支持；新版 Performance 面板从 RN 0.83 才提供，不能假定已有。[React Native DevTools](https://reactnative.dev/docs/react-native-devtools)
- Android Studio/Perfetto FrameTimeline：区分 JS、UI、布局、绘制和图片相关工作。
- JS heap、Java/Kotlin heap、native/graphics memory、进程 PSS。
- 连续多次顶部到底部再返回，并等待空闲/GC 后观察是否形成平台，而非只看一次 RSS 上升。Bitmap 等资源可能体现在 native memory，不能只检查 JS heap。[Android Memory Profiler](https://developer.android.com/studio/profile/record-java-kotlin-allocations)

### 2. 若暂停进度后明显改善，先做更新隔离

这是已知代码描述下最小、最可能有效的改动：

- 800 项业务数据保持稳定引用；音频 tick 不再 `map` 出整批新行对象。
- 高频 `progress` 由播放器控件和当前播放行订阅。切换播放项时只应使旧活动行、新活动行及播放器更新。
- 不把 `progress` 放入整张列表的 `data`、列表级 `extraData` 或等效全局失效输入。
- 行组件只接收必要的标量和稳定对象，例如 `item`、`isActive`、稳定的 `onPress(id)`。
- 静态样式移至模块级 `StyleSheet.create`；确有动态样式时只传最小变化值。
- `renderItem` 和列表级回调保持稳定依赖。
- 仅当 profiler 显示行重渲染成本显著时添加 `React.memo`；比较实际可见属性和回调，不做深比较，也不能故意忽略会影响行为的 prop。

中间验收条件：每个 100ms tick 不再导致所有可见行 commit；通常只允许播放器及活动行更新。这个结果只能证明失效范围缩小，不能单独证明掉帧已解决。

暂不降低 100ms 频率，因为这会改变进度显示语义。若隔离后活动行仍然过重，再根据检测到的 RN 版本和动画能力决定是否降低显示采样率或把纯视觉插值放到 UI 侧；不能先套用旧 Bridge 的“减少跨桥消息”结论。

### 3. 若占位图实验有效，再收缩图片成本

- 信息流请求接近实际显示尺寸的缩略图，而不是下载后解码原始高分辨率图。
- 请求像素尺寸按布局尺寸和设备像素密度确定，并保持稳定 URI/缓存键。
- 为图片预留确定尺寸或宽高比，避免加载后重新布局。
- 复用项目现有图片加载和缓存能力；先确认缓存上限、淘汰、取消和卸载行为，不直接引入新图片库。
- 用 retained object、Bitmap/native allocation 或缓存统计确认资源所有者。内存持续增长不等于已经证实泄漏。

RN 官方也建议列表使用轻量缩略图，但是否改善本项目仍须由真机内存和帧轨迹确认。[FlatList optimization](https://reactnative.dev/docs/optimizing-flatlist-configuration)

### 4. 最后才调整当前列表的虚拟化参数

不换库，只在确认当前组件及版本后逐项实验：

- 使用稳定的业务 ID 作为 key，禁止 index key。
- 行高真正固定时才提供 `getItemLayout`，并正确包含分隔线；动态高度不能伪造。
- 根据屏幕可见行数调整 `initialNumToRender`。
- 单独实验 `windowSize`、批量大小和批次周期，兼顾内存、空白区与触摸响应。
- 不把 `removeClippedSubviews` 当成内存泄漏修复：官方说明它主要将视图从原生层级脱离，并不保证释放这些视图的内存。[FlatList configuration](https://reactnative.dev/docs/optimizing-flatlist-configuration)

## 证据分支

- 冻结进度有效、占位图无效：实施状态隔离和稳定身份，暂不动图片或列表窗口。
- 占位图有效、冻结进度无效：优先缩略图、尺寸、缓存和资源生命周期。
- 两者都有效：先合入状态隔离，再处理图片；每一步重复同一测量，避免无法归因。
- 两者都无效：从 Perfetto 中继续定位布局、绘制、UI 线程阻塞或其他原生工作，不增加 memo 或切换列表库碰运气。
- 内存只在滚动期间上升、随后形成平台：更像窗口或缓存行为；若多轮操作后 retained set 仍阶梯式增长，才沿引用链调查泄漏。

## 必须在真实环境验证的结论

必须在真实 React Native 运行时确认：

- 实际 RN/Hermes/New Architecture 组合。
- 100ms 更新究竟使哪些组件 render/commit。
- `memo`、稳定对象和订阅下沉是否真正缩小失效范围。
- 当前列表组件的窗口、回收、测量及图片卸载行为。

必须在中端 Android 真机的 profile/release 条件确认：

- 滚动掉帧是否改善，以及瓶颈在 JS、UI、布局、绘制还是图片阶段。
- 图片解码、native/graphics memory 和 GC 是否主导内存变化。
- 多轮滚动后的内存是否形成稳定平台。
- 是否出现空白区、触摸延迟、错误复用、图片闪烁或滚动位置回归。
- 热机、真实刷新率和持续滚动下的结果；模拟器与 debug 构建不能支撑这些结论。Android 官方推荐用系统轨迹和帧数据定位 jank。[Android rendering diagnostics](https://developer.android.com/topic/performance/rendering/optimizing-view-hierarchies)

最终放行标准应在基线后固定：同一设备、数据、构建和操作下，帧指标达到产品目标且重复运行稳定；内存在多轮滚动后进入可解释的平台；音频进度、点击、重排、快速滚动和图片展示均无行为回归。
