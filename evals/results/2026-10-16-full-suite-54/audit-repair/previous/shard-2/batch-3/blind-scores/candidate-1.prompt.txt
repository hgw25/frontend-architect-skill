## 模块边界

`checkout` 应拥有：

- 结算草稿以及结算过程的状态转换。
- 地址、配送、优惠、支付选择等结算场景中的协调行为。
- 提交中、成功、失败、重试、重复提交处理等工作流。
- 结算专用类型、API 映射和用户可见反馈。
- 上述行为的测试。

它不应拥有：

- 登录态和授权策略。
- 商品目录或购物车的全部状态。
- 通用 HTTP、日志、日期、货币格式化能力。
- 无业务含义的按钮、输入框等 UI 基础组件。
- 服务端最终价格、库存、支付授权等权威规则的客户端副本。

若支付 SDK 目前只服务结算，适配器先留在 `checkout` 内；只有出现语义稳定的第二个消费者时，才考虑提炼为更广泛的支付能力。不能仅因“以后可能复用”提前建设通用仓储层、依赖注入框架或微前端包。

## 公开 API

跨模块消费者只能从 `features/checkout/index.ts` 导入。入口应显式导出，不使用 `export *`：

```ts
export { CheckoutScreen } from './CheckoutScreen';
export type {
  CheckoutInput,
  CheckoutOutcome,
} from './checkout.model';
```

实际名称按现有框架调整，但公开面应遵循这些原则：

- 路由只需要知道如何进入结算，以及结算完成或取消后的结果。
- 使用领域输入，而不是暴露后端 DTO。
- 不导出内部 store、reducer、selector、请求响应类型或私有 hooks。
- API 错误先在适配器中归一化，再由工作流转换成结算场景能处理的失败结果。
- 只有确有非 UI 调用方时，才公开命令函数；不要为了“API 完整”导出内部提交实现。

路由组件仍留在框架规定的位置，它只负责读取路由参数、挂接应用级能力并渲染结算入口，不重新实现结算状态。

## 依赖方向

```text
应用入口 / 路由
        ↓
checkout 公共入口
        ↓
checkout 组合层
   ↙       ↓        ↘
 UI      workflow    API adapter
  ↓       ↓   ↘          ↓
  └──── model   focused ports
                    ↓
          shared/http 等平台能力
```

具体规则：

- `model` 不依赖 UI、网络、浏览器 API或状态库生命周期。
- UI 不解析原始响应，不直接调用全局 service。
- API adapter 不决定提示文案或页面跳转。
- `shared` 不得反向导入 `checkout`。
- 其他业务模块不得导入 `checkout` 私有路径。
- 两个同级 feature 需要协调时，由路由或更高层工作流协调，不能互相读取内部 store。
- 模块内部使用直接相对导入，不经 `index.ts` 绕一圈，以免隐藏循环依赖。

## 渐进式迁移顺序

1. **先固定当前行为**

   为现有结算主路径补入口级特征测试，至少覆盖展示、提交成功、服务失败和重试。测试保护用户可见行为，不绑定当前目录或内部 hook。

2. **建立新入口，不移动所有旧代码**

   创建 `features/checkout/index.ts` 和结算组合入口。第一阶段允许组合层临时调用旧 `stores/services/hooks`，但把这些依赖列为迁移债务；新增结算代码不得继续散落到顶层技术目录。

3. **按完整行为纵向迁移**

   不要先搬完所有 types，再搬 services。一次迁移一个可验证能力，例如：

   - 订单摘要展示及其类型、映射、测试；
   - 配送选择及其状态、行为、测试；
   - 优惠应用及其请求并发策略；
   - 支付会话；
   - 最终提交与失败恢复。

   每一步结束时都应有一个从入口可运行的完整路径。

4. **为旧导入保留短期兼容层**

   某个实现迁入模块后，旧路径可暂时从新公开入口重导出，并标记弃用。迁移桥必须单向：

   ```text
   旧路径 → checkout 公共入口 → checkout 实现
   ```

   同一个符号不能同时让新模块依赖旧路径、旧路径又重导出新模块，否则会形成循环。

5. **只提升真正共享的能力**

   搬迁过程中发现的通用 HTTP、基础 UI、货币格式化等，可进入有明确名称的 `shared/http`、`shared/ui`、`shared/currency`。结算规则不能因为被两个文件调用就进入全局 `utils`。

6. **稳定后再执行约束**

   当结算模块完成至少一条纵向迁移后，可复用项目已有 lint/import 规则禁止：

   - 外部深层导入 `features/checkout/*`；
   - `shared` 导入业务 feature；
   - 新代码继续写入无明确归属的顶层 `utils/types/services`。

   若项目尚无对应 lint 能力，先通过评审约定执行，不必马上引入一套新工具。

7. **最后删除旧目录内容**

   只有当调用方全部切换、测试通过且搜索不到旧导入后，才删除兼容导出和空目录。其他业务模块仍可保持旧结构，等其下一次出现高频修改或明显散弹式变更时再迁移。

## 验证重构是否有效

用两个现实变化检查边界：

- 后端结算响应字段变化：通常只修改 `checkout.api` 的 DTO 映射和适配器测试，UI 与工作流不应理解新 DTO。
- 新增一种支付方式：主要修改支付适配、结算工作流、对应 UI 和行为测试；结算公开入口与其他业务模块通常不变。

如果这两类修改仍需横跨全局 `services`、`stores`、`types` 和多个 feature 私有文件，说明边界仍在泄漏。迁移成功的标准不是目录看起来统一，而是普通结算需求有明确起点、影响范围可预测、跨模块 API 小于内部实现面。
