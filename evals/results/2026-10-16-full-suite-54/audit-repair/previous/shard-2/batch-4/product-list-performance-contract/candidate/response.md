结论：当前版本不应继续全量发布。移动端 LCP、INP 均明显回退，CLS 虽稳定但不能抵消这两个阻断项。先确认版本归因并控制曝光，再用少量对照实验分别定位 LCP 与筛选长任务；不以单次 Lighthouse、包体变化或“渲染次数”单独下结论，也不默认重写或虚拟化列表。

仓库中没有项目代码、构建配置或既有性能流水线，因此以下是可执行的初始契约，具体设备与命令需要落入实际项目配置。

## 最小调查与修复顺序

| 顺序 | 动作 | 决策条件 |
|---|---|---|
| 1 | 按发布版本、商品列表路由、移动设备、地区/网络和登录状态切分 RUM；确认 3.1s/290ms 与改版版本同步，而非流量结构变化。记录样本量和分位数置信区间 | 若回退明确绑定新版本，暂停放量；支持开关或安全回滚时先降级到上一版本 |
| 2 | 固定“上一正常版本”和候选版本，在同一生产构建、数据集、设备及网络下采集加载瀑布、Performance trace 和构建产物 diff | 得到 LCP 阶段分解、字体依赖链、JS parse/evaluate 时间，以及筛选交互的 input delay / processing / presentation delay |
| 3 | 对 LCP 做两个独立消融实验：移除新增字体依赖；恢复新增 95KB 首路由 JS。每次只改变一个因素 | 判断回退来自资源加载延迟、JS 执行/渲染延迟，还是二者共同作用；95KB 只是线索，不直接等同于根因 |
| 4 | 对筛选的 180ms 长任务做 CPU profile，并关联组件提交、DOM 更新和布局事件 | 确认时间花在重复筛选/排序、状态广播、列表提交还是布局；未定位前不引入 Worker、全局 memo 或列表重写 |
| 5 | 按证据实施最小修复 | 先修已确认且改动最小的责任边界，修一项便复测原场景 |
| 6 | CI 回归、真实设备回归、分阶段 RUM 放量 | 所有门槛通过后才扩大流量；样本不足视为“等待”，不是“通过” |

优先修复候选：

- 字体确认为 LCP 阻塞因素：从关键链移除未使用字重/字符集；只预加载首屏实际使用的 WOFF2；采用合适的 `font-display`。若允许字体交换，需用匹配的 fallback metrics 或尺寸预留保持 CLS。
- 95KB JS 确认造成下载、解析或执行回退：将非首屏功能移出首路由、动态加载新增筛选辅助能力，或移除重复依赖。保留用户首屏必需代码。
- 180ms 任务确认为计算：将重复规范化、索引或排序移到数据变更时完成，并以数据版本作为失效边界。
- 若主要成本是一次筛选触发整个列表提交：缩小订阅和失效范围、保持商品稳定 key，只更新受影响节点。
- 只有 trace 证明 DOM 数量或布局是主因，才考虑分批渲染或虚拟化；同时验证焦点、读屏顺序、滚动恢复和可变行高。

## 初始性能预算

以下预算同时包含绝对体验门槛和相对回退门槛，避免“仍在绿色区但持续变慢”。

| 层级 | 指标 | 门槛 |
|---|---|---|
| RUM，移动商品列表 | LCP p75 | `≤ 2.5s`，且相对上一正常版本的回退 `≤ 100ms` |
| RUM，发生有效交互的页面 | INP p75 | `≤ 200ms`，且回退 `≤ 20ms` |
| RUM，移动商品列表 | CLS p75 | `≤ 0.10`，且回退 `≤ 0.02` |
| 构建产物 | 首路由 JS gzip | 不超过上一正常构建 `+20KB`；当前 `+95KB` 必须消除或走有期限的预算例外 |
| 关键加载链 | 新增字体阻塞 | 不允许出现会延迟 LCP 的新增字体依赖；预加载字体不得重复下载 |
| 受控实验室环境 | 冷启动 LCP p75 | `≤ 2.5s` 且比固定基线回退 `≤ 100ms` |
| 筛选交互 | 单个连续主线程任务 | p75 `≤ 50ms`，任何一次 `≤ 100ms` |
| 筛选交互 | 实验室端到端交互延迟 p75 | `≤ 200ms` |

预算应保存在版本控制中的构建/测试配置内，绑定路由、生产构建模式、固定数据规模、设备档位和网络配置。例外需包含原因、负责人、到期时间和恢复目标，不能永久扩大基线。

## 回归验证

使用上一正常版本与候选版本做相同条件的 A/B：

1. 固定一台代表性中端 Android 真机或可校准设备档位，记录浏览器版本、刷新率、CPU/网络配置和商品数量。
2. 冷缓存加载至少 20 次，比较 LCP p75及其资源加载延迟、加载耗时、渲染延迟。
3. 热页面执行同一筛选序列至少 20 次，记录交互阶段、最长任务、JS profile、布局和列表提交。
4. 验证筛选结果、排序、清空、快速连续输入、键盘焦点、读屏行为、滚动位置、字体回退和 CLS。
5. 将原始 trace、bundle manifest、测试 revision、环境和命令保存为可追溯产物。

Lighthouse 可以作为重复实验中的辅助信号，但不能替代浏览器 trace、真实设备交互或分版本 RUM。

## 发布门槛

- 合并前：构建预算、关键字体链、受控实验室 LCP 和筛选长任务全部通过。
- 先发布 5%–10% 流量，至少观察 24 小时；RUM 样本建议不少于 1,000 次合格页面加载和 500 次有效交互。
- 扩大流量的条件：绝对预算通过，且相对正常版本差值的 95% 置信区间上界不超过 `LCP +100ms`、`INP +20ms`、`CLS +0.02`。
- 样本不足：保持当前比例继续观察。
- 候选版本达到当前的 `LCP 3.1s / INP 290ms`，或已确认显著超过任一绝对门槛：停止放量并回滚/关闭改版。
- 每次扩容后继续按版本监控；全量后仍保留至少一个完整业务周期的回退告警。
