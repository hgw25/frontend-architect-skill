```ts
type OrderResponseDto = {
```

```ts
  totalCents: number,
```

```ts
type OrderLoadState =
```

- `fetch` 和状态码判断；

## 首次同步

### 1. 先固化未提交的表单修改

优先使用本地临时分支和提交，而不是只依赖 stash：

```bash
git branch --show-current
git status --short

git switch -c wip/form-before-template-sync-YYYY-MM
git add -- <表单相关文件...>
git commit -m "wip: preserve form changes before template sync"
git rev-parse HEAD
```

记录 WIP commit SHA，并确认没有遗漏相关的未跟踪文件。这个分支暂不推送，也不要在表单修改恢复并验证前删除。

### 2. 配置模板远端

```bash
git remote add upstream <团队确认的模板仓库URL>
git fetch --prune origin
git fetch --prune upstream
git remote show upstream
```

确认 `<team-main>` 和 `<template-main>` 的实际名称。`origin` 始终用于团队 fork，`upstream` 只用于拉取模板。

### 3. 建立同步基线

```bash
git switch <team-main>
git pull --ff-only origin <team-main>
git rev-parse HEAD
```

记录此时的团队基线 SHA。然后先运行项目已有的：

```text
<项目构建命令>
<表单回归测试命令>
```

基线本身若失败，应先记录或修复，避免把旧问题误判为模板同步引入。

### 4. 在独立分支合并模板

```bash
git switch -c chore/template-sync-YYYY-MM origin/<team-main>

git log --left-right --cherry-pick --oneline \
  origin/<team-main>...upstream/<template-main>

git diff --stat \
  origin/<team-main>...upstream/<template-main>

git merge --no-ff --no-commit upstream/<template-main>
```

冲突处理原则：

- 不要对全部冲突统一使用 `ours` 或 `theirs`。
- 业务行为属于要保留的契约；在吸收模板结构、依赖和配置变化的同时重新适配业务代码。
- `package.json` 等清单手工合并意图，锁文件用项目既有包管理器重新生成，不手改。
- 生成文件按项目已有生成流程重建。
- 表单未提交修改此时还安全地留在 WIP 分支，不参与第一轮模板冲突。

合并完成后运行：

```text
git diff --check
<项目构建命令>
<表单回归测试命令>
```

通过后再创建 merge commit：

```bash
git commit -m "chore: sync template through <upstream-sha>"
```

并验证两边历史均未丢失：

```bash
git merge-base --is-ancestor <同步前团队基线SHA> HEAD
git merge-base --is-ancestor <本次upstream SHA> HEAD
```

两条命令都应返回成功。

推送同步分支并创建 PR：


PR 必须：

- 禁止对已推送业务分支 force-push。

## 恢复表单修改

模板同步合入后，从最新团队主分支创建正式业务分支，再恢复 WIP：

```bash
git fetch origin
git switch -c feature/form-work origin/<team-main>
git cherry-pick <WIP commit SHA>
```

若模板也改动了表单区域，按新的模板接口重新解决冲突。随后重新执行构建和表单回归，并把正式业务分支推送成功；到此才能删除本地 WIP 分支。

## 回退方案

- merge 尚未提交：`git merge --abort`。
- 同步分支尚未合入：关闭 PR，团队主分支不受影响。
- 已合入团队主分支：通过新 PR revert 对应的 PR merge commit，不重写共享历史、不 force-push。
- 注意：revert merge 只撤销内容，不会删除 upstream 祖先关系。以后重新启用这批模板变化时，需要在修复问题后“revert 该 revert”或提交明确的恢复改动，不能指望下月再次 merge 自动带回。

以后每月重复“fetch → 从最新 `origin/<team-main>` 建同步分支 → merge upstream → 构建及表单回归 → 保留历史的 PR”即可。整个方案的关键是：已推送业务历史不改写、脏工作先落到可寻址的 commit、模板祖先关系持续保留、验证结果绑定到明确 SHA。未对工作区作任何修改，也未执行实际同步操作。

## 现在的结构建议

采用“页面归属 + 少量共享能力”的浅层结构，并服从实际框架的路由约定：

```text
src/
  app/                    # 应用入口、路由、全局 provider、外壳
  pages/                  # 若框架已有规定的路由目录，沿用其名称
    first-page/
      FirstPage.*
      FirstPageForm.*     # 仅在它有独立交互职责时拆分
      firstPageApi.*      # 仅该页面使用的数据访问
      firstPageRules.*    # 仅在确有独立业务规则时存在
    second-page/
      SecondPage.*
      ...
  shared/
    ui/                   # 真正跨页面、无业务策略的 UI
    http.*                # 两页共同使用且确实拥有统一请求策略时才建立
```

具体原则：

- 页面负责组装该页面的用例，不要把所有请求、表单状态和业务规则永久堆进页面组件。
- 只服务一个页面的组件、请求和规则与页面共置，不要提前搬入顶层 `features`、`services`、`types`。
- 跨页面复用不等于必须进入 `shared`；只有语义和所有权也确实共享时才提升。
- 不预建空的 `api/`、`model/`、`ui/`、`domain/` 目录，也不为每个文件创建 barrel。
- 保持简单依赖方向：`app/路由 → 页面 → 页面私有能力或 shared`；`shared` 不反向依赖页面。
- 如果两页本身属于同一个小型业务能力，继续保持浅层技术分组也可以；无需为了形式改名为 feature。

例如，给第一页增加一个只影响该页的筛选条件，应该能主要在 `pages/first-page` 内完成。若一次普通修改必须同时穿梭全局 `components`、`hooks`、`services`、`types`，才说明当前分组开始失效。

## 何时触发迁移

出现以下一种强信号，或多种信号持续出现时，再逐步引入 feature/domain 边界：

- 同一业务能力跨越多个页面，并且有自己的状态、规则、请求或错误处理。
- 普通需求反复修改多个顶层技术目录，变更位置难以预测。
- 页面组件开始协调多个相互独立的请求、重试、取消、订阅或提交流程。
- 同一业务规则在多个页面重复，或 UI、校验和数据映射各自保存一份规则。
- `components`、`services`、`types`、`utils` 逐渐成为无法说明准入规则的杂物目录。
- 页面之间开始深层互相导入，出现循环依赖或必须了解对方内部实现。
- 某个能力形成稳定的外部契约，或者开始需要独立负责人、代码分割、测试和交付节奏。

文件数、代码行数、某个组件被使用两次，或者“以后可能会复杂”本身都不是充分触发条件。

迁移时也不必一次重构全仓库：先选变更最频繁、边界最清楚的一个能力，建立一个浅层 `features/<capability>/`，只暴露必要入口；确认变更定位和依赖方向确实改善后，再迁移下一个。只有单个 feature 内部已经出现多项独立职责时，才继续增加 `model`、`api`、`ui` 等子层。
