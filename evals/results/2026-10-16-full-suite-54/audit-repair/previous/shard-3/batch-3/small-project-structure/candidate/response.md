不建议现在立即引入完整的 feature/domain 分层。

已检查工作区：仓库中没有应用源码、`package.json` 或路由配置，无法确认具体框架和现有目录；因此以下判断基于已知规模——两个页面、十几个源文件。这个规模下，完整分层大概率会产生大量单文件目录、转发入口和没有实际策略的抽象，导航成本高于收益。

## 现在的结构建议

采用“页面归属 + 少量共享能力”的浅层结构，并服从实际框架的路由约定：

```text
src/
  app/                    # 应用入口、路由、全局 provider、外壳
  pages/                  # 若框架已有规定的路由目录，沿用其名称
    first-page/
      FirstPage.*
      FirstPageForm.*     # 仅在它有独立交互职责时拆分
      firstPageApi.*      # 仅该页面使用的数据访问
      firstPageRules.*    # 仅在确有独立业务规则时存在
    second-page/
      SecondPage.*
      ...
  shared/
    ui/                   # 真正跨页面、无业务策略的 UI
    http.*                # 两页共同使用且确实拥有统一请求策略时才建立
```

具体原则：

- 页面负责组装该页面的用例，不要把所有请求、表单状态和业务规则永久堆进页面组件。
- 只服务一个页面的组件、请求和规则与页面共置，不要提前搬入顶层 `features`、`services`、`types`。
- 跨页面复用不等于必须进入 `shared`；只有语义和所有权也确实共享时才提升。
- 不预建空的 `api/`、`model/`、`ui/`、`domain/` 目录，也不为每个文件创建 barrel。
- 保持简单依赖方向：`app/路由 → 页面 → 页面私有能力或 shared`；`shared` 不反向依赖页面。
- 如果两页本身属于同一个小型业务能力，继续保持浅层技术分组也可以；无需为了形式改名为 feature。

例如，给第一页增加一个只影响该页的筛选条件，应该能主要在 `pages/first-page` 内完成。若一次普通修改必须同时穿梭全局 `components`、`hooks`、`services`、`types`，才说明当前分组开始失效。

## 何时触发迁移

出现以下一种强信号，或多种信号持续出现时，再逐步引入 feature/domain 边界：

- 同一业务能力跨越多个页面，并且有自己的状态、规则、请求或错误处理。
- 普通需求反复修改多个顶层技术目录，变更位置难以预测。
- 页面组件开始协调多个相互独立的请求、重试、取消、订阅或提交流程。
- 同一业务规则在多个页面重复，或 UI、校验和数据映射各自保存一份规则。
- `components`、`services`、`types`、`utils` 逐渐成为无法说明准入规则的杂物目录。
- 页面之间开始深层互相导入，出现循环依赖或必须了解对方内部实现。
- 某个能力形成稳定的外部契约，或者开始需要独立负责人、代码分割、测试和交付节奏。

文件数、代码行数、某个组件被使用两次，或者“以后可能会复杂”本身都不是充分触发条件。

迁移时也不必一次重构全仓库：先选变更最频繁、边界最清楚的一个能力，建立一个浅层 `features/<capability>/`，只暴露必要入口；确认变更定位和依赖方向确实改善后，再迁移下一个。只有单个 feature 内部已经出现多项独立职责时，才继续增加 `model`、`api`、`ui` 等子层。

本次是结构判断，没有应用文件可修改，也未改动 `.frontend-architect`。
