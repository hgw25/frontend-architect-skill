结论：先做两项低风险改动——把 `setData` 从“100ms 一次整页 data”改成“100ms 一次最小字段补丁”，并在页面隐藏时停止页面级订阅和 `setData`。保持行情源仍以 100ms 更新，不降低可见页面的刷新频率。暂不引入自研虚拟列表、节流到更低频率或依赖新版宿主的渲染能力。

仓库中没有业务源码，只有指定 Skill 和参考资料，因此以下是可直接执行的实现方案，没有声称已完成代码修改或性能测试。

### 最小实现方案

1. 行情业务状态不要完整镜像到页面 `data`。

   页面 `data` 只保留模板真正使用的字段。缓存、原始响应、订阅对象和计算中间值留在逻辑层或已有 store 中。

2. 每个 100ms 行情批次只调用一次 `setData`，但只传变化路径。

   例如概念上发送：

   ```js
   {
     'rows[12].price': 10.23,
     'rows[12].changeRate': 0.018,
     'rows[87].volume': 138200
   }
   ```

   不再发送：

   ```js
   this.setData(this.data)
   // 或
   this.setData({ rows: rebuiltAllRows })
   ```

   保留每行稳定的业务 ID，并使用宿主支持的稳定列表 key。若排序发生变化，应把“行内容变化”和“顺序变化”分别处理，不能继续用旧索引更新错误的行情。

   不额外等待下一个时间窗，也不把 100ms 改为 300ms，因此业务刷新频率不变。若一次批次内有多个字段变化，将它们合并为同一次语义更新。

3. 页面隐藏时停止“页面消费者”，而不必停止全局行情源。

   - `onHide`：取消页面订阅、禁止后续 `setData`。
   - `onUnload`：执行同一个幂等清理，作为兜底。
   - `onShow`：先从已有 store 获取当前版本快照，再恢复增量订阅。
   - 对已经进入队列的旧回调增加可见性或 generation 校验，避免取消订阅后仍执行一次 `setData`。

   如果行情连接被多个页面共享，只移除当前页面的订阅，不能关闭共享连接。如果业务确实要求隐藏期间持续计算，则让 store 继续接收和归并数据，但不要继续向隐藏页面传输；恢复时一次追平最新快照。

   “取快照”和“开始订阅”之间需要沿用现有 store 的原子订阅能力；若没有，应使用单调版本号避免在恢复窗口遗漏或倒退数据。

4. 不把虚拟列表作为首个改动。

   500 个已挂载节点也可能导致滚动卡顿，但题设尚未证明瓶颈在节点、布局或绘制。只有缩小传输后，真机轨迹仍显示列表布局、绘制或节点数量占主导，才采用各宿主正式支持的虚拟列表/窗口化能力，并单独验证可变行高、滚动位置、快速更新和兼容版本。

5. 为多宿主保留一个很薄的页面发布适配边界。

   适配层只负责：

   - 将业务 ID 映射到当前稳定行位置；
   - 生成该宿主支持的局部更新路径；
   - 执行一次页面更新；
   - 统计调用次数和估算载荷。

   不直接采用某一宿主的新渲染后端、worklet 或实验 API。是否能使用这些能力，必须先根据实际宿主和最低基础库版本建立兼容矩阵。

### 代码层能够验证的内容

| 可验证项 | 建议检查 |
|---|---|
| 更新范围 | 单元测试确认补丁只包含变化且被模板消费的字段 |
| 更新频率 | 每个输入批次至多一次页面 `setData`，没有额外降频 |
| 行身份 | 行更新命中正确业务 ID；排序变化后不会写入旧索引 |
| 生命周期 | `onHide` 后继续推送行情，断言页面 `setData` 调用数不再增加 |
| 恢复正确性 | 隐藏期间多次更新后 `onShow`，页面直接得到最新版本，而不是逐条补播 |
| 清理行为 | 多次 hide/unload 清理安全；旧订阅回调不能发布到新页面实例 |
| 共享资源 | 页面隐藏只解除自己的订阅，不误关其他消费者使用的连接 |
| 数据量趋势 | 在相同输入下记录调用数、字段数和序列化字节估算，比较整页与增量方案 |

序列化字节估算、调用次数和单元测试只能证明执行边界变小、生命周期正确，不能证明真机已经流畅。

### 必须由宿主工具和代表性真机证明的结论

不能仅凭代码、开发者工具或模拟器断言“卡顿已解决”。需要在每个受支持宿主上，用其性能工具和代表性真机比较修改前后：

- 实际跨逻辑层/视图层的消息数量、载荷大小、序列化时间和排队时间；
- 输入到可见反馈的延迟；
- 连续滚动时的掉帧、卡顿帧和帧时间分布；
- 逻辑线程、视图线程或主线程长任务；
- 布局、绘制、节点更新与垃圾回收占比；
- 页面隐藏后的 CPU、内存、网络及页面更新是否真正停止；
- 恢复页面时是否出现数据倒退、白屏、突发补播或明显卡顿。

测试矩阵至少应记录：宿主、基础库版本、渲染后端、操作系统、低/中档真机、屏幕刷新率、发布或性能构建模式、固定的 500 行数据和 10Hz 输入脚本。用同一滚动和输入场景多次比较基线与改后结果。

因此，目前可以合理判断整页高频传输和隐藏页持续发布是应先消除的明显浪费；但它们是否是部分真机输入延迟、滚动卡顿的主要根因，以及是否还需要宿主虚拟列表，只能由上述真机轨迹决定。
