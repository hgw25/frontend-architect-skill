结论：选择 **FLIP 作为重排策略，以 Web Animations API 负责播放和取消**。不为此单独引入动画库。`prefers-reduced-motion`、能力缺失或测量失败时直接无动画完成重排。

当前工作区没有应用源码、依赖清单或测试配置，只有 `.frontend-architect` 指南，因此本次交付是可落地的设计边界，未修改文件，也无法执行项目级验证。

## 技术层级判断

| 方案 | 判断 | 原因 |
| --- | --- | --- |
| 无动画 | 作为降级路径 | 功能正确，但默认情况下相邻卡片瞬移，快速拖拽时难以理解位置变化 |
| CSS transition | 不足以独立实现 | CSS 无法自动插值 DOM 重排产生的布局位置；手工设置位移后再 transition，本质上已经是 FLIP，且连续中断管理较弱 |
| View Transitions API | 不选 | 更适合离散的页面或 DOM 状态切换；频繁重排、持续滚动和连续中断不是它最合适的生命周期 |
| FLIP | **主方案** | 能通过稳定 ID 对应重排前后的几何位置，保持空间连续性，并只播放 `transform` |
| 动画库 | 暂不新增 | 单次 FLIP 加取消管理不值得新增依赖；若项目实际已有支持布局投影、滚动根节点和中断的库，应复用其既有能力 |

FLIP 是几何映射策略，WAAPI 是播放手段，两者不是两套叠加动画。

## 实现边界

建议将职责分成四部分：

1. **排序状态**

   - 稳定卡片 ID 和当前顺序是唯一业务真相。
   - 拖拽控制器只发出语义动作，例如 `move(cardId, beforeCardId)`，不传 DOM 坐标给业务状态。
   - 拖动过程中可更新临时顺序；放下后提交持久顺序。`Escape` 或 `pointercancel` 恢复拖拽开始时的顺序。
   - DOM 顺序必须与视觉、键盘和读屏顺序一致，不能只用 transform 制造“看似重排”。

2. **拖拽控制器**

   - 负责命中目标、指针/触摸/键盘输入及滚动容器自动滚动。
   - 只有目标索引真正变化时才触发重排；原始 `pointermove` 至多每帧处理一次，不能每个事件都读布局。
   - 拖动卡片使用独立 overlay 跟随指针，原位置保留占位；overlay 不参加兄弟卡片的 FLIP，避免两套逻辑同时写同一个 `transform`。

3. **布局动画控制器**

   - 维护 `cardId → HTMLElement` 注册表和 `cardId → Animation` 活跃句柄。
   - 只负责几何测量、动画和清理，不修改排序状态、命中规则或持久化结果。
   - 仅测量受影响区间内、重排前后都存在的卡片。新增、删除或虚拟列表中未挂载的卡片直接跳过。
   - 使用二维 `x/y` 位移，不做 scale，避免文字和图片失真；因此同一边界也可支持可变高度卡片或未来的网格布局。

一次重排的执行顺序为：

```text
目标索引变化
→ 读取受影响卡片当前可见位置
→ 取消旧动画并提交新的语义顺序
→ DOM 提交后、绘制前读取最终位置
→ 计算 first - last
→ 从 translate(deltaX, deltaY) 动画到 none
```

所有旧位置先批量读取，状态和样式再写入，最终位置再批量读取，避免逐卡片交错读写造成布局抖动。

### 快速连续拖拽

新重排到达时：

- 先读取卡片在旧动画中的**当前可见位置**；
- 在同一绘制周期内取消旧句柄；
- 以当前可见位置作为下一次 FLIP 的 First；
- 新动画替换旧动画，而不是进入队列。

这样快速来回拖动不会等待上一段动画结束，也不会从旧动画的逻辑终点突然跳回。动画完成、取消、卸载时均删除句柄和临时样式；最终 DOM 本身始终处于正确位置。

时长应使用项目 motion token；缺少现有 token 时可从约 `120–180ms` 的短 ease-out 开始，再根据真实设备调整。不要永久设置 `will-change`。

### 滚动容器

几何位置按滚动内容坐标计算，而非直接比较两次 viewport 坐标：

```text
contentX = itemRect.left - containerRect.left + scrollLeft
contentY = itemRect.top  - containerRect.top  + scrollTop
```

这能避免 First 与 Last 之间发生滚动时，把滚动距离误认为卡片重排距离。

其他约束：

- 命中检测每帧使用最新 `scrollTop/scrollLeft`。
- 自动滚动由拖拽控制器负责，先更新滚动位置，再进行该帧的命中和重排。
- 普通滚动不触发 FLIP；已有 transform 附着在内容元素上，随容器自然滚动。
- 容器 resize、方向变化或卡片异步改尺寸时，先取消当前动画并保持正确最终布局；除非实测需要，不建立持续的 ResizeObserver 重算系统。
- 初始实现不承诺支持缩放或旋转后的滚动祖先；若产品存在这种布局，应由统一坐标转换或现有拖拽库处理。

### Reduced motion 与可访问性

监听 `prefers-reduced-motion: reduce`：

- 顺序仍立即更新；
- 取消所有正在运行的重排和落点缓动；
- 不启动新的 FLIP；
- 拖动对象仍可一比一跟随指针，因为这是直接操控反馈，不应增加弹簧或惯性。

偏好在拖拽途中变化时也应立即生效。

拖拽之外还应提供“上移/下移”按钮等非拖拽操作，供鼠标、触摸和键盘使用。移动后焦点继续停留在同一张卡片，并在提交或键盘移动时宣布“已移动到第 X 项，共 N 项”；不要在每次指针经过时轰炸读屏通知。

## 验证方案

### 自动化契约

- 纯排序逻辑：首项、末项、向前/向后移动、重复目标和取消恢复。
- 连续重排：上一动画未结束时再次移动，最终 DOM 顺序和状态顺序一致。
- 删除或卸载：活动动画被取消，没有残留 transform 或句柄。
- Reduced motion：顺序即时完成，动画数量为零。
- 键盘/按钮重排：焦点保留在同一稳定 ID，状态通知正确。

测试用户可见顺序和交互结果，不绑定私有组件名或 FLIP 内部数据结构。

### 真实浏览器交互

在项目支持的浏览器中检查：

- 快速跨越多个位置并立即反向拖动；
- 动画过程中放下、按 Escape、触发 `pointercancel`；
- 滚动容器的顶部、中部、底部以及边缘自动滚动；
- 滚动与重排同时发生时，卡片没有额外跳跃；
- 不同高度、长文本、图片卡片以及窄/宽容器；
- 运行中切换 reduced-motion；
- 键盘、触摸和单指非拖拽替代操作。

### 性能证据

使用产品典型和最大可见卡片量，在代表性低端设备与发布构建中记录浏览器性能轨迹：

- 对比关闭动画和启用 FLIP 的同一拖拽路径；
- 确认原始 `pointermove` 没有引发连续同步布局；
- 每次有效重排只有成批的 First/Last 测量，没有逐元素读写交错；
- 动画主要落在合成阶段，没有大面积重绘或长期保留大量图层；
- 检查输入到显示延迟、掉帧、长任务和动画结束后的内存/句柄；
- 以目标设备刷新率和实际 hitch 证据确定门槛，不把固定 `16ms` 当成所有设备的通用结论。

本地 Skill 的“选择最轻机制、显式处理中断、滚动和 reduced motion，并以真实运行时验证”的要求，直接决定了这里采用有明确降级路径的 FLIP，而不是 CSS 快捷方案或更重的动画依赖。
