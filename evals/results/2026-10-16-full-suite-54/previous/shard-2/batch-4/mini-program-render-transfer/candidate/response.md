结论：先做两项局部改动——隐藏页停止页面级工作；可见页保持 10Hz 更新频率，但只传递变化字段。暂不引入虚拟列表、工作线程或宿主专用渲染能力，因为当前还没有证据证明瓶颈在节点数量或绘制阶段。

工作区除 `.frontend-architect` 外没有业务源码，因此这里不能给出已落库的文件修改或声称测试通过；下面是可直接实施和验收的方案。

## 最小方案

### 1. 收回隐藏页面的生命周期

明确订阅的所有者：

- 如果行情订阅只服务这个页面：`onHide` 取消订阅、清理刷新定时器，`onShow` 重新订阅并拉取一次最新快照。
- 如果其他页面或全局逻辑在隐藏期间仍必须保持实时：订阅留在全局行情服务，`onHide` 只解除该页面的监听并停止 `setData`；`onShow` 重新监听并一次性同步当前快照。
- `onUnload` 做最终清理。
- 用递增的生命周期标记拦截已经排队、但在页面隐藏后才执行的刷新，保证隐藏期间 `setData` 次数为零。

这样不会降低可见页面的行情实时性，也不会把“后台持续接收”错误地等同于“隐藏页面持续渲染”。

### 2. 保持 100ms 节奏，缩小 `setData` 传输

不要再执行类似：

```js
this.setData(this.data)
```

改为：

- 非渲染数据放在页面实例字段或行情服务中，不进入 `data`。
- 按稳定的行情 ID 维护逻辑层快照。
- 每次行情到达仍按原有 100ms 节奏处理，不把 10Hz 降成更低频率。
- 一个周期内合并为一次 `setData`，只传实际变化的展示字段，例如：

```js
{
  'rows[12].price': next.price,
  'rows[12].changeRate': next.changeRate,
  'rows[301].volume': next.volume
}
```

- 列表项使用稳定业务 ID 作为 key，不使用数组下标作为身份。
- 当增删、排序或分组变化导致索引映射失效时，整体更新 `rows`，但仍不要传整个页面 `data`。
- 如果单次绝大多数行都变化，数百个动态路径可能比一次 `rows` 传输更贵。保留一个很小的策略边界：“稀疏变化传字段，结构变化或密集变化传 `rows`”。阈值根据各宿主测量配置，不写死一个跨宿主通用数字。

建议的生命周期骨架是：

```js
Page({
  data: {
    rows: [],
  },

  onLoad() {
    this._active = false
    this._generation = 0
    this._snapshotById = new Map()
  },

  onShow() {
    this._active = true
    const generation = ++this._generation

    this._detach = quoteService.subscribe(update => {
      if (!this._active || generation !== this._generation) return
      this.applyQuoteUpdate(update)
    })

    this.replaceRows(quoteService.getSnapshot())
  },

  onHide() {
    this._active = false
    this._generation += 1
    this._detach?.()
    this._detach = null
    this.cancelPendingFlush()
  },

  onUnload() {
    this.onHide()
  },
})
```

具体生命周期名称和订阅 API 应沿用项目及目标宿主的现有契约。

### 3. 先不做的事情

首轮不要直接：

- 自研虚拟列表；
- 把 500 行分页而改变现有展示语义；
- 引入 worklet、渲染线程脚本或某一宿主的新渲染引擎；
- 用开发者工具中的流畅度宣告优化完成。

如果缩小传输并清理隐藏生命周期后，真机证据仍显示布局、绘制或节点维护占主导，再评估各宿主官方支持的虚拟列表。500 行本身不足以证明必须虚拟化。

## 代码层能够验证的内容

可以通过单元测试、生命周期测试和开发期计数器确认：

- 隐藏后页面订阅已解除，待执行刷新被取消，迟到回调不会调用 `setData`。
- 显示后只恢复一次订阅，并先提交一份当前快照。
- 普通价格变化只生成对应字段路径。
- 未变化字段、非展示业务数据不会进入传输对象。
- 增删或排序变化走完整 `rows` 更新，索引不会指向错误行情。
- 一批变化只产生一次 `setData`，可见状态仍维持原来的 100ms 提交节奏。
- 列表 ID、展示值、排序和涨跌状态与优化前结果一致。
- 开发构建可记录每秒 `setData` 次数、序列化后载荷字节数、字段数，以及隐藏期间调用数；这些适合作为回归边界。

这些检查能证明生命周期和传输契约正确，但“载荷更小”只是中间证据，不能单独证明用户卡顿已经解决。

## 必须由宿主工具和代表性真机证明的结论

以下内容无法由代码审查、模拟器或开发者工具单独确认：

- 输入到界面反馈的延迟是否下降；
- 滚动掉帧、长帧和卡顿时长是否改善；
- 逻辑层到视图层的序列化、队列和传输是否确为主要瓶颈；
- 稀疏路径更新与整体 `rows` 更新的切换点；
- 500 个已挂载节点是否仍造成布局或绘制压力；
- 不同宿主、基础库和渲染后端对动态路径、批处理及生命周期的实际行为；
- 内存、GC、CPU、耗电及后台活动是否改善；
- 某宿主专用虚拟列表或渲染侧能力能否进入公共实现。

应在相同的 500 行数据和 10Hz 行情下，分别测试“持续滚动”和“行情刷新时连续输入”，对比修改前后：

- 宿主支持的最低基础库版本和当前主流版本；
- 每个正式支持的宿主；
- 至少一台受影响的低端或中低端设备，以及一台主流设备；
- 正式或性能分析构建，而非只测调试构建。

记录输入响应延迟、长帧/掉帧、`setData` 次数与载荷、桥接队列或更新耗时、隐藏页 CPU/网络活动和内存变化。只有这些真机前后对比，才能下结论“已解决卡顿”；在此之前，能确认的是代码消除了两个明确的高风险工作源。
