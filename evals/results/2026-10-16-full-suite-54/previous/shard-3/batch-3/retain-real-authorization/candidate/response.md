## 评审结论

**高严重度、应阻断发布：服务端存在对象级越权删除。**

已登录用户可以绕过前端按钮，直接请求其他人的文档 ID。前端隐藏按钮仅是交互提示，不构成授权控制。

### 最小必要修复

在服务端删除边界使用经过认证的会话身份，并将授权条件与删除合并：

```sql
DELETE FROM documents
WHERE id = :documentId
  AND owner_id = :authenticatedUserId;
```

- `authenticatedUserId` 必须来自服务端验证过的会话，不能来自请求体或前端声明。
- 影响 1 行：返回 `204`。
- 影响 0 行：建议统一返回 `404`，避免泄露文档是否存在；若现有 API 明确约定 `403`，可保持该契约，但拒绝后必须确认文档未被删除。
- 如果删除权限不只由所有者决定，应复用现有权限规则，并在同一事务或原子删除条件内执行，避免“先检查、后删除”的权限变更竞态。
- 不需要新增通用 RBAC、权限框架或额外前端鉴权层。

服务端接口应至少从：

```text
deleteDocument(documentId)
```

收紧为表达调用者身份的契约：

```text
deleteDocument(documentId, authenticatedActor)
```

### 前端职责

- 可以继续隐藏无权删除的按钮，但仅作为 UX。
- 不把 `ownerId`、`canDelete` 或当前用户 ID 作为服务端授权凭据。
- 必须处理服务端 `401`、`403/404`；拒绝时保留文档，若使用乐观删除则恢复列表项并提示权限已变化。
- 删除成功后再以服务端结果更新界面。
- 若列表接口已经返回服务端计算的 `canDelete`，优先使用它；若没有，不必为本次修复扩建权限查询机制。未来增加管理员或协作者删除权限时，再让服务端能力字段成为展示规则来源。

### 必要验证

至少增加服务端集成测试：

1. 用户删除自己的文档成功。
2. 已登录用户直接请求删除他人的文档，被拒绝且目标文档仍存在。
3. 不存在的文档符合既有 `404` 契约。
4. 若认证中间件尚无覆盖，补充未登录请求返回 `401`。

验收标准不是“按钮看不见”，而是构造直接 HTTP 请求也无法删除无权操作的文档。
