## 结论

个人主页应以 `userId` 为唯一导航与请求标识，直接展示服务端返回的 `applications`。前端不再按“仅公开”过滤，也不能把 `developerLogin` 当成 `userId`。

当前工作区没有 Vue 源码、路由配置、API 类型或测试文件，因此下面是可直接落地、但需按实际目录和现有数据请求方案对位的最小实施设计。

## 身份与路由

| 概念 | 标识 | 用途 |
| --- | --- | --- |
| 被查看用户 | `userId` | 个人主页路由、`GET /users/{userId}` |
| 当前查看者 | 登录态中的用户身份 | 由现有 API 客户端携带凭证；参与缓存隔离 |
| 应用作者 | `developerLogin` | 开发者署名或开发者页面入口 |

新增公开可深链路由：

```text
/users/:userId
```

建议路由名为 `user-profile`，`userId` 按不透明字符串处理，不尝试解析成用户名或 `developerLogin`。同一组件需要响应参数变化，例如从 `/users/A` 导航到 `/users/B` 时重新请求。

“我的主页”入口只能使用登录态中明确提供的当前 `userId`。如果登录态没有该字段，不能用 `developerLogin` 猜测，应先补认证会话契约。

## 数据流

```text
route.params.userId
        ↓
个人主页页面/现有请求 composable
        ↓
GET /users/{userId}（现有客户端自动携带查看者凭证）
        ↓
{ profile, applications }
        ↓
用户摘要 + 应用列表
```

关键规则：

- 只调用这一条聚合接口，不再请求公开应用列表后做客户端拼接。
- `applications` 是“当前查看者可见的应用”，不是“公开应用”。
- 本人响应中的私有应用必须正常渲染；前端不得再执行 `filter(public)`。
- 是否有权获取私有应用完全由服务端决定。前端隐藏内容不能补救服务端越权返回。
- 如果应用 DTO 已有可见性字段，私有应用显示 `Private` 标识；如果没有，先正常展示，但不能通过列表位置、作者或当前用户关系猜测可见性。
- 页面保留明确的加载、空列表、404、请求失败及重试状态。

这个接口的响应会随查看者变化，因此缓存不能只考虑目标 `userId`。应复用项目现有认证缓存策略：

- 若认证切换会统一清除敏感查询，可继续使用以目标 `userId` 为主的查询键。
- 否则查询键至少包含查看者作用域，例如 `['user-profile', viewerUserId ?? 'anonymous', userId]`。
- 登出或换号后必须保证本人的私有应用不会从旧缓存继续显示。
- 若现有请求层没有竞态保护，应取消旧请求或阻止旧 `userId` 的响应覆盖新页面。

## 作者入口

应用作者只有 `developerLogin`，所以：

- 若产品已有开发者主页路由，署名链接到该开发者路由。
- 若没有开发者主页，最小方案是展示不可点击的 `developerLogin`。
- 绝不能链接到 `/users/{developerLogin}`，也不应增加客户端查询或维护映射表。
- 如果产品要求“点击作者进入用户个人主页”，当前接口契约无法支持；服务端需明确增加 `authorUserId` 或直接提供类型化的作者导航目标。

这也意味着“用户主页”和“开发者主页”应保持两套路由语义，即便某些人同时拥有两种身份。

## 页面最小形态

视觉参考 GitHub，但不照搬其领域模型：

- 宽屏：左侧用户摘要，右侧应用列表。
- 窄屏：用户摘要在上，应用列表在下。
- 使用项目已有头像、链接、列表、徽标和骨架屏组件。
- 只展示接口真实提供的资料字段，不为了贴近 GitHub 虚构 followers、贡献图等数据。
- 每个应用项展示现有 DTO 能支持的标题、描述、作者和可见性；不引入新的详情请求。

## 实现顺序

1. 修正契约来源  
   将 OpenAPI/接口描述改为“`applications` 为当前查看者可见的应用，本人可能收到公开和私有应用”，然后按项目流程重新生成客户端。不要只手改生成文件中的旧注释；若契约源在其他仓库，则记录对应修改并以已确认的产品契约实施前端。

2. 打通最小纵向流程  
   注册 `/users/:userId`，读取路由参数，调用现有 API 客户端，并直接渲染 `profile` 与 `applications`。

3. 处理身份相关生命周期  
   对路由参数变化、请求竞态以及登录、登出、换号后的缓存失效进行处理。

4. 完成 GitHub 风格布局和状态  
   添加响应式双栏/单栏布局，以及加载、空、404、失败、重试状态。

5. 接入作者入口  
   仅使用 `developerLogin` 进入已有开发者页面；没有对应页面则保持纯文本。

## 验收方式

服务端契约验收：

- 准备包含一个公开应用和一个私有应用的用户。
- 本人请求 `GET /users/{userId}`，响应包含两者。
- 匿名或其他用户请求同一 URL，响应只包含服务端允许其查看的应用。
- 验证授权发生在服务端，而不是依赖前端过滤。

前端集成验收：

- 访问 `/users/{userId}` 能展示 profile 和响应中的全部应用。
- 本人响应中的私有应用不会被客户端丢弃。
- 非本人页面不会额外请求私有应用或尝试自行判断权限。
- 从用户 A 快速切换到用户 B，A 的迟到响应不会覆盖 B。
- 本人查看后登出或换号，旧缓存中的私有应用立即不可见。
- 深链刷新仍能打开同一用户主页。
- 作者链接只进入开发者身份对应的已有路由，绝不生成 `/users/{developerLogin}`。
- 空列表、404、网络失败与重试均有可理解的页面反馈。
- 在桌面和窄屏真实浏览器中检查布局、键盘访问、焦点样式和长文本换行。

其中，前端 mock 测试只能证明“页面忠实渲染响应”；私有应用是否真正安全，必须由服务端授权集成测试证明。当前仓库没有可执行的应用或测试，因此以上检查尚未实际运行。
