## Earlier timed-out partial output

The original 900-second timeout remains an **invalid/incomplete capture**, not a quality baseline. Its partial host run was 5/6. A separate replay reproduces that failure. The default-open hydration fixture renders an **empty, unstyled** content div: browser measurement is width 1264, height 0, while that very dialog is focused, its ID matches the trigger, and no hydration error is reported. Supplying consumer text makes the visibility check pass, then exposes a second test issue: default role querying correctly excludes the background trigger under `inert`/`aria-hidden`.

In a diagnostic copy, adding consumer text and allowing hidden-role lookup **only for the trigger's ARIA relationship assertion** yields **6/6** unchanged behavior/ID/focus/error assertions. Primitive source is unchanged. This corrects the test fixture and metadata lookup; it does not require exposing the inert trigger to assistive technology or weakening the visibility/focus checks. Evidence: `timeout-dom-probe.json`, `timeout-checks.json`, `timeout-*.log`, and two narrow patches. The experiment identifies the partial output's browser failures; the original generation still exceeded its time budget and never produced a completed delivery.

## Environment versus generated code

Historical generator logs show Chromium denied at startup by macOS sandbox Mach IPC; that is a generation-environment limitation before assertions. Host replay launches Chromium and runs checks. The generated serverless harness adaptations introduced the old-guide build/transform defects; environment pressure explains the context but does not make those generated defects correct. No shared web server is configured in either historical generated Playwright config, so port collision is unsupported for these failures.

The focus defect was reproduced using the unchanged built output and then the original test command. The diagnostic source correction is evidence for the mechanism, not a general prescription for every overlay's pointer semantics. Callback cancellation, alternative focus targets, all nested outside interactions, multiple documents and other engines were not exhaustively verified by it.

The corrected probe explicitly waits for visible Dialog and focused input before both interventions; this is a diagnostic correction, not an evaluation-score replacement.
- The corrected historical hydration test covers its closed server shell followed by opening. It does not prove default-open hydration, every React/browser version, SSR ID stability across every consumer tree or release readiness.
- These experiments identify mechanisms in specific outputs. They cannot alone establish that guide compression caused the implementation failure. First attempts and repeated fresh Dialog generations in the complete comparison are needed to assess whether the final guide shows persistent differences.

Status: historical mechanisms, the fresh recovery, and both registered Dialog repeats are complete. Original failures and invalid captures remain preserved.

The evaluation feedback boundary also matters: the generator's sandbox can deny browser startup, while the parent runner checks the finished output on the host **after the generator has returned**. These captures do not test the generator receiving a host failure log and independently completing another repair turn. Manual causal experiments prove specific mechanisms; they do not replace that unperformed agent repair-loop test or excuse a failing submitted implementation. That workflow limitation is recorded rather than attributed to guide wording alone.

## Fresh 151-line output: a rejected coverage hypothesis

The fresh candidate's source `index.html` has an empty root, but its Vite `transformIndexHtml` plugin renders `App` with `renderToString` and injects that markup into the **built** HTML. Replaying the submitted test helper against that unchanged build records one root child before client execution and `hasChildNodes() === true`; the entry selects `hydrateRoot`. The submitted browser checks also run in the generator's recorded events and pass again on the host (3/3).

An earlier reviewer inference that these tests only selected `createRoot` omitted the build transformation and was incorrect. It is withdrawn, not counted as a candidate defect. Evidence is retained in `fresh151-hydration-coverage-probe.json` and hashed `inputs/fresh151/`; source, build plugin, built HTML and test helper must be traced together. This proves the selected closed-shell hydration path, not every initial-open/framework/engine/assistive-technology combination or broad release readiness. Historical initial-150 claims remain a separate output with separate missing hydration evidence.

The first fresh Dialog captures also expose a v7 audit problem. Candidate's successful metadata-only command chain becomes recognized under the narrowly tested v8 repair; previous's ordinary content diff remains unknown. Uniform re-audit and fresh scoring are complete: current 151-line initial output is valid and target (16/16); the previous initial capture remains invalid. Host check success alone is not a validity or whole-contract verdict.

## Fresh 276-line recovery: the implementation defect also appears with the long guide

The single registered recovery generation under the previous **276-line** guide fails one of its four original browser tests: outside pointer dismissal leaves focus on `body`, rather than on the trigger. Replaying the unchanged source in a diagnostic copy reproduces **3/4**. The event trace records focus restoration to the trigger followed by native mouse default behavior moving it away. Canceling only that outside pointer default retains the trigger; adding the corresponding one-line diagnostic source correction after the consumer cancellation check makes the **same four original tests 4/4**. No original artifact or assertion was changed. See [recovery inputs, hashes and commands](recovery276/results.json), [event trace](recovery276/trace-false.json), [controlled trace](recovery276/trace-true.json), and [diagnostic patch](recovery276/focused-diagnostic.patch).

This is the same concrete event-order mechanism found in the historical initial-150 output. Its appearance under the long guide rules out treating it as unique to compression. Both guides already require full interaction and evidence boundaries; execution did not reliably satisfy that contract. The evidence supports an implementation defect and an incomplete verification/feedback workflow, not a proven missing universal pointer rule in the skill. Full nested interactions, callback variants, all engines and assistive technology remain unverified.

The recovery's ordinary project diff explicitly excludes `.frontend-architect`; audit implementation 8.0 nevertheless rejected it as an unknown guidance read. The narrowly tested 8.1 correction recognizes only that exact command at the workspace root, gives no read credit, and leaves all **108 initial audit objects unchanged**. Raw recovery logs and the original invalid audit remain preserved. The corrected copy receives its first independent score: **12.8/16, fail**, because `npm run check` actually fails. Audit eligibility correction does not turn the implementation failure into a pass.


## Registered fresh repeats: long guide passes, final 151-line output has a real focus failure

The long-guide repeat passes its complete host check and receives **13.6/16, target**. It covers the original focus/keyboard/nested interactions plus an initially-open `hydrateRoot` fixture. Additional no-Trigger controlled opening, dynamic external nodes, all container/cancellation combinations and a complete release matrix are not independently verified. The empty server shell in that exact deferred-Portal tree is not evidence that `hydrateRoot` was skipped.

The final **151-line** repeat completes generation normally but is formally **invalid**: one `sed` guidance read fails to create a unified exec process (`os error 2`), then the identical read immediately succeeds. Frozen guidance is intact. This is a recorded execution/capture problem; its lower-level CLI/cwd cause is not isolated, and this protocol does not forgive it or generate another favorable sample. No normalized quality score is assigned.

Independently of that audit status, the host launches Chromium and gets **3/4 browser tests**: overlay dismissal closes the Dialog but fails trigger focus restoration. An unchanged-source replay, after restoring the package-build precondition, reproduces the failure. A trace records trigger focus restoration followed by native `mousedown` moving focus to body. Canceling the native default **after** the overlay handler requests dismissal retains trigger focus. A one-line diagnostic source change preserves the consumer cancellation hook and makes the **same original full check**, including all four browser tests, pass. Original tests, submitted source and invalid audit are untouched.

Evidence: [results, input hashes and commands](repeat151/results.json), [unmodified replay](repeat151/unchanged-full-check.log), [trace without intervention](repeat151/trace-false.json), [controlled trace](repeat151/trace-true.json), [focused diagnostic patch](repeat151/focused-diagnostic.patch), [same full check after correction](repeat151/focused-fix-same-full-check.log). This does not prove every nested/callback/device/engine combination.

The first diagnostic copy omitted generated dist files and exposed a separate check-order limitation: `npm run check` typechecks a self-package consumer before rebuilding its declared export. Its missing-build checks/probes are excluded from causal inference and retained in [the failed diagnostic setup](repeat151-v1-missing-build/README.md). The corrected replay first runs the original `build:package` command. The original host workspace already had those artifacts; this clean-copy ordering issue is not the cause of its focus failure.

The 151-line repeat response starts with “已完成可发布” while later accurately disclosing that browser startup was denied and browser assertions were not passed. Its SSR/browser-build path is real, but the readiness wording exceeds the available acceptance evidence. This is another observed delivery-judgment reliability issue despite the retained explicit guidance. The shared focus mechanism occurs under both guide versions; no isolated causal experiment proves that compressing the entrypoint caused it. The submitted code is wrong on this path; the harness/capture constraints explain different parts of the record, not that implementation defect.
