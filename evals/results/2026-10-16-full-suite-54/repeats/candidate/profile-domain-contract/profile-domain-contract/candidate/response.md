结论：最小方案应以 `/users/:userId` 作为个人主页地址，页面直接展示 `GET /users/{userId}` 返回的 `profile` 和完整 `applications`。前端不判断查看者是否本人、不自行过滤私有应用，也不能把 `developerLogin` 当成 `userId` 建立作者链接。

当前工作区的 Git 提交树为空，除 `.frontend-architect` 外没有 Vue 源码、依赖配置或测试，因此以下是可直接落地的设计决策，但无法给出真实文件名或运行项目验证。

## 身份与接口契约

| 概念 | 标识 | 前端用途 |
|---|---|---|
| 用户 | `userId` | 个人主页路由和 `/users/{userId}` 请求 |
| 开发者 | `developerLogin` | 应用作者署名 |
| 查看者 | 当前会话身份 | 由现有 HTTP 鉴权机制发送，服务端据此裁剪应用 |

确认后的契约是：

- 匿名或其他用户查看时，服务端只返回允许其查看的应用。
- 本人查看时，服务端返回公开和私有应用。
- 前端把 `applications` 视为“当前查看者可见的应用集合”，原样渲染。
- 不增加 `includePrivate` 参数，不根据登录用户和路由用户在客户端做授权判断。
- 列表数量、空状态都从返回的 `applications` 推导，不能使用可能代表全部应用的其他计数代替。
- 如果应用数据已有公开性字段，可显示“私有”标记；没有该字段时不能靠猜测标记。

旧生成注释已被产品确认和当前服务端行为推翻。应修改 API schema、生成器输入或其他权威契约来源，再按项目流程重新生成类型；不要只手改生成文件。注释建议表达为：

> `applications` contains the applications visible to the current viewer.

## 路由

新增具名路由，语义为：

```text
/users/:userId
```

具体实现沿用项目现有 `vue-router` 注册和懒加载方式。路由参数是用户域的 `userId`，应作为不透明字符串处理，不接受 `developerLogin` 作为替代值。

页面行为：

- 参数缺失或不符合已有 `userId` 约束：进入现有非法路由/404 流程。
- 用户不存在：展示现有 404 页面或页面级不存在状态。
- 请求失败：保留明确错误和重试入口。
- 从 `/users/A` 导航到 `/users/B` 时重新请求，并取消旧请求或忽略过期响应，避免 A 的慢响应覆盖 B。
- 页面标题在加载成功后使用返回的用户展示名；具体格式沿用项目现有标题规则。

如果现有登录会话已经提供当前用户的 `userId`，可以从账户菜单增加“个人主页”入口。若会话只有开发者身份或只有 `developerLogin`，本次不增加该入口。

## 数据流与所有权

建议保持一条短而完整的链路：

```text
路由 userId
  → 个人主页页面/页面 composable
  → 现有 HTTP 客户端调用 GET /users/{userId}
  → { profile, applications }
  → 页面加载状态
  → Profile 区域 + Application 列表
```

边界划分：

- API 适配层拥有 URL 构造、响应类型和错误映射。
- 页面拥有路由切换、加载、成功、失败和重试状态。
- 展示组件只接收 `profile` 或 `applications`，不读取登录状态、不决定可见性。
- 不为这个单页先建设全局用户 store；除非仓库已有统一查询缓存，否则页面级状态足够。
- 若已有查询缓存，缓存必须区分查看者身份，或在登录、退出、切换账号时失效。因为同一 `/users/{userId}` 会随查看者返回不同结果，不能把本人看到的响应复用给匿名或其他用户。
- 请求凭证交给现有 HTTP 客户端统一处理，页面不要自行拼接令牌。

页面状态可保持为一个互斥状态，而不是多组可能冲突的布尔值：

```ts
idle | loading | success(data) | error(error)
```

## 作者入口

当前不能从作者署名进入用户个人主页。原因是：

```text
developerLogin ≠ userId
```

最低风险实现为：

- 继续把 `developerLogin` 显示为作者署名。
- 若项目已有“开发者主页”且明确以 `developerLogin` 寻址，可保留那个入口。
- 不生成 `/users/${developerLogin}`，也不在前端维护猜测式映射。
- 没有既有开发者页时，作者署名暂时为文本，不伪装成可点击链接。

未来要提供用户主页入口，应由服务端返回明确关联，例如 `authorUserId` 或 `author.userId?: string`。前端届时只在该字段存在时生成 `/users/:userId` 链接。这个可选字段就是足够的小型扩展点，无需现在建设身份映射系统。

## 页面布局

视觉参考 GitHub，但复用项目现有设计系统，不引入新的 UI 依赖：

- 桌面端：左侧个人资料摘要，右侧应用列表。
- 窄屏：资料区在上、应用列表在下。
- 资料区展示接口实际提供的头像、名称、简介和元数据，不虚构字段。
- 主列表标题使用“应用”，避免写成“公开应用”。
- 每个应用使用语义化标题链接、简介和现有元数据；有可靠可见性字段时显示低强调度的“私有”标记。
- 分别处理加载骨架、零应用、请求失败和用户不存在。
- 只有一个内容区域时不复制 GitHub 的标签页、贡献图或统计模块。

## 验收方式

核心验收矩阵：

- 匿名查看用户：只渲染服务端返回的公开应用。
- 其他登录用户查看：仍只渲染服务端允许的应用。
- 本人查看：公开和私有应用全部出现，私有应用不会被前端过滤。
- 同一路径先以本人访问、再退出或切换账号：旧的私有数据不会从缓存残留。
- 快速从用户 A 切换到用户 B：最终只显示 B，慢返回的 A 不覆盖页面。
- 不存在的 `userId` 显示 404；网络错误可重试；空数组显示正常空状态。
- 只有 `developerLogin` 的作者署名不会链接到 `/users/{developerLogin}`。
- 直接打开、刷新以及前进/后退 `/users/:userId` 均能恢复正确页面。
- 桌面与移动视口无溢出；头像替代文本、标题层级、链接焦点和键盘操作可用。

自动化测试应重点覆盖 API 适配、路由参数变化、响应竞态和三种查看者返回结果；最终权限正确性必须由服务端契约或端到端测试证明，前端组件测试只能证明“没有再次过滤服务端结果”。由于工作区没有应用文件，本次未修改代码，也未运行 Vue 构建或测试。
