## 结论

采用“单写入路径 + 共享幂等凭证 + 可查询结果 + 服务端熔断开关”的迁移方式。任何一次预订意图只能写入旧接口或新接口之一，绝不做双写，也不在超时后自动切换接口重试。

如果旧、新接口不能共享幂等记录，或不能按幂等键查询最终结果，新接口不得进入真实流量。这不是前端禁用按钮可以补足的保障。

当前工作区只有 `.frontend-architect` 与 Git 元数据，没有应用源码、接口定义、测试或发布配置。因此下面是需要落到实际系统的契约与执行方案，没有假设具体框架或现有能力。

## 1. 兼容边界

页面只依赖一个稳定的领域接口，例如：

```ts
confirmBooking(
  submittedDraft: BookingRequest,
  context: {
    operationId: string
    route: 'legacy' | 'next'
  }
): Promise<BookingOutcome>
```

`BookingOutcome` 只暴露统一语义：

- `confirmed`：包含预订号、最终金额、币种、服务端状态版本。
- `rejected`：库存变化、价格变化、输入无效、权限失败等明确终态。
- `pending`：服务端已受理但尚未完成。
- `unknown`：客户端不知道写入是否成功，不能视为失败。
- `systemFailure`：服务端明确保证未创建预订时才可使用。

旧、新接口分别由 adapter 完成字段和错误映射。页面状态机、埋点、重试逻辑不感知接口版本。

兼容契约还需明确：

- 金额使用币种加最小货币单位，不用浮点数。
- 日期时间携带时区；`null`、缺失值、空字符串不能互相默默转换。
- 提交使用点击瞬间的不可变快照，后续编辑不能改变正在重试的请求。
- 库存或报价使用服务端签发的版本/quote token，服务端重新校验价格、权限、租户和库存。
- 未知的新字段可忽略；未知状态和错误码必须进入 `unknown`/不可恢复错误，不能默认成成功。
- 旧页面、缓存中的旧 bundle、当前及前一版本 adapter 都要纳入契约测试。

路由选择在一次操作开始时固定。功能开关后续发生变化，也不能让同一个 `operationId` 从新接口跳到旧接口。

## 2. 幂等与重复提交

幂等键代表“一次用户预订意图”，而不是一次 HTTP 请求：

1. 用户首次确认时生成高熵 `operationId`，在请求发出前保存。
2. 同一次操作的超时重试、刷新恢复和状态查询始终使用原键。
3. 只有上一次操作到达明确终态，且用户明确开始新的预订时才生成新键。
4. 不用表单内容哈希作幂等键，否则用户有意重复预订时无法区分。
5. 前端 pending 状态禁用按钮，并在事件处理入口再次防重入；多标签页可用 `BroadcastChannel` 或现有跨标签能力提示冲突，但这些都不是最终保障。

服务端必须保证：

- 旧、新接口共享同一幂等注册表，或共同经过一个兼容网关。
- 幂等范围至少绑定认证主体、操作类型和 `operationId`。
- 首次写入原子地登记键与请求摘要；相同键、相同请求返回原结果。
- 相同键、不同请求返回明确冲突，绝不创建第二笔。
- 下游支付或供应商调用也复用该键，或在调用前持久化可恢复状态。
- 幂等记录保留期覆盖最长重试、客服处理和异常恢复窗口。
- 提供按 `operationId` 查询 `PENDING / SUCCEEDED / REJECTED / NOT_FOUND` 的权威接口。

## 3. 错误恢复

页面状态应显式建模：

```text
editing
  -> submitting
      -> confirmed
      -> rejected
      -> reconciling
          -> confirmed
          -> rejected
          -> stillPending
          -> recoveryRequired
```

关键处理规则：

- 网络断开、超时、页面关闭和客户端取消都不证明服务端没有执行。
- 出现未知结果时，页面显示“正在确认预订结果”，保留原操作键并查询权威状态。
- 状态仍为 `PENDING` 时有限退避轮询；到达时限后提供继续查询或联系客服，不重新创建。
- 只有共享幂等契约已经验证时，才允许使用同一个键重试原提交。
- 不自动把失败的新接口请求 fallback 到旧接口。
- 刷新后只恢复不敏感的 `operationId`、路由版本和开始时间，再从服务端取状态；不在浏览器持久化旅客、证件、支付或完整行程数据。
- 回到页面、切换账号或路由变化时，旧请求的成功、失败和 `finally` 都不能覆盖当前状态。
- 已确认结果必须显示稳定预订号，避免用户因响应慢再次操作。

## 4. 两周灰度方案

比例只在前一阶段满足门槛后提升，不按日期强推。

| 阶段 | 建议时间 | 新接口流量 | 重点 |
|---|---:|---:|---|
| 准备 | 第 1–2 天 | 0% | adapter、契约测试、共享幂等、结果查询、仪表盘、熔断开关 |
| 内部 | 第 3 天 | 员工/测试账号 | 真实页面链路，限定测试库存或可撤销订单 |
| 初始灰度 | 第 4–5 天 | 1% | 低风险业务分段，覆盖一次高峰 |
| 扩大 | 第 6–7 天 | 5% | 浏览器、地区、支付方式等代表性分段 |
| 主灰度 | 第 8–9 天 | 20% | 检查业务转化与未知结果恢复 |
| 半量 | 第 10–11 天 | 50% | 至少覆盖一次完整高峰 |
| 候选全量 | 第 12–14 天 | 100% | 旧接口保持可用，熔断开关继续有效 |

分桶应对用户或租户保持稳定，但最终路由记录在每个 `operationId` 上。开关在提交时从服务端或短 TTL 配置获取，不能只烘焙在静态 bundle 中。

若第 14 天仍未达到退出条件，应延长并存期；不能因为计划到期而删除旧路径。旧 adapter 的删除应作为后续独立变更。

## 5. 生产信号

所有指标必须带 `api_version`、发布版本、灰度 cohort 和可用的非敏感业务分段。

核心正确性：

- 同一 `operationId` 对应多个预订号：目标为零，出现一例立即熔断。
- 同键不同请求摘要、幂等冲突和下游重复扣款。
- `unknown` 比例、最终收敛比例、收敛耗时。
- 处于 `PENDING` 超过时限的数量。
- 新旧接口确认率、明确拒绝率和取消率。
- 用户重复点击、刷新恢复、同键重试次数。

可靠性与体验：

- 提交成功率及错误码分布。
- p50/p95/p99 提交延迟。
- 状态查询成功率、轮询次数和恢复成功率。
- 从点击确认到可见预订号的耗时。
- 转化率、提交后退出率、重复预订取消/退款及相关客服工单。

其中“是否真的创建了两笔”必须来自服务端预订记录或下游供应商事实；前端埋点只能辅助诊断。

## 6. 停止与回滚条件

立即停止扩量并将“新操作”切回旧接口：

- 发现任一同幂等键产生多笔预订或重复扣款。
- 新接口绕过幂等注册、状态查询失真，或同键不同载荷仍被执行。
- 授权、跨租户、价格或库存校验出现错误。
- 无法通过监控判断写入是否成功。

自动或值班回滚阈值可先采用以下保守默认值，再用现有 SLO 校准：

- `unknown` 比例超过旧接口基线 2 倍，或绝对增加 0.2 个百分点，持续 10 分钟。
- 确认成功率较同时间、同分段旧接口下降 1 个百分点，持续 15 分钟且样本充足。
- p95 超过既有 SLO，或较基线上升 20%，持续 15 分钟。
- 超时未收敛的 `PENDING` 持续增长两个观察窗口。

回滚只影响尚未提交的新意图。已经发往新接口的操作继续通过共享状态接口收敛，不能改投旧接口。先用熔断开关止损，再决定是否回滚代码；保留相关服务端记录和已脱敏证据用于对账。

旧接口退出至少要求：

- 新接口 100% 流量经过两个代表性高峰。
- 没有重复预订或重复扣款。
- 未知结果率、恢复时间、成功率和延迟均在门槛内。
- 所有旧路径在途操作已终结或仍可查询。
- 回滚演练成功，客服与对账流程已验证。

## 7. 隐私与安全控制

- 埋点使用字段白名单；禁止自由文本错误、完整请求/响应和页面录屏采集预订数据。
- 不记录姓名、联系方式、证件、支付信息、完整行程或服务端会话令牌。
- 关联标识使用随机操作 ID；如需用户级聚合，使用受控的轮换 keyed hash，避免长期跨场景跟踪。
- 运维日志、产品分析与第三方工具分别控制用途、访问权限、采样和保留期。
- 第三方会话回放默认关闭，或对表单、确认页和网络载荷全量屏蔽。
- source map 存放在受控系统，不公开部署。
- 操作 ID 只用于关联和幂等，不能替代认证、授权或 CSRF 防护。
- 服务端继续校验身份、租户、资源归属、价格和库存；前端隐藏按钮不承担授权职责。

验证重点应覆盖：连点、双标签、刷新、超时后服务端成功、乱序响应、灰度开关中途变化、相同键不同载荷、旧 bundle 调新服务端，以及回滚时新接口在途操作的收敛。当前仓库没有可运行实现，因此这些检查尚未执行。
