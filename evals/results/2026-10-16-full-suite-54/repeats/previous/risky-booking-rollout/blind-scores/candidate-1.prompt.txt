CASE

artifact: 
applicable_dimensions: ["requirements_context", "solution_complexity", "runtime_delivery", "security_trust", "operability", "correctness_boundary", "verification_evidence", "communication_quality"]

RESPONSE:
结论：采用“统一预订契约 + 双适配器 + 稳定分流 + 服务端共享幂等”的迁移方式。任何一次预订只写一个接口；超时后不得自动切换接口。若旧、新接口无法共享幂等记录或权威状态查询，两周灰度不应开始，因为前端防重无法消除重复预订风险。

工作区只有 `.frontend-architect` 指导文件，没有应用代码、接口契约或现有 SLO，因此下面是可执行设计，不虚构具体框架或既有能力，也未修改文件。

## 1. 兼容边界

页面只依赖一个稳定接口，例如：

```ts
type SubmitBookingCommand = {
  bookingIntentId: string;
  operationId: string;
  snapshot: BookingInputSnapshot;
};

type BookingOutcome =
  | { status: "confirmed"; bookingReference: string }
  | { status: "rejected"; reason: RejectionReason }
  | { status: "pending" };

interface BookingGateway {
  submit(command: SubmitBookingCommand): Promise<BookingOutcome>;
  getOperation(operationId: string): Promise<BookingOutcome>;
}
```

内部结构：

```text
确认页
  -> BookingSubmissionCoordinator
       -> 稳定分流器（一次 intent 只决定一次）
            -> LegacyBookingAdapter
            -> NewBookingAdapter
```

边界规则：

- 两个适配器负责请求字段、响应字段和错误码映射，页面不感知版本差异。
- 在网络响应进入应用时做结构校验；协议不匹配必须成为可观测错误，不能降级成“空数据”。
- 统一至少三类业务结果：确认成功、明确拒绝、仍在处理。
- 网络超时、连接中断和部分 5xx 归为“结果未知”，不能解释成预订失败。
- 价格、库存、身份、权限仍由服务端权威校验。
- 不做生产双写；若需要影子验证，只允许调用明确无副作用的校验或 dry-run 接口。

这也给后续第三种数据源留下了低成本扩展点：新增适配器和路由规则即可，不需要重新修改页面状态模型。

## 2. 幂等与重复提交

必须先落实以下服务端契约：

1. 前端在用户首次确认时创建随机 `operationId`，同一次逻辑提交的所有重试保持不变。
2. `bookingIntentId` 由服务端创建并绑定用户、报价/库存上下文及有效期。
3. 旧、新接口共同识别同一幂等记录；否则在它们前面增加共享的 BFF/网关幂等层。
4. 相同 `operationId` 和相同请求指纹必须返回同一个预订结果。
5. 相同 `operationId` 携带不同请求内容必须被拒绝，不能创建第二笔预订。
6. 并发请求的去重必须是原子的，不能只是“先查再创建”。
7. 提供按 `operationId` 查询最终状态的权威接口。
8. 幂等记录的保存期至少覆盖允许恢复和人工处理的最长时间；建议最低 24 小时，最终值应由实际业务恢复窗口决定。

前端同时做体验层防重：

- `submitting`、`pending`、`unknown` 状态下禁用确认按钮，并对事件处理函数增加同步重入保护。
- 保存不可变的提交快照；重试使用原快照，不能把用户后来修改的表单静默塞进旧操作。
- `sessionStorage` 只保存 `operationId`、`bookingIntentId`、分流版本和时间，不保存姓名、证件、联系方式等预订内容。
- 页面刷新后发现未完成操作，先查询状态，不创建新操作。
- 多标签页协调可以减少误操作，但不能代替服务端幂等。

## 3. 提交状态与错误恢复

建议显式状态机：

```text
draft
  -> submitting
       -> confirmed
       -> rejected
       -> pending
       -> unknown
unknown/pending
  -> reconciling
       -> confirmed
       -> rejected
       -> pending
```

恢复策略：

| 情况 | 前端行为 |
|---|---|
| 明确业务拒绝，且服务端保证未创建预订 | 保留表单，展示可修正原因，允许创建新的提交操作 |
| 成功返回 | 展示确认号，只在此时刷新相关缓存和进入成功页 |
| 返回处理中 | 轮询权威状态接口，采用退避和总时限 |
| 超时、断网、响应丢失 | 显示“正在确认，请勿重新预订”，先按原 `operationId` 对账 |
| 对账仍无结论 | 保留未知状态与匿名支持参考号，不显示“失败，请重试” |
| 用户主动重试 | 仅在服务端允许时，用原快照和原 `operationId` 重放 |
| 灰度开关中途改变 | 已开始的操作继续使用原分流；只影响新的 booking intent |

禁止的行为：

- 超时后生成新幂等键。
- 新接口失败后自动改写旧接口。
- 仅凭取消 `fetch` 就认定服务端没有执行。
- 未对账便恢复按钮并提示重新预订。
- 用乐观“预订成功”替代服务端确认。

## 4. 两周灰度方案

分流单位是 `bookingIntentId`，分配结果在操作开始时固化。分流配置应来自可快速更新的远程配置或服务端，不使用每次请求重新随机的客户端百分比。

| 时间 | 新接口写流量 | 前提与动作 |
|---|---:|---|
| 第 1–2 天 | 0% | 发布兼容层、状态机、埋点、对账与 kill switch；验证旧路径行为不变 |
| 第 3 天 | 内部/测试账户 | 真实端到端小流量，验证重复请求和响应丢失场景 |
| 第 4–5 天 | 1% | 覆盖一个业务高峰；对照旧接口同期数据 |
| 第 6–7 天 | 5% | 检查地区、平台、登录状态、库存提供方等主要分段 |
| 第 8–9 天 | 25% | 观察恢复队列、客服反馈和尾延迟 |
| 第 10–11 天 | 50% | 保留等量或稳定的旧接口对照组 |
| 第 12 天 | 100% | 新操作全部走新接口，旧接口仍保留为 kill switch |
| 第 13–14 天 | 100% | 至少观察一个完整高峰周期，处理所有未决操作 |

每一步按证据推进，而不是到时间自动放量。若样本不足、遥测缺失或未经历代表性高峰，就保持当前比例。

第 14 天只停止旧接口接收新操作。删除旧适配器、灰度代码和开关应作为后续独立改动，并等到所有旧路径未决操作清零、幂等保存期结束后进行。

## 5. 生产信号

必须按接口版本、配置版本和前端版本对比，并保留分母：

- 权威重复预订数：同一 `bookingIntentId` 对应多个 booking ID。
- 预订确认率及明确拒绝率。
- `unknown` 结果率、未决时长、最终恢复成功率。
- 幂等重放率及“同键不同载荷”冲突数。
- 用户重复点击次数，但不能把它当作重复预订的替代指标。
- 请求成功率、超时率、错误分类、p50/p95/p99 延迟。
- 响应结构校验失败数。
- 从确认到得到确定结果的耗时。
- 客服侧“重复预订”和“扣款/预订状态不明”工单。
- kill switch 配置生效时间与客户端配置滞后率。

服务端重复检测应不采样；高容量性能 trace 可以采样。安全告警不能依赖用户可能拒绝的产品分析 SDK。

## 6. 回滚条件与动作

由于仓库没有现有基线，不能假装给出已有 SLO。建议使用以下初始门槛，发布前用最近七天旧接口数据校准：

立即将“新操作分流比例”降至 0%：

- 发现 1 个经服务端确认、可归因于新路径的重复预订。
- 出现越权、跨租户数据、敏感信息泄露或幂等键串单。
- 新接口产生无法通过状态查询确认的写入，而恢复路径失效。
- 响应契约变化导致成功与失败可能被误判。

停止继续放量并调查：

- `unknown` 比例连续 10 分钟超过旧接口两倍，且绝对差超过 0.2 个百分点。
- 新接口确认率在足够样本下低于同期旧接口 0.5 个百分点以上。
- p95 延迟超过旧接口 1.5 倍并同时突破现有业务 SLO。
- 关键遥测缺失超过 5%，无法判断重复预订风险。
- 未决操作队列持续增长，超过其恢复时限仍未收敛。

回滚只改变新创建的操作：

1. kill switch 将新 intent 路由到旧接口。
2. 已开始的新接口操作保持原路由，并继续通过权威状态接口对账。
3. 不取消或跨接口重放结果未知的请求。
4. 保留适配器、幂等记录、日志关联信息和恢复任务。
5. 若确有重复预订，进入人工核对和补偿流程；前端回滚本身不能撤销已创建的订单。

## 7. 隐私控制

- 埋点采用白名单字段，不上传姓名、电话、邮箱、证件、支付信息、完整请求体或服务端原始错误。
- 不在分析系统中发送原始 booking ID、用户 ID 或 `bookingIntentId`；需要关联时使用有期限的伪匿名标识。
- `operationId` 是随机关联号，不从用户信息派生；访问它的运维日志受权限、审计和保留期控制。
- 将产品分析与必要的运营安全监控分开，重复预订检测优先在服务端聚合完成。
- 对 URL、错误消息、breadcrumbs 和 source-map 上报做字段级脱敏，防止查询参数或表单状态被自动采集。
- 第三方分析脚本不得读取预订表单 DOM 或网络载荷。
- 前端不持有服务凭证；授权和资源归属检查必须由两个接口或统一网关执行。

## 8. 上线前必须通过的验收

- 对旧、新接口并发发送相同幂等操作，只产生一个 booking，并返回同一结果。
- 服务端成功但响应被丢弃时，刷新页面可以恢复到原确认结果。
- 双击、刷新、浏览器重试和多标签页不会生成第二笔预订。
- 灰度配置在请求途中改变，不会改写已有操作的接口归属。
- 相同幂等键配不同载荷会被明确拒绝。
