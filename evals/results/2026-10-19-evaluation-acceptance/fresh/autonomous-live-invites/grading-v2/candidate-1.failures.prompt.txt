# Team invitations: delivery design

## Scope and facts

The page uses native ESM. `src/data.mjs` supplies loaded invitation rows and an
initial overview; `src/transport.mjs` owns HTTP status handling and exposes
`sendInvitation(email)` and `readOverview()`. The browser page owns editable
email and note drafts, invitation display order, presentation state, and the
focus target that a structural redraw would otherwise lose.

Sending is accepted when `sendInvitation` resolves. A successful send always
adds the returned invitation and announces the accepted email, even if the
follow-up overview read fails. Overview failure is independently recoverable
through Refresh overview. Repeated send activation while pending is ignored.
Move controls alter only the in-memory display array and make no transport call.

## Delivery sequence

1. **Submit an invitation** — `draw`'s form handler snapshots the email and its
   edit revision, disables repeat submission, and calls `sendInvitation`.
   Completion appends the returned row and announces acceptance; it clears the
   draft only when it has not been edited since the snapshot. Check: browser
   test sends once, sees the row and live confirmation.
2. **Refresh overview independently** — `refreshOverview` calls
   `readOverview`; it publishes only the latest overview request and gives a
   read failure its own visible error. Check: a rejected overview after an
   accepted send retains the invitation and confirmation; Refresh overview can
   recover it.
3. **Maintain local interactions** — `moveRow` swaps adjacent display rows.
   `captureFocus`/`restoreFocus` preserve a moved row's same button and retain
   the user's current control when asynchronous completion redraws the page.
   Check: keyboard activation can be repeated without refocusing, and a note
   typed during send survives completion.

## Contracts and ownership

- `src/app.mjs`: `refreshOverview()` is the sole overview-effect owner. It
  returns no value; it updates `overview` or `overviewError` only when its
  sequence is current. The form submit listener owns the send request and
  accepted-send state transition. `moveRow(id, delta)` owns display order and
  has no external effects.
- `src/transport.mjs`: unchanged narrow transport contract. A rejected promise
  means that particular request has not produced usable data.
- `emailRevision`: each editable email change increments it. The submit handler
  compares its captured revision before clearing, so a later draft is never
  overwritten by an older completion.
- Focus is described by `{ kind: 'email' | 'note' | 'refresh' | 'submit' |
  'move', id?, direction? }`, rather than a stale DOM node. A draw only restores
  the still-existing target; it does not impose a submit-origin focus after a
  user has moved elsewhere.

## Architecture

```text
Browser form/list controls
       | input, submit, refresh, move
       v
src/app.mjs (page state, transitions, focus preservation)
   | sendInvitation(email)       | readOverview()
   v                             v
src/transport.mjs ------------------> /api/invitations, /api/overview
                                         |
                                         v
                                  accepted invitation / pending count
```

## Representative data flow

```text
Email draft + revision --submit--> sendInvitation(snapshot email)
  --reject--> send error live alert; retain draft
  --accept--> append invitation + success live status
                   |-- if revision unchanged --> clear email draft
                   '--> refreshOverview()
                         |-- success --> overview.pending rendered
                         '-- failure --> overview error rendered; acceptance stays visible

Move button --moveRow(id, delta)--> rows swapped locally --> redraw --> same move button focused
```

## Evolution and verification

An eventual server-side reorder can replace only `moveRow`'s local transition;
the rendering and focus contract remain local. The implementation uses native
labels, buttons, form validation, `role=status`, and `role=alert` so keyboard
and assistive-technology behavior stays with platform controls. Execute the
Playwright consumer suite, including focused regressions for degraded overview
refresh and retained keyboard focus. Final results are recorded below.

## Executed evidence

Implemented in `src/app.mjs`. `npm run check` passed on 2026-10-19: six
Chromium consumer tests cover accepted send and refreshed overview, local-only
reordering, note preservation during explicit refresh, accepted send followed by
failed overview refresh, keyboard focus continuity during repeated moves, and a
note interaction that continues while send completion redraws the page.

function captureFocus() {
  const active = document.activeElement;
  if (!active || !app.contains(active)) return null;

  if (active.dataset.focus === 'email') return { kind: 'email' };
  if (active.dataset.focus === 'note') return { kind: 'note' };
  if (active.dataset.focus === 'refresh') return { kind: 'refresh' };
  if (active.dataset.focus === 'submit') return { kind: 'submit' };
  if (active.dataset.action === 'move') {
    return { kind: 'move', id: active.dataset.rowId, direction: active.dataset.direction };
  }
  return null;
}

function restoreFocus(target) {
  if (!target) return;
  let next;
  if (target.kind === 'move') {
    next = [...app.querySelectorAll('[data-action="move"]')].find(button => (
      button.dataset.rowId === target.id && button.dataset.direction === target.direction
    ));
  } else {
    next = app.querySelector(`[data-focus="${target.kind}"]`);
  }
  next?.focus();
}

function moveRow(id, delta) {
  const index = rows.findIndex(row => row.id === id);
  const nextIndex = index + delta;
  if (index < 0 || nextIndex < 0 || nextIndex >= rows.length) return;
  [rows[index], rows[nextIndex]] = [rows[nextIndex], rows[index]];
}

}

+# Team invitations: delivery design
+
+## Scope and facts
+
+The page uses native ESM. `src/data.mjs` supplies loaded invitation rows and an
+initial overview; `src/transport.mjs` owns HTTP status handling and exposes
+`sendInvitation(email)` and `readOverview()`. The browser page owns editable
+email and note drafts, invitation display order, presentation state, and the
+focus target that a structural redraw would otherwise lose.
+
+Sending is accepted when `sendInvitation` resolves. A successful send always
+adds the returned invitation and announces the accepted email, even if the
+follow-up overview read fails. Overview failure is independently recoverable
+through Refresh overview. Repeated send activation while pending is ignored.
+Move controls alter only the in-memory display array and make no transport call.
+
+## Delivery sequence
+
+1. **Submit an invitation** — `draw`'s form handler snapshots the email and its
+   edit revision, disables repeat submission, and calls `sendInvitation`.
+   Completion appends the returned row and announces acceptance; it clears the
+   draft only when it has not been edited since the snapshot. Check: browser
+   test sends once, sees the row and live confirmation.
+2. **Refresh overview independently** — `refreshOverview` calls
+   `readOverview`; it publishes only the latest overview request and gives a
+   read failure its own visible error. Check: a rejected overview after an
+   accepted send retains the invitation and confirmation; Refresh overview can
+   recover it.
+3. **Maintain local interactions** — `moveRow` swaps adjacent display rows.
+   `captureFocus`/`restoreFocus` preserve a moved row's same button and retain
+   the user's current control when asynchronous completion redraws the page.
+   Check: keyboard activation can be repeated without refocusing, and a note
+   typed during send survives completion.
+
+## Contracts and ownership
+
+- `src/app.mjs`: `refreshOverview()` is the sole overview-effect owner. It
+  returns no value; it updates `overview` or `overviewError` only when its
+  sequence is current. The form submit listener owns the send request and
+  accepted-send state transition. `moveRow(id, delta)` owns display order and
+  has no external effects.
+- `src/transport.mjs`: unchanged narrow transport contract. A rejected promise
+  means that particular request has not produced usable data.
+- `emailRevision`: each editable email change increments it. The submit handler
+  compares its captured revision before clearing, so a later draft is never
+  overwritten by an older completion.
+- Focus is described by `{ kind: 'email' | 'note' | 'refresh' | 'submit' |
+  'move', id?, direction? }`, rather than a stale DOM node. A draw only restores
+  the still-existing target; it does not impose a submit-origin focus after a
+  user has moved elsewhere.
+
+## Architecture
+
+```text
+Browser form/list controls
+       | input, submit, refresh, move
+       v
+src/app.mjs (page state, transitions, focus preservation)
+   | sendInvitation(email)       | readOverview()
+   v                             v
+src/transport.mjs ------------------> /api/invitations, /api/overview
+                                         |
+                                         v
+                                  accepted invitation / pending count
+```
+
+## Representative data flow
+
+```text
+Email draft + revision --submit--> sendInvitation(snapshot email)
+  --reject--> send error live alert; retain draft
+  --accept--> append invitation + success live status
+                   |-- if revision unchanged --> clear email draft
+                   '--> refreshOverview()
+                         |-- success --> overview.pending rendered
+                         '-- failure --> overview error rendered; acceptance stays visible
+
+Move button --moveRow(id, delta)--> rows swapped locally --> redraw --> same move button focused
+```
+
+## Evolution and verification
+
+An eventual server-side reorder can replace only `moveRow`'s local transition;
+the rendering and focus contract remain local. The implementation uses native
+labels, buttons, form validation, `role=status`, and `role=alert` so keyboard
+and assistive-technology behavior stays with platform controls. Execute the
+Playwright consumer suite, including focused regressions for degraded overview
+refresh and retained keyboard focus. Final results are recorded below.
+
+## Executed evidence
+
+Implemented in `src/app.mjs`. `npm run check` passed on 2026-10-19: six
+Chromium consumer tests cover accepted send and refreshed overview, local-only
+reordering, note preservation during explicit refresh, accepted send followed by
+failed overview refresh, keyboard focus continuity during repeated moves, and a
+note interaction that continues while send completion redraws the page.
