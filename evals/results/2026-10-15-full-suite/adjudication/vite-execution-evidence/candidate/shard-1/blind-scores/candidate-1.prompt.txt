+# Vite feature flags
+
+`@frontend-architect-eval/feature-flags` exposes a deliberately small, typed
+subset of a server-side JSON file as `virtual:feature-flags`. It supports Vite 8
+development, production builds, watch mode, and HMR.
+
+## Setup
+
+```ts
+// vite.config.ts
+import { featureFlags } from '@frontend-architect-eval/feature-flags'
+import { defineConfig } from 'vite'
+
+export default defineConfig({
+  plugins: [
+    featureFlags({
+      source: new URL('./flags.json', import.meta.url),
+      expose: ['checkoutV2', 'theme'],
+    }),
+  ],
+})
+```
+
+`source` accepts a file URL, an absolute path, or a path relative to Vite's
+project root. The file must be a JSON object. Every exposed value must be a
+boolean, finite number, or string.
+
+Add the package's virtual-module declaration to the application TypeScript
+configuration:
+
+```json
+{
+  "compilerOptions": {
+    "types": ["@frontend-architect-eval/feature-flags/virtual"]
+  }
+}
+```
+
+Then declare the application's flag schema. This is intentionally owned by the
+consumer because a TypeScript declaration cannot infer a runtime JSON file:
+
+```ts
+// src/feature-flags.d.ts
+import 'virtual:feature-flags'
+
+declare module 'virtual:feature-flags' {
+  interface FeatureFlags {
+    readonly checkoutV2: boolean
+    readonly theme: 'dark' | 'light'
+  }
+}
+```
+
+Application code receives exact, readonly keys:
+
+```ts
+import { flags } from 'virtual:feature-flags'
+
+if (flags.checkoutV2) {
+  // ...
+}
+```
+
+The declaration describes the expected contract; startup/build validation
+ensures exposed values exist and use a supported primitive type. A flag's more
+specific domain (for example the `theme` literals above) remains application
+policy and should be checked when the source file is produced.
+
+## Runtime, security, and caching
+
+The JSON file stays in Node/Vite. Only names in `expose` are serialized into the
+generated client module. Treat this allowlist as a security boundary: review it
+like client-visible environment variables and never add credentials, private
+tokens, or server authorization decisions. Values not in `expose` are absent
+from generated code, diagnostics, and source maps.
+
+The plugin validates configuration during Vite startup, before the virtual
+module is imported, and reports the option or source file plus a corrective
+action. Diagnostics identify exposed keys but never print their values or the
+contents of the source file.
+
+One filtered module string is cached per plugin instance. Production and watch
+builds refresh it in `buildStart`; the dev server watches the source and refreshes
+the cache before invalidating `virtual:feature-flags` during HMR. The cache key is
+effectively the immutable plugin options plus the watched source file, so every
+behavior-affecting input has an invalidation path. A single-file polling fallback
+for virtualized and network file systems forwards only missed changes into Vite's
+watcher; it is removed when the plugin container closes and does not alter the
+application's global watch settings.
+
+Consumer source is not transformed, so its existing source maps remain intact.
+The generated virtual module returns a source-free map: the server JSON is never
+listed as a source and cannot re-enter a client artifact through
+`sourcesContent`. The published plugin JavaScript and declarations include their
+own maps, and `src` is shipped so those maps resolve for maintainers; package
+exports still prevent applications from depending on source internals.
+
+## Public surface and release policy
+
+The root package export contains `featureFlags`, `FeatureFlagsOptions`, and
+`FeatureFlagValue`. `@frontend-architect-eval/feature-flags/virtual` is a
+type-support entry point; application runtime code must continue importing
+`virtual:feature-flags`. Other files are internal and are blocked by package
+exports. The package is ESM-only and currently supports Vite 8 and Vite's Node
+runtime range.
+
+Use SemVer based on consumer impact:
+
+- patch: fixes that preserve generated values, diagnostics, types, and supported
+  host versions;
+- minor: optional configuration or additive exports;
+- major: virtual-module shape changes, stricter accepted values, removed options,
+  changed HMR behavior, or dropped Vite/Node versions.
+
+Type changes and stricter validation can be breaking even when the JavaScript
+function name is unchanged. Deprecations should name the replacement and remain
+for one major line. Validate risky host-version changes with a prerelease before
+widening the peer range.
+
+## Release verification
+
+Run `npm run check` from the repository root. It builds declarations and maps,
+type-checks the exact consumer schema, runs a real Vite production build, starts
+a real dev server and edits the source to exercise HMR, checks actionable failure
+diagnostics, scans bundles and maps for a server-only token, and installs the
+packed tarball into a temporary consumer. Publish only that verified tarball;
+do not publish directly from unbuilt source.
