# Behavioral Evaluation Protocol

行为评测用于判断 Skill 是否改善了代理的工程决策，而不是检查固定标题或措辞。
结构化的单一用例源位于 [cases.yaml](cases.yaml)，评分规则位于
[rubric.md](rubric.md)。

## 前向评测流程

1. 固定生成模型、模型版本、代理配置和评测日期；同时记录独立评分者配置。
2. 为每个用例创建彼此隔离的新会话，提供 `prompt` 和可选 `artifact`。
3. 先在不加载任何本地、已安装或全局 frontend-architect Skill 的条件下运行一次，作为
   baseline；实际 reference 读取必须为零。
4. 再只加载隔离工作区中的当前 `SKILL.md` 和按需 reference，作为 candidate；读取全局
   副本仍视为无效运行。默认读取零到两个专题；具体决策缺口可触发额外读取，必须说明原因。
   超过默认宽度或读取多个渲染平台时，采集器记录 `breadth_review_required`，不自动判失败，
   也不自动批准。渲染平台仍须配合 common reference。第二阶段独立审查执行记录中的
   触发点、每个额外专题的必要性，以及多平台是否对应真实跨平台任务；理由不成立或证据不足
   均不能通过。第一阶段不接收路由日志，保持质量盲评。历史 `breadth_ok` 和
   `rendering_route_ok` 保留原先默认路由含义，旧版本记录仍按原门槛解释。
5. 第一阶段评测者在看不到 `must_observe`、`fail_if` 和另一条件结果时评分，避免按
   预期答案补分；仅评分用例声明的 `applicable_dimensions`。
6. 第二阶段在仍看不到另一条件和 `must_observe` 的情况下，只根据当前回答、diff 和
   验证证据审计该用例自己的 `fail_if`。全局失败项由第一阶段记录。
7. 使用 `rubric.md` 归一化分数；任一 case-specific 或 global failure 必须覆盖
   分数并将 verdict 设为失败。
8. 实现型用例应在一次性工作区应用候选修改，并运行该 fixture 声明的类型、测试或
   构建检查；评分实际 diff 和运行结果，不只评分解释文字。
   对不能由候选改写的核心验收条件使用 `protected_paths`；候选可以增加独立测试，但修改、
   删除或弱化受保护 harness 必须先于其他验证失败。
9. 记录原始输出、实际 diff、检查结果、各维度分数、触发的失败项、模型版本和
   未验证条件。
10. 比较 baseline 与 candidate。单次分数下降先视为需要调查的信号；对边界分数或
    高方差任务进行相同配置的重复运行。发布门槛是没有可复现的实质退化，并且新规则
    改善目标行为或消除其复现失败，而不是要求每次随机采样都严格高于 baseline。

对于实现完整性、公共基建、安全或发布门槛等高风险用例，最终发布证据不能只来自同一
模型的一次生成和一次评分。优先使用不同模型系列或人工评审者复核实际 diff、命令日志和
失败项；如果只能使用同一模型，至少在隔离上下文中重复高方差用例，并把相关性限制写入
结论。交叉评分用于发现盲点，不允许混入同一个可比批次后计算一个伪精确平均值。

同一个结果目录只能使用一种评分模型和 reasoning effort；需要更换评分配置时创建新
目录，避免不同配置的批次被合并成一份不可比较的证据。

仓库提供 `scripts/run_behavior_evals.py` 生成隔离工作区、原始回答、实际 diff、命令日志
和机器信息。生成阶段与评分阶段保持分离，避免生成代理看到评分项或另一组答案。
候选指导副本包含入口、references 和 CONTRIBUTING.md，供确实涉及技能维护的请求
访问原维护约定；普通前端任务无需读取维护说明。无技能 baseline 不包含这些文件。

### 运行有效性与评分缓存

评分前先检查生成是否成功、skill 加载与隔离证据、必需产物和受保护 harness。
不满足条件的样本写为 `verdict: invalid`，保留原因并使评分命令返回非零；不调用模型评分，
也不保留该样本原来的通过结论。普通行为测试失败仍属于有效样本，但最终 verdict 必须为
`fail`，不能由模型的高分覆盖。`invalid` 不应被计入质量均分，应先修复采集条件后重跑。
评分启动时先将所有选中条件的旧结论原子写为待评分的 `invalid`，再核验和调用模型；
逐批保存完成结果。模型超时、返回错误或进程中断时，尚未完成的案例不能留下旧 `target`。
未选择的案例按下面的显式选择规则保留。

采集记录保存原始 `events.jsonl` 的摘要和阅读审计。评分必须取得非空原始日志、核对
摘要、重新计算审计并确认有完成的 turn；缺日志、日志变化或摘要不一致均要求重跑。
验证契约随采集冻结：任务请求、输入材料、任务类型、夹具文件内容、保护文件及验证命令。
这些内容改变后需重新采集，不能仅用新要求重评旧回答；rubric 和失败评分规则仍可单独重评。
实际验证须按声明顺序执行；普通测试失败后停止是有效的失败样本，全绿但少跑检查则无效。

两个评分阶段的缓存绑定当前请求、回答、diff、验证结果与日志、需求快照、rubric、失败项、
路由审计证据、输出 schema 和评分配置，并校验缓存输出内容。输入变化自动重评；缺少
指纹的旧缓存不复用。`--force` 强制重评。`--case` 更新已有案例并追加新案例，保留未选择的
结果；修改未选择案例的证据后，需要显式选中它重新评分。

reference 阅读审计是执行事件审计，不是操作系统文件访问隔离。候选读取入口应使用单独的
`cat` 命令和明确文件路径；reference 也支持 `sed -n` 数字打印范围。不要在指导读取命令中
使用通配符、变量、管道或串联命令。`ls`、`stat` 和 `rg --files` 仅列文件，不算读取。
`find` 仅在使用字面路径与 `-type f`、`-maxdepth N`、`-print` 的枚举形式时按元数据处理；
执行、写文件、删除等动作不在允许范围内。候选指导文件保持只读，维护讨论以回答描述
拟议调整，不能改写被评测指令。
未成功返回内容的读取、无法识别的可见指导访问和不完整事件标为 `unknown`，不能当成
零读取或隔离通过。任意程序内部未出现在事件中的隐式文件访问不在此审计能力内。
审计按 item ID 跟踪未完成事件。已知 reference 的文件名读取也会被识别；若事件没有工作
目录，则无法判断来源，标为 unknown。CLI 不记录工作目录时，优先使用明确的完整路径。
没有当前原始日志摘要、验证契约或兼容阅读审计的历史采集需重新生成；历史原始结果保留，
不自动改写为新协议证据。这些一致性检查防止缺失、混用和过期证据，不是防篡改签名。

### 多文件只读审查场景

`task_type: review` 使用 `fixture` 中的 `before/`、`after/` 仓库快照。采集器不给它附加
实现任务指令，并核对被审文件与新建文件均未改变。原始快照在生成前冻结为
`review-context.md`，两个盲评阶段都能看到原始需求和代码，不依赖回答中的自述。
差异比较固定到夹具初始化时的提交，而非代理执行后的 HEAD；提交修改不能清除审查差异。
`validation_commands` 可选；如果提供，应验证快照中已有的检查，而不替 reviewer 修复代码。

`community-review-mixed-diff` 与 `community-review-bounded-coverage` 共享社区模块快照：
34 个文件变化、分散的需求与已接受/草案决策、实际 UI 到控制器的调用关系、一个未变化但
遗漏新职责的生命周期入口，以及正确的并发处理和本地状态例外。既有十项 Node 测试通过，
但不覆盖四个契约缺陷（三个预埋缺陷和独立前向审查发现的查询失败后旧游标复用）。
后一个案例明确限制审查范围，检查遗漏行为类别的披露。
这比集中展示几段代码更接近真实混合变更，但仍不是数千行生产 diff 的规模证明。

维护者的独立行为检查在 `evals/oracles/community-review.mjs`，通过
`scripts/test_review_fixture.py` 验证缺陷仍然可观察、针对性修复能通过相同契约检查。
oracle 与案例的 `must_observe`、`fail_if` 均不得提供给生成代理；前者也不提供给盲评者。
Node 用于这些确定性检查；本地缺少 Node 时会显式跳过对应测试，CI 先确认 Node 可用。

不要让同一代理一边生成答案一边为自己评分。没有独立评测者时，至少在新的上下文中
评分。第一阶段隐藏用例预期观察项和失败项；第二阶段只显示失败项，不显示
`must_observe` 或另一条件结果。

## 用例设计约束

- `prompt` 必须可以直接交给代理，不依赖评测者临时补充问题背景。
- 需要评审代码时，把完整最小代码放入 `artifact`。
- 需要评估实现完整性时，提供可独立复制到一次性工作区的最小 fixture、依赖版本和
  验证命令；若暂时只有内联 artifact，必须明确记录没有执行编译或测试。
- 将决定用例是否通过的既有脚本和命令入口列入 `protected_paths`，但不要保护候选为完成
  产品实现而必须正常修改的源码、公共包清单或新增测试位置。
- `must_observe` 描述决策不变量，不要求唯一实现。
- `fail_if` 只放足以判定失败的行为，不收集个人风格偏好。
- `applicable_dimensions` 只包含当前请求真正可以观察的维度。
- 修改 Skill 行为时，至少更新一个现有用例或新增一个失败复现用例。

CI 校验用例结构、维度名称和必填字段，但不会伪装成模型行为评测。模型输出的生成与
盲评仍是独立的发布检查。

## 从真实使用记录验证改进

将真实失败转为脱敏、可独立复现的输入，不把私人对话、项目数据或答案写进 fixture。
区分已确认加载 Skill 的任务与仅有相似问题的补充案例；记录其他技能、仓库规则、模型
和后续人工纠正的影响，不能把最终代码质量全部归因于本 Skill。

评估稳定性时，除了最终分数，还记录首次方案是否符合业务契约、需要多少实质纠正、
失败实验是否清理，以及决定性验证是否覆盖原问题。最终修复成功不抵消首轮错误，
新增需求也不算原实现缺陷。只有文字方案的用例不能证明可编译、运行或实际交互质量。
对新版改进的判断应使用固定配置的对照和必要复测，不能根据一次前向检查宣称能力提升。

实现型场景可增加[连续需求检查](followups/README.md)：冻结首轮代码后再提供第二轮
需求和受保护测试，观察已有结构如何演进。分别保存首轮与次轮证据，不把后续修复后的
最终成功写成首轮一次通过，也不把文字方案检查当作实现型证据。
