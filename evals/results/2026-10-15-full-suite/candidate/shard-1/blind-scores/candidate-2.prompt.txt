request: 接口适配层已运行时验证订单金额为有限数值并返回类型明确的对象。内部汇总函数 只消费这些对象，不修改输入，没有其他入口。请给出汇总实现与错误处理原则， 并说明将来增加外部输入入口时的调整位置。

applicable_dimensions: ["solution_complexity", "security_trust", "correctness_boundary"]

RESPONSE:
建议直接采用纯 TypeScript 汇总，不在内部重复验证：

```ts
export interface ValidatedOrder {
  readonly amount: number;
}

export function sumOrderAmounts(
  orders: readonly ValidatedOrder[],
): number {
  return orders.reduce((total, order) => total + order.amount, 0);
}
```

决策原则：

- 信任适配层已经建立的 `ValidatedOrder` 契约，不在汇总函数中重复 `typeof`、`Number.isFinite`、可选链或默认值处理。
- 使用 `readonly` 表达“不修改输入”；空集合明确汇总为 `0`。
- 不用 `try/catch` 将错误吞成 `0`，否则契约破坏会伪装成合法业务结果。内部违规属于编程错误，应直接暴露并修复调用链。
- 沿用 JavaScript `number` 的精度语义，不在汇总阶段擅自四舍五入。若金额要求精确货币运算，应把契约改为整数最小货币单位或既有 Decimal 类型，并在适配层完成转换。
- “每项有限”不保证极端数值相加后仍有限。当前没有总额必须有限或金额上限的要求，不额外发明检查；若将来确认该领域约束，应在金额领域类型/适配层加入合理范围，并为汇总结果定义明确的溢出错误。

最有价值的测试是：多订单求和、空数组返回 `0`、输入对象保持不变。无需测试非法金额，因为它不属于该函数的可达输入契约。

将来增加表单、URL、存储或其他外部入口时，调整点应是新入口的适配层：

```ts
function parseExternalOrder(input: unknown): ValidatedOrder {
  // 在这里验证结构与 amount，并返回内部类型；
  // 失败时返回项目既有的结果类型或抛出可识别的边界错误。
}
```

如果多个外部入口遵循相同订单契约，就在适配层提取共享解析器；各入口负责把验证失败映射为对应的 UI/请求错误。不要扩大 `sumOrderAmounts` 的参数类型，也不要让它开始接收和修复原始外部数据。

工作区没有应用源码、测试或包配置，因此未修改文件，也无法运行项目级验证；`.frontend-architect` 保持未变。

## 目标结构

在项目现有源码根目录增加一个业务模块：

```text
features/
  checkout/
    index.ts                 # 唯一跨模块入口
    checkout-model.ts        # 领域类型、纯规则、状态转换
    checkout-workflow.ts     # 提交、重试、并发等用例
    checkout-api.ts          # 请求与服务端 DTO 映射
    CheckoutView.*           # 页面或功能入口
    CheckoutView.test.*
```

先保持扁平。只有内容增长并形成真实职责后，再拆成：

```text
features/checkout/
  index.ts
  model/
  application/
  api/
  ui/
```

不要预先创建空的 `model`、`api`、`ui` 层级，也不要把模块内部重新变成 `utils.ts`、`types.ts` 这类杂物箱。

### 结算模块拥有

- 收货、配送、优惠、支付选择等结算草稿。
- 草稿校验和可提交条件。
- 提交、失败、重试、防重复提交等状态转换。
- 结算接口调用及外部 DTO 到内部模型的转换。
- 结算专用 UI、交互行为和测试。

### 结算模块不拥有

- 登录身份和授权判定；客户端权限只用于展示，服务端仍负责授权。
- 购物车、商品目录等其他能力的源数据。
- 通用 HTTP、日志、货币格式化和无业务含义的 UI 基础组件。
- 服务端定价、库存或订单创建规则的另一份前端真相。前端只展示确认结果并做必要的输入反馈。

状态默认留在模块内最小共同所有者。只有存在跨路由恢复、多个独立消费者或持久化需求时，才把结算状态提升到现有 store；不能因为项目已有 `stores` 就默认新增全局 checkout store。

## 公开 API

所有外部调用方只能导入 `features/checkout/index`。该入口应有意地导出：

- 一个页面或功能入口组件；
- 宿主确实需要传入的稳定标识或能力；
- 完成、取消等宿主需要处理的结果事件；
- 消费者确实需要引用的领域结果类型。

不导出：

- API DTO；
- 内部 store、reducer action；
- 请求客户端；
- 表单字段实现；
- 私有 hooks、selectors 和辅助函数。

示意而非仓库既有代码：

```ts
export { CheckoutEntry } from './CheckoutEntry'
export type {
  CheckoutEntryProps,
  CheckoutCompleted,
} from './checkout-contract'
```

如果其他功能需要了解结算结果，应扩展这个公开契约，而不是导入 `checkout/model/*`。不要通过 `index.ts` 无差别 `export *`。

## 依赖方向

```text
应用入口 / 路由
        ↓
checkout 公共入口
        ↓
checkout 组合层
   ↙        ↓        ↘
 UI      workflow    API adapter
  ↓          ↓          ↓
model      model     shared/http
```

约束如下：

- `model` 不依赖 UI、网络、浏览器 API或框架生命周期。
- UI 使用领域值和命令，不解析服务端响应。
- workflow 组织提交顺序和状态，不直接承担展示。
- API adapter 隔离传输格式、运行时校验和错误映射，不决定 UI 文案。
- `shared` 不得反向依赖 `features/checkout`。
- 结算与购物车、身份等模块只能依赖对方公开入口；如果双方开始互相调用，由路由或更高层流程协调。
- 模块内部使用相对直接导入，不经公共 barrel 绕行，避免隐藏循环依赖。

若现有 service 已经完整拥有请求、错误和映射策略，可以暂时复用；不要为了目录整齐再套一层只改名的 wrapper。

## 渐进迁移步骤

1. 建立行为基线  
   先记录结算关键路径：进入、编辑、提交成功、服务端校验失败、网络失败与重试。补测试时保护这些可观察行为，不镜像私有文件结构。

2. 交付第一条纵向切片  
   新建 `features/checkout`，让一条完整结算路径的 UI、状态、API 和测试共处其中。应用入口只从 `features/checkout` 导入。

3. 随改随迁  
   每次结算变更只迁移归属明确的文件：

   - 仅结算使用的 component、hook、store slice、type、helper 移入模块；
   - 真正跨业务且不含结算政策的能力暂留原处；
   - 搬迁后若还有旧消费者，旧路径临时重新导出新公开 API，并标记待移除，禁止新增旧路径调用；
   - 每次只迁一个完整行为，保证可以单独回退。

4. 再整理共享层  
   当第二个业务模块也开始迁移时，才把已证明通用的能力收敛为有名字的共享模块，例如 `shared/http`、`shared/currency`、`shared/ui`。不能把原有六个顶层目录直接整体改名为 `shared`。

5. 固化边界  
   当模块模式稳定后，复用现有 lint 或构建能力限制跨模块私有导入。没有现成工具且违规尚不频繁时，先用代码评审约定，避免立刻引入复杂架构插件。

6. 退休旧目录  
   只有当某个旧顶层目录已无真实消费者时才删除。迁移成功标准是普通结算修改集中在 checkout 模块、公开 API 稳定且不存在循环依赖，不是目录图一次变整齐。

## 验证重点

- 用户通过公开 UI 完成一次结算；

- 纯领域规则由 model 测试验证；
