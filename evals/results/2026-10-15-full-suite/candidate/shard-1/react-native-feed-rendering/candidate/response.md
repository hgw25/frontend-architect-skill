结论：最小修复应先切断“100ms 音频进度更新 → 整个信息流失效”的路径，再处理图片尺寸与资源生命周期；暂不更换列表库，也不基于旧 Bridge 推断瓶颈。

工作区除 `.frontend-architect` 和 Git 元数据外没有应用源码、依赖清单或 Android 配置，因此目前无法确认 RN 版本、New Architecture、列表/图片组件，也无法直接提交代码。Git 工作区保持干净。

## 1. 先建立可区分原因的基线

在同一台目标中端 Android 真机上，用 profile 或 release 构建运行固定场景：800 项、正常图片数据、音频播放、连续上下滚动若干轮。分别测试冷、热图片缓存。

记录：

- RN 版本、JS 引擎、实际 Android 构建是否启用 New Architecture。
- 当前列表和图片组件及版本。
- RN Profiler 中每次进度更新触发的组件范围和 commit。
- Android FrameTimeline/System Trace 中的卡顿帧、JS/UI/RenderThread 活动。
- Memory Profiler 中 Java、Native、Graphics/图片内存、GC 和保留对象。
- 已挂载行数量是否随滚动持续增长。

这一步用于区分：

- 大量行随 100ms tick 更新：状态归属或 props 身份问题。
- JS 较空闲但 UI/RenderThread 忙：图片解码、布局、绘制或 GPU 问题。
- 已挂载行持续增加：虚拟化被破坏或资源没有释放。
- 内存只在首次浏览图片时增长并最终稳定：可能是缓存预热，不足以判定泄漏。
- 多轮往返后仍单调增长且能找到保留链：才可称为泄漏。

## 2. 第一批最小代码修改

只改更新边界，不动列表实现：

1. 把音频进度从页面/列表数据所有者中拆出，由播放器或独立的 `AudioProgress` 视图订阅。
2. 进度 tick 期间保持列表 `data` 数组和未变化 item 的引用稳定，不再重建 800 个行对象。
3. 不通过列表级 `extraData`、宽泛 Context 值或等价机制广播进度。
4. 如果只有当前播放行需要进度，让该行内部的小型进度子组件按稳定 item ID 订阅；其他行不更新。
5. 静态样式移到 `StyleSheet.create`。动态进度样式限制在进度子组件内。
6. 使用稳定的语义 key。列表回调和 `renderItem` 仅在其真实依赖变化时变化。
7. 在 props 身份稳定后再给行组件加 `React.memo`。暂不写复杂 `areEqual`，也不批量 `useMemo`/`useCallback`。

应保留的核心不变量是：

```text
音频进度变化
  -> 进度视图更新
  -> feed data、普通行 props、普通行 host view 不变
```

如果当前页面还有其他原因必须每 100ms 渲染，可以把列表本身隔离成 memoized 子树，但仍需保证传入的 `data`、样式和回调稳定。

不要先降低 100ms 更新频率，因为这可能改变产品行为。只有当隔离后进度视图自身仍是瓶颈，才根据项目已有能力选择兼容当前 RN 架构的动画方案。

## 3. 第二批：图片内存

继续使用现有图片组件：

- 请求或解码接近实际显示物理像素尺寸的缩略图，而不是把原始高分辨率图交给小卡片。
- 给图片明确布局尺寸，避免滚动中重复测量和尺寸跳变。
- 检查是否预取了全部 800 张图片；预取范围应与可见窗口及近期滚动需求匹配。
- 核实当前图片组件的缓存键、缓存上限、取消和卸载行为。
- 检查行内监听器、定时器、动画句柄及图片请求是否由其生命周期清理。

不能仅凭 JS heap 判断图片泄漏；解码位图和缓存可能主要位于 Native 或 Graphics 内存。也不应通过频繁清空缓存掩盖所有权问题。

## 4. 最后才调列表参数

只有证据显示挂载、测量或批次工作过多时，才调整现有列表库：

- 排查嵌套在同方向 `ScrollView` 中、关闭虚拟化或一次渲染全部数据等情况。
- 固定高度行且当前列表支持时，提供确定性的布局信息。
- 一次只调整一个窗口、批次或裁剪参数，并同时观察空白项、交互正确性和内存。
- 不复制“通用最佳参数”；设备、行高度和图片成本会改变取舍。

若完成这些步骤后，证据才证明现有列表实现无法满足要求，更换库应作为独立决策，而不是本次默认修复。

## 必须在哪里验证

真实 React Native 运行时必须确认：

- 实际 RN 版本、JS 引擎和 New Architecture 状态。
- 100ms tick 是否只更新目标进度组件。
- 当前列表的虚拟化、回收和图片组件生命周期是否符合预期。
- memoization 是否确实减少了 commit，而没有造成旧数据或错误交互。

Android 真机必须确认：

- 滚动掉帧是否改善，以及瓶颈位于 JS、UI、RenderThread、图片解码还是 GPU。
- 冷/热缓存下的图片加载和滚动表现。
- Java、Native、Graphics 内存是否在预热后稳定。
- 多轮滚动、返回页面和后台/前台切换后，资源是否释放。
- 目标刷新率、设备负载和热状态下的结果是否可重复。

模拟器和 debug 构建可验证功能，但不能证明滚动性能或内存问题已经解决。最终验收必须使用同一场景、同类中端 Android 真机、profile/release 构建，并至少重复多轮比较修改前后的帧与内存证据。
