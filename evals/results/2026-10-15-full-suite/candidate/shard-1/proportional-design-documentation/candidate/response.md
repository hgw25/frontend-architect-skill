结论：A、B 不需要单独持久化设计文档；C 需要在编码前形成一份简洁、可更新的迁移设计。文档是跨阶段协作依据，不是审批门槛。

| 任务 | 是否需要持久化设计文档 | 最小准备 | 后续行动 |
|---|---|---|---|
| A：按钮间距 8px → 6px | 不需要 | 定位按钮专属 spacing token，确认实际消费者及各尺寸/变体；验收条件是视觉间距变为 6px，交互、焦点、尺寸语义和 API 不变 | 直接修改 token；检查主要按钮变体和受影响页面，运行既有视觉或组件测试。若该 token 还服务非按钮组件，应先收窄到按钮语义 token，但仍不因此创建设计文档 |
| B：列表页增加 URL 状态筛选 | 通常不需要独立设计文档 | 确认既有查询参数解析/序列化约定、合法状态值、默认值、未知值处理、清除筛选行为，以及 URL 更新采用 push 还是 replace | 按现有约定完成“URL → 筛选状态 → 请求/展示”的完整链路；验证刷新、分享链接、前进后退和清除筛选。若已有路由契约文档则同步更新，否则以验收条件和测试固化即可 |
| C：三个应用统一登录状态 | 需要 | 先盘点三个应用和新旧会话接口的身份定义、cookie/token 与域名边界、刷新/退出流程、服务端撤销能力和现有负责人；明确旧新接口并存的准确起止时间 | 先写迁移设计并解决所有权，再通过兼容层逐应用迁移；每阶段验证后再推进，保留回滚路径，满足退出与刷新一致性后才移除旧接口 |

C 的最小持久化内容应包括：

- 权威身份与会话来源：谁定义当前用户，服务端与客户端分别拥有什么。
- 所有权表：刷新、过期、退出、跨标签页/跨应用传播、缓存清理、故障诊断分别由哪个模块和团队负责。
- 必须成立的不变量：旧刷新响应不能复活已退出会话；账户切换不能遗留前一用户数据；隐藏 UI 不替代服务端授权与会话撤销。
- 新旧接口兼容策略：选择、回退和错误规则，禁止无定义的双写或静默降级。
- 分阶段顺序：每个应用的接入方、交接条件、观测信号、回滚方法，以及旧接口删除条件和日期。
- 可验证的验收场景：刷新成功/失败、过期、单应用退出、传播退出、账户切换、旧新接口故障及迁移回滚。

目前“用户身份、刷新与退出传播的所有权尚未确定”是实质性架构缺口。可以立即开展盘点、契约核实和兼容层原型，但不应先把任一应用偶然的实现定成统一方案。授权已经具备，因此所有权一旦确定即可继续实施，无需额外设置文档评审关卡。

仓库检查显示当前工作区只有 `.frontend-architect` 与 Git 元数据，没有可供核实的应用代码或既有文档目录，因此无法指定实际 token、URL 模块或文档文件名，也没有修改任何文件。上述判断采用了本地 Skill 的比例化原则：局部既有契约直接实现，跨应用且涉及所有权、兼容和分阶段交接的决策才持久化。
