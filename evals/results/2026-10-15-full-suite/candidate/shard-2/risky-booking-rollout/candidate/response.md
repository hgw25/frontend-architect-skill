结论：采用“单一领域契约 + 新旧适配器 + 按预订意图固定分流”的迁移方式。任何真实预订只写一个接口，绝不做前端双写。重复预订的最终防线必须是服务端共享幂等；如果旧、新接口不能共享幂等记录和结果查询能力，新写链路不得进入生产灰度。

当前仓库没有应用源码、接口定义或发布配置，因此下面是可执行的迁移设计，其中服务端能力是明确的上线前置条件，不假设它们已经存在。

## 1. 兼容边界

页面只依赖一个稳定的领域接口，例如：

```ts
interface BookingGateway {
  loadConfirmation(input: ConfirmationQuery): Promise<Confirmation>
  submit(command: BookingCommand): Promise<SubmitOutcome>
  getOutcome(intentId: BookingIntentId): Promise<BookingOutcome>
}

type SubmitOutcome =
  | { status: 'confirmed'; bookingId: BookingId }
  | { status: 'rejected'; reason: RejectionReason }
  | { status: 'unknown'; intentId: BookingIntentId }
```

旧、新接口各有一个适配器，负责：

- 校验外部响应结构，并归一化成同一个领域模型。
- 统一错误分类、金额和时间语义、可空字段及状态枚举。
- 隐藏接口版本、URL、DTO 和灰度规则；组件不得出现 `if (useV2)`。
- 保持现有数据层对加载、缓存、取消和错误展示的所有权，不新增第二套长期缓存。

读取和提交使用两个独立开关：`confirmation-read-v2` 可以先灰度；`booking-submit-v2` 必须等幂等契约完成后再开。

真实提交禁止影子双写。影子验证只能用于无副作用读取、录制脱敏请求的离线回放，或隔离环境中的契约比较。

## 2. 幂等和重复提交

首选由服务端创建不可猜测的 `bookingIntentId`，在用户进入确认流程时绑定账户、租户、报价版本和预订快照。提交时携带该 ID 作为幂等键。

服务端契约必须保证：

- 幂等记录与预订创建原子提交。
- 同一意图、同一请求重复调用，返回第一次提交的权威结果。
- 同一幂等键搭配不同请求内容，返回明确冲突，不能创建第二笔预订。
- 旧、新接口共享同一幂等域；否则不得在未知结果后跨接口重试。
- 幂等记录保留时间至少覆盖最长用户恢复、客户端重试和延迟请求窗口。
- 提供按 `bookingIntentId` 查询 `pending | confirmed | rejected | not_found` 的授权接口。
- 权限、资源归属和租户隔离均在服务端校验。

前端同时提供体验层防护，但不把它当作幂等保证：

- 网络发送前持久化意图 ID。
- 指针、键盘和程序调用统一经过一个提交入口。
- `submitting`、`unknown` 状态禁止再次创建新意图。
- 重试使用原来的意图 ID和不可变请求快照。
- 用户修改日期、房型、人数等业务内容后，旧提交先完成核对，再建立新的意图。
- 多标签页可同步“正在提交/已确认”提示，但跨标签、跨设备的正确性仍由服务端保证。
- 迟到的旧请求不得覆盖较新的确认、错误或 loading 状态。

不要用请求内容哈希代替意图 ID：用户可能合法地预订两个内容相同的订单。

## 3. 错误恢复

页面状态应明确区分：

| 状态 | 页面行为 |
|---|---|
| `ready` | 允许首次确认 |
| `submitting` | 锁定提交，显示处理中 |
| `confirmed` | 展示唯一权威预订结果 |
| `rejected` | 展示明确业务原因；修改内容后建立新意图 |
| `unknown` | 告知“结果仍在确认，请勿重新预订”，自动查询权威状态 |
| `recovery-failed` | 保留意图参考号，提供继续查询或人工处理入口，仍不允许盲目新建 |

恢复规则：

- 明确的校验拒绝：允许修正，不当成成功。
- `409` 幂等冲突：查询原结果；若请求内容不同则停止并提示重新开始。
- 超时、断网、连接中断、部分 `5xx`：一律视为结果未知，而不是失败。
- 未知结果先按退避策略查询状态；只有查询明确为 `not_found` 且服务端保证未提交时，才用原幂等键重试。
- 登录过期：重新认证后先查询原意图，不能直接创建新意图。
- 刷新、返回或重新挂载：从服务端会话恢复待处理意图并继续核对。
- 自动回退到旧接口只在两套接口共享幂等域时才安全；否则禁止。

## 4. 两周灰度

发布控制在服务端或可信的边缘层完成，提供可在一分钟内生效的 kill switch。分流以 `bookingIntentId` 为单位固定：同一意图的首次提交、重试和状态查询不能在两个接口间漂移。

建议节奏如下，但每一阶段都由指标门槛驱动，日期不是强制晋级条件：

1. 第 1–2 天：部署兼容层，仍为旧接口 100%；验证状态机、幂等键透传和生产信号。
2. 第 2–3 天：仅灰度 V2 读取，比较归一化结果；不发送影子预订。
3. 第 3 天：内部账户或明确白名单使用 V2 提交。
4. 随后按 `0.5% → 2% → 5% → 10% → 25% → 50% → 100%` 推进。
5. 每档至少覆盖一个业务高峰，并达到预先计算的最小样本量。
6. 先覆盖代表性随机流量，再检查登录状态、地区、语言、浏览器、支付/供应商等关键分段，避免只验证低风险用户。
7. 到达 100% 后仍保留旧适配器和 kill switch，完成至少一个高峰周期的稳定观察。

两周结束不等于自动删除旧链路。只有满足以下条件才单独提交清理变更：

- V2 已全量并跨过约定观察期。
- 没有未完成的旧链路意图。
- 重复预订和未知结果指标符合门槛。
- 回滚演练完成。
- 服务端确认旧接口的下线窗口。

## 5. 生产信号

必须同时有前端流程信号和服务端权威业务信号。核心看板按接口版本、灰度组、发布版本和关键业务分段对比：

- 每万次预订意图产生的重复预订数；以服务端事实为准。
- 提交意图数、确认成功率、明确拒绝率。
- `unknown` 结果率、持续时长及最终恢复成功率。
- 幂等命中、幂等冲突、同键多订单等服务端计数。
- 用户重复点击、同意图请求次数和重试次数分桶。
- 提交及状态查询的 p50、p95、p99 延迟。
- V2 相对固定 V1 对照组的错误率和转化率。
- 认证失败、跨租户拒绝、响应解析失败。
- JavaScript 异常、页面放弃率以及人工客服升级量。

`submit_started`、`confirmed`、`rejected`、`outcome_unknown`、`reconciled` 等事件要有稳定语义；不能只用“按钮点击”推断预订结果。告警需要链接对应操作手册和 kill switch。

## 6. 隐私控制

- 遥测采用字段白名单，不记录姓名、邮箱、证件、手机号、完整行程、请求体或接口响应体。
- 不把幂等键、预订号、令牌放入 URL、前端错误消息或第三方分析工具。
- 关联排障使用短期、不可猜测的追踪 ID；原始业务标识只在受控服务端日志中可见。
- 对追踪 ID、IP、设备信息等可关联数据规定访问角色、保留期限和删除流程。
- 业务必要的可靠性日志与营销分析分离；第三方 SDK 不应在敏感确认页获得 DOM、用户对象或网络载荷。
- 错误采集和 source map 上传前检查请求面包屑、上下文及自动序列化内容，关闭请求体抓取。
- 灰度分组不是授权机制，所有账户和资源权限仍由服务端执行。

## 7. 停线与回滚条件

以下任一情况立即把“新意图的 V2 提交比例”切到 0：

- 出现一例可归因于 V2 的同意图多订单。
- 同一幂等键得到不同预订结果，或幂等记录无法查询。
- 发现越权、跨租户或敏感数据泄漏。
- 未知结果无法通过权威查询恢复。
- 响应兼容错误导致金额、日期、库存或预订状态解释错误。

以下情况冻结晋级；连续两个观测窗口仍存在则回滚：

- V2 成功率低于匹配 V1 对照组，超过预先约定的业务 SLO或统计波动带。
- `unknown` 结果率、解析失败率或人工恢复量超过基线阈值。
- p95/p99 延迟明显恶化并造成重复操作或放弃增长。
- 关键用户分段出现整体均值掩盖的显著退化。

回滚只影响尚未创建的意图。已经路由到 V2 的意图继续通过 V2 状态查询完成核对；不得为了“回滚”把未知请求重新投递给旧接口。保留兼容层和恢复页面，直到所有在途意图进入终态。

## 8. 上线前必须通过的验证

- 两个适配器对同一契约样例生成相同领域结果，包括缺失字段、未知枚举和错误响应。
- 双击、回车连按、慢网、断网、超时、刷新、返回、标签页并发均只产生一个预订。
- 构造乱序完成：旧失败不得覆盖新成功，旧 `finally` 不得清除当前 loading。
- 相同幂等键重复调用返回原订单；相同键不同内容被拒绝。
- 提交超时后刷新页面，仍能恢复到唯一权威结果。
- kill switch 演练证明新意图回到 V1、在途 V2 意图继续安全核对。
- 验证日志、分析事件和错误平台中不存在敏感请求或预订数据。

这次 Skill 的影响主要体现在三点：将两套接口差异收口到适配器；把超时建模为“结果未知”而非普通失败；让灰度和回滚以可观测、可证伪的生产条件推进。由于工作区没有产品代码，本次只完成了设计，未进行实现或运行时验证。
