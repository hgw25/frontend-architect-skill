不建议现在立即引入完整的 feature/domain 分层。

两个页面、十几个源文件时，完整的 `features / domains / entities / shared / services / model / ui` 层级大概率只会增加跳转、空目录和转发文件，并没有隐藏足够的复杂度。此时更合适的是“按页面就近组织，按真实职责轻量拆分”。

建议结构

```text
src/
  app/                    # 入口、路由、全局 Provider、应用外壳
  pages/                  # 或沿用框架规定的路由目录
    first-page/
      FirstPage.*
      FirstPage.test.*
      firstPageApi.*      # 只有存在页面专属接口映射时才拆
      firstPageModel.*    # 只有存在独立业务规则时才拆
    second-page/
      SecondPage.*
      SecondPage.test.*
  shared/
    ui/                   # 真正跨页面、无业务策略的 UI
    http.*                # 确实被多处使用的请求策略
```

具体原则：

- 继续遵守当前框架和路由器的目录约定；不要为了套模板同时创建 `app`、`pages`、`views` 等同义层。
- 页面私有的组件、请求和规则留在页面附近，可以先保持扁平。
- 只有出现不同变更原因、独立状态/生命周期、外部接口映射或清晰业务规则时才拆文件。
- “用了两次”不自动等于 `shared`；共享模块应当有真正跨页面的语义和所有权。
- 暂不增加全量 barrel 文件、repository/interface 层、依赖注入或目录级 `api/model/ui` 对称结构。
- 页面负责组合，不应长期吞下所有请求、表单、订阅和错误恢复逻辑。

例如，未来增加第三个页面也要编辑“客户筛选”逻辑时：如果筛选规则、请求映射和交互语义一致，可以把它提炼成一个 `customer-search` capability；如果只是两个页面碰巧都有下拉框，则继续分别放在页面内。这样今天容易理解，以后也有自然迁移路径。

触发迁移的信号

出现以下一个或多个持续性信号时，再按能力逐步迁移：

- 一次普通功能修改经常横跨全局 `components`、`hooks`、`services`、`types` 等多个目录。
- 某个用户能说出名字的能力跨越多个页面，并且能相对独立地演进。
- 页面文件开始同时管理多套独立请求、表单草稿、订阅、重试或竞态策略。
- 业务规则需要脱离渲染独立测试，或者同一规则已在多个位置重复。
- API/存储的数据形状频繁泄漏到 UI，替换后需要修改大量调用方。
- 全局 `utils`、`common`、`types` 或 `components` 逐渐成为无准入规则的杂物箱。
- 页面之间开始互相导入内部文件，或出现循环依赖、共享状态所有权不清。
- 不同团队开始独立负责不同产品能力，或能力需要独立发布、按路由拆包。
- 一个模块已经有足够内部实现，需要通过窄公共入口保护调用方。

迁移时不要整库重排。选择最明显的一个能力，建立窄公共入口，移动它拥有的 UI、规则和数据适配；保持依赖方向为：

```text
app / routes → features → shared platform
```

同级 feature 不应互相读取内部文件，应由页面协调或通过明确公共契约协作。

当前工作区除 `.frontend-architect` 指导文件外没有可检查的应用源码，因此无法确认实际框架、路由目录或现有命名；以上结构是基于题述规模给出的决策，不应机械替换项目已有约定。此次没有修改任何文件。
