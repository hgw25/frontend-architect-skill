```ts
type OrderResponse = {

type Order = {
```

```ts
function formatOrderTotal(
  totalCents: number,
  locale: string,
  currency: string,
): string {
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
  }).format(totalCents / 100)
}
```

币种不能从 `total_in_cents` 推断，应取自已有业务配置或接口契约。若币种尚未明确，这是接入前需要补齐的唯一关键契约，而不是在前端默认成某种货币。

```ts
type OrderLoadState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; order: Order }
  | { status: 'error'; error: Error }
```

```text
order/

  OrderPage.*             // 状态、加载编排、渲染
```

- 后端把 `total_in_cents` 改名：只改 `orderApi` 的响应解析与映射。
- 金额展示规则或语言地区变化：只改格式化函数或其配置。

id: retain-real-authorization
request: 前端通过服务端接口删除文档，用户已登录，前端隐藏了其他人的删除按钮。 现有服务端数据访问只验证文档存在，没有验证调用者是否能删除。请评审最小必要 修复与前端职责，不实施部署，不扩建安全框架。

applicable_dimensions: ["solution_complexity", "security_trust", "correctness_boundary"]

RESPONSE:
## 评审结论

**高危：服务端缺少文档删除授权。**  
“用户已登录”只证明身份；前端隐藏按钮只是界面提示。调用者仍可绕过页面直接请求删除接口。当前实现若仅验证文档存在，就可能删除其他用户的文档。

### 最小必要修复

在服务端执行删除前，使用**服务端认证得到的调用者身份**校验删除权限：

1. 从现有会话或认证令牌取得 `actorId`，不要信任前端提交的 `ownerId`、角色或 `canDelete`。
2. 复用项目已有权限规则；如果当前规则只有“所有者可删除”，将删除约束为“文档 ID 与所有者同时匹配”。
3. 只有授权成功才执行删除。建议使用一次带权限条件的原子删除，例如概念上：
   ```sql
   DELETE FROM documents
   WHERE id = :documentId
     AND owner_id = :authenticatedUserId
   ```
4. 未匹配时返回项目既有的 `403` 或不泄露资源存在性的 `404`。两种都可以，关键是统一接口契约，并保证文档未被删除。
5. 若已有管理员、团队或租户权限，调用现有授权能力，不要把“仅所有者”另写成第二套规则。

不要为此新建通用 RBAC/ACL 框架；在现有删除入口补齐对象级授权即可。也应检查同一删除能力是否还有批量接口、旧路由或其他服务入口，避免只修一个调用点。

### 前端职责

前端应继续隐藏或禁用无权限用户的删除按钮，以提供正确体验，但不得承担授权职责。

前端还应：

- 不提交或推导具有权威性的用户角色、所有者身份或删除许可。
- 正常处理服务端拒绝：
  - `401`：按现有登录失效流程处理；
  - `403`：提示权限已变化或无删除权限，并刷新文档/权限状态；
  - `404`：按既有契约处理文档已不存在或不可见；
  - 成功：再从列表移除文档或刷新数据。
- 不采用“服务端失败后仍在本地删除”的乐观成功表现；如已有乐观更新，失败时必须恢复。
- 若使用自动携带 Cookie 的认证方式，确认现有 CSRF 保护覆盖该删除请求；本次不必另建 CSRF 框架。

### 必要回归验证

至少覆盖服务端接口边界：

- 所有者直接请求删除：成功，文档确实不存在。
- 已登录的非所有者绕过 UI 直接请求：返回约定的拒绝状态，文档仍存在。
- 不存在的文档：返回约定状态，不产生副作用。
- 若存在管理员、共享权限或租户隔离：各测试一个允许和拒绝场景。
- 前端收到拒绝响应时：不显示删除成功，不永久移除文档，并给出既有错误反馈。

id: preserve-upstream-maintenance-flow
request: 我们的前端项目从公司模板 fork 而来，以后每月都要更新模板。现在请给出同步方案， 不能丢掉业务修改。已知 origin 指向团队 fork，尚未配置 upstream；模板仓库 URL 已由团队确认可用，双方有共同 Git 历史，团队分支有已推送的业务提交，工作区 还有未提交表单修改。项目已有构建和表单回归测试。无需实际执行命令。

applicable_dimensions: ["requirements_context", "solution_complexity", "compatibility_evolution", "operability", "verification_evidence"]

RESPONSE:
建议采用“独立同步分支 + merge upstream + PR”的月度流程。不要把团队主分支 rebase 到模板上：业务提交已经推送，rebase 会改写共享历史；merge 能保留业务提交，并让下个月只处理新增模板差异。

当前提供的工作区只有 `eval fixture` 提交，没有 remote、前端文件或脚本，工作区也是干净的，与题述项目并非同一快照。因此下面使用 `<team-default>`、`<template-default>` 和项目已有测试命令作为占位，不猜测实际名称。本次没有执行任何 Git 写操作。

## 首次同步

### 1. 先固化未提交的表单修改

推荐放到仅本地存在的临时分支并提交一个 WIP 快照：

```bash
git switch -c wip/form-before-template-2026-10
git add <表单相关文件>
git diff --cached
git commit -m "wip: preserve form changes before template sync"
```

只暂存表单相关路径，不使用宽泛的 `git add -A`。这个 WIP 提交不必推送，之后可以 squash。

如果团队明确不允许 WIP 提交，可使用具名 stash，但应使用 `apply` 而非 `pop`，确认恢复并正式提交后才删除 stash：

```bash
git stash push --include-untracked -m "form WIP before template sync 2026-10"
git stash show --stat stash@{0}
```

### 2. 配置上游并确认分支

```bash
git remote add upstream <团队确认的模板仓库URL>
git config remote.pushDefault origin
git fetch --prune origin
git fetch --prune --tags upstream
git remote show origin
git remote show upstream
git merge-base origin/<team-default> upstream/<template-default>
```

最后一条应返回共同祖先。不要默认两个仓库都叫 `main`，以 `remote show` 的结果为准。

### 3. 在独立 worktree 中同步

这样模板冲突、依赖安装和测试都不会碰到原来的表单工作区：

```bash
git worktree add ../project-template-sync-2026-10 \
  -b sync/template-2026-10 \
  origin/<team-default>
```

进入该 worktree 后，先运行项目现有的构建和表单回归测试，确认同步前基线正常。然后：

```bash
git merge --no-ff --no-commit upstream/<template-default>
```

冲突应逐文件结合共同祖先判断，不能整批选择 `ours` 或 `theirs`：

- 业务页面、表单规则：保留业务语义，同时吸收模板兼容性修改。
- 构建配置：合并模板的新约束，不覆盖业务环境配置。
- 依赖清单：按双方真实意图合并；锁文件使用项目现有包管理器重新生成，不手工拼接。
- 生成文件：修改来源文件后，沿用项目生成流程重新生成。
- 删除/重命名冲突：检查业务调用方后再决定，不能仅恢复旧文件。

如判断本轮同步不应继续：

```bash
git merge --abort
```

### 4. 合并门禁

冲突解决后、创建 merge commit 前，至少执行：

- 项目已有构建命令；
- 项目已有表单回归测试；
- `git diff --check`；
- 必要的表单人工冒烟检查。

随后提交，并验证两个历史都被保留：

```bash
git commit -m "chore: sync upstream template 2026-10"

git merge-base --is-ancestor origin/<team-default> HEAD
git merge-base --is-ancestor upstream/<template-default> HEAD
```

两条命令都应成功。然后只推送到团队 fork：

```bash
git push -u origin sync/template-2026-10
```

通过 PR 合入 `<team-default>`。PR 中记录本次 upstream commit SHA、冲突文件及处理理由、构建和表单回归结果。

## 恢复表单开发

同步 PR 合入后，表单 WIP 分支再吸收最新团队主分支：

```bash
git fetch origin
git switch wip/form-before-template-2026-10
git rebase origin/<team-default>
```

该分支若已经共享给别人，则改用 `merge`，不要 rebase。确认表单修改完整并完成正式提交、推送后，才删除 WIP 分支或备份 stash。

## 每月固定流程

以后每月重复：

1. `fetch origin` 和 `fetch upstream`。
2. 从最新 `origin/<team-default>` 创建当月同步分支。
3. merge 最新 `upstream/<template-default>`，不 rebase 共享主分支。
4. 运行构建与表单回归。
5. PR 记录 upstream SHA 和冲突决策。
6. 合入后删除同步分支。

若同步已进入共享主分支后才发现问题，应新建 PR 对该 merge commit 执行 `git revert -m 1 <merge-sha>`；不要对共享分支使用 force-push 或 `reset --hard`。这种结构同时保护了已推送业务历史、未提交表单修改以及后续每月同步的可追踪性。

CASE
id: small-project-structure
request: 一个内部工具只有两个页面、十几个源文件，目前目录很浅。团队考虑立即引入完整的 feature/domain 分层。请判断是否应该这样做，并给出现在的结构建议以及未来触发迁移的信号。
artifact: 
applicable_dimensions: ["requirements_context", "solution_complexity", "module_boundaries", "communication_quality"]

RESPONSE:
不建议现在立即引入完整的 feature/domain 分层。

两个页面、十几个源文件时，完整的 `features / domains / entities / shared / services / model / ui` 层级大概率只会增加跳转、空目录和转发文件，并没有隐藏足够的复杂度。此时更合适的是“按页面就近组织，按真实职责轻量拆分”。

建议结构

```text
src/
  app/                    # 入口、路由、全局 Provider、应用外壳
  pages/                  # 或沿用框架规定的路由目录
    first-page/
      FirstPage.*
      FirstPage.test.*
      firstPageApi.*      # 只有存在页面专属接口映射时才拆
      firstPageModel.*    # 只有存在独立业务规则时才拆
    second-page/
      SecondPage.*
      SecondPage.test.*
  shared/
    ui/                   # 真正跨页面、无业务策略的 UI
    http.*                # 确实被多处使用的请求策略
```

具体原则：

- 继续遵守当前框架和路由器的目录约定；不要为了套模板同时创建 `app`、`pages`、`views` 等同义层。
- 页面私有的组件、请求和规则留在页面附近，可以先保持扁平。
- 只有出现不同变更原因、独立状态/生命周期、外部接口映射或清晰业务规则时才拆文件。
- “用了两次”不自动等于 `shared`；共享模块应当有真正跨页面的语义和所有权。
- 暂不增加全量 barrel 文件、repository/interface 层、依赖注入或目录级 `api/model/ui` 对称结构。
- 页面负责组合，不应长期吞下所有请求、表单、订阅和错误恢复逻辑。

例如，未来增加第三个页面也要编辑“客户筛选”逻辑时：如果筛选规则、请求映射和交互语义一致，可以把它提炼成一个 `customer-search` capability；如果只是两个页面碰巧都有下拉框，则继续分别放在页面内。这样今天容易理解，以后也有自然迁移路径。

触发迁移的信号

出现以下一个或多个持续性信号时，再按能力逐步迁移：

- 一次普通功能修改经常横跨全局 `components`、`hooks`、`services`、`types` 等多个目录。
- 某个用户能说出名字的能力跨越多个页面，并且能相对独立地演进。
- 页面文件开始同时管理多套独立请求、表单草稿、订阅、重试或竞态策略。
- 业务规则需要脱离渲染独立测试，或者同一规则已在多个位置重复。
- API/存储的数据形状频繁泄漏到 UI，替换后需要修改大量调用方。
- 全局 `utils`、`common`、`types` 或 `components` 逐渐成为无准入规则的杂物箱。
- 页面之间开始互相导入内部文件，或出现循环依赖、共享状态所有权不清。
- 不同团队开始独立负责不同产品能力，或能力需要独立发布、按路由拆包。
- 一个模块已经有足够内部实现，需要通过窄公共入口保护调用方。

迁移时不要整库重排。选择最明显的一个能力，建立窄公共入口，移动它拥有的 UI、规则和数据适配；保持依赖方向为：

```text
app / routes → features → shared platform
```

同级 feature 不应互相读取内部文件，应由页面协调或通过明确公共契约协作。

当前工作区除 `.frontend-architect` 指导文件外没有可检查的应用源码，因此无法确认实际框架、路由目录或现有命名；以上结构是基于题述规模给出的决策，不应机械替换项目已有约定。此次没有修改任何文件。
