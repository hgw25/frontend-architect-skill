```jsx
    <User key={user.id} user={user} />

}
```

```jsx

  [users, query],

```

它只适合在真实数据规模下确认过滤是瓶颈后使用。这里没有依赖稳定数组引用的下游消费者，而且 `useMemo` 还会要求调用方始终以新引用表达 `users` 变化，可能引入额外的陈旧结果风险；它不能作为正确性机制。

- 初次渲染只出现名称包含 `query` 的用户。
- rerender 后分别改变 `query`、`users`，结果立即对应最新 props。
- 覆盖空查询、无匹配、空用户列表、多个匹配及原有顺序。
- 保留当前 `includes` 的大小写和 Unicode 行为，不擅自改成模糊或忽略大小写匹配。
- 如果项目支持 SSR，检查服务端 HTML 与客户端首次渲染一致且已过滤。
- 运行项目既有组件测试、类型检查和 lint；若列表规模确实可能很大，再用代表性数据做前后性能测量，测出瓶颈后才考虑 `useMemo`。

request: 请安全评审下面的 React 富文本组件。后端声称已经“过滤过输入”，正文来自用户， 其中允许有限 HTML 和链接。请给出最小、可维护的修复方向和验证方案，说明 CSP 在 其中的角色；不要通过去掉全部富文本来回避产品要求。

RESPONSE:
## 评审结论

**高危：当前组件存在存储型 XSS 风险。**

`html` 来自用户，而 `dangerouslySetInnerHTML` 会绕过 React 的默认转义。后端“过滤过”不足以构成可验证的安全契约：只要后端规则遗漏危险属性、URL scheme、SVG/MathML 或 HTML 解析边界，恶意内容就会进入浏览器执行。

不需要取消富文本；最小修复是在唯一的富文本渲染边界使用成熟、基于 allowlist 的 HTML sanitizer。

## 建议修复

使用项目现有包管理器引入并锁定类似 DOMPurify 的成熟库，不要自行用正则过滤 HTML：

```tsx
import DOMPurify, { type Config } from "dompurify";

const ARTICLE_HTML_POLICY: Config = {
  ALLOWED_TAGS: [
    "p",
    "br",
    "strong",
    "em",
    "ul",
    "ol",
    "li",
    "blockquote",
    "a",
  ],
  ALLOWED_ATTR: ["href", "title"],
  ALLOW_DATA_ATTR: false,
};

function sanitizeArticleHtml(html: string): string {
  return DOMPurify.sanitize(html, ARTICLE_HTML_POLICY);
}

export function ArticleBody({ html }: { html: string }) {
  const safeHtml = sanitizeArticleHtml(html);

  return <article dangerouslySetInnerHTML={{ __html: safeHtml }} />;
}
```

这里保留 `dangerouslySetInnerHTML` 是合理的：危险 sink 被收敛在一个组件中，并且输入在紧邻 sink 的明确边界完成净化。

还需明确以下策略，而不能沿用“有限 HTML”这样的口头约定：

- 哪些标签和属性确实属于产品能力。
- 链接是否只允许相对地址、HTTP 和 HTTPS；是否允许 `mailto:` 或 `tel:`。
- 默认不要允许 `style`、事件属性、`iframe`、`object`、`svg`、`math`、表单元素和资源加载标签。
- 若允许 `target="_blank"`，组件必须统一补充 `rel="noopener noreferrer"`；更小的初始方案是不允许 `target`。
- 后端继续在写入或输出边界净化，并把 allowlist、URL 规则和策略版本变成明确契约。前端净化是浏览器 sink 的保障，不应成为后端放弃治理的理由。
- 若应用包含 SSR，必须选用项目运行环境支持的 sanitizer 接入方式，确保首屏服务端输出已经净化，不能等 hydration 后才处理。

不要通过类型断言把普通字符串伪装成 `SafeHtml`；类型不能证明运行时内容安全。

## 验证方案

先为 sanitizer 策略建立表驱动测试：

- 合法的段落、强调、列表和链接被保留。
- `<script>`、事件属性和不允许的标签被移除。
- `javascript:`、`data:`、实体编码或混合大小写形式的危险链接不能保留可点击能力。
- 覆盖 `<img onerror>`, `<svg>`, `<math>`, `<iframe>`, `<base>`, `style` 和畸形嵌套 HTML。
- 若允许外链新窗口，验证最终 DOM 上的 `rel`，而不是只比较输入字符串。

再做一个真实浏览器测试：

1. 渲染上述攻击样本。
2. 用哨兵变量或测试回调确认脚本、事件处理器均未执行。
3. 点击保留下来的链接，验证实际导航 scheme 和新窗口行为。
4. 确认合法富文本仍然按产品要求显示。

DOM 模拟器适合检查净化后的结构，但不能单独证明浏览器中不会执行恶意内容。sanitizer 升级时应重复运行这组攻击语料。

## CSP 的角色

CSP 是第二道防线，不是 sanitizer 的替代品。建议通过 HTTP 响应头部署，并先用 Report-Only 收集违规，再切换到强制模式。适配现有资源来源后的基线通常包括：

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-<每次响应随机值>';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none'
```

避免 `script-src 'unsafe-inline'` 和 `'unsafe-eval'`。条件允许时，再引入 Trusted Types，把原始 HTML sink 限制到命名策略。

CSP 可以降低遗漏脚本、内联事件和外部脚本注入的可利用性，但它不会定义允许的富文本格式，也不能可靠解决恶意链接、内容欺骗或所有浏览器解析问题。因此正确顺序是：**明确 allowlist → sanitizer 守住 sink → CSP/Trusted Types 提供纵深防御**。

## 1. 兼容边界

页面只依赖一个稳定的领域接口，例如：

```ts
interface BookingGateway {
  loadConfirmation(input: ConfirmationQuery): Promise<Confirmation>
  submit(command: BookingCommand): Promise<SubmitOutcome>
  getOutcome(intentId: BookingIntentId): Promise<BookingOutcome>
}

type SubmitOutcome =
  | { status: 'confirmed'; bookingId: BookingId }
  | { status: 'rejected'; reason: RejectionReason }
  | { status: 'unknown'; intentId: BookingIntentId }
```

旧、新接口各有一个适配器，负责：

- 校验外部响应结构，并归一化成同一个领域模型。
- 统一错误分类、金额和时间语义、可空字段及状态枚举。
- 隐藏接口版本、URL、DTO 和灰度规则；组件不得出现 `if (useV2)`。
- 保持现有数据层对加载、缓存、取消和错误展示的所有权，不新增第二套长期缓存。

读取和提交使用两个独立开关：`confirmation-read-v2` 可以先灰度；`booking-submit-v2` 必须等幂等契约完成后再开。

真实提交禁止影子双写。影子验证只能用于无副作用读取、录制脱敏请求的离线回放，或隔离环境中的契约比较。

## 2. 幂等和重复提交

首选由服务端创建不可猜测的 `bookingIntentId`，在用户进入确认流程时绑定账户、租户、报价版本和预订快照。提交时携带该 ID 作为幂等键。

服务端契约必须保证：

- 幂等记录与预订创建原子提交。
- 同一意图、同一请求重复调用，返回第一次提交的权威结果。
- 同一幂等键搭配不同请求内容，返回明确冲突，不能创建第二笔预订。
- 旧、新接口共享同一幂等域；否则不得在未知结果后跨接口重试。
- 幂等记录保留时间至少覆盖最长用户恢复、客户端重试和延迟请求窗口。
- 提供按 `bookingIntentId` 查询 `pending | confirmed | rejected | not_found` 的授权接口。
- 权限、资源归属和租户隔离均在服务端校验。

前端同时提供体验层防护，但不把它当作幂等保证：

- 网络发送前持久化意图 ID。
- 指针、键盘和程序调用统一经过一个提交入口。
- `submitting`、`unknown` 状态禁止再次创建新意图。
- 重试使用原来的意图 ID和不可变请求快照。
- 用户修改日期、房型、人数等业务内容后，旧提交先完成核对，再建立新的意图。
- 多标签页可同步“正在提交/已确认”提示，但跨标签、跨设备的正确性仍由服务端保证。
- 迟到的旧请求不得覆盖较新的确认、错误或 loading 状态。

不要用请求内容哈希代替意图 ID：用户可能合法地预订两个内容相同的订单。

## 3. 错误恢复

页面状态应明确区分：

| 状态 | 页面行为 |
|---|---|
| `ready` | 允许首次确认 |
| `submitting` | 锁定提交，显示处理中 |
| `confirmed` | 展示唯一权威预订结果 |
| `rejected` | 展示明确业务原因；修改内容后建立新意图 |
| `unknown` | 告知“结果仍在确认，请勿重新预订”，自动查询权威状态 |
| `recovery-failed` | 保留意图参考号，提供继续查询或人工处理入口，仍不允许盲目新建 |

恢复规则：

- 明确的校验拒绝：允许修正，不当成成功。
- `409` 幂等冲突：查询原结果；若请求内容不同则停止并提示重新开始。
- 超时、断网、连接中断、部分 `5xx`：一律视为结果未知，而不是失败。
- 未知结果先按退避策略查询状态；只有查询明确为 `not_found` 且服务端保证未提交时，才用原幂等键重试。
- 登录过期：重新认证后先查询原意图，不能直接创建新意图。
- 刷新、返回或重新挂载：从服务端会话恢复待处理意图并继续核对。
- 自动回退到旧接口只在两套接口共享幂等域时才安全；否则禁止。

## 4. 两周灰度

发布控制在服务端或可信的边缘层完成，提供可在一分钟内生效的 kill switch。分流以 `bookingIntentId` 为单位固定：同一意图的首次提交、重试和状态查询不能在两个接口间漂移。

建议节奏如下，但每一阶段都由指标门槛驱动，日期不是强制晋级条件：

1. 第 1–2 天：部署兼容层，仍为旧接口 100%；验证状态机、幂等键透传和生产信号。
2. 第 2–3 天：仅灰度 V2 读取，比较归一化结果；不发送影子预订。
3. 第 3 天：内部账户或明确白名单使用 V2 提交。
4. 随后按 `0.5% → 2% → 5% → 10% → 25% → 50% → 100%` 推进。
5. 每档至少覆盖一个业务高峰，并达到预先计算的最小样本量。
6. 先覆盖代表性随机流量，再检查登录状态、地区、语言、浏览器、支付/供应商等关键分段，避免只验证低风险用户。
7. 到达 100% 后仍保留旧适配器和 kill switch，完成至少一个高峰周期的稳定观察。

两周结束不等于自动删除旧链路。只有满足以下条件才单独提交清理变更：

- V2 已全量并跨过约定观察期。
- 没有未完成的旧链路意图。
- 重复预订和未知结果指标符合门槛。
- 回滚演练完成。
- 服务端确认旧接口的下线窗口。

## 5. 生产信号

必须同时有前端流程信号和服务端权威业务信号。核心看板按接口版本、灰度组、发布版本和关键业务分段对比：

- 每万次预订意图产生的重复预订数；以服务端事实为准。
- 提交意图数、确认成功率、明确拒绝率。
- `unknown` 结果率、持续时长及最终恢复成功率。
- 幂等命中、幂等冲突、同键多订单等服务端计数。
- 用户重复点击、同意图请求次数和重试次数分桶。
- 提交及状态查询的 p50、p95、p99 延迟。
- V2 相对固定 V1 对照组的错误率和转化率。
- 认证失败、跨租户拒绝、响应解析失败。
- JavaScript 异常、页面放弃率以及人工客服升级量。

`submit_started`、`confirmed`、`rejected`、`outcome_unknown`、`reconciled` 等事件要有稳定语义；不能只用“按钮点击”推断预订结果。告警需要链接对应操作手册和 kill switch。

## 6. 隐私控制

- 遥测采用字段白名单，不记录姓名、邮箱、证件、手机号、完整行程、请求体或接口响应体。
- 不把幂等键、预订号、令牌放入 URL、前端错误消息或第三方分析工具。
- 关联排障使用短期、不可猜测的追踪 ID；原始业务标识只在受控服务端日志中可见。
- 对追踪 ID、IP、设备信息等可关联数据规定访问角色、保留期限和删除流程。
- 业务必要的可靠性日志与营销分析分离；第三方 SDK 不应在敏感确认页获得 DOM、用户对象或网络载荷。
- 错误采集和 source map 上传前检查请求面包屑、上下文及自动序列化内容，关闭请求体抓取。
- 灰度分组不是授权机制，所有账户和资源权限仍由服务端执行。

## 7. 停线与回滚条件

以下任一情况立即把“新意图的 V2 提交比例”切到 0：

- 出现一例可归因于 V2 的同意图多订单。
- 同一幂等键得到不同预订结果，或幂等记录无法查询。
- 发现越权、跨租户或敏感数据泄漏。
- 未知结果无法通过权威查询恢复。
- 响应兼容错误导致金额、日期、库存或预订状态解释错误。

以下情况冻结晋级；连续两个观测窗口仍存在则回滚：

- V2 成功率低于匹配 V1 对照组，超过预先约定的业务 SLO或统计波动带。
- `unknown` 结果率、解析失败率或人工恢复量超过基线阈值。
- p95/p99 延迟明显恶化并造成重复操作或放弃增长。
- 关键用户分段出现整体均值掩盖的显著退化。

+# Vite feature flags
+
+`@frontend-architect-eval/feature-flags` exposes a deliberately small, typed
+subset of a server-side JSON file as `virtual:feature-flags`. It supports Vite 8
+development, production builds, watch mode, and HMR.
+
+## Setup
+
+```ts
+// vite.config.ts
+import { featureFlags } from '@frontend-architect-eval/feature-flags'
+import { defineConfig } from 'vite'
+
+export default defineConfig({
+  plugins: [
+    featureFlags({
+      source: new URL('./flags.json', import.meta.url),
+      expose: ['checkoutV2', 'theme'],
+    }),
+  ],
+})
+```
+
+`source` accepts a file URL, an absolute path, or a path relative to Vite's
+project root. The file must be a JSON object. Every exposed value must be a
+boolean, finite number, or string.
+
+Add the package's virtual-module declaration to the application TypeScript
+configuration:
+
+```json
+{
+  "compilerOptions": {
+    "types": ["@frontend-architect-eval/feature-flags/virtual"]
+  }
+}
+```
+
+Then declare the application's flag schema. This is intentionally owned by the
+consumer because a TypeScript declaration cannot infer a runtime JSON file:
+
+```ts
+// src/feature-flags.d.ts
+import 'virtual:feature-flags'
+
+declare module 'virtual:feature-flags' {
+  interface FeatureFlags {
+    readonly checkoutV2: boolean
+    readonly theme: 'dark' | 'light'
+  }
+}
+```
+
+Application code receives exact, readonly keys:
+
+```ts
+import { flags } from 'virtual:feature-flags'
+
+if (flags.checkoutV2) {
+  // ...
+}
+```
+
+The declaration describes the expected contract; startup/build validation
+ensures exposed values exist and use a supported primitive type. A flag's more
+specific domain (for example the `theme` literals above) remains application
+policy and should be checked when the source file is produced.
+
+## Runtime, security, and caching
+
+The JSON file stays in Node/Vite. Only names in `expose` are serialized into the
+generated client module. Treat this allowlist as a security boundary: review it
+like client-visible environment variables and never add credentials, private
+tokens, or server authorization decisions. Values not in `expose` are absent
+from generated code, diagnostics, and source maps.
+
+The plugin validates configuration during Vite startup, before the virtual
+module is imported, and reports the option or source file plus a corrective
+action. Diagnostics identify exposed keys but never print their values or the
+contents of the source file.
+
+One filtered module string is cached per plugin instance. Production and watch
+builds refresh it in `buildStart`; the dev server watches the source and refreshes
+the cache before invalidating `virtual:feature-flags` during HMR. The cache key is
+effectively the immutable plugin options plus the watched source file, so every
+behavior-affecting input has an invalidation path. A single-file polling fallback
+for virtualized and network file systems forwards only missed changes into Vite's
+watcher; it is removed when the plugin container closes and does not alter the
+application's global watch settings.
+
+Consumer source is not transformed, so its existing source maps remain intact.
+The generated virtual module returns a source-free map: the server JSON is never
+listed as a source and cannot re-enter a client artifact through
+`sourcesContent`. The published plugin JavaScript and declarations include their
+own maps, and `src` is shipped so those maps resolve for maintainers; package
+exports still prevent applications from depending on source internals.
+
+## Public surface and release policy
+
+The root package export contains `featureFlags`, `FeatureFlagsOptions`, and
+`FeatureFlagValue`. `@frontend-architect-eval/feature-flags/virtual` is a
+type-support entry point; application runtime code must continue importing
+`virtual:feature-flags`. Other files are internal and are blocked by package
+exports. The package is ESM-only and currently supports Vite 8 and Vite's Node
+runtime range.
+
+Use SemVer based on consumer impact:
+
+- patch: fixes that preserve generated values, diagnostics, types, and supported
+  host versions;
+- minor: optional configuration or additive exports;
+- major: virtual-module shape changes, stricter accepted values, removed options,
+  changed HMR behavior, or dropped Vite/Node versions.
+
+Type changes and stricter validation can be breaking even when the JavaScript
+function name is unchanged. Deprecations should name the replacement and remain
+for one major line. Validate risky host-version changes with a prerelease before
+widening the peer range.
+
+## Release verification
+
+Run `npm run check` from the repository root. It builds declarations and maps,
+type-checks the exact consumer schema, runs a real Vite production build, starts
+a real dev server and edits the source to exercise HMR, checks actionable failure
+diagnostics, scans bundles and maps for a server-only token, and installs the
+packed tarball into a temporary consumer. Publish only that verified tarball;
+do not publish directly from unbuilt source.
