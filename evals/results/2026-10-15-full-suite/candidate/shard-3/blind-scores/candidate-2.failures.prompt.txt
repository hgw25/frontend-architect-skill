## 结论

**不建议把这段实现原样放入前端基础库，也暂时没有足够证据需要自研一个通用 `groupBy`。**

它存在可稳定复现的正确性缺陷；同时没有定义返回结构、键语义、顺序和兼容范围。现代环境应优先在调用处选择 `Object.groupBy()` 或 `Map.groupBy()`。只有目标运行时不支持、且项目确有多个语义一致的消费者时，才值得提供兼容实现或统一垫片。

仓库中没有源码、包清单、调用方或浏览器支持矩阵，因此目前无法证明基础库抽象的实际消费者与兼容需求。

## 阻断问题

### 1. 普通对象会与原型属性冲突

```js
if (result[key]) result[key].push(item)
```

`result` 继承 `Object.prototype`。当键为 `constructor`、`toString` 或 `__proto__` 时，读到的不是分组数组，而是继承属性，随后调用 `.push()` 会抛出异常。

我在仓库当前 Node v22.22.2 环境中执行了原实现，三个键都会得到：

```text
TypeError: result[key].push is not a function
```

这不是罕见的纯理论输入：按对象字段分组时，后端数据、标签或用户输入完全可能出现这些字符串。它至少是可靠性问题；若键来自外部输入，还可以造成可控异常。

仅改成 `key in result` 或 `hasOwnProperty` 不足以完整处理 `__proto__`。对象型结果应使用 null prototype，并采用 own-property-safe 的写入策略。原生 `Object.groupBy()` 已经返回 null-prototype 对象。

### 2. 键被隐式转换，可能无声合并不同分组

对象属性只能使用字符串或 Symbol。选择器返回其他值时会发生强制转换：

```js
1       // "1"
"1"     // "1"

{ a: 1 } // "[object Object]"
{ b: 2 } // "[object Object]"
```

原实现会把上述不同值合并。实测结果包括：

```js
{ "1": ["number", "string"] }
{ "[object Object]": ["left", "right"] }
```

如果调用者需要对象身份、数字与字符串的区分，正确返回类型应是 `Map`，不能把这种合并留作未声明的偶然行为。

## API 设计问题

### 3. 一个参数承担两种完全不同的协议

`generateKey` 既可以是函数，也可以是字符串属性名：

```js
groupBy(items, item => item.status)
groupBy(items, "status")
```

这会带来几个问题：

- 参数名声称它是函数，但运行时又把字符串解释成属性名。
- JavaScript 调用者传入其他错误值时，报错时机取决于集合是否为空：`groupBy([], null)` 会静默成功，非空输入才抛错。
- TypeScript 类型会变成回调与属性名的重载；还要表达属性值是否可作为对象键。
- 字符串捷径排除了 Symbol 属性名。
- 属性名拼错时，所有项目会被静默归入 `"undefined"` 分组。

除非真实调用点证明属性名简写明显降低了使用成本，否则保留单一回调接口更清楚：

```ts
groupBy(items, item => item.status)
```

若简写确有独立价值，应使用单独命名的函数，例如 `groupByProperty`，而不是在一个参数里做运行时分派。

### 4. 回调的第三个参数扩大了契约

```js
generateKey(item, index, items)
```

`items` 可能是数组、Set、生成器或一次性迭代器。把正在遍历的输入暴露给回调：

- 鼓励回调依赖或修改遍历源；
- 对生成器而言几乎没有稳定、通用的集合语义；
- 与现代原生 `Object.groupBy`/`Map.groupBy` 的 `(element, index)` 回调形状不一致。

建议只传 `item` 和 `index`。如果分组依赖整个集合，通常已经不是普通 `groupBy`，应由调用方显式建模。

### 5. 返回契约没有确定

进入基础库前至少要明确：

- 返回 `Object` 还是 `Map`；
- 键是否允许对象、Symbol、数字；
- 是否执行字符串强制转换；
- 分组和组内元素的顺序保证；
- 是否接受任意 `Iterable`；
- 返回数组是否允许调用方修改；
- 选择器异常是否原样传播；
- 缺失分组在 TypeScript 中如何表达。

尤其是对象结果中，整数形式的属性名不总按首次出现顺序枚举。如果调用者依赖严格的分组插入顺序，应使用 `Map`。

## 建议方案

优先让调用方按键语义直接选择平台能力：

```ts
// 键最终就是属性键，需要对象访问
const byStatus = Object.groupBy(items, item => item.status)

// 键可能是对象，或必须保留类型、身份与插入顺序
const byOwner = Map.groupBy(items, item => item.owner)
```

若项目目标环境尚不支持这些 API：

1. 先确认构建目标和运行时矩阵；TypeScript/Babel 能识别语法并不等于会自动补齐新的全局 API。
2. 优先采用项目已有 polyfill 方案，避免再创造一套近似但不同的语义。
3. 如果确实需要本地兼容实现，建议明确拆成对象版与 Map 版，而不是一个会隐式转换键的万能函数。
4. 对象版至少应具有类似契约：

```ts
function groupByPropertyKey<T, K extends PropertyKey>(
  items: Iterable<T>,
  keyOf: (item: T, index: number) => K,
): Partial<Record<K, T[]>>
```

其中：

- 使用 null-prototype 对象；
- 不继承 `constructor`、`toString`、`__proto__`；
- 类型返回 `Partial<Record<...>>`，因为并非每个可能的键都有分组；
- 文档明确遵循 PropertyKey 转换与对象枚举顺序；
- 不额外传入遍历源。

需要任意键时另提供 Map 语义，而不是放宽上述返回类型。

## 进入基础库前的最低验证

如果最终仍决定维护自定义实现，测试应通过公开 API 覆盖：

- 空输入、重复键以及元素顺序；
- `""`、`0`、`false`、`undefined`、Symbol；
- `constructor`、`toString`、`__proto__`；
- 数字 `1` 与字符串 `"1"` 的既定语义；
- 对象键的身份语义；
- 数组、Set、生成器等声称支持的 Iterable；
- 选择器抛错；
- TypeScript 推断、缺失分组以及无效键类型；
- 最终打包导出的函数与声明文件，而不只测试源码内部函数。

综合来看，真正需要解决的是“调用者应该选择对象键语义还是身份键语义”，不是把 `for...of` 换成 `reduce`。当前实现既没有安全实现前者，也无法提供后者，因此不适合作为通用基础库 API。未修改任何仓库文件。

## 状态与副作用所有权

| 所有者 | 拥有的状态/副作用 | 内部契约 |
|---|---|---|
| `useCheckoutDraft` | 可编辑草稿、dirty/touched、同步校验、草稿重置 | 暴露领域字段更新、`validate()` 和只读草稿快照；若已有表单库，应封装或直接复用其模型，不再复制一套表单状态 |
| `pricing.ts` | 不拥有状态和副作用 | 输入商品、配送选择、已确认优惠等数据，返回 `PricingBreakdown`；金额、折扣、税费、合计只从这些输入派生 |
| `useCouponApplication` | 优惠券输入、请求状态、已应用优惠、可恢复错误、请求身份 | `apply(code)`、`clear()`、`retry()`；请求使用提交时的完整价格上下文快照 |
| `useInventoryAvailability` | 当前商品集合对应的库存快照、连接状态、订阅错误 | 输入稳定的商品身份集合；负责订阅、更换订阅、退订和忽略旧订阅回调 |
| `usePaymentSession` | SDK 实例、支付会话、ready/error 状态及销毁 | 向提交工作流提供窄的 `confirmPayment(...)` 能力，不向页面泄漏原始 SDK 实例 |
| `useCheckoutSubmission` | 一次下单尝试的不可变快照、提交中/成功/失败/结果未知状态、重复触发策略 | `submit(snapshot)`；借用支付能力并调用下单 adapter，但不重新拥有草稿、库存、优惠或 SDK 生命周期 |
| `CheckoutPage` | 只负责组合上述能力、建立页面级提交顺序和路由结果处理 | 不复制子能力状态，不实现请求细节，不集中处理所有 cleanup |
| 展示组件 | 局部输入交互、焦点与反馈呈现 | 只接收领域值和动作，不解析网络响应，不直接调用 SDK 或 HTTP |

草稿和提交快照必须分开。用户点击提交时创建只读快照；之后继续编辑表单，不能改变进行中请求或“重试上一次提交”的含义。

价格权威性必须保持当前契约：若现有金额是服务端报价，`pricing.ts` 只能做投影和格式化，不能在客户端重新实现权威规则；若当前确实由客户端计算，则原计算完整迁移为纯函数，不借重构偷偷改变舍入和优惠顺序。

## 关键异步策略

优惠券通常适用“最新请求才可发布”：

```text
申请 A → 申请 B → B 成功 → A 失败
最终状态仍应是 B 成功，A 的错误和 finally 也不能覆盖 B。
```

中止旧请求可以节省工作，但仍需请求身份检查，因为中止不保证服务端或客户端停止完成回调。

库存订阅必须由 `useInventoryAvailability` 完整拥有：

- 商品身份变化时先让旧订阅失效，再建立新订阅。
- cleanup 只释放该 hook 获取的订阅，不能关闭共享连接。
- 卸载或替换后，旧回调不得发布库存状态。

支付 SDK 的获取、部分初始化失败、替换和销毁属于一个生命周期。`PaymentMethodSection` 负责挂载位置和本地可访问性表现，`usePaymentSession` 负责资源；不可由页面、组件和提交 hook 分别销毁同一个实例。

提交策略应明确区分：

- 页面内重复点击：按钮禁用加命令级 guard。
- 重试或多客户端重复请求：只有服务端支持稳定幂等键时才能声称幂等。
- 请求超时：如果无法确认服务端结果，应进入“结果未知/待核对”状态，而不是直接显示明确失败并盲目重试。
- 支付确认与创建订单的顺序应作为一个工作流保留，不要拆成需要页面手工按顺序调用的多个步骤。

## 错误呈现

错误在能够恢复或准确呈现的层处理，避免同一错误既 toast 又内联又写入总错误：

- 优惠券拒绝：`CouponField` 就地显示并提供重试/清除。
- 支付初始化或确认错误：`PaymentMethodSection` 显示。
- 库存变化：在相关商品或 `InventoryNotice` 显示；若阻止提交，也参与页面级校验摘要。
- 服务端稳定字段错误：映射回对应表单字段。
- 无稳定字段身份的下单错误：进入 `CheckoutErrorSummary`，并按既有无障碍约定移动焦点或通过 live region 宣告。
- 意外运行时错误：沿用项目现有错误边界与日志机制，不在每个 adapter 中 catch 后伪装为空成功。

```text

        ↓
CheckoutPage（组合）
   ├── components
```

## 停止继续拆分的条件

达到以下状态即可停止，不设页面行数目标：

- 普通维护者能直接找到草稿、价格、优惠券、库存、支付和提交的唯一所有者。
- `CheckoutPage` 展现组合与提交主路径，而不是转发几十个无意义的包装函数。
- 每项外部资源只有一个获取与释放者，每个异步操作有明确的竞态策略。
- 状态没有在 page、hook 和 component 中重复保存。
- 新文件有独立的规则、生命周期、错误或交互契约；若只是改名转发，就不拆。
- 私有单次使用 helper 与所有者一起修改且抽出后更难阅读，就继续内联或同文件放置。
- 新目录若只含一个没有独立概念的文件，不创建目录。
- 删除某个边界若不会损害所有权、可测试性或变更定位，该边界就不应存在。

- 替换支付 SDK 应主要限定在 `paymentSdk`、`usePaymentSession`、支付区及其测试，草稿和定价无需感知。
