当前版本应判定为性能发布不通过：移动端 LCP 回退约 41%，INP 回退约 71%。如果仍在逐步放量，应先暂停扩量；有安全开关或兼容的旧版本时，回退到旧列表以控制用户影响。

新增 95KB JS、阻塞字体和 180ms 长任务都是强嫌疑，但还不能直接当作根因。工作区没有应用源码、构建配置或现有性能脚本，因此下面定义的是可落地的调查与发布契约，不虚构项目命令。

## 最小调查与修复顺序

1. 固定可比较基线

   - 保留最后一个良好版本及其构建产物、chunk manifest。
   - 旧版和候选版使用相同移动设备档位、浏览器版本、网络、数据集、登录态与缓存条件。
   - RUM 按商品列表路由、版本、移动端、设备档位和网络质量分组；不要拿全站聚合值比较。
   - 记录 LCP 元素、LCP 四阶段耗时，以及导致 INP 的具体筛选交互。
   - 若当前 RUM 无法区分版本或交互，先补这两个维度，再归因。

2. 先拆解 LCP，不先改列表结构

   对同一冷启动导航交替测量旧版和候选版，确认增加发生在哪一段：

   - TTFB；
   - LCP 资源发现延迟；
   - 资源下载时间；
   - 下载完成后的渲染延迟。

   同时做两个单变量实验：

   - 恢复旧字体配置，其他不变；
   - 恢复旧首路由 JS 图或禁用新增模块，其他不变。

   如果 LCP 是文本，重点验证字体 CSS、字体权重和 `font-display` 是否推迟首绘；如果是图片，检查新增 JS 是否推迟资源发现、主线程渲染或图片解码。不要无证据地增加 preload，它也可能争抢关键带宽。

3. 单独定位筛选的 180ms 长任务

   在发布构建、代表性商品数量下记录从输入到下一次绘制的浏览器 trace，拆出：

   - input delay；
   - 事件处理和筛选计算；
   - 框架更新及组件失效范围；
   - DOM 提交；
   - style/layout/paint。

   用 flame chart 判断主耗时究竟是过滤/排序、整表重渲染、同步布局还是其他脚本。组件 render 次数只能辅助定位，不能作为完成标准。

4. 按证据做最小修复

   推荐顺序如下：

   - 删除意外打入首路由的代码、重复依赖、整库导入或开发期代码。
   - 对首屏不需要的能力做 capability-level 拆分。若筛选需要该代码，不要等用户点击后才加载；可在 LCP 后空闲加载或在明确意图出现时预取，并重新测 INP。
   - 优先复用已有字体/权重。若新字体确属产品要求，再选择子集化、减少字重、合理 `font-display` 或经 trace 证明有效的 preload，同时守住 CLS。
   - 对筛选长任务先移除重复计算，缩小状态订阅，保持商品稳定 key/identity，只更新受影响项。
   - 只有当 trace 显示 DOM、布局或挂载节点数是瓶颈时，才考虑增量渲染或虚拟列表，并验证焦点、读屏顺序、滚动恢复和可变高度。
   - 只有纯计算仍然占主导时，才考虑预索引、分片让出主线程或 Worker；Worker 必须把序列化和结果过期处理一起计入。

   这一路径不需要默认重写列表。

## 可执行性能预算

以下预算同时包含用户结果和可诊断的代理指标；代理指标通过并不能替代 RUM。

| 层级 | 指标 | 发布预算 |
|---|---|---|
| 移动端 RUM | 商品列表 LCP p75 | `≤ 2.5s`，且相对匹配控制组回退 `≤ 10%`；以 2.2s 基线计算约为 `≤ 2.42s` |
| 移动端 RUM | 商品列表 INP p75 | `≤ 200ms`，且相对匹配控制组回退 `≤ 10%`；以 170ms 基线计算约为 `≤ 187ms` |
| 移动端 RUM | CLS p75 | `≤ 0.05`，且相对控制组绝对增量 `≤ 0.01` |
| 构建产物 | 首路由 JS gzip | 不高于最后良好版本 `+10KiB`；当前 `+95KB` 不通过 |
| 请求瀑布 | 新增阻塞字体请求 | `0`；必要字体不得形成比旧版更长的关键请求链 |
| 筛选 trace | 单个主线程任务 | 不得出现 `>50ms` 的任务 |
| 筛选实验室交互 | 输入至下一次绘制 p75 | 代表性移动设备档位上 `≤150ms`，为线上 200ms 留出余量 |
| 实验室加载 | LCP | 相同条件下相对旧版 p75 回退 `≤10%`，同时不得超过 `2.5s` |
| 实验室布局 | CLS | `≤0.05`，并覆盖字体完成加载后的状态 |

JS 预算应通过构建 manifest 对比执行；字体、长任务、LCP 和交互预算应从浏览器 trace 或 Performance API 产物读取。阈值和基线产物都应进入版本控制或 CI 制品，而不是依赖人工截图。

## 回归验证

使用两组固定场景：

- 冷缓存首次进入商品列表，数据量取线上商品数的中位数和高位样本。
- 已加载页面后连续执行典型筛选、清除筛选和快速切换筛选。

验证方式：

- 旧版与候选版在同一设备上交替运行，避免温度、网络和后台负载只偏向某一版本。
- 发布候选至少执行 20 组冷启动和 30 次独立筛选交互，比较 p50、p75及最差 trace。
- 同时验证筛选结果正确性、输入反馈、键盘/焦点、滚动位置、读屏访问和字体加载后布局。
- 保存 bundle diff、请求瀑布和代表性 trace，确保失败能归因到具体模块或阶段。
- Lighthouse 可以用于重复实验和发现线索，但不使用某次总分作为通过证据。

## 发布门槛

1. PR/构建门槛：首路由 JS、阻塞请求和功能回归全部通过。
2. 发布候选门槛：两批独立实验室测量均满足上述 LCP、交互长任务和 CLS 预算。
3. 先放量 5%，至少观察 24 小时；每组至少取得 1,000 个合格页面样本及足够的 INP 样本，不足则延长观察。
4. 使用匹配控制组和 bootstrap 置信区间。只有绝对预算通过，且相对回退的 95% 置信区间未越过 10%，才升至 25%。
5. 25% 阶段重复同一判断后才能全量；全量后继续观察完整 7 天，覆盖工作日与周末流量。
6. 任一有足够样本的连续两个观察窗口超过预算，停止扩量并回退；错误率、筛选正确性或关键业务指标明显异常时不等待性能样本成熟。

当前给出的 3.1s LCP 和 290ms INP 均明显越过门槛，因此在完成归因和候选验证前不应继续全量发布。未修改工作区文件。
