## 模块边界

`checkout` 应拥有：

- 结算流程状态及状态转换，例如编辑、提交中、失败、成功。
- 结算特有的校验、金额展示所依赖的领域结果和提交规则。
- 结算接口的请求/响应 DTO、领域映射和错误归一化。
- 结算 UI、局部交互状态及对应测试。
- 提交的重试、取消、重复点击和过期响应处理策略。

不应拥有：

- 通用 HTTP 客户端、日志、货币格式化等产品无关能力。
- 路由器初始化和应用级 Provider。
- 购物车、账户等其他业务模块的内部状态。
- 仅因为结算使用过一次就被命名为“共享”的工具。
- 服务端权限、价格或库存的最终裁决；客户端只能展示和处理服务端结果。

状态按真实所有者放置：

- 输入框展开、焦点等短生命周期状态留在 UI。
- 提交状态和流程转换归 `checkout-workflow`。
- 领域规则和可派生数据归 `checkout-model`，不要存成第二份状态。
- 只有确实跨路由、跨生命周期共享的状态才接入全局 store；不要为了沿用现有 `stores` 目录而把整个结算放进全局状态。

## 公开 API

所有外部消费者只从 `features/checkout/index.ts` 导入。若当前只有路由使用结算，公开面应尽量小：

```ts
// features/checkout/index.ts
export { CheckoutEntry } from './CheckoutEntry'
export type {
  CheckoutEntryProps,
  CheckoutOutcome,
} from './checkout-public'
```

名称需按实际框架调整。原则是：

- 输入只包含调用者真正拥有的标识、初始数据或能力。
- 输出使用业务结果或事件，如完成、取消，而不是暴露内部 store。
- 不公开 HTTP DTO、API 客户端、内部 reducer、selectors 或所有内部类型。
- 只有出现真实的非 UI 调用方时，才增加程序化命令 API。
- 单元测试可以在模块内直接测试私有规则；模块外集成测试应通过公开入口验证行为。

禁止新代码这样导入：

```ts
import { submit } from '@/features/checkout/api/submit'
```

应通过公开入口、上层组装或模块内调用完成。

## 依赖方向

```text
应用入口 / 路由
        ↓
checkout 公开入口
        ↓
结算组装层 ─────→ UI
        ├────────→ workflow
        └────────→ API adapter
                       ↓
model ←──────── workflow
  ↓                    ↓
无 UI/网络依赖      通用平台能力
                       ↓
                HTTP、日志、存储等
```

具体约束：

- `model` 不依赖 UI、路由、HTTP、浏览器全局对象。
- UI 消费领域值和命令，不解析接口响应。
- API adapter 负责把外部 DTO 转成结算模型，不决定页面如何提示。
- `shared` 或现有通用目录不能反向依赖 `checkout`。
- 其他业务模块不能导入结算内部路径。
- 多模块协作由路由、页面或更高层流程组装，不让两个功能模块相互读取内部 store。
- 只有在确有替换实现、测试隔离或外部系统边界时，才引入 gateway/port 接口；无需为了“架构完整”增加仓储层和依赖注入框架。

## 渐进迁移步骤

1. **建立准入规则**

   新增的结算行为、状态、API、类型和测试一律进入 `features/checkout`。旧顶层目录暂不搬动，也不阻塞功能开发。

2. **先交付一个完整纵向切片**

   从一个可观察的结算流程开始，让 UI、状态转换、接口适配和行为测试都在模块内闭环。不要先搭完整目录再逐层填空。

3. **迁移被结算修改到的旧代码**

   每次只迁移一个明确所有者：

   - `components` 中仅供结算使用的组件移入结算 UI。
   - `hooks` 中仅管理结算生命周期的 hook 移入 workflow 或 UI。
   - `services` 中结算专用调用移入 API adapter。
   - `stores` 中结算 slice 移入模块，由根 store 只负责注册。
   - `types` 中结算领域类型移入 model，DTO 移入 API。
   - `utils` 中仅服务结算的函数移到其调用者附近。

   不要同时保留新旧两份状态并做同步，否则会形成双重事实来源。

4. **按需提供兼容层**

   若旧导入点消费者很多，可让原文件暂时重新导出新实现，并标记迁移范围。新代码不得继续使用旧路径。消费者清零后删除兼容文件。消费者较少时，直接同一提交迁移，避免长期维护 shim。

5. **再治理真正的共享能力**

   只有所有权确实跨业务模块时，才将代码整理为精确命名的共享能力，例如 `http`、`currency`、`storage`、`ui`。不要把原有六个顶层目录整体改名为 `shared`，那只是在搬迁原来的问题。

6. **扩大到其他功能**

   后续商品、购物车、账户等模块在发生实质修改时采用同样方式迁移。等边界稳定且违规开始造成成本后，再使用现有 lint/import 规则约束跨模块深层导入；不必一开始增加新的架构工具。

## 每一步的验收条件

- 现有可观察行为保持不变，或明确记录产品行为变化。
- 新结算需求主要在 `features/checkout` 内完成。
- 外部消费者只依赖公开入口。
- API 字段变化能被限制在 adapter 和其契约测试附近。
- 结算步骤变化只影响 model、workflow、UI 及相应行为测试。
- 没有新旧 store 双写、循环依赖或共享目录反向依赖业务模块。
- 每次迁移后运行项目已有的类型检查、测试和构建命令。

用两个现实变化检验该边界：如果后端调整结算响应字段，应主要修改 API 映射；如果增加一种结算步骤，应主要修改结算模型、流程和 UI。若这两种变化仍然需要横跨全局 `services/stores/types/utils`，说明边界仍在泄漏。

本次只提出方案；工作区没有可供修改或验证的应用代码，`.frontend-architect` 保持未改动。
