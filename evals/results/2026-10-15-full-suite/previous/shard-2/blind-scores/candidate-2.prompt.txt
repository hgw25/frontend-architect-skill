### 推荐结构

order/

  OrderPage.*       # 渲染与用户事件

### 1. 接口字段止步于适配边界

```ts
// 仅 orderApi.ts 知道服务端字段名
type OrderDto = {
  total_in_cents: number
}

export type Order = {
  totalCents: number
}

function toOrder(dto: OrderDto): Order {
  if (!Number.isSafeInteger(dto.total_in_cents) || dto.total_in_cents < 0) {
    throw new Error('Invalid order total')
  }

  return {
    totalCents: dto.total_in_cents,
  }
}

export async function fetchOrder(/* 当前请求所需参数 */): Promise<Order> {
  const dto = await existingHttpClient.get<OrderDto>(/* ... */)
  return toOrder(dto)
}
```

页面及其事件函数只使用 `totalCents`，不再读取 `total_in_cents`。若项目已有生成类型或运行时 schema，应复用；不值得仅为这一个字段引入新的校验依赖。无效响应应作为失败暴露，不能默认为 `0`。

### 2. 格式化保持为纯展示转换

```ts
export function formatOrderTotal(
  totalCents: number,
  options: { locale: string; currency: string },
): string {
  return new Intl.NumberFormat(options.locale, {
    style: 'currency',
    currency: options.currency,
  }).format(totalCents / 100)
}
```

不要把格式化字符串存进请求状态，它可以从 `totalCents` 派生。货币不能从字段名猜测：若接口提供币种，应一起映射；若产品明确固定币种，应定义一个订单功能内的业务常量。

### 3. 请求生命周期由一个所有者管理

状态至少应能区分：

```ts
type OrderLoadState =
  | { status: 'loading' }
  | { status: 'success'; order: Order }
  | { status: 'error'; error: unknown }
```

请求所有者负责：

- 调用 `fetchOrder`
- 设置 loading、success、error
- 页面卸载或参数变化后的过期结果策略
- retry 使用原失败请求的参数
- 将错误交给页面统一渲染或通知

事件函数只表达意图，例如 `reload()`，不再各自 `try/catch`、重复格式化或重复弹提示。底层只在能够翻译错误时捕获；不要在多层重复捕获，也不要把请求失败转换成“空订单”。

### 暂时不要建设

目前只有一个调用方，也没有第二数据源路线图，因此不建议增加：

- `OrderRepository` 接口及唯一实现
- provider/adapter 注册表
- 通用 `Result<T, E>` 体系
- 全局订单 store
- DTO → entity → domain → view-model 的多级复制

`fetchOrder(): Promise<Order>` 本身已经是一个足够小的替换缝。未来真有第二数据源时，再根据两者实际差异提取端口。

这个边界也能应对两个现实变化：接口字段改名只修改 DTO 和映射；金额展示规则或 locale 改变只修改格式化入口。页面调用方式和请求状态无需随之扩散修改。

## 最小必要修复

在所有删除入口共用的服务端写边界强制授权：

1. 从服务端已验证的会话/令牌上下文取得调用者身份，不能信任请求体或查询参数中的 `userId`、`ownerId`。
2. 删除条件同时约束文档和调用者权限。若规则只是“所有者可删除”，优先做原子条件删除，例如：

```sql
DELETE FROM documents
WHERE id = :documentId
  AND owner_id = :authenticatedUserId;
```

3. 若已有管理员、租户或共享权限规则，复用现有策略；不要另建通用权限框架。

   - `403`：产品明确允许区分“存在但无权”时。
   
   不能确认仓库约定时，不应擅自改错误语义。
5. 避免“先查存在、再无条件删除”的竞态。若权限规则无法写进删除条件，应在同一事务内完成授权读取和删除。

## 前端职责

- 最好消费服务端返回的 `canDelete` 等权限结果；若目前通过所有者 ID 判断，也不能把该判断当作授权保证。

## 首次同步

### 1. 先保护未提交的表单修改

不要把 stash 当作唯一备份。将表单修改放到独立 WIP 分支，并备份到团队远端：

```bash
git status --short
git diff
git switch -c wip/form-before-template-2026-10
git add -- <确认属于表单修改的文件>
git diff --cached
git commit -m "wip: preserve form changes before template sync"
git push -u origin HEAD
```

只暂存确认过的表单文件，避免把本地配置、密钥或生成文件一起提交。

随后切回团队长期分支。这个 WIP 分支先不要删除，也不要混入模板同步 PR。

### 2. 配置并核验 upstream

```bash
git switch <团队长期分支>
git remote get-url origin
git remote add upstream <团队确认的模板仓库URL>
git remote get-url upstream
git fetch origin --prune
git fetch upstream --prune
```

确认 `<模板默认分支>` 后，验证双方仍有共同历史：

```bash
git merge-base origin/<团队长期分支> upstream/<模板默认分支>
```

如果没有输出，应停止同步并调查仓库来源；不能使用 `--allow-unrelated-histories` 强行拼接。题设说明存在共同历史，因此正常情况下会得到共同祖先。

### 3. 建立独立同步分支并取得基线

从远端团队分支创建同步分支，避免依赖可能落后的本地分支：

```bash
git switch -c sync/template-2026-10 origin/<团队长期分支>
```

先运行项目已有的构建和表单回归命令，记录同步前基线。具体脚本在当前快照中不可见，不能据此假设为 `npm run build` 或某个固定测试命令。

### 4. 合并模板，不重写业务历史

```bash
git merge --no-ff --no-commit upstream/<模板默认分支>
```

选择 merge 的原因：

- 已推送的业务提交保持原 SHA 和祖先关系；
- 模板提交也保留原历史；
- 合并提交的第二父提交明确记录本次模板版本；
- 下个月再次 merge 时，Git 只处理新的模板变化。

解决冲突时逐项理解双方意图，不能整仓使用 `ours` 或 `theirs`：

- 业务页面和表单：保留业务行为，同时吸收模板的安全修复、API 或结构变化。
- `package.json` 等清单：先合并实际依赖意图。
- 锁文件：按项目固定的包管理器重新生成，不手工拼接冲突段。
- 生成文件：修改其来源后，使用项目原有生成流程重新生成。
- 构建、Lint、TypeScript 配置：核对模板新要求与业务自定义，而不是默认保留任一侧。

完成冲突处理后：

```bash
git diff --check
git status
```

运行同步前使用的同一套构建和表单回归测试。通过后再创建合并提交：

```bash
git commit -m "chore: sync upstream template 2026-10"
git push -u origin sync/template-2026-10
```

- 每个重要冲突的处理理由；
- 模板带来的运行时、依赖或迁移要求。

该 PR 必须以普通 merge commit 合入团队长期分支，不能 squash 或 rebase merge。否则 upstream 的父子关系会丢失，后续月度同步容易重复引入改动或产生无意义冲突。

合并前还应验证同步分支包含原团队分支：

```bash
git merge-base --is-ancestor origin/<团队长期分支> sync/template-2026-10
```

退出码为 `0` 才说明同步分支没有丢掉已推送业务历史。

## 恢复表单开发

模板同步合入后，从更新后的团队分支新建正式功能分支，再重放 WIP 提交：

```bash
git fetch origin --prune
git switch -c feature/form-after-template origin/<团队长期分支>
git cherry-pick <WIP表单提交SHA>
```

若表单与模板发生冲突，在这个功能分支解决，并再次运行表单回归和构建。表单 PR 合入后，才删除本地及远端 WIP 分支。这样无需 force-push，也不会把未完成表单代码混进模板同步 PR。

## 后续每月流程

以后每月重复：

1. `fetch` 两个远端。
2. 从最新 `origin/<团队长期分支>` 创建当月 `sync/template-YYYY-MM`。
3. 先跑基线检查。
4. `git merge --no-ff --no-commit upstream/<模板默认分支>`。
5. 审核模板变更、处理冲突、运行构建和表单回归。
6. 创建保留 merge commit 的独立 PR。
7. 发现上线问题时，用 `git revert -m 1 <同步合并提交>` 回滚，不 reset、不 force-push 共享分支。

本方案受本地 Frontend Architect 指引中的可恢复迁移和真实契约验证原则影响：模板历史、业务历史和未提交工作分别有明确归属，且每次同步都有可重复的构建及表单验证路径。未执行任何改变仓库状态的命令，也未修改任何文件。

### 现在建议的结构

优先遵循框架的路由约定，在此基础上保持浅层、按所有权就近放置：

```text
src/
  app/                 # 应用入口、路由、全局 provider、应用壳
  pages/
    first-page/        # 页面及其专属组件、请求、状态、测试
    second-page/
  shared/              # 仅放确实被多个页面共同拥有的能力
    ui/
    http/
```

实际文件很少时，页面甚至不必建立目录：

```text
src/
  app.tsx
  routes.tsx
  pages/
    FirstPage.tsx
    SecondPage.tsx
  shared/
    http.ts
```

具体原则：

- 页面专属组件、请求映射和业务逻辑与页面共置，不提前拆成 `api/model/ui`。
- `shared` 只接收语义和所有权确实跨页面的代码；“用了两次”本身不等于共享边界。
- 不建立全局 `types`、`utils`、`services` 等杂物目录；一次性辅助逻辑留在调用者附近。
- 只有独立职责、状态生命周期、外部系统边界或稳定复用契约，才值得拆成单独模块。
- 暂不增加 barrel 文件、仓储接口、依赖注入、跨层导入规则等配套机制。

### 未来触发迁移的信号

出现以下一种或多种持续性信号时，再逐步提取 `features/<capability>` 或领域模块：

- 一个正常需求经常同时修改多个全局技术目录。
- 某项用户可识别的能力跨越多个页面，并且大部分变化可以独立发生。
- 页面开始协调多个独立的表单、请求、订阅、重试或错误生命周期。
- 同一业务规则、状态转换或传输映射在多个地方重复。
- `components`、`services`、`utils`、`types` 开始成为无法说明准入规则的杂物箱。
- 页面之间开始互相导入内部文件，或出现循环依赖。
- 团队形成明确的产品区域所有权，或者需要按功能独立测试、懒加载或交付。
- 新增第三个页面时，需要复用现有页面中的完整业务能力，而不只是一个视觉组件。

迁移时不必全仓重构。以首个已经形成稳定边界的能力为单位，将其 UI、状态、规则和数据适配器一起迁入：

```text
src/
  app/
  pages/
  features/
    capability-name/
      CapabilityView.tsx
      capabilityModel.ts
      capabilityApi.ts
      index.ts
  shared/
```

页面通过该能力的窄公开入口进行组合，其他代码不要导入其内部文件。只有当一个 feature 内部文件已经多到影响导航时，再增加 `ui/`、`model/`、`api/` 等子目录。

现实的结构检查是：将来新增一个复用现有业务能力的页面时，是否可以把该能力局部提取，而无需重写路由和另外一个页面。上述浅层共置结构满足这一点，同时避免现在为尚不存在的边界支付导航和维护成本。
