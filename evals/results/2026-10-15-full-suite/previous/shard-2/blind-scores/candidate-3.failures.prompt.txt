结论：`filteredUsers` 是由 `users` 和 `query` 完全派生的数据，不需要独立 state，也不需要 Effect。默认也不应加入 memoization。

### 主要问题：派生状态造成短暂错误显示

当前组件存在两个数据源：

- 权威数据：`users`、`query`
- 副本：`filteredUsers`

```jsx
function UserList({ users, query }) {
  const filteredUsers = users.filter((user) =>
    user.name.includes(query),
  )

  return filteredUsers.map((user) => (
    <User key={user.id} user={user} />
  ))
}
```

这保持了公开 API、匹配规则、结果顺序和 `User` 的 key 不变。

### Memoization 判断

暂时不要使用 `useMemo`：

```jsx
const filteredUsers = useMemo(
  () => users.filter((user) => user.name.includes(query)),
  [users, query],
)
```

它只在过滤已经成为可测量瓶颈，并且父组件能较稳定地复用 `users` 数组引用时才可能有价值。若父组件每次都创建新数组，缓存基本不会命中。`useMemo` 也不应用来修复正确性或保证引用稳定，除非下游确实存在这一公开契约。

- 首次以非空 `query` 渲染时，只出现匹配用户。
- 修改 `query` 后，列表立即对应新查询，不残留旧结果。

request: 请安全评审下面的 React 富文本组件。后端声称已经“过滤过输入”，正文来自用户， 其中允许有限 HTML 和链接。请给出最小、可维护的修复方向和验证方案，说明 CSP 在 其中的角色；不要通过去掉全部富文本来回避产品要求。

RESPONSE:
## 评审结论

**高风险：当前组件把字符串直接送入 HTML sink。**

```tsx
dangerouslySetInnerHTML={{ __html: html }}
```

React 不会对这里的内容做转义或过滤。只要后端过滤存在遗漏、配置回退、历史脏数据或绕过，攻击者就可能执行存储型 XSS。仅凭“后端过滤过”的口头保证，无法判定当前实现安全；需要明确其 sanitizer、允许列表及测试证据。

## 最小、可维护的修复

保留富文本，但在这个唯一的渲染边界使用项目已有的成熟 HTML sanitizer；如果项目没有，可采用 DOMPurify。不要自行用正则或黑名单过滤。

客户端渲染时可采用类似结构：

```tsx
import DOMPurify from "dompurify";
import { useMemo } from "react";

const ARTICLE_HTML_POLICY = {
  ALLOWED_TAGS: [
    "p",
    "br",
    "strong",
    "em",
    "ul",
    "ol",
    "li",
    "blockquote",
    "code",
    "pre",
    "a",
  ],
  ALLOWED_ATTR: ["href", "title"],
  ALLOW_DATA_ATTR: false,
} satisfies DOMPurify.Config;

function sanitizeArticleHtml(input: string): string {
  return DOMPurify.sanitize(input, ARTICLE_HTML_POLICY);
}

export function ArticleBody({ html }: { html: string }) {
  const sanitizedHtml = useMemo(() => sanitizeArticleHtml(html), [html]);

  return (
    <article dangerouslySetInnerHTML={{ __html: sanitizedHtml }} />
  );
}
```

关键决策：

- 允许列表应来自产品需求，而不是 DOMPurify 默认集合；上例仅为最小候选，需要确认真实格式。
- 链接协议也必须有明确策略，例如只允许相对 URL、`https:`，以及确实需要时的 `mailto:`。不要打开 `ALLOW_UNKNOWN_PROTOCOLS`，也不要随意自定义宽松正则。
- 当前例子不允许 `target`，因此没有反向 tabnabbing 问题。如果产品要求新窗口打开链接，应由清洗边界统一增加 `target="_blank"` 和 `rel="noopener noreferrer"`，不能信任正文提供的属性。
- 如果允许图片，应另行限制图片协议和来源，同时考虑第三方图片的追踪与隐私风险。
- 后端仍应采用解析器驱动、允许列表式的清洗。前端清洗不是替代后端，而是保护这个高风险 DOM sink，避免单个上游回归直接成为 XSS。
- 如果页面参与 SSR，必须在服务器输出 HTML 之前用同一策略清洗；只在 hydration 后由浏览器清洗已经太晚。具体同构方案取决于项目现有 SSR 和依赖，当前仓库没有这些信息。
- 可进一步让组件接收 `sanitizedHtml` 或不透明的 `SanitizedHtml` 类型，使信任契约可见；但类型标记本身不是安全措施，值仍必须只能由清洗函数产生。

## 验证方案

为清洗策略增加表驱动单元测试：

- 合法的段落、列表、强调、代码和 `https`/相对链接能够保留。
- 删除 `onclick`、`onerror` 等事件属性。
- 拒绝 `javascript:`、大小写或实体编码变体以及未知协议。
- 删除 `script`、`style`、`iframe`、`object`、`embed`、`form`、`base`。
- 覆盖 SVG、MathML、畸形嵌套标签等常见解析器绕过载荷。
- 确认 `data-*`、`style` 和未允许属性不会意外保留。

再用真实浏览器做一条集成测试：渲染恶意正文，通过哨兵变量、弹窗、导航和网络请求断言没有代码执行或意外外联，同时确认合法富文本仍可读、链接仍可用。若有 SSR，应直接检查首次响应 HTML，而不只是 hydration 后的 DOM。

## CSP 的角色

CSP 是第二道防线，不是 sanitizer：

- 使用响应头部署严格的 `script-src`，基于动态 nonce 或 hash，并避免 `unsafe-inline`、`unsafe-eval`。
- 通常同时设置 `object-src 'none'`、`base-uri 'none'`，并按产品需要配置 `form-action`、`frame-ancestors`、`img-src` 和 `connect-src`。
- 先以 `Content-Security-Policy-Report-Only` 在测试或灰度环境观察违规，再转为强制策略。
- CSP 能降低部分漏网 XSS 的可利用性，但不会清除危险 HTML，也不能阻止钓鱼链接或在策略过宽时的数据外传。
- Trusted Types 可作为后续硬化，集中限制 `innerHTML` 类 sink；它同样不能替代内容清洗，并需要验证当前 React、SSR 和第三方代码兼容性。

CASE

request: 团队准备替换高流量预订确认页的数据层。旧接口和新接口将在两周内并存，失败会导致 用户重复预订。请设计可渐进交付的前端改造：说明兼容边界、灰度、幂等与重复提交、 错误恢复、需要的生产信号、隐私控制和回滚条件。不要假设一次全量发布成功。

RESPONSE:

## 1. 兼容边界

前端只暴露一个预订领域接口，例如：

```ts
interface BookingGateway {
  submit(command: BookingCommand, attempt: BookingAttempt): Promise<SubmitResult>;
  getStatus(attempt: BookingAttempt): Promise<BookingStatus>;
}

interface BookingAttempt {
  attemptId: string;
  apiVersion: "legacy" | "next";
}
```

实现上保留 `LegacyBookingAdapter` 和 `NextBookingAdapter`，分别负责：

- 请求字段、枚举、日期和金额格式转换。
- 在网络边界验证响应并转换成统一领域结果。
- 将错误归一为 `validation`、`rejected`、`conflict`、`unknown`。
- 隐藏接口版本、HTTP 状态码和传输结构，页面不直接判断新旧接口。

必须保持的统一语义：

- 成功只表示服务端返回权威 `bookingId` 和已确认状态。
- 超时、断网、连接中断和未定义语义的 5xx 都是“结果未知”，不是失败。
- 同一 `attemptId` 只能绑定一份不可变的提交快照。
- 改动旅客、日期、房型等业务字段后，必须创建新的尝试；普通重试必须沿用原快照和原 `attemptId`。
- 缓存键包含业务身份和接口契约版本，避免新旧响应互相覆盖。
- 旧请求的成功、失败或 `finally` 不得覆盖当前尝试的页面状态。

这应是预订功能自己的边界，不需要建设通用请求框架。

## 2. 幂等与重复提交

仅禁用按钮不能阻止多标签页、刷新、代理重试或超时重发。上线写流量前，服务端必须提供以下契约：

1. 前端首次提交时生成随机、不可推断的 `attemptId`，后续重试始终使用同一个值。
2. 新旧接口共享同一个幂等权威：数据库唯一约束或事务性幂等账本，键至少包含租户/用户和 `attemptId`。
3. 首次请求把 `attemptId`、规范化请求摘要和处理结果绑定：
   - 相同键、相同内容：返回原结果或 `processing`。
   - 相同键、不同内容：返回明确的冲突，绝不创建第二笔预订。
4. 幂等记录的保留时间必须覆盖最长网络重试、用户恢复和下游处理窗口；建议最低 24 小时，最终值由实际业务窗口确定。
5. 提供受鉴权保护的状态查询能力，允许按 `attemptId` 恢复未知结果。
6. 新旧接口若最终进入不同写服务，幂等判断必须发生在分叉之前，或共享同一事务性账本。

如果旧接口无法遵守该契约，应由 BFF/API 网关为两条路径提供共同幂等边界。在此之前，新接口只能进行无副作用验证，不能承接真实预订写入。

前端补充防护包括：

- 提交后立即禁用按钮并显示明确的处理中状态。
- 同一页面内串行化写入；页面刷新后从 `sessionStorage` 恢复 `attemptId`、版本和时间戳，不保存旅客资料。
- 多标签页可用 `BroadcastChannel` 做提示和软锁，但它只是体验优化，正确性仍由服务端保证。
- Service Worker、HTTP 客户端和自动重试机制不得生成新键。
- 不做新旧接口双写；所谓“影子流量”只能调用无副作用的校验/dry-run 能力。

## 3. 页面状态与错误恢复

```text
草稿
  └─提交→ 提交中
             ├─权威确认→ 已确认
             ├─明确业务拒绝→ 可修改
             └─超时/断网/不确定 5xx→ 结果核验中
                                      ├─查询到确认→ 已确认
                                      ├─查询到明确拒绝→ 可修改
                                      └─仍未知→ 保持阻断并提供人工协助
```

恢复规则：

- `202/processing`：指数退避查询状态，页面隐藏或重新进入后仍可继续。
- 超时或断网：先查询状态；必要时使用原 `attemptId` 重发原请求。
- 结果仍未知：明确提示“预订可能已经成功，正在核实”，禁止以新键再次提交；提供不含敏感信息的查询参考号和客服入口。
- 明确的校验/库存拒绝：允许编辑；业务字段发生变化后开启新尝试。
- 幂等内容冲突：停止自动恢复，记录诊断信号并提示重新开始，不能静默覆盖。
- 页面卸载或请求取消只停止前端等待，不代表服务端取消。
- 成功页刷新时以服务端状态恢复，不依赖内存中的成功标志。

## 4. 灰度计划

分流应在服务端/BFF 或统一远程配置层完成，并以用户和 `attemptId` 稳定分桶。第一次提交后将接口版本固定到该尝试；配置变化和 kill switch 只影响新尝试。

建议两周安排如下，但晋级由信号决定，不由日期自动触发：

| 阶段 | 流量 | 要求 |
|---|---:|---|
| 0 | 0% 写入 | 契约测试、故障注入；新适配器仅本地转换或服务端 dry-run |
| 1 | 员工/测试账号 | 真实端到端预订和人工核对 |
| 2 | 1% | 低风险地区或库存，至少观察一个业务高峰 |
| 3 | 5% → 10% | 每档至少稳定一个完整业务周期 |
| 4 | 25% → 50% | 保留同期旧接口对照组，检查分群差异 |
| 5 | 90% | 保留 10% 旧接口对照，至少稳定 24–48 小时 |
| 6 | 100% | 旧适配器、开关和服务端兼容路径继续保留 |

每次晋级必须人工确认仪表盘和告警正常。不要在 100% 后立即删除旧路径；至少等所有未知尝试解决、幂等保留窗口结束，并完成一个完整高峰周期。若两周硬期限与这些条件冲突，应延长兼容期，而不是删除恢复能力。

## 5. 生产信号

服务端业务事实是重复预订的权威信号，浏览器事件只能补充用户体验。

至少按 `apiVersion`、灰度组、地区、设备、网络和登录状态分组监控：

- 每个 `attemptId` 对应的预订数；大于 1 必须为零。
- 同一用户、同一规范化业务意图在短窗口内产生多笔确认的疑似重复率。
- 幂等命中、处理中、载荷冲突和去重失败数量。
- 预订确认率、明确拒绝率、技术失败率。
- 结果未知率、未知状态持续时间及最终解决方向。
- 创建及状态查询的 p50/p95/p99 延迟。
- 重试次数、刷新后恢复率、人工协助率。
- 从点击提交到权威确认的漏斗损失。
- 新旧适配器对相同只读/dry-run 输入的语义差异。

在取得现网基线后冻结阈值。可先使用这些保守默认值：

- 同一 `attemptId` 出现两笔权威预订：立即停止新流量，不等待样本量。
- 新路径确认率在至少 1000 次尝试的 15 分钟窗口内低于同期旧路径 1 个百分点：回滚新流量。
- 未知结果率超过 0.5%，且高于旧路径 0.2 个百分点，持续 10 分钟：回滚。
- 技术失败率同时超过旧路径两倍且绝对增加超过 0.2 个百分点：回滚。
- p95 延迟增加 30%：暂停晋级；若同时引起超时或确认率下降则回滚。

低样本阶段遇到重复预订、幂等绕过或错误路由，仍应立即停止，不受统计阈值限制。

## 6. 隐私控制

遥测只记录决策所需字段：

- 可记录：随机 `attemptId`、接口版本、灰度组、阶段、结果分类、延迟、重试次数、错误类别和 trace ID。
- 不记录：姓名、邮箱、电话、证件信息、备注、完整行程、请求/响应正文、Cookie、令牌和支付信息。
- 不把预订页 DOM、表单字段或网络正文发送给第三方分析与会话回放工具。
- 如需识别疑似相同业务意图，由服务端使用轮换密钥进行 HMAC；不能在浏览器生成可反推的明文拼接哈希。
- 日志和 trace 默认脱敏，限制访问、地区和保留周期；调试采样不能绕过这些规则。
- 状态查询必须验证当前用户对该尝试的所有权，`attemptId` 本身不是授权凭证。

## 7. 回滚方式与完成条件

回滚不应依赖重新发布前端：

1. kill switch 将所有新尝试切回旧接口，远程配置获取失败时也默认旧路径。

+# Vite Feature Flags
+
+Expose an explicit, client-safe subset of a JSON feature-flag file through
+`virtual:feature-flags`. The same virtual module implementation is used by the
+Vite development server, SSR module loading, production builds, and watch/HMR.
+
+## Usage
+
+```ts
+// vite.config.ts
+import { featureFlags } from '@frontend-architect-eval/feature-flags'
+import { defineConfig } from 'vite'
+
+export default defineConfig({
+  plugins: [
+    featureFlags({
+      source: new URL('./flags.json', import.meta.url),
+      expose: ['checkoutV2', 'theme'],
+    }),
+  ],
+})
+```
+
+Load the virtual-module declaration once in the consumer's `tsconfig.json`:
+
+```json
+{
+  "compilerOptions": {
+    "types": ["@frontend-architect-eval/feature-flags/virtual"]
+  }
+}
+```
+
+Then import the readonly flags:
+
+```ts
+import { flags } from 'virtual:feature-flags'
+
+flags.checkoutV2
+```
+
+By default, values are typed as `boolean | number | string`. Applications that
+own a narrower schema can add a declaration file and get exact keys and values:
+
+```ts
+import 'virtual:feature-flags'
+
+declare module 'virtual:feature-flags' {
+  interface FeatureFlagSchema {
+    checkoutV2: boolean
+    theme: 'dark' | 'light'
+  }
+}
+```
+
+The main package exports `featureFlags`, `FeatureFlagsOptions`,
+`FeatureFlagValue`, and `FeatureFlags`. The `./virtual` export is the declaration
+entry point; application code imports the Vite-owned `virtual:feature-flags`
+module, not that package subpath at runtime. Internal files are intentionally not
+exported.
+
+## Security and diagnostics
+
+`expose` is a required allowlist. The plugin builds a new object containing only
+those keys before it serializes any data, so other fields never enter generated
+JavaScript or its source maps. Do not expose credentials: flags are public
+client data, not authorization controls or secrets.
+
+The source must be a top-level JSON object whose exposed values are strings,
+finite numbers, or booleans. Invalid options, unreadable or malformed JSON,
+missing flags, and unsupported values fail startup/build with a stable diagnostic
+code, the source path when relevant, and a corrective action.
+
+## Source maps, cache, and HMR
+
+This plugin does not transform consumer source, so it cannot discard or offset
+consumer source maps. It returns a dedicated virtual module containing only the
+allowlisted projection. When Vite emits source maps, any `sourcesContent` for
+that module is therefore client-safe by construction. The package's own build
+also publishes JavaScript and declaration source maps.
+
+Vite's module graph is the sole runtime cache. The plugin reads and validates
+the source whenever Vite loads the virtual module, registers the JSON file as a
+watch dependency, and invalidates that exact module when the file changes. A
+single-file polling bridge covers filesystems where native watch events are not
+reliable; it feeds Vite's normal watcher/module graph and is disposed with the
+plugin. The plugin does not maintain a second flag cache, so dev, build, rebuild,
+and SSR cannot disagree because of stale plugin state.
+
+## Verification and releases
+
+From the repository root, `npm run check` verifies declarations, a real Vite
+production build, source-map secret exclusion, dev/SSR HMR, actionable
+diagnostics, and installation from `npm pack`. `npm test --workspace
+@frontend-architect-eval/feature-flags` adds focused public-API and adversarial
+key checks.
+
+Version changes by consumer impact:
+
+- Patch: diagnostics wording improvements that preserve codes, fixes, and wider
+  compatible Vite ranges after matrix verification.
+- Minor: optional configuration or new exports that preserve generated module
+  semantics.
+- Major: changing accepted flag values, virtual exports, diagnostic codes,
+  runtime mutability, package entry points, or the supported Vite/Node floor.
+
+Deprecations should name the replacement in release notes and remain available
+for at least one minor line before a major removal. High-risk lifecycle changes
+should ship as a prerelease and be exercised against representative consumer
+projects before promotion.
