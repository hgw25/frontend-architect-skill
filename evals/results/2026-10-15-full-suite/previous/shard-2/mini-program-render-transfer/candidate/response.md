结论：最小方案不是降低行情更新频率，而是把“业务数据实时更新”和“向页面渲染层传输数据”拆开。继续以 100ms 接收并更新最新行情，但只在页面可见时，通过 `setData` 发送发生变化的展示字段；页面隐藏后停止 `setData`，再次显示时先同步一份最新快照。

当前工作区没有应用源码，只有 `.frontend-architect` 指导文件，因此以下是可直接落地的改造边界，不能声称已经对具体代码完成验证。

## 最小改造

1. 保留一个权威行情状态

行情订阅更新逻辑层中的最新状态，不再把整个 `page.data` 当作行情存储。页面 `data` 只保留模板实际使用的展示字段，例如：

```js
data: {
  quotes: [
    { id, priceText, changeText, trend }
  ]
}
```

订阅消息中的原始字段、索引、统计值和非展示业务数据不要通过 `setData` 传递。

2. 保持 100ms 节奏，只发送变化字段

每个行情周期仍正常处理，不额外节流。将同一个周期内的变化合并成一次 `setData`：

```js
{
  'quotes[12].priceText': '10.32',
  'quotes[12].changeText': '+1.18%',
  'quotes[87].trend': 'down'
}
```

优先从行情消息携带的变更标识生成补丁，避免每次扫描和复制整个页面数据。如果上游只能提供完整快照，则只比较模板使用的字段。

使用稳定的行情 ID 维护 `id -> rowIndex`。插入、删除、排序等结构变化可以重新发送一次精简后的 `quotes`；普通价格变化继续发送字段补丁。这样结构变化有清楚的处理位置，也不会为少见情况建立复杂通用 diff 框架。

3. 页面隐藏时停止渲染层更新

生命周期策略应明确为：

- `onShow`：用权威状态同步一次最新快照，然后恢复增量补丁。
- `onHide`：取消待发送的补丁并禁止后续 `setData`。
- `onUnload`：释放订阅、定时器和待执行任务，防止旧回调继续操作页面。

订阅本身按业务契约处理：

- 如果隐藏期间仍必须持续接收行情，就把订阅放在页面之外的 store/service 中；隐藏页面只是不再接收渲染更新。
- 如果重新订阅能获得完整最新快照，可以在隐藏时退订、显示时重新订阅。
- 两种方式都不降低可见页面的 100ms 实时性，也不会让重新显示后的数据停留在旧状态。

需要处理 `onShow` 全量同步期间又收到行情的情况：快照同步完成后，再把同步期间积累的变化补上，或者按版本重新生成一次差异，避免旧快照覆盖较新的行情。

4. 暂不引入虚拟列表或宿主专用渲染能力

500 行可能存在节点、布局或绘制成本，但目前只有现象，没有性能轨迹证明它是主瓶颈。第一轮只消除两个明确浪费：

- 每 100ms 传整个页面 `data`；
- 页面不可见时仍持续 `setData`。

如果真机数据表明桥接传输已经明显下降，而滚动仍由布局、绘制或节点数主导，再评估宿主原生虚拟列表或只同步可视区。不要第一步就自研虚拟列表。

## 多宿主和基础库兼容

先列出实际支持的“宿主 × 最低/当前基础库版本”矩阵，确认它们对以下能力的契约：

- 路径形式的局部 `setData`；
- `setData` 完成回调或等价机制；
- 页面隐藏、卸载的生命周期顺序；
- 可用的性能面板和数据传输诊断。

第一版应使用支持矩阵的公共能力，不依赖某个宿主的新渲染引擎、worklet 或未经确认的数值限制。若局部路径语法确实不同，把差异封装在一个很薄的补丁生成适配器中；不支持时回退到“仅发送精简的 `quotes`”，仍不要回退到整个页面 `data`。

## 代码层能够验证的内容

可以通过单元和集成测试验证：

- 可见状态下，100ms 的每个行情周期仍能触发一次语义更新，没有新增较慢的节流窗口。
- 普通行情变化不会把整份 `page.data` 或完整业务对象交给 `setData`。
- 只包含实际变化的行和字段；`0`、空字符串、涨跌方向变化等不会被错误忽略。
- 排序、插入和删除会重建正确的索引或精简快照。
- `onHide` 后 `setData` 调用数为零，但需要持续运行的业务订阅仍更新权威状态。
- `onShow` 先恢复最新快照，随后收到的增量不会被旧快照覆盖。
- `onUnload` 后订阅、定时器和回调均不再触碰页面。
- 输入框等非行情页面状态不会被行情补丁覆盖。

测试还可以统计每个周期的 `setData` 次数、字段数及 `JSON.stringify` 后的近似字节数，用来证明代码确实减少了调用和候选载荷。但这个字节数不等于宿主真实序列化或桥接开销。

## 必须由宿主工具和真机证明的结论

代码检查不能证明以下结果：

- 真正的逻辑层到渲染层传输字节数、排队时间和序列化耗时；
- 输入到响应或绘制的端到端延迟；
- 滚动掉帧、卡顿时长、布局和绘制成本；
- 不同基础库、渲染后端及设备上的行为差异；
- 持续运行后的内存、GC、温升和降频情况；
- 优化后用户可感知卡顿是否确实改善。

应在优化前后使用完全相同的发布或性能构建、500 行代表性数据和 100ms 更新源，执行持续滚动、连续输入及页面隐藏/恢复场景。至少覆盖每个宿主的最低支持版本和当前版本，以及出现问题的低端或中端代表性真机。记录：

- 每秒 `setData` 次数、实际载荷和队列时间；
- 行情到可见结果的延迟，确认实时性没有退化；
- 输入响应延迟；
- 帧时间、卡顿或掉帧；
- 逻辑线程和渲染线程耗时；
- 内存随时间的变化。

开发者工具只能用于定位和回归辅助，不能作为“真机卡顿已经解决”的交付证据。

本地 Skill 的指导使方案优先处理更新传输边界和页面生命周期，并把虚拟列表等更重的改造推迟到真机轨迹能够证明其必要之后。
