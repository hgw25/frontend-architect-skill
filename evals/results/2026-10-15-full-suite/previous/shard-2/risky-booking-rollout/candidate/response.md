建议采用“单写入 + 服务端共享幂等 + 按预订尝试固定路由”的迁移方案。任何阶段都不并行调用新旧创建接口，也不在超时后自动切换接口；否则无法排除第一次请求已经成功，重复预订风险不可接受。

## 1. 兼容边界

前端只暴露一个预订领域接口，例如：

```ts
interface BookingGateway {
  submit(command: BookingCommand, attempt: BookingAttempt): Promise<SubmitResult>;
  getStatus(attempt: BookingAttempt): Promise<BookingStatus>;
}

interface BookingAttempt {
  attemptId: string;
  apiVersion: "legacy" | "next";
}
```

实现上保留 `LegacyBookingAdapter` 和 `NextBookingAdapter`，分别负责：

- 请求字段、枚举、日期和金额格式转换。
- 在网络边界验证响应并转换成统一领域结果。
- 将错误归一为 `validation`、`rejected`、`conflict`、`unknown`。
- 隐藏接口版本、HTTP 状态码和传输结构，页面不直接判断新旧接口。

必须保持的统一语义：

- 成功只表示服务端返回权威 `bookingId` 和已确认状态。
- 超时、断网、连接中断和未定义语义的 5xx 都是“结果未知”，不是失败。
- 同一 `attemptId` 只能绑定一份不可变的提交快照。
- 改动旅客、日期、房型等业务字段后，必须创建新的尝试；普通重试必须沿用原快照和原 `attemptId`。
- 缓存键包含业务身份和接口契约版本，避免新旧响应互相覆盖。
- 旧请求的成功、失败或 `finally` 不得覆盖当前尝试的页面状态。

这应是预订功能自己的边界，不需要建设通用请求框架。

## 2. 幂等与重复提交

仅禁用按钮不能阻止多标签页、刷新、代理重试或超时重发。上线写流量前，服务端必须提供以下契约：

1. 前端首次提交时生成随机、不可推断的 `attemptId`，后续重试始终使用同一个值。
2. 新旧接口共享同一个幂等权威：数据库唯一约束或事务性幂等账本，键至少包含租户/用户和 `attemptId`。
3. 首次请求把 `attemptId`、规范化请求摘要和处理结果绑定：
   - 相同键、相同内容：返回原结果或 `processing`。
   - 相同键、不同内容：返回明确的冲突，绝不创建第二笔预订。
4. 幂等记录的保留时间必须覆盖最长网络重试、用户恢复和下游处理窗口；建议最低 24 小时，最终值由实际业务窗口确定。
5. 提供受鉴权保护的状态查询能力，允许按 `attemptId` 恢复未知结果。
6. 新旧接口若最终进入不同写服务，幂等判断必须发生在分叉之前，或共享同一事务性账本。

如果旧接口无法遵守该契约，应由 BFF/API 网关为两条路径提供共同幂等边界。在此之前，新接口只能进行无副作用验证，不能承接真实预订写入。

前端补充防护包括：

- 提交后立即禁用按钮并显示明确的处理中状态。
- 同一页面内串行化写入；页面刷新后从 `sessionStorage` 恢复 `attemptId`、版本和时间戳，不保存旅客资料。
- 多标签页可用 `BroadcastChannel` 做提示和软锁，但它只是体验优化，正确性仍由服务端保证。
- Service Worker、HTTP 客户端和自动重试机制不得生成新键。
- 不做新旧接口双写；所谓“影子流量”只能调用无副作用的校验/dry-run 能力。

## 3. 页面状态与错误恢复

```text
草稿
  └─提交→ 提交中
             ├─权威确认→ 已确认
             ├─明确业务拒绝→ 可修改
             └─超时/断网/不确定 5xx→ 结果核验中
                                      ├─查询到确认→ 已确认
                                      ├─查询到明确拒绝→ 可修改
                                      └─仍未知→ 保持阻断并提供人工协助
```

恢复规则：

- `202/processing`：指数退避查询状态，页面隐藏或重新进入后仍可继续。
- 超时或断网：先查询状态；必要时使用原 `attemptId` 重发原请求。
- 结果仍未知：明确提示“预订可能已经成功，正在核实”，禁止以新键再次提交；提供不含敏感信息的查询参考号和客服入口。
- 明确的校验/库存拒绝：允许编辑；业务字段发生变化后开启新尝试。
- 幂等内容冲突：停止自动恢复，记录诊断信号并提示重新开始，不能静默覆盖。
- 页面卸载或请求取消只停止前端等待，不代表服务端取消。
- 成功页刷新时以服务端状态恢复，不依赖内存中的成功标志。

## 4. 灰度计划

分流应在服务端/BFF 或统一远程配置层完成，并以用户和 `attemptId` 稳定分桶。第一次提交后将接口版本固定到该尝试；配置变化和 kill switch 只影响新尝试。

建议两周安排如下，但晋级由信号决定，不由日期自动触发：

| 阶段 | 流量 | 要求 |
|---|---:|---|
| 0 | 0% 写入 | 契约测试、故障注入；新适配器仅本地转换或服务端 dry-run |
| 1 | 员工/测试账号 | 真实端到端预订和人工核对 |
| 2 | 1% | 低风险地区或库存，至少观察一个业务高峰 |
| 3 | 5% → 10% | 每档至少稳定一个完整业务周期 |
| 4 | 25% → 50% | 保留同期旧接口对照组，检查分群差异 |
| 5 | 90% | 保留 10% 旧接口对照，至少稳定 24–48 小时 |
| 6 | 100% | 旧适配器、开关和服务端兼容路径继续保留 |

每次晋级必须人工确认仪表盘和告警正常。不要在 100% 后立即删除旧路径；至少等所有未知尝试解决、幂等保留窗口结束，并完成一个完整高峰周期。若两周硬期限与这些条件冲突，应延长兼容期，而不是删除恢复能力。

## 5. 生产信号

服务端业务事实是重复预订的权威信号，浏览器事件只能补充用户体验。

至少按 `apiVersion`、灰度组、地区、设备、网络和登录状态分组监控：

- 每个 `attemptId` 对应的预订数；大于 1 必须为零。
- 同一用户、同一规范化业务意图在短窗口内产生多笔确认的疑似重复率。
- 幂等命中、处理中、载荷冲突和去重失败数量。
- 预订确认率、明确拒绝率、技术失败率。
- 结果未知率、未知状态持续时间及最终解决方向。
- 创建及状态查询的 p50/p95/p99 延迟。
- 重试次数、刷新后恢复率、人工协助率。
- 从点击提交到权威确认的漏斗损失。
- 新旧适配器对相同只读/dry-run 输入的语义差异。

在取得现网基线后冻结阈值。可先使用这些保守默认值：

- 同一 `attemptId` 出现两笔权威预订：立即停止新流量，不等待样本量。
- 新路径确认率在至少 1000 次尝试的 15 分钟窗口内低于同期旧路径 1 个百分点：回滚新流量。
- 未知结果率超过 0.5%，且高于旧路径 0.2 个百分点，持续 10 分钟：回滚。
- 技术失败率同时超过旧路径两倍且绝对增加超过 0.2 个百分点：回滚。
- p95 延迟增加 30%：暂停晋级；若同时引起超时或确认率下降则回滚。

低样本阶段遇到重复预订、幂等绕过或错误路由，仍应立即停止，不受统计阈值限制。

## 6. 隐私控制

遥测只记录决策所需字段：

- 可记录：随机 `attemptId`、接口版本、灰度组、阶段、结果分类、延迟、重试次数、错误类别和 trace ID。
- 不记录：姓名、邮箱、电话、证件信息、备注、完整行程、请求/响应正文、Cookie、令牌和支付信息。
- 不把预订页 DOM、表单字段或网络正文发送给第三方分析与会话回放工具。
- 如需识别疑似相同业务意图，由服务端使用轮换密钥进行 HMAC；不能在浏览器生成可反推的明文拼接哈希。
- 日志和 trace 默认脱敏，限制访问、地区和保留周期；调试采样不能绕过这些规则。
- 状态查询必须验证当前用户对该尝试的所有权，`attemptId` 本身不是授权凭证。

## 7. 回滚方式与完成条件

回滚不应依赖重新发布前端：

1. kill switch 将所有新尝试切回旧接口，远程配置获取失败时也默认旧路径。
2. 已经进入新接口的尝试继续按其固定版本查询和恢复，不能改走旧创建接口。
3. 新接口及共享幂等记录保持可用，直到所有在途尝试终结并超过保留窗口。
4. 必要时回滚前端资源，但旧版本客户端仍必须能读取新路径已经创建的预订结果。
5. 修复后从员工流量重新开始，不直接恢复原百分比。

最终移除旧路径前，应同时满足：

- 100% 新流量经历至少一个完整高峰周期；
- 无未解决的重复预订或幂等缺陷；
- 未知结果、确认率和延迟均不劣于既定门槛；
- 在途尝试已清空并超过恢复窗口；
- kill switch 演练、回滚演练和客服恢复流程均通过。

工作区中没有应用源码、接口契约或测试设施，只有指定的 Skill 资料，因此本次没有修改文件，也不能执行项目级验证。落地前最关键的阻塞项是确认“新旧接口共享服务端幂等权威”和“按尝试查询状态”这两项契约；缺少其中任一项，都不应开放真实灰度写流量。
