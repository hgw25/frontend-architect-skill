结论：个人主页应以 `userId` 为唯一身份键；`developerLogin` 只属于开发者域，不能拼成用户主页地址。前端完整展示服务端返回的 `applications`，不自行过滤私有应用，但必须避免把“本人可见”的响应缓存泄露给其他查看者。

当前仓库是空 fixture，除 `.frontend-architect` 与 Git 元数据外没有 Vue 源码、路由、接口生成物或测试配置，因此本次没有可安全修改、运行或验证的项目文件。以下方案不虚构目录和字段名，落地时应套用真实项目已有约定。

## 1. 路由

新增用户域路由：

```text
/users/:userId
route name: user-profile
```

决策：

- `userId` 是不透明标识，只用于用户主页路由和 `GET /users/{userId}`。
- 页面内切换 `userId` 时必须重新请求，不能只依赖组件首次挂载。
- “我的主页”入口从当前用户会话中的 `userId` 生成。若会话只有 `developerLogin`，这是契约缺口，不能用它代替 `userId`。
- 使用现有 Vue Router、鉴权守卫、懒加载和页面布局惯例，不为单页另建一套路由机制。
- 404 显示“用户不存在”；其他失败沿用全局错误样式并提供重试。

GitHub 风格仅用于视觉组织：桌面端左侧个人资料、右侧应用列表，窄屏改为单列；不照搬 GitHub 的用户名模型或仓库权限逻辑。

## 2. 数据流与权限边界

```text
route.params.userId
  → 个人主页页面/查询组合函数
  → 已有 API client：GET /users/{userId}
  → { profile, applications }
  → 资料区与应用列表
```

具体规则：

- 接口响应是页面的唯一服务端数据源，不再分别请求 profile 和 applications。
- 前端按原样渲染返回的 `applications`：
  - 本人查看时，服务端可能返回公开和私有应用。
  - 非本人查看时，服务端只返回其允许查看的应用。
  - 前端不得通过 `isSelf` 再过滤列表，也不得把“未返回”解释成“没有私有应用”。
- `isSelf = session.userId === routeUserId` 只可用于展示型行为，例如文案或编辑入口；它不是授权判断。
- 只有响应类型明确提供可见性字段时才渲染 “Private” 标记，不能根据列表位置、作者或当前用户身份推断。
- 快速从用户 A 导航到用户 B 时，应使用项目既有查询库的请求身份/取消机制，或 `AbortController`，确保 A 的迟到响应不能覆盖 B。

### 缓存要求

该响应依赖查看者身份，不能只按 URL 做跨身份共享缓存。

- 客户端查询键至少包含 `userId` 和稳定的查看者作用域，例如：

```text
['user-profile', userId, viewerScope]
```

- `viewerScope` 可以是当前用户 ID或会话世代标识；不要把 token 放进缓存键或日志。
- 登录、退出或账号切换时，清除或失效所有查看者相关的个人主页缓存。
- 如果存在 SSR、CDN 或 Service Worker，共享公共缓存不得保存该响应；服务端需使用私有缓存策略或正确区分授权上下文。前端无法补救服务端缓存泄露。

## 3. 作者入口

应用上的作者只有 `developerLogin`，没有 `userId` 映射，因此：

- 不得生成 `/users/{developerLogin}`。
- 如果项目已有开发者详情路由，则作者链接进入开发者域，例如既有的 `/developers/:developerLogin`。
- 如果尚无开发者详情能力，最小方案是显示不可点击的作者署名；不要新增猜测式跳转。
- 若产品确实希望作者署名进入个人主页，需要服务端提供显式关联，例如 `authorUserId` 或受支持的 developer-to-user 解析接口，再增加入口。

这样将来增加映射时，只需修改作者入口适配处，不会改变个人主页的路由和查询契约。

## 4. 契约注释处理

旧生成注释“applications 仅公开”与已确认的运行时契约冲突。应修改 OpenAPI/接口描述源，再按项目流程重新生成客户端，而不是直接编辑生成文件。

建议描述：

> `applications` contains applications visible to the current viewer. The profile owner may receive both public and private applications; other viewers receive only applications they are authorized to view. Authorization is enforced by the server.

若接口 schema 本身没有变化，错误注释不应阻塞页面实现，但应与功能一同修正，避免后续维护者在前端重新加入错误过滤。

## 5. 最小实现顺序

1. 修正接口描述源并重新生成客户端，确认响应类型能够表达现有 `profile` 和 `applications`。
2. 增加 `/users/:userId` 路由，完成“路由参数 → 单次接口请求 → 页面渲染”的纵向闭环。
3. 完成加载、404、一般错误、重试和空应用列表状态。
4. 接入会话身份，处理查看者作用域缓存与登录状态切换失效。
5. 按 GitHub 式双栏/单栏布局补齐视觉与语义结构。
6. 接入作者署名：只链接既有开发者路由；没有则保持文本。
7. 最后补行为测试和真实身份验收，不先建设通用 profile 框架、全局 store 或额外 repository 层。

## 6. 验收方式

| 场景 | 必须观察到的结果 |
|---|---|
| 本人访问 `/users/{自己的 userId}` | 页面准确展示接口返回的公开和私有应用 |
| 其他用户或匿名者访问同一地址 | 只展示该请求实际返回的应用；前端不出现私有数据残留 |
| 本人查看后退出或切换账号 | 重新请求或命中隔离后的缓存，旧私有应用不可见 |
| 连续快速访问用户 A、B | 最终只显示 B，A 的迟到响应不能覆盖 |
| 用户无应用 | 展示明确空状态，不把它描述为“没有公开应用” |
| 用户不存在 | 展示 404 状态，不退化为空 profile |
| 请求失败 | 展示错误和可操作的重试入口 |
| 点击作者署名 | 进入既有开发者路由；绝不进入 `/users/{developerLogin}` |
| 直接打开、刷新、前进后退 | 路由与请求保持同一个 `userId` |
| 键盘和窄屏 | 作者链接、应用链接、重试可操作；双栏正确收为单栏；私有状态不只依赖颜色 |

测试优先级：

- 路由组件测试：参数变化、加载、空、404、错误与重试。
- 数据层测试：请求使用同一 `userId`、迟到响应不会覆盖、鉴权变化会失效缓存。
- 集成或 E2E：本人/非本人两种服务端响应，以及“本人查看后退出”这一条防泄露路径。
- 后端契约测试负责证明服务端确实按查看者过滤；前端测试只证明不二次篡改响应且不跨身份复用数据。
