## 2. 数据流与权限边界

```text
route.params.userId
  → 个人主页页面/查询组合函数
  → 已有 API client：GET /users/{userId}
  → { profile, applications }
  → 资料区与应用列表
```

具体规则：

- 接口响应是页面的唯一服务端数据源，不再分别请求 profile 和 applications。
- 前端按原样渲染返回的 `applications`：
  - 本人查看时，服务端可能返回公开和私有应用。
  - 非本人查看时，服务端只返回其允许查看的应用。
  - 前端不得通过 `isSelf` 再过滤列表，也不得把“未返回”解释成“没有私有应用”。
- `isSelf = session.userId === routeUserId` 只可用于展示型行为，例如文案或编辑入口；它不是授权判断。
- 只有响应类型明确提供可见性字段时才渲染 “Private” 标记，不能根据列表位置、作者或当前用户身份推断。
- 快速从用户 A 导航到用户 B 时，应使用项目既有查询库的请求身份/取消机制，或 `AbortController`，确保 A 的迟到响应不能覆盖 B。

### 缓存要求

该响应依赖查看者身份，不能只按 URL 做跨身份共享缓存。

- 客户端查询键至少包含 `userId` 和稳定的查看者作用域，例如：

```text
['user-profile', userId, viewerScope]
```

- `viewerScope` 可以是当前用户 ID或会话世代标识；不要把 token 放进缓存键或日志。
- 登录、退出或账号切换时，清除或失效所有查看者相关的个人主页缓存。
- 如果存在 SSR、CDN 或 Service Worker，共享公共缓存不得保存该响应；服务端需使用私有缓存策略或正确区分授权上下文。前端无法补救服务端缓存泄露。

## 3. 作者入口

应用上的作者只有 `developerLogin`，没有 `userId` 映射，因此：

- 不得生成 `/users/{developerLogin}`。
- 如果项目已有开发者详情路由，则作者链接进入开发者域，例如既有的 `/developers/:developerLogin`。
- 如果尚无开发者详情能力，最小方案是显示不可点击的作者署名；不要新增猜测式跳转。
- 若产品确实希望作者署名进入个人主页，需要服务端提供显式关联，例如 `authorUserId` 或受支持的 developer-to-user 解析接口，再增加入口。

## 评审结论

高优先级缺陷：disabled 资格规则没有贯穿所有路径。

提供片段第 6 行只按 `field.validate` 过滤，因此 disabled 字段的自定义校验仍会执行。它可能产生错误、触发副作用，甚至阻止整个表单提交。

此外，启用字段的校验器收到完整 `values`，disabled 字段仍可能影响跨字段校验。按“disabled 字段不参与校验”的契约，也应从校验上下文中剔除。

建议将字段资格计算一次，并复用于必填校验、自定义校验和提交：

```js
async function processForm(fields, values, send) {
  const enabledFields = fields.filter(field => !field.disabled);
  const enabledValues = Object.fromEntries(
    enabledFields.map(field => [field.name, values[field.name]])
  );

  const errors = {};

  for (const field of enabledFields) {
    if (field.required && !enabledValues[field.name]) {
      errors[field.name] = 'Required';
    }
  }

  for (const field of enabledFields) {
    if (!field.validate) continue;

    const error = await field.validate(
      enabledValues[field.name],
      enabledValues
    );

    if (error) errors[field.name] = error;
  }

  if (Object.keys(errors).length) return { errors };
  return send(enabledValues);
}
```

这不是规则引擎，只是让一个明确的不变量拥有单一计算点。以后字段的 disabled 状态变化，只需维护这一处资格判断。

建议覆盖三个行为测试：

1. disabled 字段即使 `required: true` 且校验器返回错误，也不调用校验器、不产生错误，并且不进入 payload。
2. 启用字段的跨字段校验上下文不包含 disabled 字段。
3. 启用字段校验失败时仍返回错误且不调用 `send`，防止修复时误跳过全部自定义校验。
