建议采用 **FLIP 负责重排几何计算，Web Animations API 负责播放与中断**，不引入动画库。

工作区中没有应用源码、依赖或测试配置，因此当前只能完成技术设计，不能绑定到具体框架或实现文件。

## 层级判断

| 方案 | 结论 | 原因 |
|---|---|---|
| 无动画 | 仅作为降级路径 | 排序会造成多张卡片换位，缺少空间连续性，快速拖拽时不易判断落点 |
| CSS transition | 不足以独立完成 | DOM 重排改变的是布局位置，普通 transition 无法直接插值旧、新布局坐标 |
| View Transitions API | 不选 | 更适合离散的页面或 DOM 状态切换；连续拖拽需要频繁中断、重定向，并与滚动同时发生 |
| FLIP | **选择** | 能把真实 DOM 重排转换为卡片的 `transform` 位移动画，正好表达空间连续性 |
| 动画库 | 暂不引入 | 当前没有既有依赖或更复杂的编排需求；若项目以后已经采用支持 layout projection 的库，应复用其能力而不是维护两套动画 |

FLIP 是几何策略；播放层使用 WAAPI，主要因为它比单纯切换 CSS class 更容易取消、查询当前视觉位置和清理动画。

## 实现边界

排序数据是唯一事实来源，动画不得持有另一份顺序：

```text
拖拽命中新的索引
  → 记录当前视觉位置
  → 立即更新真实顺序
  → DOM 按最终顺序提交
  → 测量最终位置
  → 对保留的卡片播放 translate(delta → 0)
```

具体约束：

- 使用稳定的卡片 ID，不能用数组索引作为 key。
- 拖拽控制器负责指针/键盘输入、碰撞判断、自动滚动和最终顺序。
- 动效控制器只拥有：
  - `id → 首帧位置`
  - `id → 当前 Animation`
  - reduced-motion 状态
- 被拖动卡片或 drag overlay 继续由拖拽层控制；FLIP 只移动让位的兄弟卡片，避免两个系统同时写同一个 `transform`。
- 若无法避免 transform 冲突，在卡片内增加专用 motion wrapper：外层由拖拽系统控制，内层由 FLIP 控制。
- 每个动画周期统一“读全部位置—提交布局—读全部位置—写全部动画”，禁止逐卡片读写交错。
- 只使用 `translate`，不默认使用 `scale`，避免文字和图片在卡片尺寸变化时失真。
- 新增、删除、虚拟列表窗口外的节点不参与本次 FLIP；只匹配前后都存在且 ID 相同的可见节点。

### 快速连续拖拽

每次真正跨过排序阈值时：

1. 从 `getBoundingClientRect()` 捕获当前视觉位置，包括尚未结束动画的中间位置。
2. 取消该控制器拥有的旧动画。
3. 提交最新顺序。
4. 从当前视觉位置重新计算到新布局位置并播放。

因此新输入会“接管”旧动画，而不是排队等待。指针移动可合并到每个动画帧最多一次排序提交；松手时必须立即处理尚未提交的最后目标索引。

动画建议从约 140–180ms 的短时长开始，以明确让位关系为目标；最终数值需要在实际设备上调整，而不是成为排序逻辑的一部分。

### 滚动容器

位置应换算为滚动内容坐标，而不是直接比较两次 viewport 坐标：

```text
contentY = itemRect.top - scrollerRect.top + scroller.scrollTop
contentX = itemRect.left - scrollerRect.left + scroller.scrollLeft
delta = firstContentPosition - lastContentPosition
```

这样 First 与 Last 之间发生自动滚动时，滚动位移不会被误算成重排位移；滚动自身仍由浏览器正常呈现。

首版明确支持一个指定的滚动所有者。嵌套滚动容器、容器自身移动、拖拽中改变卡片高度时，取消并在下一帧重新测量，不建设通用坐标系统。

### Reduced motion 与清理

当 `prefers-reduced-motion: reduce` 生效时：

- 立即取消现有重排动画；
- 跳过 FLIP 测量和播放；
- DOM 顺序仍立即更新；
- 不用淡入淡出替代，避免把一种非必要运动换成另一种。

监听偏好在运行期的变化，并在组件卸载、列表替换或拖拽取消时清理 `Animation`、媒体查询监听器和待执行帧。

排序交互本身还应提供非拖拽的单指针/键盘替代方式。焦点跟随稳定 ID 对应的卡片；位置变更只在确认后播报，避免拖动经过每个索引时反复打扰读屏用户。

## 验证方案

先做纯逻辑测试：

- 普通纵向和横向重排的 delta 正确。
- First 与 Last 之间 `scrollTop` 改变时，不把滚动量计入 FLIP delta。
- 新增、删除或缺少对应 ID 的节点被安全跳过。
- reduced motion 下不创建动画。

再用真实浏览器做交互测试：

- 在前一轮动画结束前连续跨越多个索引，最终 DOM 顺序等于最后一次输入，动画不排队、不回跳。
- 在滚动容器中边自动滚动边重排，滚动位置连续，兄弟卡片从合理位置让位。
- 松手发生在帧合并之前时，最后目标仍被提交。
- 拖拽取消、列表卸载和路由离开后无残留动画或帧回调。
- 模拟 `prefers-reduced-motion: reduce`，确认顺序立即变化且没有运动。
- 键盘排序后焦点仍在同一卡片，最终位置通知正确。
- 若使用虚拟列表，滚出再滚入的复用节点不会继承其他卡片的动画。

最后在发布构建、代表性数据量和较弱的受支持设备上录制性能轨迹。检查：

- 一次接受的重排至多发生一组批量 First/Last 测量；
- 指针移动没有逐事件触发多次同步布局；
- 没有持续丢帧或明显输入延迟；
- 动画主要发生在合成阶段，没有大面积重复绘制；
- 连续拖拽结束后，活动 Animation 数量归零。

帧预算应按目标设备的实际刷新率制定，不能直接把 16ms 当作所有环境的固定标准。
