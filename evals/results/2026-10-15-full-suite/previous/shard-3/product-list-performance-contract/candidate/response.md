结论：当前数据足以暂停继续放量，但不足以直接认定根因。LCP 回退约 41%，INP 回退约 71%；CLS 稳定，因此不应把调查扩成列表重写或布局专项。若已有实验开关，应先保留旧版作为并行对照和回滚路径。

## 最小调查顺序

1. **确认是真回归，不是样本或埋点变化**

   - 用 `build_id/experiment_id` 比较同一时段的新旧版本，不只比较改版前后两个自然时间段。
   - 固定商品列表路由、移动端、导航类型、浏览器、设备档位、网络地区和登录状态。
   - 检查采样率、指标库版本、软/硬导航定义是否变化。
   - 为 LCP 保留元素及 TTFB、资源等待、资源下载、渲染延迟分解；为 INP 保留交互类型、目标以及输入延迟、处理时间、呈现延迟。
   - 若回归不能稳定归属于新版本，先修测量或分群，不改生产实现。

2. **在一个代表性场景中复现三条假设**

   用发布构建、项目支持的一台中端 Android 真机、固定浏览器版本、代表性商品量执行：

   - 构建产物差异：定位新增 95KB gzip 的模块、入口和导入链，区分首屏必需代码、重复依赖和仅筛选时需要的代码。
   - 冷缓存瀑布：定位字体请求的发起者，确认 LCP 元素是否真的等待该字体。
   - 筛选交互 trace：把 180ms 拆成计算、框架更新、样式/布局、绘制和 GC；同时记录受影响节点数与交互目标。

   做三个只用于归因的 A/B 实验：临时使用 fallback font、恢复旧入口依赖图、旁路筛选中的可疑阶段。只有相关指标随实验改善，才把该项视为原因。

3. **按“小改动、可独立验证”修复**

   默认顺序如下，但以前一步的归因结果为准：

   1. 消除字体对 LCP 的阻塞：优先复用现有字体；必须保留时采用合适的 WOFF2 子集、fallback metrics 和 `font-display: swap/optional`。不要用无条件 preload 掩盖错误字体策略。
   2. 收回首路由新增的 95KB：先删除重复依赖和意外入口导入，再沿项目现有 route/capability 边界拆分。首屏必需逻辑不能为了数字被延后；筛选代码若延迟加载，应在空闲期或用户接近交互前预取，避免把成本转成首次 INP。
   3. 修复筛选长任务：
      - 计算占主导：减少重复派生或采用针对当前数据模型的索引；
      - 广泛重渲染占主导：收窄状态订阅、保持商品 identity 和 key 稳定；
      - layout 占主导：批量 DOM 读写；
      - 节点规模占主导：才考虑增量渲染或虚拟化，并验证焦点、滚动恢复和可访问遍历。
      
      Debounce、worker、全量 memoization、列表重写都不能作为默认答案。

每项修复单独提交或挂独立开关，重复同一 trace；没有改善目标阶段的改动应撤回。

## 可执行性能预算

字段结果预算和实验室代理预算必须同时满足。

| 层级 | 指标 | 预算与失败条件 |
|---|---|---|
| RUM | 移动端商品列表 p75 LCP | `≤2.5s`，且候选版相对并行旧版的差值，其 95% bootstrap CI 上界 `≤+200ms` |
| RUM | 移动端商品列表 p75 INP | `≤200ms`，且差值 CI 上界 `≤+20ms` |
| RUM | 移动端商品列表 p75 CLS | `≤0.05`，且差值 CI 上界 `≤+0.01` |
| 构建 | 首路由 JS | 与改版前相同压缩器比较，gzip 总量 `≤基线+10KB`；新增模块必须能追溯到首屏需求 |
| 瀑布 | 字体 | LCP 不等待下载字体；关键请求链中不得新增字体 stylesheet/font 依赖 |
| 实验室导航 | LCP | 基线与候选交错执行至少 15 次冷启动；候选 p75 不得比基线慢 `>100ms` |
| 实验室筛选 | Event Timing | 30 次独立交互的 duration p75 `≤200ms` |
| 实验室筛选 | 主线程任务 | 筛选触发的应用任务 p95 `≤50ms`，任何一次 `>100ms` 即失败 |
| 实验室布局 | CLS | 每次场景 `≤0.05`，字体切换后也必须满足 |

上述 `+10KB` 是本次回归的临时硬预算；如果确有首屏必要能力超过预算，需要以 RUM 改善证明并单独批准，而不是静默抬高基线。

## 回归验证

- 基线与候选使用同一设备、浏览器、发布构建、网络配置、区域、locale、字体缓存状态和数据 fixture，并交错运行，避免机器漂移。
- 导航用冷缓存；筛选在页面稳定后的暖状态测量。数据至少覆盖典型商品量和线上高位商品量。
- 保存原始构建 manifest、network waterfall、性能 trace 和每次运行结果，CI 比较原始指标；Lighthouse 分数只作诊断线索。
- 功能验证覆盖商品数量与排序、单项筛选、快速连续输入以最后一次结果为准、清空筛选、空结果、键盘和焦点、滚动位置。
- 字体修复额外验证慢网、首次访问、重复访问以及 fallback 到目标字体的布局稳定性。
- 在项目支持的移动浏览器中做真实浏览器检查；DOM 模拟器不能证明 LCP、布局或交互延迟。

## 发布门槛

1. **PR 门槛**：功能检查通过，首路由 JS、字体关键链、重复实验室指标全部满足预算。单次 Lighthouse 高分不能放行。
2. **5% 灰度**：与旧版并行至少 24 小时，并且每组每项指标至少有 1,000 个有效页面样本；不足则延长观察，不扩大流量。
3. **逐级放量**：5% → 25% → 50% → 100%，每一级都重新检查总体及主要移动设备/浏览器分群；分群样本至少 200 才作阻断判断。
4. **立即暂停或回滚**：任一小时窗口样本达到 200 后，候选版出现 LCP `>3.0s`、INP `>250ms`、CLS `>0.10`，或 LCP/INP 相对旧版恶化超过 20%。
5. **完成判定**：100% 发布后继续观察完整 7 天，字段预算持续满足，且现有错误率、筛选成功率和业务护栏无异常，才关闭回归事项。

按这些标准，当前 `3.1s / 290ms / 0.04` 明确不能继续全量发布；CLS 只作为防止字体修复引入新问题的护栏。
