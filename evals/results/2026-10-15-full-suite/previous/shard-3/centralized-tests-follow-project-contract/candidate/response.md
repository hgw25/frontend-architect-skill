结论：应将测试与测试基础设施统一迁至顶层 `tests/`，最终让 Vitest 只发现该目录。迁移期间保留短暂的双目录发现范围，避免测试因路径变更而悄然漏跑。

## 迁移方案

目标结构：

```text
tests/
  setup.ts
  app/
  components/
  features/
```

具体执行：

1. 迁移前，用项目现有测试脚本运行一次完整测试，保存：

   - 被发现的测试文件清单
   - 测试用例名称及数量
   - 通过、跳过、失败数量

2. 将 `src/test-setup.ts` 移至 `tests/setup.ts`，更新 Vitest 的 `setupFiles`。保留其中已有的 DOM 扩展、全局清理和 mock，不重新实现一套 setup。

3. 将测试按其保护的功能归档：

   - 组件旁测试迁至 `tests/` 下对应的源码相对目录。
   - `src` 根目录中的工单回归测试迁至其实际保护的功能目录。
   - 只有真正跨功能的应用级测试才放入 `tests/app/`。
   - 快照随对应测试迁移；fixture 和 helper 放在实际共享范围内，避免形成无归属的公共目录。

   例如：

   ```text
   src/components/Button.test.tsx
   → tests/components/Button.test.tsx
   ```

4. 修正迁移导致的相对导入路径。若项目已有稳定的路径别名，应继续复用；不要为了迁移增加源码转发文件或新的业务抽象。

5. 分阶段调整 Vitest：

   - 迁移阶段：`include` 同时覆盖原 `src` 测试和新 `tests` 测试，保证每一批移动后都可运行。
   - 全部迁完后：删除 `src` 发现规则，仅保留 `tests`。
   - 最终配置形态应类似：

   ```ts
   test: {
     include: ['tests/**/*.{test,spec}.{ts,tsx}'],
     setupFiles: ['./tests/setup.ts'],
   }
   ```

   实际后缀集合应沿用仓库现状；环境、alias、coverage、globals 和排除规则保持不变。

6. 删除已迁移的旧测试路径和 `src/test-setup.ts`，不保留兼容副本，避免测试被重复执行或后续继续散落。

## 验收方式

迁移完成需同时满足以下条件：

- `tests/` 包含全部测试、setup、对应快照及必要测试辅助文件。
- `src/test-setup.ts` 不再存在。
- `rg --files src -g '*.test.*' -g '*.spec.*'` 无输出。
- Vitest 最终配置只发现 `tests/`，且 `setupFiles` 指向 `tests/setup.ts`。
- 使用详细 reporter 运行完整测试后，迁移前后的测试文件和用例清单一一对应；差异只能是路径变化，不能只以“命令退出成功”作为验收。
- 所有工单回归用例都能在最终测试输出中明确找到。
- 完整测试全部通过，没有因重复发现导致的用例数量增加。
- “零测试”不能被当作成功；不得启用 `passWithNoTests` 来掩盖发现配置错误。
- 运行项目已有的类型检查、lint 和构建脚本，确认测试迁移没有破坏模块解析。
- 最终 diff 仅涉及测试文件、测试配置及必要的测试脚本路径，不包含业务行为变更。
