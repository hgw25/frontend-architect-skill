这条链路的主要成本，按“最小改动优先”排序：

1. `pointermove -> 根组件 state`
   指针位置写进看板根组件 state，会让 300 张卡片所在子树一起进入 React render/commit。这里的首要问题不是“是否给每张卡片加 `memo`”，而是高频、交互态数据放错了层级。最小改动是把拖拽中的指针坐标、当前拖拽卡片 id、临时位移改成 `ref` 或外部可变对象，只让真正需要变的那一个拖拽层更新；非拖拽卡片在拖动期间不走 React render。

2. `commit -> layout effect`
   你描述的 effect 是“先改 class，再立刻读 `getBoundingClientRect`，再写 `top`”。这会把浏览器推入典型的强制同步布局：写样式使之前布局失效，随后读取几何信息必须立刻做 Style/Layout，后续再写 `top` 又触发下一轮失效。Chrome trace 里反复出现 `Style`、`Layout`、`Paint`，根因大概率就在这里。最小改动是把读写分相：
   - 先统一读：收集所有需要的 rect
   - 再统一写：批量应用 class / position
   - 禁止在同一个 effect/同一帧里交错“写-读-写”

3. `top/class -> layout + paint`
   如果卡片位置通过 `top` 推动，而且 class 还影响文档流或尺寸，那么每次拖动都可能让 300 张卡片重排并重绘。这里第二优先级的改动不是动画库，而是把拖拽中的视觉位移尽量收敛到合成层：
   - 拖拽中的卡片用 `transform: translate(...)`
   - 占位符或排序预览尽量维持稳定尺寸，避免反复改高度/边距
   - 只在落点确认时再提交真实顺序

4. `paint -> final pixels`
   即使 React render 压下去了，只要每帧都在改会触发布局和大面积重绘的属性，像素阶段还是会卡。最后一层优化边界是把交互帧目标收敛为“少量 JS + 尽量不 layout + 尽量只 composite”。

实现边界建议：

- 第一阶段，只改交互态数据通路：
  把 pointer 坐标和拖拽瞬时位移从 board 根 state 移出，不改业务数据结构，不引入新库，不做全量 `memo`。
- 第二阶段，只改 effect 的读写顺序：
  保持现有排序逻辑，但拆掉“改 class 后马上测量”的交错流程；必要时把测量放到单独阶段，或缓存未变化卡片的 rect。
- 第三阶段，只改拖拽中的定位属性：
  拖拽预览优先改 `transform`，避免持续写 `top/left` 触发布局。不要顺手重做整套 DnD 架构。

验证方案：

- React 侧：
  用 React Profiler 看一次拖动期间，确认从“整棵 board 子树频繁 commit”下降到“只有拖拽层或极少节点更新”。
- Chrome Performance：
  对比生产构建 trace。目标是拖动期间长任务明显下降，主线程上的 `Style`/`Layout` 次数和总时长下降，`Paint` 不再跟随每次 pointermove 大面积出现。
- 指标门槛：
  关注 `pointermove` 到下一帧的主线程耗时，目标单帧稳定低于 16ms；如果设备基线较低，至少要把长任务切碎，不再连续阻塞交互。
- 回归点：
  验证排序结果、占位符位置、自动滚动、拖拽取消、跨列移动。因为第一阶段会绕开 React state，最容易引入的是视觉状态和最终提交状态不一致。

决策上，我建议先做这两个最小改动，再看 trace：
1. 把高频 pointer 数据移出根 state。
2. 把布局 effect 改成“先读后写”，并停止拖动中持续写 `top`。
