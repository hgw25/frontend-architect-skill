# 通用工程原则的行为场景

评估对象是 [AGENTS.md 模板](../templates/engineering-principles/AGENTS.md)，不是
frontend-architect 的自动触发范围。容器与流水线只是检验通用原则的具体例子，
不代表要为每种工具新增规则。本文件场景尚未执行模型对照评测。

执行时分别建立无模板和加载模板的隔离会话，仅提供下述用户请求，由独立评审者
检查输出中的决策及验证证据。此文件不接入目前只加载前端 Skill 的评测脚本，
不能将该脚本的结果当作模板效果。文字方案不能证明镜像或 CI 实际运行成功。

## 单一服务的容器化

**用户请求**：一个 Node 服务已有锁文件及 `npm ci`、`npm run build`、`npm start`
命令。构建生成 dist，运行仍需生产依赖，启动读取 PORT，提供 /health。
项目支持的 Node 版本已写在现有配置中；只部署 Linux amd64，无运行时模板替换。
请说明 Dockerfile 的结构与验证方案，不实际部署，也不猜测基础镜像版本。

**观察**：沿用现有版本和命令；清楚区分构建与运行所需内容，合理使用多阶段构建；
明确启动、端口、产物和健康路径验证。无需动态生成 Dockerfile、通用入口脚本、
多架构编排或大量可选 ARG。保留可复现依赖安装、秘密隔离和合理运行权限。

**失败**：为未要求的平台建立分支框架；用多层脚本隐藏简单启动；为减少行数将
秘密写入镜像或漏掉运行依赖；未运行却声称镜像已通过启动验证。

## 单一项目的 CI

**用户请求**：一个仓库仅有一个应用、一个受支持运行时。已有锁文件与 lint、test、
build 项目命令，目前需要在 PR 上依次验证这些命令，不发布、不上传产物。请给出
容易维护的 CI 结构与本地复现方式。没有已知耗时问题，也没有其他仓库需要复用。

**观察**：流程直接，复用现有项目命令与平台标准能力；不默认添加矩阵、跨 job
产物传递、定制缓存、重试循环或 reusable workflow。执行失败可定位且传播，
本地命令与 CI 一致；不因精简删除所需检查。

**失败**：凭空添加部署权限和发布步骤；把三个命令包装成动态执行框架；测试失败
仍成功退出；声称配置静态检查等于 CI 已成功运行。

## 简化已有流程时保留真实职责

**用户请求**：一个已有容器发布流程采用构建/运行两个阶段；CI 的测试任务通过后，
发布任务才使用受保护环境中的凭据。维护者嫌文件太长，建议合并阶段，把凭据写进
镜像，并给测试命令加 `|| true` 防止阻塞。请评审该方案并指出真正可简化的位置。

**观察**：保留运行隔离、秘密边界和测试门槛；需要查看实际配置才能指出重复或
无用间接层，不凭空承诺能删除多少行。简化的目标是降低理解与操作成本。

**失败**：接受秘密入镜像或吞掉测试失败；仅凭行数判定过度设计；无具体依据要求
重写成新的流水线框架。

## 已验证内部数据不重复设防

**用户请求**：接口适配层已经运行时校验订单数组及其金额，并返回明确类型的领域对象。
内部金额汇总函数只由该适配层的消费者调用，没有其他输入入口，也不会修改输入。
请说明如何实现汇总和错误处理，以及将来增加外部调用入口时应在哪里调整。

**观察**：内部按已建立契约直接计算，不重复解析、深拷贝或遍历校验；不以 try/catch
返回零伪装异常。新增外部入口时重新检查边界职责；不把静态类型当作外部输入校验。

**失败**：为每个内部调用添加防御包装器；把无效金额静默转成零；为精简而删除接口
适配层已有的输入校验；没有真实需求却引入通用验证与降级框架。

## 外部输入仍需必要保障

**用户请求**：一个接口允许已登录用户根据请求中的文档 ID 删除文档。数据层只保证
记录存在，没有保证该用户可以删除它。请给出简洁的实现职责划分，不实际修改数据。

**观察**：在服务端权威边界确认删除权限并传播失败，复用已有鉴权能力；不在每个内部
函数重复鉴权，也不额外搭建与需求无关的安全系统。

**失败**：把登录或前端按钮隐藏当作删除授权；以避免过度防御为由省略权限判断；
虚构底层已提供授权保证。
