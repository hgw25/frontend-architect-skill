# 工程思想的成熟实现方法

用户要求为技能中的思想补齐已有的实际解决方法，并明确不能自行创造一套方法。初版把
三个自写业务示例放在实现指导中心，虽然检查通过，却没有建立思想与成熟方法之间的
来源关系。初版记录保留在[历史验收](../../evals/results/2026-11-11-implementation-patterns/report.md)，
其通过结果不作为本轮修订或“方法已有规范”的证明。

## 修订顺序与归属

共三步，先查明来源，再改变指导，最后验证。

1. **核实原始方法。** 对照入口和专题中已有思想，查原作者、标准制定方、框架或库的
   官方资料，记录成熟方法的名称、实施过程、适用条件和来源性质。区分正式规范、
   原作者设计方法和具体框架机制，不把推荐实践称为统一行业标准。
2. **替换实现指导。** `references/implementation-patterns.md` 按问题映射到原始方法与
   具体实施步骤，既有专题链接所需章节。入口和贡献流程要求来源可追溯、项目适配明确。
   删除初版自写的三个 `.mjs` 示例、示例测试及其 Python 测试入口；原有项目 fixture 和
   历史评测产物继续保留。项目业务代码可以依据已有方法实现，不能将自写示例当作方法来源。
3. **检验实际变化。** 更新行为用例，检验是否正确选择已有方法、保留原方法语义和项目
   契约，避免为了匹配名称而强装框架。运行现有仓库校验、官方校验和确定性测试；
   独立检查以真实任务核对方法选择与边界，不以来源数量或文档长度判断改善。

| 归属 | 最终应承担的契约 |
| --- | --- |
| `SKILL.md` | 在选择思想后，查有来源的成熟方法及已有项目能力，落实算法、状态转移或生命周期；不要求简单任务重新做文献调查 |
| `references/implementation-patterns.md` | 思想到成熟方法、主要来源、实施步骤、适用边界的条件导航；不发布自命名方法或维护第二套业务实现 |
| 既有专题 | 保留原有工程判断，相关实现问题直达上述方法章节；实际框架 API 按项目版本核实 |
| `CONTRIBUTING.md` | 加入重要思想时同时说明成熟解决方法与出处；没有统一方法时如实说明取舍，不补造所谓规范 |
| `evals/cases.yaml` | 以原请求和实际契约评价方法是否应用，不绑定自写示例的 API 或强制使用某个依赖 |
