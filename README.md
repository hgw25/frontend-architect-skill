# Frontend Architect

一个面向 AI 编码代理的高级前端与前端架构 Skill，将需求开发与架构设计贯通，并提供代码审查，
覆盖 Web、App/跨端和小程序运行时。用户说明目标与对象后，技能自行发现上下文、选择流程，
完成适用的设计、实现、工程质量检查和验证，无需再列一遍工程要求。
它既要求代理完成高质量产品代码，也要求代理在真实共性问题出现时具备建设组件库、
设计系统、SDK、共享数据层、构建插件、代码生成器和 Monorepo 包的能力。

当前发布版本：[v0.6.0](https://github.com/hgw25/frontend-architect-skill/releases/tag/v0.6.0)。
版本变化见 [CHANGELOG.md](CHANGELOG.md)。

## 它解决什么问题

AI 很容易写出“能运行”的前端代码，也很容易产生另一种问题：为了显得高级而增加
抽象、状态、配置、依赖和目录层级。本项目将高级前端工程经验转成决策门槛：

- 先复用项目已有能力、标准工具与合适的成熟方案，再补必要的自研逻辑；
- 按变化、所有权和依赖方向确定模块边界；
- 在功能模块化与职能模块化之间做场景化选择；
- 在函数、Reducer、状态机、闭包和类之间选择合适表示；
- 把状态、副作用、异步竞态和错误状态当成产品行为；
- 明确服务端、浏览器、缓存、包和序列化边界；
- 从状态更新、调度、跨层传输、宿主更新到布局、绘制、栅格化和呈现定位渲染成本；
- 使用同一套高级工程标准，并按消费者数量、影响范围和迁移风险提高设计与验证深度；
- 将公共 API、类型、构建产物、诊断、兼容性和发布视为基建正确性；
- 把不可信数据、授权、秘密和第三方代码视为信任边界；
- 将语义、可访问性、布局、动效和性能纳入实现质量；
- 让高风险变更可观测、可灰度、可回滚；
- 通过行为与风险验证代码，而不是追求形式上的覆盖率。

## 非目标

- 不强迫所有项目采用同一技术栈或文件结构；
- 不把某位工程师的个人风格当成绝对规范；
- 不要求所有代码函数式，也不鼓励到处创建类；
- 不将 Atomic Design、Feature-Sliced Design 或 FLIP 当成必用模板；
- 不替代项目自己的 `AGENTS.md`、架构约束和验证命令。

### 跨项目工程原则：用 AGENTS.md 承载

[可维护工程原则模板](templates/engineering-principles/AGENTS.md) 独立于前端技能，
适用于后端、脚本、代码同步和其他工程任务。它规定先检查已有机制、优先复用成熟方案、
保留可持续的维护流程，以及让接手者能够理解和验证实现。
模板约束整个解决方案的理解成本，统一适用于代码、配置、脚本和工具操作：
每层抽象和可选机制都有现实理由，执行链可读，简化时保留真正承担正确性与恢复的结构。
防护也按真实信任边界和已有保障设计，避免重复校验、吞错兜底及假想风险驱动的防御框架。
允许为有依据的后续扩展和调用便利适度增加复杂度，不以最少行数或只满足眼前需求为目标。
对应的[通用原则评测场景](evals/engineering-principles.md)与前端技能评测分开维护。

- 需要某个项目默认遵守：把模板中的相关章节合并到该项目已有的 `AGENTS.md`，保留
  项目原有约束；不要直接覆盖整个文件。
- 需要作为个人 Codex 默认偏好：可将相同章节合并到个人 `~/.codex/AGENTS.md`，再由
  各项目补充具体工具、命令和约束。
- `frontend-architect` 保持独立可用，在前端任务中应用这些通用原则；无需安装另一项通用技能，
  也不要求每次读取模板。精简通用原则也完整包含在技能入口中，单独安装即可在技能触发时使用。

选择常驻规则是因为这些属于日常工程工作的默认要求，而非仅在特定任务中触发的能力。
模板在本仓库中是待采用的资源，**不会自动影响其他项目或个人配置**。修改模板也不会
自动更新已合并的副本；维护时保留项目差异。安装 frontend-architect 本身不等于启用
跨项目规则。个人默认配置需单独合并；维护者应同时检查入口、模板与个人副本的一致性。

渲染专题采用两级按需加载：先读取跨平台成本模型，再只读取 Web、App/跨端或小程序
中与当前运行时匹配的一个扩展；Hybrid WebView 等真实混合场景才会组合多个扩展。

## 开发、发布与安装

开发目录 → 验证与评测 → 不可变 Git tag → 官方 skill-installer 暂存 → 统一安装事务。
从 [v0.6.0](https://github.com/hgw25/frontend-architect-skill/releases/tag/v0.6.0) 起，主技能与独立维护技能使用同一发布版本，
安装维护包含下述统一执行器。

安装、检查版本、更新与回滚统一使用独立的
`frontend-architect-update`（源码 `skills/frontend-architect-update/SKILL.md`）。
只维护这一份操作流程，README 不再提供另一套手动移动目录的升级命令。
首次引导时，通过系统 skill-installer 从同一不可变发布标签的
`skills/frontend-architect-update` 路径安装独立维护技能，再请求
`$frontend-architect-update` 安装或更新主技能。检查版本不会自动升级。

当前源码维护可使用已审查的
`manage_installation.py`（独立维护技能的 `scripts/` 目录），
对已暂存并验证的候选执行 `inspect`、`activate` 或 `rollback`。
具体参数、授权边界与官方暂存命令只有维护技能一个权威来源。
执行器统一处理首次安装、更新、回滚、并发锁、文件核对、外部备份、失败恢复和回执；
移除主技能中的嵌套维护技能，保留独立安装的维护技能。备份在技能发现目录之外，
并与目标使用同一文件系统。本地变更和来源未知按已有授权处理，不静默覆盖。

开发时沿用本仓库校验与行为评测；发布前核对 VERSION、CHANGELOG、标签和验证提交。
[评测及安装维护技术设计](docs/engineering/evaluation-and-maintenance.md)记录本轮职责、数据流与验收。
实际生成、正反例与剩余限制见[本轮复核](evals/results/2026-10-19-evaluation-acceptance/report.md)，
发布检查见[v0.6.0 发布验收](evals/results/2026-10-19-release-0.6.0/report.md)。

## 使用

显式调用示例：

```text
使用 $frontend-architect 实现这个需求。
```

```text
使用 $frontend-architect 设计这个模块的架构。
```

```text
使用 $frontend-architect 审查这个模块。
```

该 Skill 默认也允许 Codex 在匹配的前端开发与架构任务中自动发现。

需求开发与架构设计相辅相成：拆解功能时确定职责、函数或类契约和数据流，按依赖逐步实现，
再用实际调用与验证结果修正设计、实施步骤和图示，交付前保持文档与代码一致。
共同工程原则和相关专题贯穿这条过程：复用、模块与函数职责、依赖方向、编程范式、状态与
资源所有权、扩展边界，以及适用的运行时、交互、安全和性能要求，都要对应到具体设计取舍。
重要选择在原技术文档中留下理由和检查依据，设计稿与实际代码均按同一标准自审；不以列出
原则名称、文档齐全或功能测试通过代替工程质量判断，也不机械地给每个任务套上所有模式。
具体方法也由业务行为触发：重排与空间连续性会引出 FLIP 等过渡机制的取舍；共享界面部件会
引出 Atomic Design 与组合边界；独立业务变化会引出 Colocation/FSD；状态与副作用会引出
函数式核心、对象或状态机；响应与帧成本会引出 RAIL 和渲染链路分析。适用条件、停止条件
及原专题位置见[行为到设计方法的导航](references/architecture-and-code.md#match-design-lenses-to-behavior)。
用户只提出开发目标，也默认包含适用的架构设计、代码质量检查和验证；明确只要设计时，
沿同一过程交付可实施的技术文档，并在该交付边界停止。代码审查自行寻找当前有效契约，沿调用
关系检查需求符合度及完整的适用工程标准，给出具体发现和有证据边界的质量结论。
仅审查时不修改实现；已有测试全绿不能代替函数、模块、所有权和维护成本的判断。
“最高标准”落实为同一套可检查的工程要求，范围和验证深度随任务调整，不以更多抽象、
目录或假想防护证明质量，也不作超出实际覆盖的全面达标承诺。

## 核心观点

### 统一的判断体系

Skill 按四个部分组织：入口中的核心判断体系和任务执行方式、按需读取的专题参考、
以及维护阶段使用的行为评测。评测规则不作为每次业务开发必须读取的清单。

核心主线是：**行为 → 事实 → 模型 → 边界 → 实现 → 证据**。重要规则需要能对应到
状态或资源的所有者、实际执行位置和可发现错误的验证；新边界用有现实依据的变化
检验，而不靠目录数量证明架构质量。证据变化时可以回到前面的决定重新调整。

执行方式按局部修改、功能、故障、重构、共享基建、迁移和只读评审区分。新建或改变
业务流程、重新分配职责的重构、共享基建和迁移，默认先形成技术文档再改实现，无需
用户额外提醒。文档明确拆成多少步、每步功能与依赖、支撑的类型及函数或类契约、
技术架构图、数据流转图和逐步验收；实现中同步修订，交付时补回实际验证结果。
文案、间距或沿用既有契约的局部接线仍可直接完成。文档不增加默认审批门槛。
详见[需求到技术设计](references/architecture-and-code.md#turn-requirements-into-an-executable-technical-design)。

验证还要沿实际消费路径检查跨步骤结果：结构变化后能否继续键盘操作，已确认命令遇到
后续读取失败时用户能否仍看到确认，性能样本是否来自原始与最终代码的可比条件。
成本基线在实现前取得；交付前通过定义和调用查找核对技术文档的重要契约与两类图示。
已有测试没有覆盖的重要完成组合，由代理自主补查。

领域概念和重要决策优先沉淀到项目已有说明：定义保存概念、身份和关系，决策记录保留
选择与理由，技术设计保存功能拆分、代码契约、图示及验收。已确认的修订及时更新原记录；未解决的
契约冲突保持明确，不猜测身份映射。按需创建有后续用途的简短记录，小改动无需先建
词汇表、ADR 或初始化会话。详见[领域知识与决策指导](references/architecture-and-code.md#preserve-domain-knowledge-and-decisions)。

### 模块化

对于具有明确业务能力的中大型产品应用，通常以功能或领域作为上层边界，再在功能
内部根据真实需要继续划分页面编排、业务流程、状态与纯规则、外部适配、UI 和测试；
组件、hook/composable、函数与文件也用语义、变化原因、生命周期和契约判断是否拆分。
`ui`、`model`、`api` 只是可能的职责，不是必须补齐的目录模板。小项目、基础库和强
框架约束项目可以采用不同结构。评价标准是变化是否集中、所有权是否清楚、依赖方向
是否稳定，以及是否在继续拆分不再增加清晰度时及时停止。

### 编程范式

默认优先考虑“函数式核心、命令式外壳”：将计算和状态转换保持纯净，把网络、DOM、
存储和生命周期留在明确边界。具有稳定身份、资源生命周期或需要保护可变不变量的
对象，可以使用类或对象封装。范式按边界选择，不按项目站队。

### 抽象

抽象应减少调用者需要理解的细节，把共同变化的规则和状态交给合适的所有者；允许为
领域常见变化预留适度边界，但应对当前调用或维护已有收益。相似语法不代表相同语义。
实现与 review 使用同一质量标准：检查真实函数、调用链、输入输出和副作用，区分功能
正确与结构好维护，不用文件数、函数数、行数或全绿测试代替判断。

代码构造指导覆盖主流程与辅助函数、数据归一化与草稿/权威值的区别，以及真实调用方
需要理解的契约。异步专题区分过期结果、取消、排队、去重、幂等和乐观回滚，优先复用
已有数据层。平台 API 不自动优于已承担兼容性和生命周期策略的项目封装。

按任务的未决问题读取所需章节；标题发现与正文消费分开记录，不设主题配额或逐文件旁白。
任务或已检查证据能建立扩读理由，读取数量本身不代表必要或过量。

### 前端基建

基建不是更多目录或设计模式，而是被多个消费者依赖、需要长期维护的公共契约。组件
原语、设计系统、SDK、状态/数据层、构建插件、lint 规则、codemod 和 workspace 包
必须同时设计 API、类型、错误诊断、运行环境、兼容范围、构建产物、测试矩阵和发布
演进。Skill 同时要求：没有真实消费者时不预建基建；一旦任务确实是基建，就不能用
只能服务单一页面的临时封装交付。

前端基建不是另一套开发思想，而是在同一套状态建模、模块化、依赖方向、类型设计、
可访问性、性能和测试标准上，进一步承担多消费者、兼容性和发布演进责任。

### 运行与信任边界

现代前端代码可能运行在构建环境、服务端、边缘节点、浏览器或 Worker。Skill 要求
根据秘密、权限、交互、延迟、缓存和 Bundle 成本决定放置位置，并把跨环境数据设计成
明确的序列化契约。客户端权限判断只负责体验，服务端仍必须执行权威授权。

### 跨平台渲染与性能

Skill 先按目标运行时建立“状态或数据变化 → 调度与依赖计算 → 可选跨线程或跨层传输
→ 宿主节点更新 → 布局 → 绘制或栅格化 → 合成与呈现”的最小模型，再根据证据处理
真实瓶颈。浏览器、React Native、Flutter、原生声明式 UI、Hybrid WebView 和小程序
拥有不同线程、树和通信边界，不能机械套用同一套优化。memoization、虚拟列表、GPU
合成和固定帧预算都不是默认答案；性能结论必须来自目标版本、生产或 profile 构建、
代表性设备和相同用户路径的前后测量。

### 交付与可观测性

高风险改动需要考虑兼容迁移、灰度、回滚、错误恢复和生产信号。实验室检查用于诊断，
真实用户数据用于判断实际影响；日志、错误和分析数据不得无边界收集秘密或个人信息。

## 开发与验证

首次开发时创建隔离环境并安装校验依赖：

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements-dev.txt
```

运行仓库校验：

```bash
python3 scripts/validate_skill.py
```

该命令解析并检查 Skill Frontmatter、代理元数据、仓库链接、Python 语法和结构化评测
用例。行为变更还应按照 [评测协议](evals/cases.md)，使用
[结构化用例](evals/cases.yaml) 和 [评分标准](evals/rubric.md) 做 baseline/candidate
前向测试。评测关注代理的决策和风险识别，不匹配固定措辞。

新增[无原对话接手检查](evals/followups/README.md)：冻结第一版后由新代理仅凭仓库接手，
检查理解、修改集中程度和契约回归。[本轮记录](evals/results/2026-09-15-maintainer-handoff/summary.md)
仅支持单场景未观察到退化，不代表已证明对人类维护或整套规则的显著提升。

原始失败、夹具纠错、焦点遗漏、性能基线与文档对齐缺口均保留，不将术语或一次全绿视为最高标准证明。

状态仍有遗漏，尚未稳定满足四项自主验收。

可以用隔离的 Codex CLI 会话生成可复查的原始输出、fixture diff 和验证日志：

```bash
python3 scripts/run_behavior_evals.py \
  --mode both \
  --results-dir evals/results/$(date +%F)-gpt-5.4
```

该脚本关闭插件发现，并审计实际 reference 读取：baseline 必须保持零 Skill 引用，
candidate 只能加载隔离工作区中的 `SKILL.md` 与按需 reference；读取全局副本或修改
受保护验收脚本会使运行失败。正文读取按任务相关性和实际范围独立审查，标题发现不算正文；
既不以数量直接判错，也不因只读一份就免于相关性判断。运行后仍需按照 rubric 盲评。

实现型诊断可加 `--host-feedback`：真实宿主检查失败后最多交回一次修复，首次交付和修复
分别保留并校验。无效捕获、保护文件被改、只读 review 和无夹具任务不进入该环节。
已有生成必须另建结果目录；`--append` 只追加新案例。

生成完成后，可在与生成会话分离的上下文中执行两阶段评测。脚本先在隐藏
`must_observe`、`fail_if` 和另一条件的情况下盲评分，再为同一匿名条件单独执行
case-specific `fail_if` 审计；任一 case-specific 或 global failure 都会覆盖分数并将
verdict 设为失败。同一结果目录会拒绝混用不同评分模型或 reasoning effort：

```bash
python3 scripts/score_behavior_evals.py \
  --results-dir evals/results/$(date +%F)-gpt-5.4
```

评分脚本的确定性回归测试：

```bash
python3 scripts/test_score_behavior_evals.py
```

评分会拒绝执行失败、隔离证据不足或原始产物缺失的样本，将其记录为 `invalid`。
两阶段缓存跟随实际输入失效；追加案例评分会保留旧案例并加入新结果。历史采集若没有
当前阅读审计字段，需要重跑，不能用旧的路径匹配记录证明已读取或隔离通过。
评分还会核验原始执行日志及冻结的验证契约；补加测试或修改夹具后需要重新采集。
选中案例在评分开始前撤销旧结论，评分服务失败或中断不会保留未完成案例的旧通过结果。
可用 `--model` 指定当前账户支持的模型；脚本默认模型不可用时应更换配置并使用新结果目录。

新增多文件只读审查案例使用 `before/` 与 `after/` 仓库快照，要求代理自己定位有效需求和
受影响路径。维护者侧的缺陷检查与 reviewer 输入隔离。完整回归检查需要 Python 和 Node：

```bash
python3 -m unittest discover -s scripts -p 'test_*.py'
```

运行有效性、缓存和审查快照的详细约定见 [评测协议](evals/cases.md)。

## 贡献原则

请阅读 [CONTRIBUTING.md](CONTRIBUTING.md)。新增规则需要说明它改变了什么决策、
适用边界是什么，并增加或更新至少一个行为评测场景。避免因单个失败案例不断累加
全局禁令。

维护时先定位已确认的失败：产品问题修负责的源码；机械约束复用 validator、测试或
构建检查；检查没接通则修命令或 CI；难以发现的概念补原文档和导航；取舍判断问题
才修改 Skill 指导。精简按修改前后的行为与实际产物验证，文本变短本身不代表改进。
